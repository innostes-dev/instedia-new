# Module 03: High-Throughput Production Serving (Ollama & vLLM)
## 3.2 High-Throughput vLLM Serving

### Phase A: The Core Concept

#### 1. Real-World Pain Point (The Why)
Ollama is amazing for local development and single-user testing. But now your startup has launched, and your fine-tuned model needs to serve 1,000 concurrent users per minute. You try using HuggingFace `pipeline` or Ollama in production, but users complain that it takes 45 seconds to get a response.
Why? Standard inference engines process requests sequentially (or with inefficient static batching). If User A asks for a 10-page essay and User B asks for a 1-sentence summary, User B is stuck waiting for User A's massive generation to finish. You have a massive GPU, but it's sitting idle 90% of the time waiting for memory to be organized.

#### 2. Plain English Metaphor (The What)
Imagine a restaurant kitchen (the GPU).
**Standard Inference:** A chef gets an order (prompt), cooks the entire meal (generates tokens), plates it, and *then* looks at the next ticket. If an order takes 30 minutes, the next customer waits 30 minutes.
**vLLM (PagedAttention & Continuous Batching):** The chef is a master multitasker. They chop onions for Order 1, stir the soup for Order 2, and plate Order 3 all at the same time. Furthermore, they store ingredients in identical small, neat containers (`PagedAttention`) instead of giant messy piles, so they never waste counter space. They can serve 100 people at once.

#### 3. Complete Runnable Code
Here is a conceptual simulation showing the throughput difference between standard batching and continuous batching (the core of vLLM).

```python
import time
import random

def simulate_standard_batching(requests):
    """Wait for all requests in a batch to finish before moving on."""
    start_time = time.time()
    # Batch is limited by the longest request!
    max_tokens = max(requests)
    print(f"Standard Batch: Waiting for longest request ({max_tokens} tokens)...")
    time.sleep(max_tokens * 0.01) # Simulate generation time
    throughput = sum(requests) / (time.time() - start_time)
    return throughput

def simulate_vllm_continuous_batching(requests):
    """Requests enter and exit the GPU pool dynamically at the token level."""
    start_time = time.time()
    print("vLLM Continuous Batching: Processing dynamically...")
    # Time taken is roughly total tokens / parallel capacity
    total_tokens = sum(requests)
    # vLLM is highly efficient, simulating high parallel throughput
    time.sleep((total_tokens * 0.01) / 4) # 4x faster due to dense packing
    throughput = total_tokens / (time.time() - start_time)
    return throughput

# 10 Concurrent user requests of varying lengths (e.g., short chats vs long documents)
incoming_requests = [50, 800, 10, 450, 120, 900, 30, 200, 600, 15]

std_throughput = simulate_standard_batching(incoming_requests)
vllm_throughput = simulate_vllm_continuous_batching(incoming_requests)

print(f"\n--- Production Throughput (Tokens per Second) ---")
print(f"Standard Inference Engine: {std_throughput:.2f} tok/s")
print(f"vLLM Engine:               {vllm_throughput:.2f} tok/s")
print(f"Speedup:                   {vllm_throughput / std_throughput:.2f}x faster!")

# Note: In production, you run vLLM via CLI:
# python -m vllm.entrypoints.openai.api_server --model my-fine-tuned-model --gpu-memory-utilization 0.90
```

#### 4. Progressive Step-by-Step Breakdown

**Step 1: The KV Cache Bottleneck**
As an LLM generates words, it remembers previous words using a "Key-Value (KV) Cache". In standard engines, this cache takes up huge, contiguous blocks of VRAM. If a sentence ends early, that huge block of VRAM is wasted (fragmentation).

**Step 2: PagedAttention (The Magic)**
vLLM invented PagedAttention (borrowing the concept of virtual memory from Operating Systems). It breaks the KV cache into tiny, non-contiguous blocks (pages). This eliminates memory waste, allowing you to fit vastly more requests into VRAM at the same time.

**Step 3: Continuous Batching**
Because memory is managed so well, vLLM doesn't wait for a "batch" of users to finish. As soon as User B gets their 1-sentence answer, they are ejected from the GPU, and User C is instantly slotted into that empty space, token-by-token.

#### 5. ASCII Data Flow

```text
Standard Batching (Wasteful):
User 1: [== Done ==] (GPU Idle here ->) [        ]
User 2: [====== Generating full 10 pages ======= ]

vLLM Continuous Batching (Dense Packing):
User 1: [== Done ==] -> User 3 slots in: [===] -> User 4: [==]
User 2: [====== Generating full 10 pages ======= ]
```

#### 6. Noob Trap vs Pro Tip
*   **Noob Trap:** Using vLLM for single-user local testing. vLLM has high initialization overhead and doesn't support CPU offloading as easily as Ollama/llama.cpp. If it's just you typing in a terminal, vLLM will actually feel *slower* and clunkier to set up.
*   **Pro Tip:** vLLM provides an OpenAI-compatible API server out of the box (`vllm.entrypoints.openai.api_server`). This means you can drop it into any existing application (like LangChain, AutoGen, or frontend UIs) just by changing the `base_url` to your server's IP address. No code rewrite needed!

### Phase B: Engineering Challenges

#### Level 1: Warm-Up
**Challenge:** vLLM has a parameter called `--gpu-memory-utilization` (default 0.90). This tells vLLM what percentage of the GPU VRAM to reserve entirely for the KV cache. If you have an 80GB A100 GPU, and the model weights take up 20GB, how many GBs are reserved for the PagedAttention KV Cache?
<details>
<summary>Hint</summary>
Total utilization = 80GB * 0.90. Subtract the weights from that total.
</details>
<details>
<summary>Solution Walkthrough</summary>
```python
total_gpu_ram = 80
utilization_target = 0.90
model_weights = 20

reserved_total = total_gpu_ram * utilization_target # 72 GB
kv_cache_space = reserved_total - model_weights     # 72 - 20 = 52 GB

print(f"Space reserved for serving thousands of users (KV Cache): {kv_cache_space} GB")
# If this was standard PyTorch, it might crash trying to allocate this much!
```
</details>

#### Level 2: Real-World
**Challenge:** Write a mock Python script using the `openai` python package to connect to a local vLLM server. You must change the `base_url` to point to `http://localhost:8000/v1` and use a dummy API key.
<details>
<summary>Hint</summary>
Instantiate the `OpenAI` client with `base_url="http://localhost:8000/v1"` and `api_key="EMPTY"`.
</details>
<details>
<summary>Solution Walkthrough</summary>
```python
from openai import OpenAI

# vLLM acts exactly like the OpenAI API!
client = OpenAI(
    base_url="http://localhost:8000/v1",
    api_key="EMPTY" # vLLM doesn't require keys by default
)

def get_vllm_response(prompt):
    try:
        response = client.chat.completions.create(
            model="my-fine-tuned-model", # Must match the model vLLM loaded
            messages=[{"role": "user", "content": prompt}],
            max_tokens=100
        )
        return response.choices[0].message.content
    except Exception as e:
        return "Server not running. Start with: python -m vllm.entrypoints.openai.api_server"

# print(get_vllm_response("Hello vLLM!"))
```

#### Level 3: Boss Level (Cumulative)
**Challenge:** You are the Lead AI Engineer. You need to serve a fine-tuned Llama-3 70B model to 10,000 users.
1. The 70B model is quantized to 4-bit (AWQ format, which vLLM supports). How much VRAM for weights? (Module 2.2)
2. You have a node with 4x 24GB GPUs (96GB total). Will the model weights fit?
3. If vLLM `--gpu-memory-utilization` is 0.90, how much VRAM is left over for the PagedAttention KV Cache across all 4 GPUs?
<details>
<summary>Hint</summary>
4-bit = 0.5 bytes per parameter. 70 * 0.5 = VRAM for weights.
Total GPU VRAM = 96.
Total Allowed VRAM = 96 * 0.90.
KV Cache = Total Allowed - Weights.
</details>
<details>
<summary>Solution Walkthrough</summary>
```python
model_params = 70.0
# 1. 4-bit (AWQ) takes 0.5 bytes per param
weights_vram = model_params * 0.5 # 35 GB

total_hardware_vram = 4 * 24 # 96 GB

# 2. Yes! 35GB easily fits inside 96GB. We can serve a 70B model!

# 3. Calculate KV Cache space for vLLM
utilization = 0.90
total_usable_vram = total_hardware_vram * utilization # 86.4 GB

kv_cache_vram = total_usable_vram - weights_vram

print(f"Weights VRAM: {weights_vram} GB")
print(f"Total Usable VRAM (90%): {total_usable_vram:.1f} GB")
print(f"KV Cache VRAM for Concurrent Users: {kv_cache_vram:.1f} GB")
# Output: 51.4 GB for KV Cache.
# Thanks to PagedAttention, 51.4GB of cache can serve hundreds
# of concurrent requests per second flawlessly on consumer hardware!
```
</details>
