# 1.2 Primitive Types and Inference: Types Without the Typing

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
In JavaScript, a variable that starts as a string can silently turn into a number, and then into an array. This causes bizarre bugs where `1 + "1"` equals `"11"` instead of `2`. In large codebases, tracking what a variable currently holds requires holding the entire application state in your head—which is impossible for human brains.

### 2. Plain English Metaphor (The What)
Think of primitive types like specialized shipping containers. A liquid container (number) can only hold liquids. A refrigerated container (string) can only hold perishables. Inference is when the port authority (the TypeScript compiler) looks at the container being filled with milk and automatically slaps a "Liquid" sticker on it, saving you the effort of labeling it manually.

### 3. Complete Runnable Code: Stripe Tax Calculation Function

```typescript
// Explicit type annotations
const VAT_RATE: number = 0.20;
let isTaxHoliday: boolean = false;
let storeName: string = "Tech Haven";

// Type Inference (TypeScript guesses the types automatically)
let inferredDiscount = 5; // inferred as number
let inferredCurrency = "USD"; // inferred as string

// The 'void' type: Function returns nothing
function logTransaction(message: string): void {
  console.log(`[TRANSACTION LOG]: ${message}`);
}

// The 'never' type: Function never finishes (throws or infinite loop)
function throwCriticalError(errorMsg: string): never {
  throw new Error(`CRITICAL: ${errorMsg}`);
}

function calculateStripeTax(amount: number, region: string): number {
  if (amount < 0) {
    throwCriticalError("Amount cannot be negative");
  }

  const tax = isTaxHoliday ? 0 : amount * VAT_RATE;
  logTransaction(`Calculated tax for ${region}: ${tax}`);

  return tax;
}

const finalTax = calculateStripeTax(100, "NY");
```

### 4. Progressive Step-by-Step Breakdown

*   **Step 1: Explicit Annotations (`const VAT_RATE: number`)**
    We explicitly state the type. If we ever try to assign `VAT_RATE = "20%"`, the compiler will yell at us immediately.
*   **Step 2: Type Inference (`let inferredDiscount = 5`)**
    We didn't write `: number`. TypeScript saw `5` and figured it out. It's best practice to let TypeScript infer types for simple local variables to reduce visual clutter.
*   **Step 3: The `void` Type**
    `logTransaction` returns nothing. By marking it `void`, we prevent another developer from accidentally assigning its result to a variable (`const result = logTransaction(...)`).
*   **Step 4: The `never` Type**
    `throwCriticalError` always throws an exception. It *never* successfully returns. This is distinct from `void` (which returns `undefined`). It's crucial for control flow analysis.

### 5. ASCII Data Flow

```text
[let score = 100]  ======(TS looks at value)====>  [Inferred as 'number']
       |
[score = "high"]   =====(Checks against type)===>  [ERROR: Type 'string' is not
                                                     assignable to type 'number']
```

### 6. Noob Trap vs Pro Tip
*   **Noob Trap:** Typing everything explicitly. `let name: string = "Alice";`. This is redundant and makes the code noisy.
*   **Pro Tip:** Rely on Type Inference for variable initialization. Only explicitly annotate function parameters, function return types, and variables where the initial value doesn't give away the full type (e.g., an empty array).

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**Task:** Create a variable `appVersion` initialized to `"1.0.0"`. Let TypeScript infer the type. Then, create a function `updateVersion` that takes a `newVersion` string and updates `appVersion`. The function should return nothing (`void`).

<details>
<summary>Hint</summary>
Let TS infer `appVersion`. Annotate the parameter of `updateVersion` and its return type.
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
let appVersion = "1.0.0"; // Inferred as string

function updateVersion(newVersion: string): void {
  appVersion = newVersion;
}
```
*Walkthrough:* We save keystrokes on `appVersion`, but strictness is maintained. If we try `updateVersion(2)`, it fails.
</details>

### Level 2: Real-World
**Task:** Write a logging function `fatalCrash` that takes a `reason` (string), logs it to `console.error`, and then calls `process.exit(1)`. What is the correct return type for this function?

<details>
<summary>Hint</summary>
Because the function kills the process, it will never reach the end of its execution block.
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
function fatalCrash(reason: string): never {
  console.error(`FATAL: ${reason}`);
  process.exit(1);
}
```
*Walkthrough:* `never` is the correct type. This tells the compiler (and other developers) that calling this function stops the program dead in its tracks.
</details>

### Level 3: Boss Level
**Task:** You are building a payment gateway. Create a function `processPayment` that takes an `amount` (number).
If `amount` is less than 0, call a `panic` function (which you must also create) that throws an error.
If `amount` is 0, return a boolean `false`.
Otherwise, return a boolean `true`.
Use inference for local variables, but strict typing for all signatures.

<details>
<summary>Hint</summary>
You need two functions. `panic` will return `never`. `processPayment` will return `boolean`.
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
function panic(message: string): never {
  throw new Error(`Payment Gateway Error: ${message}`);
}

function processPayment(amount: number): boolean {
  if (amount < 0) {
    panic("Negative amount detected");
  }

  if (amount === 0) {
    return false;
  }

  const processingFee = 0.30; // Inferred as number
  // Complex logic here...

  return true;
}
```
*Walkthrough:* This challenge combines `number`, `boolean`, `never`, and inference. The compiler knows that after `panic()`, code execution stops, so it doesn't complain about missing return statements in that branch.
</details>
