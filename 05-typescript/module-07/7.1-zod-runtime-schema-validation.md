# 7.1 Zod: Runtime Safety Meets Static Types

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
TypeScript is a compile-time only tool. When you receive JSON from a `fetch` request or an Express `req.body`, it enters your app as `any` or `unknown`. If you just cast it `const user = req.body as User;`, TypeScript assumes you are correct. If the JSON is missing a required field, TS won't warn you, and your app will crash in production when it tries to read `user.id.toUpperCase()`.

### 2. Plain English Metaphor (The What)
TypeScript is like an architect's blueprint. It ensures the building is designed correctly on paper. Zod is the building inspector who stands at the door when people (data) try to enter. Zod checks their ID, measures their height, and ensures they strictly match the architect's blueprint *before* letting them inside. If they don't match, Zod kicks them out immediately with a detailed error report.

### 3. Complete Runnable Code: Production API Inbound Payload Validator

```typescript
import { z } from "zod";

// 1. Defining the Runtime Schema (The Inspector)
const UserSchema = z.object({
  id: z.string().uuid(), // Must be a string AND a valid UUID format
  email: z.string().email(),
  age: z.number().min(18, "Must be an adult"),
  role: z.enum(["admin", "user"]).default("user"), // Optional with default
});

// 2. Extracting the Static Type (The Blueprint)
// `z.infer` magically converts the Zod schema into a standard TypeScript type!
type User = z.infer<typeof UserSchema>;

/* This generates the equivalent of:
type User = {
  id: string;
  email: string;
  age: number;
  role: "admin" | "user";
}
*/

// 3. Validating Incoming Data
function handleApiRequest(reqBody: unknown) {
  // .safeParse doesn't throw. It returns a Discriminated Union { success: true | false }
  const result = UserSchema.safeParse(reqBody);

  if (!result.success) {
    // result.error contains detailed information about EXACTLY what failed
    console.error("Validation Failed:", result.error.issues);
    return;
  }

  // If success is true, TS knows `result.data` is strictly typed as `User`!
  const validUser: User = result.data;
  console.log(`Welcome, ${validUser.email}. Role: ${validUser.role}`);
}

// Simulating an incoming API request with missing data
handleApiRequest({
  id: "not-a-uuid", // Fails UUID check
  email: "invalid-email", // Fails Email check
  age: 12 // Fails minimum age check
});
```

### 4. Progressive Step-by-Step Breakdown

*   **Step 1: The Schema (`z.object`)**
    You define your rules using JavaScript objects via Zod. This code *actually runs* at runtime. You can chain validations like `.email()` or `.min()`.
*   **Step 2: Type Inference (`z.infer`)**
    Instead of writing a TypeScript `interface` *and* a validation schema (which violates DRY and risks them getting out of sync), you let Zod generate the TypeScript type for you. Single Source of Truth!
*   **Step 3: Parsing (`.parse` vs `.safeParse`)**
    - `UserSchema.parse(data)` will throw an Error if validation fails.
    - `UserSchema.safeParse(data)` returns a Discriminated Union, allowing you to handle the error gracefully without `try/catch`.

### 5. ASCII Data Flow

```text
Incoming JSON (req.body: unknown)
        |
        v
[ Zod Schema (UserSchema) ]
        |
    (Validation)
    /          [FAIL]       [PASS]
  |            |
Error Log    Returns Strongly Typed `User` Object
             (Available to the rest of the TS app safely)
```

### 6. Noob Trap vs Pro Tip
*   **Noob Trap:** Using `as` type assertions on API payloads. `const data = await res.json() as MyInterface`. This is literally lying to the compiler and is the #1 cause of runtime crashes in TS apps.
*   **Pro Tip:** Treat the boundary of your application (APIs, LocalStorage, File System) as a "Quarantine Zone". All data entering the app must pass through a Zod schema before it is allowed to touch your core business logic.

### Level 1: Warm-Up
**Task:** Create a Zod schema `ProductSchema` for an object with `name` (string) and `price` (number, minimum 0).
Use `z.infer` to extract a `ProductType`.
Create a valid object of `ProductType`.

<details>
<summary>Hint</summary>
Use `z.object({ name: z.string(), price: z.number().min(0) })`.
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
import { z } from "zod";

const ProductSchema = z.object({
  name: z.string(),
  price: z.number().min(0)
});

type ProductType = z.infer<typeof ProductSchema>;

const validProduct: ProductType = {
  name: "Mouse",
  price: 25.99
};
```
*Walkthrough:* We defined the schema and extracted the type. Zod acts as the bridge between the dynamic JS runtime and the static TS compiler.
</details>

### Level 2: Real-World
**Task:** Write a function `fetchConfig(jsonString: string)` that parses a JSON string.
The expected shape is `{ port: number, env: "development" | "production" }`.
Create the Zod schema (using `z.enum` for the env).
Use `Schema.parse()` inside a try/catch block. If it fails, log the error. If it succeeds, return the typed config.

<details>
<summary>Hint</summary>
Use `JSON.parse(jsonString)` first (which returns `any`), then pass that result to `ConfigSchema.parse()`.
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
import { z } from "zod";

const ConfigSchema = z.object({
  port: z.number(),
  env: z.enum(["development", "production"])
});

type Config = z.infer<typeof ConfigSchema>;

function fetchConfig(jsonString: string): Config | null {
  try {
    const rawData = JSON.parse(jsonString);
    // .parse will throw an error if validation fails
    const validConfig = ConfigSchema.parse(rawData);
    return validConfig;
  } catch (error) {
    console.error("Invalid Configuration", error);
    return null;
  }
}

console.log(fetchConfig('{"port": 8080, "env": "development"}')); // OK
console.log(fetchConfig('{"port": "8080"}')); // ERROR: port is string, missing env
```
*Walkthrough:* This is how you safely read config files or LocalStorage. `JSON.parse` is dangerous. Zod wraps that danger in a completely secure envelope.
</details>

### Level 3: Boss Level
**Task:** (Cumulative) Create a reusable, generic validation function `validatePayload<T>(schema: z.Schema<T>, payload: unknown): T`.
It takes *any* Zod schema, and an unknown payload.
It uses `.safeParse`. If it fails, it throws a standard `Error("Validation Error")`.
If it succeeds, it returns the strictly typed data.
Test it using the `ProductSchema` from Level 1.

<details>
<summary>Hint</summary>
The parameter `schema` is typed as `z.Schema<T>`. The function returns `T`. Use `schema.safeParse()`.
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
import { z } from "zod";

const ProductSchema = z.object({
  name: z.string(),
  price: z.number().min(0)
});

// A truly generic validation wrapper!
function validatePayload<T>(schema: z.Schema<T>, payload: unknown): T {
  const result = schema.safeParse(payload);

  if (!result.success) {
    throw new Error(`Validation Error: ${result.error.message}`);
  }

  return result.data;
}

// Simulating an incoming Express.js req.body
const reqBody: unknown = { name: "Keyboard", price: 100 };

try {
  // We pass the Zod Schema. TS infers `T` as the Product type automatically!
  const safeData = validatePayload(ProductSchema, reqBody);
  console.log(`Saved product: ${safeData.name}`);
} catch (e) {
  console.error(e);
}
```
*Walkthrough:* This combines Generics (`<T>`) with Zod schemas (`z.Schema<T>`). This specific utility function is found in almost every modern TS backend to sanitize all inbound API traffic cleanly and generically.
</details>
