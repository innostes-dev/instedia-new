# 4.2 Exhaustive Pattern Matching: Bulletproofing with `never`

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
You wrote a perfect `switch` statement for your Discriminated Union of `PaymentMethod`s (Credit Card, PayPal, Cash). Six months later, a coworker adds a new `"crypto"` payment method to the Union. They forget to update your `processPayment` function. TypeScript silently allows this. When a user tries to pay with crypto, your function does nothing, fails to charge them, and ships the product anyway.

### 2. Plain English Metaphor (The What)
Imagine a sorting machine that puts red, green, and blue balls into three distinct bins. What happens if a yellow ball comes down the chute? It rolls off the edge and breaks the machine. Exhaustiveness checking is like putting a laser sensor at the end of the chute. If *any* ball reaches the sensor (meaning it wasn't sorted into a bin), the laser triggers an alarm (a compiler error) *before* the factory even opens.

### 3. Complete Runnable Code: Exhaustive Payment Processor

```typescript
interface CreditCard { type: "credit_card"; cardToken: string; }
interface PayPal { type: "paypal"; email: string; }
// A coworker adds this later:
// interface Crypto { type: "crypto"; walletAddress: string; }

// type PaymentMethod = CreditCard | PayPal | Crypto; // Uncommenting this breaks the build!
type PaymentMethod = CreditCard | PayPal;

function processPayment(method: PaymentMethod) {
  switch (method.type) {
    case "credit_card":
      return chargeCard(method.cardToken);
    case "paypal":
      return chargePayPal(method.email);
    default:
      // THE EXHAUSTIVENESS CHECK
      // If we handled every possible `case`, TS knows `method` can be nothing else.
      // Therefore, it assigns `method` the type of `never`.
      // We assign it to a variable explicitly typed as `never`.
      const _exhaustiveCheck: never = method;

      // If a coworker adds "crypto" to the union but doesn't add a case block,
      // `method` will fall through to here as type `Crypto`.
      // TS will throw an ERROR: Type 'Crypto' is not assignable to type 'never'.

      return _exhaustiveCheck;
  }
}

// Dummy functions for compilation
function chargeCard(t: string) {}
function chargePayPal(e: string) {}
```

### 4. Progressive Step-by-Step Breakdown

*   **Step 1: The Switch and the Default Block**
    You write your `switch` statement as usual, handling every variant of the Discriminated Union. Crucially, you *must* include a `default` block.
*   **Step 2: The `never` Assignment**
    Inside the `default` block, you declare `const _check: never = variableName`.
*   **Step 3: How the Compiler Reasons**
    If you handled all cases, TypeScript's Control Flow Analysis removes every type from the union one by one. By the time it reaches the `default` block, there are no types left. The variable is reduced to `never`. Assigning `never` to `never` is valid.
*   **Step 4: The Alarm Bell**
    If you *missed* a case (e.g., `"crypto"`), it falls into the `default` block. TS sees `const _check: never = Crypto`. This is an illegal assignment. The compiler throws a massive red error, forcing the developer to add the missing `case` block before the code can be built.

### 5. ASCII Data Flow

```text
Union: [A | B | C]
            |
  (case A) -> Removes A -> Remaining: [B | C]
            |
  (case B) -> Removes B -> Remaining: [C]
            |
  (default) -> Variables arrives as type `C`!
               Try to assign `C` to `never` -> ERROR!
```

### 6. Noob Trap vs Pro Tip
*   **Noob Trap:** Using `eslint` rules to enforce `default` cases, but just throwing a generic runtime `Error("Unknown type")`. This catches the bug in production, not at compile time.
*   **Pro Tip:** Create a reusable utility function for exhaustiveness checking:
    ```typescript
    function assertUnreachable(x: never): never {
      throw new Error("Didn't expect to get here");
    }
    // usage in default block:
    default: return assertUnreachable(method);
    ```
    This gives you compile-time safety *and* a clean runtime fallback just in case some weird JS data slips through.

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**Task:** Create a union `type TrafficLight = "red" | "yellow" | "green"`. Write a function `nextLight(light: TrafficLight)` with a switch statement that returns the next color. Implement the `_exhaustiveCheck: never` pattern in the `default` block.

<details>
<summary>Hint</summary>
Switch on `light`. Return "green" for red, "red" for yellow, "yellow" for green. Add the default block.
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
type TrafficLight = "red" | "yellow" | "green";

function nextLight(light: TrafficLight): string {
  switch (light) {
    case "red": return "green";
    case "yellow": return "red";
    case "green": return "yellow";
    default:
      const _exhaustiveCheck: never = light;
      return _exhaustiveCheck;
  }
}
```
*Walkthrough:* Because we handled all three strings, TS successfully reduces `light` to `never` in the default block. Try adding `"blue"` to the union type and watch the compiler yell!
</details>

### Level 2: Real-World
**Task:** Implement the `assertUnreachable` utility function mentioned in the Pro Tip. Then, use it in a function that processes a Discriminated Union of `Notification` events (EmailNotification, SMSNotification).

<details>
<summary>Hint</summary>
The utility function signature is `function assertUnreachable(x: never): never`. Call it in the `default` block of your switch statement.
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
function assertUnreachable(x: never): never {
  throw new Error(`Unhandled case: ${JSON.stringify(x)}`);
}

interface EmailNotification { type: "email", emailAddress: string }
interface SMSNotification { type: "sms", phoneNumber: string }
type NotificationEvent = EmailNotification | SMSNotification;

function handleNotification(event: NotificationEvent) {
  switch (event.type) {
    case "email":
      console.log(`Emailing ${event.emailAddress}`);
      break;
    case "sms":
      console.log(`Texting ${event.phoneNumber}`);
      break;
    default:
      // This guarantees compile-time AND runtime safety!
      assertUnreachable(event);
  }
}
```
*Walkthrough:* This is the production-standard way to write robust code. If a new notification type is added, the code won't compile. If somehow invalid JS bypasses the compiler, it throws a descriptive error at runtime.
</details>

### Level 3: Boss Level
**Task:** (Cumulative) Combine Interfaces, Narrowing, Discriminated Unions, and Exhaustive Checks.
1. Create a `BaseAction` interface with `timestamp: number`.
2. Create `CreateUserAction` (extends Base, type: "CREATE", username: string).
3. Create `DeleteUserAction` (extends Base, type: "DELETE", userId: string).
4. Create a `ReduxAction` union of those two.
5. Write a `reducer(state: string[], action: ReduxAction): string[]` function.
6. Use a switch on `action.type`.
7. Enforce exhaustiveness.
(For CREATE, return a new array with the username. For DELETE, return the exact same state array for now).

<details>
<summary>Hint</summary>
You must extend the `BaseAction` correctly while specifying the literal string for `type`.
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
interface BaseAction {
  timestamp: number;
}

interface CreateUserAction extends BaseAction {
  type: "CREATE";
  username: string;
}

interface DeleteUserAction extends BaseAction {
  type: "DELETE";
  userId: string;
}

type ReduxAction = CreateUserAction | DeleteUserAction;

function assertUnreachable(x: never): never {
  throw new Error("Unhandled action");
}

function reducer(state: string[], action: ReduxAction): string[] {
  switch (action.type) {
    case "CREATE":
      // TS knows action is CreateUserAction here
      return [...state, action.username];
    case "DELETE":
      // TS knows action is DeleteUserAction here
      // (Actual deletion logic omitted for brevity)
      return state;
    default:
      // Exhaustive check
      return assertUnreachable(action);
  }
}
```
*Walkthrough:* This completely models a strongly-typed Redux or useReducer architecture. It guarantees that reducers handle every single action dispatched to them, completely eliminating a massive category of state management bugs.
</details>
