# 4.1 Discriminated Unions: Eliminating Impossible States

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
You are building a React component that fetches data. You model the state like this: `{ isLoading: boolean, error: string | null, data: any[] | null }`. This allows a completely impossible state: `{ isLoading: true, error: "Network Error", data: [{ id: 1 }] }`. Is it loading? Did it fail? Did it succeed? The UI doesn't know, and the developer has to write complex `if` statements to guess what's happening.

### 2. Plain English Metaphor (The What)
Think of an impossible state like a traffic light showing Red, Yellow, and Green simultaneously. It's dangerous and confusing. A Discriminated Union (or Tagged Union) is like a mechanical switch that physically forces the light to be *exactly one* color at a time. It uses a specific "tag" (like `status: "loading"`) to guarantee that only the properties relevant to that specific state exist.

### 3. Complete Runnable Code: Resilient Network Request State Machine

**The Bad Way (Allows Impossible States)**
```typescript
interface BadState {
  status: string;
  loading: boolean;
  error?: string;
  data?: any[];
}
const invalid: BadState = { status: "success", loading: true, error: "Failed", data: [] }; // TS allows this nonsense
```

**The Good Way (Discriminated Unions)**
```typescript
interface LoadingState {
  status: "loading"; // The Discriminant (Tag)
}

interface SuccessState {
  status: "success"; // The Discriminant (Tag)
  data: string[];
}

interface ErrorState {
  status: "error"; // The Discriminant (Tag)
  errorMessage: string;
}

type NetworkState = LoadingState | SuccessState | ErrorState;

function renderUI(state: NetworkState) {
  // We check the Discriminant property.
  // TS automatically narrows the type based on this check!

  if (state.status === "loading") {
    // TS knows `state` is LoadingState. `data` and `errorMessage` DO NOT exist here.
    return "Spinner...";
  }

  if (state.status === "error") {
    // TS knows `state` is ErrorState.
    return `Error: ${state.errorMessage}`;
  }

  if (state.status === "success") {
    // TS knows `state` is SuccessState.
    return `Loaded ${state.data.length} items.`;
  }
}
```

### 4. Progressive Step-by-Step Breakdown

*   **Step 1: The Discriminant Property**
    Every interface in the union must share exactly *one* property name (usually `type`, `kind`, or `status`). The value of this property *must* be a unique Literal Type (e.g., `"loading"`).
*   **Step 2: The Union**
    We combine these interfaces into a Union (`type State = A | B | C`).
*   **Step 3: The Switch/If Check**
    When we check the value of the discriminant (`state.status === "success"`), TypeScript acts like a switch on train tracks. It instantly drops the other possibilities and gives you strict, safe access to the specific properties of the `SuccessState`.

### 5. ASCII Data Flow

```text
[NetworkState] ---> Has property `status`
                         |
           (Switch on `status` property)
            /            |                 "loading"      "success"     "error"
         |               |             |
   [LoadingState]  [SuccessState] [ErrorState]
   (No extra data) (Has `data`)   (Has `errorMessage`)
```

### 6. Noob Trap vs Pro Tip
*   **Noob Trap:** Putting all possible properties into one giant interface and making them all optional (`?`). This creates "Swiss Army Knife" types that are full of `undefined` checks and impossible states.
*   **Pro Tip:** If your object's shape completely changes based on a specific property (like an event `type` or a request `status`), always use a Discriminated Union. It is the single most powerful pattern in TypeScript for modeling business logic safely.

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**Task:** Create a system for Shapes.
1. `Square` interface with `kind: "square"` and `size: number`.
2. `Rectangle` interface with `kind: "rectangle"`, `width: number`, `height: number`.
3. Create a `Shape` union.
4. Write a function `getArea(shape: Shape): number` that uses an `if` statement on `kind` to calculate the correct area.

<details>
<summary>Hint</summary>
Use the exact literal strings `"square"` and `"rectangle"` for the `kind` property.
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
interface Square {
  kind: "square";
  size: number;
}

interface Rectangle {
  kind: "rectangle";
  width: number;
  height: number;
}

type Shape = Square | Rectangle;

function getArea(shape: Shape): number {
  if (shape.kind === "square") {
    return shape.size * shape.size;
  }
  return shape.width * shape.height; // TS knows it's a Rectangle here!
}
```
*Walkthrough:* This is the textbook example of a discriminated union. The `kind` property guarantees that if it's a square, we have `size`, and if it's a rectangle, we have `width` and `height`.
</details>

### Level 2: Real-World
**Task:** Model a payment system.
A payment method can be `"credit_card"` (requires `cardNumber` and `cvv`), `"paypal"` (requires `email`), or `"cash"` (no extra properties).
Create the interfaces, the union `PaymentMethod`, and a function `processPayment(method: PaymentMethod)` that logs the relevant details safely based on the `type` property.

<details>
<summary>Hint</summary>
The discriminant property should be called `type`. Ensure the `"cash"` interface has NO extra properties besides the `type`.
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
interface CreditCard {
  type: "credit_card";
  cardNumber: string;
  cvv: string;
}

interface PayPal {
  type: "paypal";
  email: string;
}

interface Cash {
  type: "cash";
}

type PaymentMethod = CreditCard | PayPal | Cash;

function processPayment(method: PaymentMethod) {
  switch (method.type) {
    case "credit_card":
      console.log(`Charging card ending in ${method.cardNumber.slice(-4)}`);
      break;
    case "paypal":
      console.log(`Sending invoice to ${method.email}`);
      break;
    case "cash":
      console.log(`Expecting physical cash`);
      break;
  }
}
```
*Walkthrough:* Using a `switch` statement is highly recommended for Discriminated Unions. It keeps the code clean and perfectly aligns with how TS narrows the types in each `case` block.
</details>
