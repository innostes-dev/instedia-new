# 5.3 Generic Classes and Defaults: Flexible Data Structures

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
You need to build a custom caching system (or a Queue, Stack, etc.). You write a `Cache` class that stores `string` values. Tomorrow, another team needs to cache API response objects. You either have to copy-paste the whole class and create `ObjectCache`, or you change the storage to `any`, instantly destroying type safety for the entire application.

### 2. Plain English Metaphor (The What)
A Generic Class is like a customizable storage unit facility. You define the architecture of the building once (how doors lock, how items are stored and retrieved). But when a customer rents a unit, they specify exactly what goes inside (`<Car>`, `<Furniture>`). The facility enforces that rule for that specific unit. Generic Defaults (`<T = string>`) are like saying "If you don't specify what you're storing, we assume you're storing boxes."

### 3. Complete Runnable Code: High-Performance LRU In-Memory Cache

```typescript
// 1. Generic Class Definition
class MemoryCache<T> {
  // We use the generic type T for our internal data structure
  private store: Record<string, T> = {};

  // We use T for parameters
  set(key: string, value: T): void {
    this.store[key] = value;
  }

  // We use T for return types
  get(key: string): T | undefined {
    return this.store[key];
  }
}

// 2. Instantiating the Generic Class
interface UserSession {
  userId: string;
  token: string;
}

// The Cache is locked strictly to UserSession objects
const sessionCache = new MemoryCache<UserSession>();
sessionCache.set("sess_123", { userId: "u1", token: "abc" });
// sessionCache.set("sess_456", "invalid string"); // ERROR

// 3. Generic Defaults
// If no type is provided, it defaults to `string`
class SimpleBox<T = string> {
  constructor(public content: T) {}
}

const stringBox = new SimpleBox("Hello"); // T inferred as string
const numberBox = new SimpleBox<number>(42); // Explicitly overriden to number
```

### 4. Progressive Step-by-Step Breakdown

*   **Step 1: Class Declaration (`class Name<T>`)**
    The type variable `T` is declared at the class level. This means it is available to *every* method and property inside that class.
*   **Step 2: Internal State**
    We typed our internal dictionary as `Record<string, T>`. This ensures the class internals remain completely type-safe based on whatever the user requests.
*   **Step 3: Generic Defaults (`<T = DefaultType>`)**
    Just like default function parameters (`function(x = 5)`), you can provide a fallback type. This is incredibly useful for providing a sensible default behavior while allowing advanced users to override it if needed.

### 5. ASCII Data Flow

```text
new MemoryCache<UserSession>()
       |
       v
Class Blueprint is generated:
  store: Record<string, UserSession>
  set(key: string, value: UserSession)
  get(key: string): UserSession | undefined
       |
       v
Runtime enforces this specific blueprint for this specific instance.
```

### 6. Noob Trap vs Pro Tip
*   **Noob Trap:** Using Generics on the methods instead of the class (`class Cache { set<T>(val: T) }`). If you do this, you can set a string, and then fetch it as a number, breaking safety. The generic must be at the class level to link the `set` and `get` operations together!
*   **Pro Tip:** Combine Generic Constraints and Defaults: `class Repository<T extends BaseEntity = UserEntity>`. This is highly common in ORMs (like TypeORM or Prisma) to ensure data validity while keeping the API clean.

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**Task:** Create a generic class `Queue<T>`. It should have a private `data: T[] = []`. It should have an `enqueue(item: T)` method that pushes to the array, and a `dequeue(): T | undefined` method that returns `data.shift()`. Test it with a number queue.

<details>
<summary>Hint</summary>
Declare the class as `class Queue<T>`, and use `T` in the method signatures.
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
class Queue<T> {
  private data: T[] = [];

  enqueue(item: T): void {
    this.data.push(item);
  }

  dequeue(): T | undefined {
    return this.data.shift();
  }
}

const numQueue = new Queue<number>();
numQueue.enqueue(10);
// numQueue.enqueue("hello"); // ERROR
const first = numQueue.dequeue(); // Inferred as number | undefined
```
*Walkthrough:* We encapsulated the array logic. Because `T` is tied to the class instance, `enqueue` and `dequeue` are perfectly synchronized. You cannot enqueue a string into a number queue.
</details>

### Level 2: Real-World
**Task:** Create a generic class `APIResponseParser<T = unknown>`.
It takes a JSON string in its constructor.
It has a method `parse(): T` that returns `JSON.parse(theString)`.
Instantiate it once relying on the default (so `parse()` returns `unknown`), and instantiate it again passing an explicit interface `<User>` (so `parse()` returns a `User`).

<details>
<summary>Hint</summary>
`class APIResponseParser<T = unknown> { constructor(private jsonStr: string) {} ... }`
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
interface User { name: string; }

class APIResponseParser<T = unknown> {
  constructor(private jsonStr: string) {}

  parse(): T {
    // We cast it to T because JSON.parse returns any natively
    return JSON.parse(this.jsonStr) as T;
  }
}

const safeParser = new APIResponseParser('{"name": "Alice"}');
const unknownData = safeParser.parse(); // Type is unknown

const userParser = new APIResponseParser<User>('{"name": "Alice"}');
const userData = userParser.parse(); // Type is User
```
*Walkthrough:* The generic default `<T = unknown>` protects developers who are lazy. If they don't provide a type, TS forces them to deal with `unknown` safely. If they do provide a type, they get a clean, typed response.
</details>

### Level 3: Boss Level
**Task:** (Cumulative) Build a `DataStore<T extends { id: string }>` class.
It requires that all items stored have an `id` string.
- Private property `items: T[] = []`.
- `add(item: T): void`
- `findById(id: string): T | undefined`
Create a `Document` interface (id: string, title: string) and test the store.

<details>
<summary>Hint</summary>
Use the `.find()` array method in `findById`. The generic constraint `<T extends { id: string }>` is crucial to allow you to check `item.id === id` inside the `.find()` callback.
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
// The constraint guarantees that `item.id` will ALWAYS exist
class DataStore<T extends { id: string }> {
  private items: T[] = [];

  add(item: T): void {
    this.items.push(item);
  }

  findById(id: string): T | undefined {
    // We can safely access item.id because of the constraint!
    return this.items.find(item => item.id === id);
  }
}

interface Document {
  id: string;
  title: string;
}

const docStore = new DataStore<Document>();
docStore.add({ id: "doc_1", title: "My Specs" });

const found = docStore.findById("doc_1"); // Type is Document | undefined
if (found) {
  console.log(found.title);
}

// const badStore = new DataStore<number>(); // ERROR: number doesn't satisfy { id: string }
```
*Walkthrough:* This is how enterprise-grade libraries are built. The constraint guarantees that internal logic (like searching by ID) will always work, while remaining completely generic regarding what *other* properties the stored objects might have.
</details>
