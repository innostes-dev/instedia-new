# 6.2 Pick, Omit, Exclude, and Extract: Sculpting Your Types

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
Your database `User` model has a `passwordHash`, `ssn`, and `creditCardToken`. You need to return this user to the frontend via an API. If you accidentally use the `User` interface for the API response, you might accidentally leak sensitive data. You need a way to say: "Give me the User object, but remove the password and SSN."

### 2. Plain English Metaphor (The What)
Think of these as sculptors for your types.
- `Omit`: A chisel. You take a block of stone (an object) and chip away the specific pieces you don't want (`passwordHash`).
- `Pick`: A magnet. You wave it over the block of stone and it pulls out *only* the specific pieces you asked for (`id`, `username`).
- `Exclude` / `Extract`: These do the same thing, but for Unions (like `"A" | "B" | "C"`) instead of Objects.

### 3. Complete Runnable Code: Public User DTO Builder

```typescript
interface DBUser {
  id: string;
  username: string;
  email: string;
  passwordHash: string;
  createdAt: Date;
}

// 1. Omit<Type, Keys>
// Creates a new type by removing the specified keys.
// Useful when you want ALMOST everything.
type PublicUser = Omit<DBUser, "passwordHash" | "createdAt">;

const safeResponse: PublicUser = {
  id: "123",
  username: "alice",
  email: "a@b.com"
  // passwordHash is not allowed here!
};

// 2. Pick<Type, Keys>
// Creates a new type with ONLY the specified keys.
// Useful when you only want a tiny fraction of a massive object.
type UserAvatarData = Pick<DBUser, "id" | "username">;

const avatar: UserAvatarData = {
  id: "123",
  username: "alice"
};

// 3. Exclude<UnionType, ExcludedMembers>
// Removes specific literal types from a Union.
type Status = "pending" | "approved" | "rejected" | "banned";
type ActiveStatus = Exclude<Status, "banned" | "rejected">;
// ActiveStatus is now exactly: "pending" | "approved"

// 4. Extract<UnionType, ExtractedMembers>
// The opposite of Exclude. Keeps only the matching members.
type BannedStatus = Extract<Status, "banned">;
```

### 4. Progressive Step-by-Step Breakdown

*   **Step 1: `Omit` vs `Pick`**
    Use `Omit` when you want to remove 1 or 2 fields from a 20-field object. Use `Pick` when you want to extract 1 or 2 fields from a 20-field object. They are functionally opposites, applied to *Objects/Interfaces*.
*   **Step 2: `Exclude` vs `Extract`**
    These do the exact same conceptual thing, but they operate on *Unions of primitives* (like strings), not objects.
*   **Step 3: The Pipe Operator `|`**
    When providing the keys to `Omit` or `Pick`, you use a string literal union: `Omit<User, "key1" | "key2">`.

### 5. ASCII Data Flow

```text
{ a: 1, b: 2, c: 3 }
        |
   Pick<Obj, "a">  ===> { a: 1 }
        |
  Omit<Obj, "c">   ===> { a: 1, b: 2 }

"A" | "B" | "C"
        |
Exclude<Union, "B"> ===> "A" | "C"
```

### 6. Noob Trap vs Pro Tip
*   **Noob Trap:** Duplicating interfaces manually (`interface PublicUser { ... }`) to hide private fields. If the database `email` field changes to `contactEmail`, `PublicUser` won't update automatically, causing runtime bugs.
*   **Pro Tip:** Always build your Data Transfer Objects (DTOs) using `Pick` and `Omit` from the master database schema type. This creates a Single Source of Truth. If the DB schema changes, the DTOs instantly flag compiler errors if they are impacted.

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**Task:** Create an interface `Car` (make: string, model: string, year: number, vinNumber: string).
Use `Omit` to create a `PublicCar` type that hides the `vinNumber`.
Create a valid object of type `PublicCar`.

<details>
<summary>Hint</summary>
`type PublicCar = Omit<Car, "vinNumber">;`
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
interface Car {
  make: string;
  model: string;
  year: number;
  vinNumber: string;
}

type PublicCar = Omit<Car, "vinNumber">;

const myCar: PublicCar = {
  make: "Toyota",
  model: "Camry",
  year: 2022
};
// myCar.vinNumber = "123"; // ERROR
```
*Walkthrough:* We successfully hid the sensitive Vehicle Identification Number from the resulting type without duplicating the `make`, `model`, and `year` definitions.
</details>

### Level 2: Real-World
**Task:** You have `interface Product { id: number, name: string, price: number, inStock: boolean, category: string }`.
You are building a lightweight dropdown menu. It only needs the `id` and `name`. Use `Pick` to create a `ProductDropdownData` type.

<details>
<summary>Hint</summary>
`type ProductDropdownData = Pick<Product, "id" | "name">;`
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
interface Product {
  id: number;
  name: string;
  price: number;
  inStock: boolean;
  category: string;
}

type ProductDropdownData = Pick<Product, "id" | "name">;

const dropdownItem: ProductDropdownData = {
  id: 1,
  name: "Laptop"
};
```
*Walkthrough:* Using `Pick` is much cleaner than using `Omit` here, because we want to ignore 3 properties and only keep 2. Always choose the one that requires less typing!
</details>

### Level 3: Boss Level
**Task:** (Cumulative) Combine Utility Types!
1. `interface User { id: string, name: string, passwordHash: string, role?: string }`.
2. Create `CreateUserPayload`. When creating a user, we don't have an `id` yet (the DB generates it). We don't want to allow passing `role` either (for security).
3. Use `Omit` to remove `id` and `role` from `User`.
4. However, `name` and `passwordHash` might have been optional originally? Wait, they weren't. But just to be safe, wrap your `Omit` result in `Required` so that `name` and `passwordHash` are 100% strictly required for account creation.

<details>
<summary>Hint</summary>
Utility types can be nested! `type CreateUserPayload = Required<Omit<User, "id" | "role">>;`
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
interface User {
  id: string;
  name: string;
  passwordHash: string;
  role?: string;
}

// 1. Remove id and role
// 2. Ensure everything that remains is absolutely required
type CreateUserPayload = Required<Omit<User, "id" | "role">>;

const validPayload: CreateUserPayload = {
  name: "Alice",
  passwordHash: "hash123"
};

// const invalidPayload: CreateUserPayload = { name: "Bob" }; // ERROR: missing passwordHash
// const hackerPayload: CreateUserPayload = { name: "Eve", passwordHash: "h", role: "admin" }; // ERROR: Object literal may only specify known properties
```
*Walkthrough:* This is peak TypeScript. We dynamically sculpted the exact data requirement for a POST request based entirely on our core database model. By nesting utilities, we guarantee perfect safety and a Single Source of Truth.
</details>
