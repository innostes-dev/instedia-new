# 6.1 Partial, Required, and Readonly: The Core Transformers

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
You have a strict `User` interface with 15 required fields. Now you need to build an "Update Profile" API endpoint. The user might only send an `email` to update, or maybe just their `bio`. Do you create a duplicate `UpdateUser` interface where every single property is marked as optional (`?`)? That violates DRY. If you add a new field to `User`, you'll inevitably forget to add it to `UpdateUser`.

### 2. Plain English Metaphor (The What)
Utility Types are built-in TypeScript blueprints that take an existing mold and automatically reshape it.
- `Partial` takes your rigid mold and makes every single section optional.
- `Required` takes a mold with optional sections and forces them to be mandatory.
- `Readonly` takes a mold and covers it in glass—you can look at the data, but you can never alter it.

### 3. Complete Runnable Code: User Settings Patch Update Form

```typescript
interface UserSettings {
  id: string;
  theme?: "light" | "dark";
  notificationsEnabled?: boolean;
}

// 1. Partial<T>
// Makes everything optional. Great for PATCH requests!
type UpdateSettingsDTO = Partial<UserSettings>;

function updateSettings(id: string, patch: UpdateSettingsDTO) {
  // It's perfectly fine to only pass ONE of the properties.
  console.log(`Updating user ${id} with:`, patch);
}
updateSettings("u1", { theme: "dark" }); // OK

// 2. Required<T>
// Strips away the `?` modifiers. Everything is mandatory.
type CompleteSettings = Required<UserSettings>;

const defaultSettings: CompleteSettings = {
  id: "u1",
  theme: "light",
  notificationsEnabled: true
}; // If we leave out `theme`, it will error!

// 3. Readonly<T>
// Prevents mutation of properties. Great for Redux state or Context!
type ImmutableSettings = Readonly<UserSettings>;

const state: ImmutableSettings = {
  id: "u1",
  theme: "dark"
};
// state.theme = "light"; // ERROR: Cannot assign to 'theme' because it is a read-only property.
```

### 4. Progressive Step-by-Step Breakdown

*   **Step 1: The Base Interface**
    Always define your strictest, most comprehensive data model first (e.g., the database schema or core domain object).
*   **Step 2: Deriving with Utilities**
    Instead of writing new interfaces, derive them using `<T>` generics. `Partial<UserSettings>` reads the `UserSettings` type, iterates over its keys, and slaps a `?` on every single one behind the scenes.
*   **Step 3: Shallow vs Deep**
    By default, `Partial`, `Required`, and `Readonly` are **shallow**. If you have nested objects (`user.preferences.color`), `Readonly<User>` will freeze `user.preferences`, but it will *not* freeze `user.preferences.color`. (We will build a DeepReadonly utility in the Engineering Challenges!).

### 5. ASCII Data Flow

```text
interface Config { port: number; host?: string; }
       |
       v
Partial<Config>  ====> { port?: number; host?: string; }
       |
       v
Required<Config> ====> { port: number; host: string; }
       |
       v
Readonly<Config> ====> { readonly port: number; readonly host?: string; }
```

### 6. Noob Trap vs Pro Tip
*   **Noob Trap:** Using `Partial<T>` for object creation (POST requests). If you make everything optional, a developer might send `{}` to your API, and the compiler won't stop them. `Partial` is almost exclusively for updates (PATCH requests) or state diffs.
*   **Pro Tip:** You can combine them! `Readonly<Partial<Config>>` creates an object where everything is optional, but whatever *is* provided cannot be changed later.

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**Task:** Create an interface `Todo` (title: string, description: string). Create a function `editTodo(id: number, changes: Partial<Todo>)`. Call the function, passing only the `description` to update.

<details>
<summary>Hint</summary>
Use the `Partial<T>` utility type for the `changes` parameter.
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
interface Todo {
  title: string;
  description: string;
}

function editTodo(id: number, changes: Partial<Todo>) {
  console.log(`Updating ${id}`, changes);
}

// Valid because Partial made `title` optional!
editTodo(1, { description: "Buy milk instead" });
```
*Walkthrough:* Without `Partial`, the compiler would throw an error demanding `title`. This is the perfect use case for `Partial`.
</details>

### Level 2: Real-World
**Task:** You are reading environment variables. You have `interface Env { PORT?: string, DB_URL?: string }`.
Write a function `startApp(env: Required<Env>)`.
Create a raw config object that is missing a field. Attempt to pass it in. Observe the error.

<details>
<summary>Hint</summary>
The compiler will complain that a property is missing because `Required` strips the `?` modifiers.
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
interface Env {
  PORT?: string;
  DB_URL?: string;
}

function startApp(env: Required<Env>) {
  console.log(`Starting on ${env.PORT}, connecting to ${env.DB_URL}`);
}

const myConfig: Env = {
  PORT: "8080"
};

// ERROR: Property 'DB_URL' is missing in type 'Env' but required in type 'Required<Env>'.
// startApp(myConfig);
```
*Walkthrough:* `Required` is fantastic for boundary layers. It guarantees that by the time data reaches the core of your app, all optional fields have been filled in with defaults or validated.
</details>

### Level 3: Boss Level
**Task:** (Cumulative) Create a state management hook signature.
Create `interface State { count: number; user: string }`.
Write a function `useState(initial: State): [Readonly<State>, (patch: Partial<State>) => void]`.
(This mimics React's useState but with an object patcher).
Implement a dummy version of the function and try to mutate the state directly to prove `Readonly` works.

<details>
<summary>Hint</summary>
The return type is a tuple: `[Readonly<State>, (patch: Partial<State>) => void]`.
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
interface State {
  count: number;
  user: string;
}

function useState(initial: State): [Readonly<State>, (patch: Partial<State>) => void] {
  let state = { ...initial };

  const setState = (patch: Partial<State>) => {
    state = { ...state, ...patch };
    console.log("New state:", state);
  };

  return [state, setState];
}

const [state, setState] = useState({ count: 0, user: "Alice" });

// state.count = 1; // ERROR: Cannot assign to 'count' because it is a read-only property!

// Correct way to update (using Partial patch)
setState({ count: 1 });
```
*Walkthrough:* This completely models a Redux or React Context architecture. We use `Readonly` to prevent direct mutations by the consumer, and `Partial` to allow the consumer to send small diffs rather than the whole object.
</details>
