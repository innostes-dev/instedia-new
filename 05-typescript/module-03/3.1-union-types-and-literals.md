# 3.1 Union Types and Literals: Accepting Multiple Realities

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
In JavaScript, a function parameter like `status` might expect the exact strings `"pending"`, `"shipped"`, or `"delivered"`. If a developer makes a typo and passes `"shiped"`, JavaScript happily accepts it. Downstream, your database query fails or a customer sees a broken UI because the code didn't account for `"shiped"`.

### 2. Plain English Metaphor (The What)
Think of a standard type (like `string`) as a massive warehouse containing every possible word in the universe. A Literal Type (`"pending"`) is a single, specific box in that warehouse. A Union Type (`|`) is a strict VIP list. If a value isn't on the list (`"pending" | "shipped" | "delivered"`), the bouncer (the compiler) kicks it out at the door.

### 3. Complete Runnable Code: Order Status State Indicator

```typescript
// A Union of Primitive Types
function printId(id: string | number) {
  console.log(`Your ID is: ${id}`);
}
printId(101); // OK
printId("202-A"); // OK
// printId(true); // ERROR: boolean not assignable to string | number

// Literal Union Types (The VIP List)
type OrderStatus = "pending" | "shipped" | "delivered" | "cancelled";

function updateStatus(orderId: string, newStatus: OrderStatus) {
  console.log(`Updating order ${orderId} to ${newStatus}`);
}

updateStatus("ORD-1", "shipped"); // OK
// updateStatus("ORD-1", "shiped"); // ERROR: Typo caught immediately!

// Mixing Literal Types with Interfaces
interface BaseConfig {
  retries: number;
}
type Strategy = "fast" | "reliable";

function setupConnection(config: BaseConfig | Strategy) {
  // We will learn how to narrow this safely in 3.2!
}
```

### 4. Progressive Step-by-Step Breakdown

*   **Step 1: The `|` Operator**
    The pipe `|` means "OR". `string | number` means the variable can be *either* a string *or* a number.
*   **Step 2: Literal Types**
    TypeScript allows you to use specific values as types. `"pending"` is a type that only accepts the exact string `"pending"`.
*   **Step 3: Combining Literals into Unions**
    By chaining literal types (`"pending" | "shipped"`), you create an incredibly strict contract. It acts like an Enum, but is often much cleaner and faster because it compiles away entirely in JavaScript (unlike standard Enums which generate bulky JS objects).

### 5. ASCII Data Flow

```text
Input: "shiped"
         |
[Is it "pending"?] ---> No
         |
[Is it "shipped"?] ---> No
         |
[Is it "delivered"?]--> No
         |
    [REJECTED]
```

### 6. Noob Trap vs Pro Tip
*   **Noob Trap:** Using TypeScript `enum` everywhere. Enums in TS have weird edge cases, generate extra JavaScript code, and don't behave like standard types.
*   **Pro Tip:** Stick to String Literal Unions (`type Role = "admin" | "user"`) instead of `enum`. They are idiomatic, safer, and have zero runtime overhead.

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**Task:** Create a type `Size` that only allows the strings `"S"`, `"M"`, `"L"`, or `"XL"`. Write a function `printTag` that accepts a `Size` and logs it.

<details>
<summary>Hint</summary>
Use the pipe operator `|` to join the literal strings.
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
type Size = "S" | "M" | "L" | "XL";

function printTag(size: Size) {
  console.log(`Printed tag for size: ${size}`);
}
```
*Walkthrough:* We constrained the domain of possible strings down to just four valid options.
</details>

### Level 2: Real-World
**Task:** Create a type `HTTPCode` that allows the literal numbers `200`, `400`, `404`, and `500`. Create an interface `ErrorResponse` that requires an `HTTPCode` and a `message` string.

<details>
<summary>Hint</summary>
Literal types aren't just for strings! You can use numbers too.
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
type HTTPCode = 200 | 400 | 404 | 500;

interface ErrorResponse {
  code: HTTPCode;
  message: string;
}

const badReq: ErrorResponse = {
  code: 400,
  message: "Missing parameter"
};
```
*Walkthrough:* By restricting `code` to specific literal numbers, we prevent a developer from accidentally throwing an error with code `999`.
</details>

### Level 3: Boss Level
**Task:** (Cumulative) Create a `User` interface with `name` (string).
Create an `Admin` interface extending `User` with `adminLevel` (number).
Create a union type `Person` that can be *either* a `User` *or* an `Admin`.
Finally, write a function `logPerson` that accepts a `Person`. If you try to access `person.adminLevel` directly, TS will throw an error. Why? (Just write a comment explaining why it fails; we solve this in the next lesson).

<details>
<summary>Hint</summary>
When you have a union of objects (`A | B`), TypeScript only allows you to access properties that exist on *both* `A` and `B` safely, until you narrow it.
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
interface User {
  name: string;
}

interface Admin extends User {
  adminLevel: number;
}

type Person = User | Admin;

function logPerson(person: Person) {
  console.log(person.name); // OK, exists on both

  // console.log(person.adminLevel);
  // ERROR EXPLANATION:
  // TS knows `person` MIGHT be a regular User.
  // Regular Users don't have an `adminLevel`.
  // Therefore, accessing it directly is unsafe and TS blocks it.
}
```
*Walkthrough:* This illustrates the fundamental challenge of Union types. You can accept multiple realities, but you must *prove* to the compiler which reality you are currently in before accessing unique properties.
</details>
