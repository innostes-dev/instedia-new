# 3.3 Custom Type Predicates: Building Your Own Guards

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
You write a complex validation function like `isUser(obj)`. It checks 10 different properties. But when you use it in an `if` statement (`if (isUser(myData))`), TypeScript *still* complains that `myData` is `unknown`. Why? Because `isUser` just returns a `boolean`. TypeScript doesn't automatically know that returning `true` means the data *is* a User.

### 2. Plain English Metaphor (The What)
A standard boolean function is like a security guard telling the boss "Yes, I checked them." The boss (TypeScript) says, "Okay, but you didn't tell me *who* they are, so they still can't come in." A Type Predicate (`val is Type`) is the guard saying, "Yes, I checked them, AND I certify they are an Official Employee." The boss now trusts the specific identity of the data.

### 3. Complete Runnable Code: HTTP Error Payload Detector

```typescript
interface NetworkError {
  code: number;
  retryable: boolean;
}

// Standard boolean function (Does NOT narrow types)
function isNetworkErrorBad(err: unknown): boolean {
  return typeof err === "object" && err !== null && "retryable" in err;
}

// Custom Type Predicate (DOES narrow types)
// Notice the return type: `err is NetworkError`
function isNetworkErrorGood(err: unknown): err is NetworkError {
  return typeof err === "object" && err !== null && "retryable" in err;
}

function handleApiFailure(errorPayload: unknown) {
  if (isNetworkErrorBad(errorPayload)) {
    // TS ERROR: Object is of type 'unknown'.
    // console.log(errorPayload.retryable);
  }

  if (isNetworkErrorGood(errorPayload)) {
    // SUCCESS! TS trusts the predicate and narrows the type.
    if (errorPayload.retryable) {
      console.log(`Retrying error code: ${errorPayload.code}...`);
    }
  }
}
```

### 4. Progressive Step-by-Step Breakdown

*   **Step 1: The Predicate Syntax (`arg is Type`)**
    You replace the standard `boolean` return type with `parameterName is TypeName`.
*   **Step 2: The Contract**
    By using this syntax, you make a promise to the TypeScript compiler: "If this function returns `true`, I guarantee on my life that the argument matches this type."
*   **Step 3: The Danger**
    TypeScript trusts you blindly here. If you write bad logic inside the predicate, but return `true`, TypeScript will narrow the type anyway, potentially causing a runtime crash. *With great power comes great responsibility.*

### 5. ASCII Data Flow

```text
errorPayload (unknown)
         |
    isNetworkErrorGood(errorPayload)
         |
     [Returns True] ---> TS sees `err is NetworkError`
         |
  Inside the `if` block, errorPayload is strongly typed!
```

### 6. Noob Trap vs Pro Tip
*   **Noob Trap:** Using type predicates for simple primitive checks (like `isString(val)`). Just use inline `typeof` checks; they are easier to read and TS understands them natively.
*   **Pro Tip:** Use Custom Type Predicates when filtering arrays! `const users = mixedArray.filter(isUser);`. TS will automatically infer `users` as a strictly typed `User[]` array instead of `(User | string)[]`.

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**Task:** Create an interface `Car` with `wheels` (number). Write a custom type predicate function `isCar(vehicle: unknown): vehicle is Car`. It should check if the object exists and has the `wheels` property.

<details>
<summary>Hint</summary>
The return type must be `vehicle is Car`. The logic needs to verify it's an object before using the `in` operator.
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
interface Car {
  wheels: number;
}

function isCar(vehicle: unknown): vehicle is Car {
  return typeof vehicle === "object" && vehicle !== null && "wheels" in vehicle;
}
```
*Walkthrough:* We establish the contract `vehicle is Car`. We perform standard runtime safety checks (not null, is object) before checking for the specific property.
</details>

### Level 2: Real-World
**Task:** You have an array of mixed data: `const data = ["apple", null, "banana", undefined, "cherry"];`. Write a generic type predicate `isNotNullish<T>(val: T | null | undefined): val is T`. Use it in a `.filter()` to create a clean array of strings, properly inferred by TS.

<details>
<summary>Hint</summary>
`(val: T | null | undefined): val is T` means "If I return true, strip away null and undefined from the type."
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
function isNotNullish<T>(val: T | null | undefined): val is T {
  return val !== null && val !== undefined;
}

const data = ["apple", null, "banana", undefined, "cherry"];

// cleanData is inferred as string[]
const cleanData = data.filter(isNotNullish);
```
*Walkthrough:* This is an incredibly powerful utility function you will see in almost every production TS codebase. Without the predicate, `cleanData` would be inferred as `(string | null | undefined)[]`.
</details>

### Level 3: Boss Level
**Task:** (Cumulative) Create interfaces `Admin` (role: "admin", delete(): void) and `User` (role: "user").
Create a type predicate `isAdmin(person: Admin | User): person is Admin`.
Notice that the parameter type is `Admin | User`, not `unknown`. This means you can just check the `role` property directly.
Write a function `execute(person: Admin | User)` that uses the predicate to safely call `person.delete()` if they are an admin.

<details>
<summary>Hint</summary>
Since the input is already a union of objects with a `role` property, your predicate logic just needs to be `return person.role === "admin";`
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
interface Admin {
  role: "admin";
  delete(): void;
}

interface User {
  role: "user";
}

// Notice we restrict the input to our known domain, rather than `unknown`
function isAdmin(person: Admin | User): person is Admin {
  return person.role === "admin";
}

function execute(person: Admin | User) {
  if (isAdmin(person)) {
    // Safely narrowed to Admin
    person.delete();
  } else {
    // Safely narrowed to User
    console.log("Access denied");
  }
}
```
*Walkthrough:* Type predicates aren't just for `unknown` data. They are perfect for extracting complex narrowing logic (like checking a specific union discriminator) into a clean, reusable helper function.
</details>
