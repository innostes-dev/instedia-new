# 2.1 Interfaces vs Type Aliases: Shaping Your Data

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
You are building an app with a User object passed through a dozen functions. Some functions expect a `username`, others an `email`. Sometimes a user has a `billingPlan`, sometimes they don't. Without a central source of truth for what a "User" actually is, you end up checking `if (user.billingPlan)` over and over, and inevitably miss one, causing a crash when you try to charge a non-existent card.

### 2. Plain English Metaphor (The What)
Think of an `interface` or `type` like a rigid mold at a plastic factory. If you pour data into the mold, it must perfectly fill all the required sections. If the plastic is missing a piece (a missing property), the factory rejects it. If there's extra plastic spilling out (an unknown property), it also rejects it. Optional properties are like sections of the mold you can choose to block off if you don't need them.

### 3. Complete Runnable Code: User Profile & Subscription Account Contract

```typescript
// Using a Type Alias
type Plan = "free" | "pro" | "enterprise";

// Using an Interface for an object contract
interface UserProfile {
  id: string;
  email: string;
  // The '?' makes this property optional. It might be a string, or it might be undefined.
  displayName?: string;
  // 'readonly' prevents this property from being reassigned after creation.
  readonly createdAt: Date;
  plan: Plan;
}

function processSubscription(user: UserProfile) {
  // Safe to access because it's guaranteed to exist
  console.log(`Processing ${user.email} on ${user.plan} plan.`);

  // Safe to check optional property
  if (user.displayName) {
    console.log(`Sending welcome email to ${user.displayName}.`);
  }

  // Compiler Error: Cannot assign to 'createdAt' because it is a read-only property.
  // user.createdAt = new Date();
}

const newUser: UserProfile = {
  id: "usr_123",
  email: "alice@example.com",
  createdAt: new Date(),
  plan: "pro"
  // displayName is omitted, which is perfectly valid due to the '?'
};

processSubscription(newUser);
```

### 4. Progressive Step-by-Step Breakdown

*   **Step 1: The Base Contract (`interface UserProfile`)**
    We define the fundamental shape. Every UserProfile *must* have an `id` and `email`.
*   **Step 2: Optional Properties (`?`)**
    `displayName?: string;` means `displayName` can either be a `string` or `undefined`. This forces developers to check if it exists before using string methods on it.
*   **Step 3: Immutability (`readonly`)**
    `readonly createdAt: Date;` ensures that once the object is constructed, the `createdAt` timestamp cannot be accidentally mutated later in the codebase.
*   **Step 4: Interfaces vs Types**
    We used `type Plan = "free" | "pro"`. You *cannot* use an interface to define a union of strings. Interfaces are strictly for defining the shapes of objects. Type aliases (`type`) can be used for objects, unions, primitives, and more.

### 5. ASCII Data Flow

```text
[Raw Object literal]
  { id: "1", email: "a@b.com", createdAt: ... }
           |
           v
[(Checking against Interface)]
  - Has id? Yes.
  - Has email? Yes.
  - Has createdAt? Yes.
  - Has displayName? No (But it's optional, so OK)
           |
           v
       [ACCEPTED] -> Handed to Function
```

### 6. Noob Trap vs Pro Tip
*   **Noob Trap:** Using `?` optional properties excessively as a band-aid when different variations of an object are passed around. If an object is so different, it should probably be two distinct interfaces.
*   **Pro Tip:** Use `interface` by default for object shapes, as they give slightly better error messages and can be declaration-merged. Use `type` for unions, intersections, and primitive aliases.

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**Task:** Create an interface `Product` with an `id` (readonly string), `price` (number), and an optional `description` (string). Write a function `printProduct` that logs the ID, price, and description (or "No description" if none exists).

<details>
<summary>Hint</summary>
Use `readonly id: string` and `description?: string`. Use the `??` (nullish coalescing) operator or an `if` statement for the description.
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
interface Product {
  readonly id: string;
  price: number;
  description?: string;
}

function printProduct(product: Product) {
  console.log(`Product ${product.id} costs $${product.price}.`);
  console.log(`Description: ${product.description ?? "No description"}`);
}
```
*Walkthrough:* The `readonly` modifier protects the `id`. The `?` on description forces us to handle the case where it isn't provided, which we handle cleanly with `??`.
</details>

### Level 2: Real-World
**Task:** Define a type `Method` which can only be `"GET"`, `"POST"`, or `"DELETE"`. Create an interface `ApiRequest` that requires a `url` (string), a `method` (of type `Method`), and an optional `body` (type `unknown`).

<details>
<summary>Hint</summary>
Use a union string type for `Method`.
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
type Method = "GET" | "POST" | "DELETE";

interface ApiRequest {
  url: string;
  method: Method;
  body?: unknown;
}

const req: ApiRequest = {
  url: "/api/users",
  method: "POST",
  body: { name: "Alice" }
};
```
*Walkthrough:* We combine a union type (`Method`) with an interface. The `body` is `unknown` because an API request body could be anything, forcing whoever reads it to validate it (as learned in 1.3).
</details>

### Level 3: Boss Level
**Task:** Combine concepts. Create an `AppSettings` interface. It should have a readonly `appId` (string). It should have an optional `theme` (string, either "light" or "dark"). It must have an `updateTheme` function property that takes a string and returns nothing. Implement an object that satisfies this interface.

<details>
<summary>Hint</summary>
Function properties in interfaces look like `updateTheme(theme: string): void;` or `updateTheme: (theme: string) => void;`.
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
type Theme = "light" | "dark";

interface AppSettings {
  readonly appId: string;
  theme?: Theme;
  updateTheme(newTheme: Theme): void;
}

const mySettings: AppSettings = {
  appId: "app_999",
  theme: "light",
  updateTheme(newTheme: Theme) {
    this.theme = newTheme;
    console.log(`Theme updated to ${newTheme}`);
  }
};

mySettings.updateTheme("dark");
// mySettings.appId = "new_id"; // Error: Cannot assign to 'appId'
```
*Walkthrough:* We defined a `Theme` union for strictness. `AppSettings` requires a method. The implementation `mySettings` perfectly adheres to the contract, preventing reassignment of the ID while allowing strict theme updates.
</details>
