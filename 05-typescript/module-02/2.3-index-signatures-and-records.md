# 2.3 Index Signatures and Records: Dynamic Keys

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
You need to store a cache of currency exchange rates where the key is the currency code (e.g., "USD", "EUR") and the value is the rate. Or you need a dictionary of HTTP headers. The keys are dynamic—you don't know them in advance—so you can't explicitly define `USD: number; EUR: number;` in an interface. If you just type it as `any` or `object`, you lose all type safety on the values.

### 2. Plain English Metaphor (The What)
Think of an index signature like a coat check room at a fancy restaurant. You don't know exactly *which* coat tickets (the keys) will be handed to you today, but you know that *every* ticket you accept must be paired with exactly one coat (the value). You are enforcing a rule on the *pattern* of data, not the specific names of the properties.

### 3. Complete Runnable Code: Real-Time Currency Exchange Rate Cache

**Using Index Signatures (Interfaces)**
```typescript
interface CurrencyCache {
  // "Any string key used on this object MUST return a number"
  [currencyCode: string]: number;
}

const rates: CurrencyCache = {
  USD: 1.0,
  EUR: 0.85,
  GBP: 0.75
};

rates["JPY"] = 110.2; // OK
// rates["AUD"] = "invalid"; // ERROR: Type 'string' is not assignable to type 'number'
```

**Using `Record<K, V>` (Utility Type - Cleaner syntax)**
```typescript
// Record<KeyType, ValueType> does the exact same thing, but is often preferred for readability
type HeaderMap = Record<string, string>;

const headers: HeaderMap = {
  "Content-Type": "application/json",
  "Authorization": "Bearer token123"
};

headers["X-Custom-Header"] = "hello"; // OK
```

### 4. Progressive Step-by-Step Breakdown

*   **Step 1: The Index Signature Syntax (`[key: string]: number`)**
    The word `key` or `currencyCode` inside the brackets is just for developer readability. It tells TS: "Whenever this object is indexed with a string, the value must be a number."
*   **Step 2: The `Record` Utility**
    `Record<string, number>` is a built-in generic (we'll learn generics later) that generates an index signature under the hood. It is the modern, preferred way to define dictionaries in TypeScript.
*   **Step 3: Mixing Static and Dynamic Keys**
    You can mix them! But the dynamic type must be broad enough to encompass the static types.
    ```typescript
    interface MixedCache {
      lastUpdated: number;          // Static key
      [currencyCode: string]: number; // Dynamic keys (must match the static type!)
    }
    ```

### 5. ASCII Data Flow

```text
Object: { "USD": 1.0, "EUR": 0.85 }

Request: object["JPY"] = "high"
              |
[Is Key a String?] --> Yes
              |
[Is Value a Number?] --> NO ("high" is a string)
              |
       (COMPILER ERROR)
```

### 6. Noob Trap vs Pro Tip
*   **Noob Trap:** Using `[key: string]: any` when building dynamic objects. This completely defeats the purpose of TypeScript.
*   **Pro Tip:** Be careful when reading from index signatures! TypeScript assumes *every* string key exists and returns the value type.
    ```typescript
    const val = rates["INVALID_CURRENCY"]; // TS thinks this is a 'number', but at runtime it is 'undefined'!
    ```
    For absolute safety, enable `noUncheckedIndexedAccess` in `tsconfig.json` to force TS to treat index signature returns as `number | undefined`.

### Level 2: Real-World
**Task:** You are building an internationalization (i18n) dictionary. Create an interface `Translations` using an index signature. The keys are language codes (like "en", "es"). The values should be *another* object where the keys are string IDs (like "greeting") and the values are the translated strings (like "Hello").

<details>
<summary>Hint</summary>
The value type in the index signature will itself be a `Record<string, string>` or another index signature.
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
interface Translations {
  [languageCode: string]: Record<string, string>;
}

const appStrings: Translations = {
  en: {
    greeting: "Hello",
    farewell: "Goodbye"
  },
  es: {
    greeting: "Hola",
    farewell: "Adiós"
  }
};
```
*Walkthrough:* We nested dictionaries. The top level maps a language string to a dictionary object. The inner dictionary maps a key string to a translated string.
</details>

### Level 3: Boss Level
**Task:** (Cumulative) Create a system to manage server environments.
1. Define a `ServerConfig` interface (port: number, env: "dev" | "prod").
2. Create an `EnvironmentMap` type using `Record` where the keys are server names (string) and the values are `ServerConfig` objects.
3. Write a function `getServerPort(envMap: EnvironmentMap, serverName: string): number | null` that returns the port if the server exists, or `null` if it doesn't. (Assume `noUncheckedIndexedAccess` is NOT on, so you must check if the property actually exists at runtime).

<details>
<summary>Hint</summary>
Use the `in` operator or check if `envMap[serverName]` is undefined to safely handle the runtime check.
</details>

<details>
<summary>Solution Walkthrough</summary>

```typescript
interface ServerConfig {
  port: number;
  env: "dev" | "prod";
}

type EnvironmentMap = Record<string, ServerConfig>;

function getServerPort(envMap: EnvironmentMap, serverName: string): number | null {
  const config = envMap[serverName];

  // Runtime check because TS trusts index signatures too much by default
  if (!config) {
    return null;
  }

  return config.port;
}

const servers: EnvironmentMap = {
  authApi: { port: 4000, env: "prod" },
  paymentApi: { port: 4001, env: "prod" }
};

console.log(getServerPort(servers, "authApi")); // 4000
console.log(getServerPort(servers, "unknownApi")); // null
```
*Walkthrough:* We combined exact interfaces, union types (`"dev" | "prod"`), and dynamic `Record` types. Crucially, in the function logic, we acknowledged that reading a dynamic key might return undefined at runtime, and we handled it gracefully.
</details>
