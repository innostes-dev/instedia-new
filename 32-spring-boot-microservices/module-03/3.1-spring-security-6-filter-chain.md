# 3.1 Spring Security 6 & The Filter Chain

## Phase A: The Core Concept

### Real-World Pain Point (The Why)
You build a beautiful REST API. You secure the `/admin` endpoints by adding an `if (user.role != ADMIN) return 403;` check to every single controller method. Six months later, a junior developer adds a new `/admin/export` endpoint but forgets the `if` statement. A malicious user finds it and dumps your entire database to CSV. Security cannot be an afterthought scattered across your business logic; it must be an impenetrable wall that requests must pass through *before* they ever touch your code.

### Plain English Metaphor (The What)
The Spring Security Filter Chain is like airport security.
Before a passenger (HTTP Request) can reach their gate (your `@RestController`), they must pass through a series of checkpoints (Filters).
1.  **CORS Filter:** "Are you flying from an approved country?"
2.  **Authentication Filter:** "Show me your ID and boarding pass." (Verifies who you are)
3.  **Authorization Filter:** "Does this boarding pass allow you into the First Class Lounge?" (Verifies what you can do)

If you fail any checkpoint, security kicks you out immediately (HTTP 401 or 403). Your actual application code never has to worry about checking IDs.

### Complete Runnable Code
Let's build an Enterprise Role-Based Access Control (RBAC) Gateway using the modern Spring Security 6 component-based architecture.

```java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.HttpMethod;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configuration.EnableWebSecurity;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.security.web.authentication.UsernamePasswordAuthenticationFilter;

@Configuration
@EnableWebSecurity
public class SecurityConfig {

    private final JwtAuthenticationFilter jwtAuthFilter;

    public SecurityConfig(JwtAuthenticationFilter jwtAuthFilter) {
        this.jwtAuthFilter = jwtAuthFilter;
    }

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
            // 1. Disable CSRF (Safe for Stateless REST APIs using JWTs)
            .csrf(csrf -> csrf.disable())

            // 2. Define Authorization Rules
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/auth/**").permitAll() // Public login/register
                .requestMatchers(HttpMethod.GET, "/api/products/**").permitAll() // Anyone can view products
                .requestMatchers("/api/admin/**").hasRole("ADMIN") // Only admins
                .anyRequest().authenticated() // Everything else requires a valid login
            )

            // 3. Make the API Stateless (No JSESSIONID cookies)
            .sessionManagement(session -> session
                .sessionCreationPolicy(SessionCreationPolicy.STATELESS)
            )

            // 4. Insert our custom JWT filter BEFORE the standard Spring login filter
            .addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class);

        return http.build();
    }
}
```

### Progressive Step-by-Step Breakdown

**Step 1: The @Configuration and SecurityFilterChain Bean**
```java
@Configuration
@EnableWebSecurity
public class SecurityConfig {
    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception { ... }
}
```
*Why this precedes the next step:* In Spring Security 5 and earlier, you extended `WebSecurityConfigurerAdapter`. In Spring Security 6, that class is deleted. Security is now completely component-based. You define a `@Bean` of type `SecurityFilterChain` which configures the `HttpSecurity` builder.

**Step 2: Authorization Rules**
```java
.authorizeHttpRequests(auth -> auth
    .requestMatchers("/api/auth/**").permitAll()
    .requestMatchers("/api/admin/**").hasRole("ADMIN")
    .anyRequest().authenticated()
)
```
*Why this precedes the next step:* We define the routing rules from most specific to least specific. `permitAll()` means the request bypasses authorization checks. `hasRole("ADMIN")` ensures the authenticated user's `GrantedAuthorities` contains `ROLE_ADMIN`. `anyRequest().authenticated()` acts as our safety net: if a dev adds a new endpoint and forgets to configure it, it will default to requiring a login, preventing data leaks.

**Step 3: Statelessness and Custom Filters**
```java
.sessionManagement(sess -> sess.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
.addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class);
```
*Why this is the final step:* By default, Spring creates an HTTP Session (cookie) after login. Microservices should be stateless, so we disable that. Because there are no sessions, Spring doesn't know who is logged in on subsequent requests. We must inject our custom `JwtAuthenticationFilter` early in the chain to inspect the incoming request headers for a token and manually set the user in the `SecurityContextHolder`.

### ASCII Architecture Data Flow

```text
HTTP Request (GET /api/admin/reports, Header: Auth Bearer <token>)
       |
[ DelegatingFilterProxy ] -> Handoff to Spring Security Filter Chain
       |
       v
[ JwtAuthenticationFilter ] (Our Custom Filter)
   1. Extracts <token>
   2. Validates signature & expiration
   3. Extracts User ID & "ROLE_ADMIN"
   4. Saves into `SecurityContextHolder`
       |
       v
[ AuthorizationFilter ] (Spring's Built-in Filter)
   1. Looks at `SecurityContextHolder` -> User has "ROLE_ADMIN"
   2. Looks at rules for `/api/admin/**` -> Requires "ROLE_ADMIN"
   3. PASS! Allows request to proceed.
       |
       v
[ AdminController.getReports() ] -> Business Logic Execution
```

### Noob Trap vs Pro Tip
*   **Noob Trap:** Hardcoding roles like `hasRole("ADMIN")` in the configuration class, and then scattering `@PreAuthorize("hasRole('ADMIN')")` on the controller methods as well. If you rename the role to `SUPER_ADMIN`, you have to find and replace it in two entirely different layers of the app, risking a mismatch.
*   **Pro Tip:** Choose *one* approach. Either define all URL-based routing in the `SecurityFilterChain` (great for simple apps), OR use `@EnableMethodSecurity` and place `@PreAuthorize` on your Controller/Service methods (great for fine-grained, data-level authorization where you need to evaluate method arguments, like `@PreAuthorize("#userId == authentication.principal.id")`).

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**Task:** Configure a `SecurityFilterChain` that disables CSRF, allows all `GET` requests to `/public/**`, but requires authentication for absolutely everything else.
<details>
<summary>💡 Hint</summary>
Use `HttpMethod.GET` inside the `requestMatchers`.
</details>

<details>
<summary>✅ Solution</summary>

```java
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http.csrf(csrf -> csrf.disable())
        .authorizeHttpRequests(auth -> auth
            .requestMatchers(HttpMethod.GET, "/public/**").permitAll()
            .anyRequest().authenticated()
        );
    return http.build();
}
```
</details>

### Level 2: Real-World
**Task:** You need to configure CORS (Cross-Origin Resource Sharing) so your React frontend running on `http://localhost:3000` can access your Spring Boot API. Add a global CORS configuration to your security setup that allows GET and POST requests from that specific origin.
<details>
<summary>💡 Hint</summary>
You need to call `.cors(Customizer.withDefaults())` on the `HttpSecurity` builder, and then expose a `@Bean` of type `CorsConfigurationSource`.
</details>

<details>
<summary>✅ Solution</summary>

```java
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http.cors(Customizer.withDefaults()) // Tells Spring to look for a CorsConfigurationSource bean
            .csrf(csrf -> csrf.disable())
            .authorizeHttpRequests(auth -> auth.anyRequest().authenticated());
        return http.build();
    }

    @Bean
    public CorsConfigurationSource corsConfigurationSource() {
        CorsConfiguration configuration = new CorsConfiguration();
        configuration.setAllowedOrigins(List.of("http://localhost:3000"));
        configuration.setAllowedMethods(List.of("GET", "POST"));
        configuration.setAllowedHeaders(List.of("Authorization", "Content-Type"));

        UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
        source.registerCorsConfiguration("/**", configuration); // Apply to all endpoints
        return source;
    }
}
```
</details>

### Level 3: Boss Level
**Task:** Create a custom `OncePerRequestFilter` named `ApiKeyFilter`. It should look for an `X-API-KEY` header. If the header equals "secret-key", it should manually authenticate the request with the role `ROLE_SYSTEM`. Add this to your filter chain before the `UsernamePasswordAuthenticationFilter`.
<details>
<summary>💡 Hint</summary>
To manually authenticate, create a `UsernamePasswordAuthenticationToken` (or a custom `Authentication` implementation) and set it using `SecurityContextHolder.getContext().setAuthentication(...)`.
</details>

<details>
<summary>✅ Solution Walkthrough</summary>

```java
// 1. The Custom Filter
@Component
public class ApiKeyFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain) throws ServletException, IOException {

        String apiKey = request.getHeader("X-API-KEY");

        if ("secret-key".equals(apiKey)) {
            // 1a. Create the authorities (Roles)
            List<GrantedAuthority> authorities = List.of(new SimpleGrantedAuthority("ROLE_SYSTEM"));

            // 1b. Create the Authentication object (Principal, Credentials, Authorities)
            UsernamePasswordAuthenticationToken auth =
                new UsernamePasswordAuthenticationToken("system-user", null, authorities);

            // 1c. Inject it into the Security Context for this specific thread/request
            SecurityContextHolder.getContext().setAuthentication(auth);
        }

        // 1d. Pass the request down the chain! If we don't call this, the request hangs forever.
        filterChain.doFilter(request, response);
    }
}

// 2. The Configuration
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    private final ApiKeyFilter apiKeyFilter;
    public SecurityConfig(ApiKeyFilter apiKeyFilter) { this.apiKeyFilter = apiKeyFilter; }

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http.csrf(c -> c.disable())
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/system/**").hasRole("SYSTEM")
                .anyRequest().authenticated()
            )
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            // Insert our filter into the chain!
            .addFilterBefore(apiKeyFilter, UsernamePasswordAuthenticationFilter.class);

        return http.build();
    }
}
```
*Walkthrough:* This is how you implement custom authentication mechanisms (API Keys, HMAC Signatures, custom JWTs). The `OncePerRequestFilter` guarantees this logic fires exactly once per HTTP request. The critical step is `SecurityContextHolder.getContext().setAuthentication()`. Spring Security's downstream filters (like the Authorization filter) don't care *how* you authenticated. They just look inside the `SecurityContextHolder`. If there is a valid `Authentication` object there, you pass. If it's null, you fail.
</details>
