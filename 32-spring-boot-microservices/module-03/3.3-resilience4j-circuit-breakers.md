# 3.3 Resilience4j & Circuit Breakers

## Phase A: The Core Concept

### Real-World Pain Point (The Why)
Microservice A calls Microservice B. Microservice B is struggling under heavy load and takes 30 seconds to respond.
Microservice A starts piling up thousands of threads, all waiting 30 seconds for B. Suddenly, Microservice A runs out of memory and crashes. Now, Microservice C, which relies on A, also crashes. This is a **Cascading Failure**. A tiny slowdown deep in your infrastructure just took down your entire platform.

### Plain English Metaphor (The What)
A Circuit Breaker in software is exactly like the electrical circuit breaker in your house.
*   **CLOSED (Normal):** Electricity (requests) flows freely.
*   **OPEN (Tripped):** If you plug in too many appliances, the breaker "trips" to prevent a fire. The flow of electricity is instantly cut off. In software, if Microservice B fails 50% of the time, the breaker trips. Subsequent calls to B fail instantly (Fail-Fast) without actually making the network call, giving B time to recover.
*   **HALF-OPEN (Testing):** After a cooldown period, the breaker lets a *single* test request through. If it succeeds, the breaker Closes (recovers). If it fails, it Opens again.

### Complete Runnable Code
Let's build a Resilient E-Commerce Product Details Aggregator using Spring Boot and Resilience4j.

```java
// 1. pom.xml dependencies
/*
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-circuitbreaker-resilience4j</artifactId>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-aop</artifactId>
</dependency>
*/

// 2. application.yml Configuration
/*
resilience4j:
  circuitbreaker:
    instances:
      inventoryService:
        slidingWindowSize: 10              # Look at the last 10 calls
        failureRateThreshold: 50           # If 50% fail, OPEN the circuit
        waitDurationInOpenState: 10000ms   # Wait 10s before attempting HALF-OPEN
        permittedNumberOfCallsInHalfOpenState: 3 # Allow 3 test calls in HALF-OPEN
*/

// 3. The Resilient Service
import io.github.resilience4j.circuitbreaker.annotation.CircuitBreaker;
import org.springframework.stereotype.Service;
import org.springframework.web.client.RestTemplate;

@Service
public class ProductAggregatorService {

    private final RestTemplate restTemplate = new RestTemplate();

    // The name matches the instance in application.yml
    @CircuitBreaker(name = "inventoryService", fallbackMethod = "fallbackInventory")
    public String getInventoryStatus(String productId) {
        System.out.println("Attempting real network call to Inventory Service...");
        // If this service is down, or times out, it counts as a failure.
        return restTemplate.getForObject("http://inventory-api/api/stock/" + productId, String.class);
    }

    // The Fallback method. MUST have the exact same signature + an Exception parameter.
    public String fallbackInventory(String productId, Throwable throwable) {
        System.out.println("Circuit is OPEN (or call failed). Returning cached/default data.");
        // We gracefully degrade the user experience instead of crashing.
        return "Stock status temporarily unavailable. Check back later.";
    }
}
```

### Progressive Step-by-Step Breakdown

**Step 1: The Configuration**
```yaml
failureRateThreshold: 50
slidingWindowSize: 10
```
*Why this precedes the next step:* Resilience4j uses a sliding window to calculate the failure rate. It records the outcome of the last 10 calls. If 5 of them (50%) throw an Exception (like an HTTP 500 or a Timeout), the Circuit transitions to the **OPEN** state.

**Step 2: The @CircuitBreaker Annotation**
```java
@CircuitBreaker(name = "inventoryService", fallbackMethod = "fallbackInventory")
public String getInventoryStatus(String productId) { ... }
```
*Why this precedes the next step:* Spring AOP wraps this method in a proxy. When the circuit is CLOSED, the proxy allows the execution. When the circuit is OPEN, the proxy *intercepts* the call. It does not execute the method body. Instead, it instantly throws a `CallNotPermittedException`.

**Step 3: The Fallback Method**
```java
public String fallbackInventory(String productId, Throwable throwable) { ... }
```
*Why this is the final step:* If the original method throws an exception (because of a network timeout), OR if the Circuit is OPEN (throwing `CallNotPermittedException`), Resilience4j catches it and looks for `fallbackInventory`. It executes the fallback and returns that value to the caller. The user gets a graceful message instead of a terrifying HTTP 500 error page, and we stop hammering the struggling backend service.

### ASCII Architecture Data Flow

```text
[ Product Service ]
       |
       |-- Call getInventoryStatus()
       |
    (Resilience4j Proxy)
       |
       |-- [ CLOSED STATE ] -> Proceeds to Network -> HTTP 200 (Success)
       |
       |-- [ CLOSED STATE ] -> Proceeds to Network -> HTTP 500 (Fail 1)
       |-- [ CLOSED STATE ] -> Proceeds to Network -> HTTP 500 (Fail 2 - Trips Threshold!)
       |
       |-- (Circuit Switches to OPEN)
       |
       |-- Call getInventoryStatus()
       |
    (Resilience4j Proxy)
       |-- [ OPEN STATE ] -> INSTANT BLOCK. Does NOT hit Network.
       |                     Calls fallbackInventory() -> Returns "Status Unavailable"
       |
       |-- (10 seconds pass... Switches to HALF-OPEN)
       |
       |-- [ HALF-OPEN ]  -> Proceeds to Network -> HTTP 200 (Success! Closes Circuit.)
```

### Noob Trap vs Pro Tip
*   **Noob Trap:** Using Fallbacks to throw different exceptions or perform heavy, failure-prone logic (like calling a *second* external database). If your fallback throws an exception, you still crash.
*   **Pro Tip:** Fallbacks should be virtually guaranteed to succeed. They should return static defaults, pull from a fast local Redis cache, or enqueue a message to a Dead Letter Queue. If you *must* do something risky in a fallback, it needs its own `@CircuitBreaker`.

### Level 1: Warm-Up
**Task:** Add a `@Retry` annotation to `getInventoryStatus` so that before the Circuit Breaker records a failure, it tries the network call up to 3 times.
<details>
<summary>💡 Hint</summary>
Use `io.github.resilience4j.retry.annotation.Retry`.
</details>

<details>
<summary>✅ Solution</summary>

```java
@Service
public class ProductAggregatorService {

    // Order matters in configuration, but Retry is generally applied inside the CircuitBreaker.
    // So it retries 3 times, and if all 3 fail, it counts as ONE failure for the Circuit Breaker.
    @Retry(name = "inventoryService")
    @CircuitBreaker(name = "inventoryService", fallbackMethod = "fallbackInventory")
    public String getInventoryStatus(String productId) {
        // ... network call
    }
    // ... fallback
}
```
</details>

### Level 2: Real-World
**Task:** Rate Limiting. You expose an expensive `/export-pdf` API endpoint. You want to ensure that no single user (or the system globally) can hit this method more than 5 times per second. Implement this using Resilience4j's `@RateLimiter`.
<details>
<summary>💡 Hint</summary>
Configure `resilience4j.ratelimiter.instances.pdfExport.limitForPeriod=5` and `limitRefreshPeriod=1s`. Apply `@RateLimiter` to the method.
</details>

<details>
<summary>✅ Solution</summary>

```yaml
# application.yml
resilience4j:
  ratelimiter:
    instances:
      pdfExport:
        limitForPeriod: 5
        limitRefreshPeriod: 1s
        timeoutDuration: 0s # If limit is reached, reject immediately without waiting
```

```java
@Service
public class ReportService {

    @RateLimiter(name = "pdfExport", fallbackMethod = "rateLimitFallback")
    public byte[] generatePdf(String data) {
        System.out.println("Generating heavy PDF...");
        return new byte[0]; // simulate PDF
    }

    public byte[] rateLimitFallback(String data, RequestNotPermitted ex) {
        throw new ResponseStatusException(HttpStatus.TOO_MANY_REQUESTS, "Slow down!");
    }
}
```
</details>

### Level 3: Boss Level
**Task:** The TimeLimiter and Bulkhead. You are calling a legacy Mainframe system that normally responds in 500ms, but sometimes hangs for 60 seconds, tying up Tomcat threads.
1. Use `@TimeLimiter` to force the method to timeout and fail if it takes longer than 2 seconds.
2. Use `@Bulkhead` to ensure that *at most* 10 threads can ever be concurrently executing this method, saving the rest of your server's resources.
<details>
<summary>💡 Hint</summary>
`@TimeLimiter` in Resilience4j requires the method to return a `CompletableFuture<T>`.
</details>

<details>
<summary>✅ Solution Walkthrough</summary>

```yaml
resilience4j:
  timelimiter:
    instances:
      mainframe:
        timeoutDuration: 2s
  bulkhead:
    instances:
      mainframe:
        maxConcurrentCalls: 10
```

```java
import io.github.resilience4j.bulkhead.annotation.Bulkhead;
import io.github.resilience4j.timelimiter.annotation.TimeLimiter;
import org.springframework.stereotype.Service;

import java.util.concurrent.CompletableFuture;

@Service
public class MainframeIntegrationService {

    // Thread pool isolation! Only 10 threads allowed in this Bulkhead.
    // If it takes > 2s, the CompletableFuture is cancelled and an exception is thrown.
    @Bulkhead(name = "mainframe", type = Bulkhead.Type.SEMAPHORE)
    @TimeLimiter(name = "mainframe", fallbackMethod = "mainframeFallback")
    public CompletableFuture<String> fetchCustomerHistory(String accountId) {

        return CompletableFuture.supplyAsync(() -> {
            try {
                // Simulate a 45 second hang
                Thread.sleep(45000);
            } catch (InterruptedException e) {
                // TimeLimiter interrupts the thread!
                Thread.currentThread().interrupt();
            }
            return "Mainframe Data";
        });
    }

    public CompletableFuture<String> mainframeFallback(String accountId, Throwable t) {
        return CompletableFuture.completedFuture("Cached/Empty History");
    }
}
```
*Walkthrough:* This is the ultimate defensive architecture. The **Bulkhead** pattern comes from shipbuilding (separating the hull into watertight compartments so one leak doesn't sink the ship). By limiting `maxConcurrentCalls` to 10, even if the mainframe completely locks up, it can only consume 10 of your Tomcat worker threads. Your server remains healthy to serve other API requests. The **TimeLimiter** ensures those 10 threads are forcefully freed after 2 seconds, maintaining system fluidity.
</details>
