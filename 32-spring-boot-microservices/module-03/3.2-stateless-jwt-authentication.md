# 3.2 Stateless JWT Authentication

## Phase A: The Core Concept

### Real-World Pain Point (The Why)
You build an application using standard HTTP Sessions. A user logs in, and Spring creates a session in server memory holding their user data, returning a `JSESSIONID` cookie to the browser.
Your app gets popular, so you put 3 servers behind a Load Balancer.
User A logs into Server 1. Their session is saved in Server 1's RAM.
The Load Balancer routes User A's next request to Server 2. Server 2 doesn't have User A's session in memory! It redirects User A back to the login page. You now have forced logouts, memory exhaustion under heavy load, and a system that cannot scale horizontally.

### Plain English Metaphor (The What)
Stateful Sessions are like an exclusive nightclub keeping a physical guest list at the door. If they open a second door (Server 2), the bouncer there doesn't have the list.
JSON Web Tokens (JWT) are like digital, cryptographically signed passports. The nightclub doesn't need to keep a list anymore. The bouncer simply looks at the passport, verifies the official government signature (the Secret Key), reads your age and name right off the passport, and lets you in. The bouncer (the Server) stores zero state.

### Complete Runnable Code
Let's build a Stateless JWT Authentication Service.

```java
import io.jsonwebtoken.Claims;
import io.jsonwebtoken.Jwts;
import io.jsonwebtoken.SignatureAlgorithm;
import io.jsonwebtoken.security.Keys;
import org.springframework.stereotype.Service;

import javax.crypto.SecretKey;
import java.util.Date;

@Service
public class JwtService {

    // In production, this MUST be injected from a secure environment variable!
    // It must be at least 256 bits (32 bytes) long for HS256.
    private static final String SECRET = "my-super-secret-key-that-is-very-long-and-secure";
    private final SecretKey secretKey = Keys.hmacShaKeyFor(SECRET.getBytes());

    private static final long EXPIRATION_TIME_MS = 1000 * 60 * 60; // 1 Hour

    // 1. Generate the Token
    public String generateToken(String username, String role) {
        return Jwts.builder()
                .setSubject(username)                 // "sub" claim
                .claim("role", role)                  // Custom claim
                .setIssuedAt(new Date())              // "iat" claim
                .setExpiration(new Date(System.currentTimeMillis() + EXPIRATION_TIME_MS)) // "exp"
                .signWith(secretKey, SignatureAlgorithm.HS256) // Cryptographic signature
                .compact();
    }

    // 2. Validate and Parse the Token
    public Claims extractClaims(String token) {
        // If the signature is invalid or token is expired, this throws an exception!
        return Jwts.parserBuilder()
                .setSigningKey(secretKey)
                .build()
                .parseClaimsJws(token)
                .getBody();
    }

    public String extractUsername(String token) {
        return extractClaims(token).getSubject();
    }

    public boolean isTokenValid(String token) {
        try {
            extractClaims(token);
            return true;
        } catch (Exception e) {
            return false;
        }
    }
}
```

### Progressive Step-by-Step Breakdown

**Step 1: The Cryptographic Key**
```java
private final SecretKey secretKey = Keys.hmacShaKeyFor(SECRET.getBytes());
```
*Why this precedes the next step:* A JWT is just Base64 encoded JSON. Anyone can decode it. What makes it secure is the *Signature* appended to the end. The server uses this `secretKey` to hash the data. If a user tampers with the token (e.g., changes their role from "USER" to "ADMIN"), the hash will no longer match the signature, and the server will reject it.

**Step 2: Token Generation**
```java
.setSubject(username)
.claim("role", role)
.signWith(secretKey, SignatureAlgorithm.HS256)
```
*Why this precedes the next step:* When a user provides a valid username/password, we generate the token. We embed their identity (`subject`) and authorizations (`claims`) directly into the payload. The client will store this string and send it in the `Authorization: Bearer <token>` header on every subsequent request.

**Step 3: Token Validation**
```java
return Jwts.parserBuilder().setSigningKey(secretKey)...
```
*Why this is the final step:* When a protected endpoint is called, our Spring Security Filter intercepts the request, grabs the token, and passes it here. Because we pass the `secretKey` to the parser, it recalculates the hash. If it matches, and the `exp` (expiration) date hasn't passed, we trust the claims and inject the user into the `SecurityContextHolder`. Zero database calls required!

### Noob Trap vs Pro Tip
*   **Noob Trap:** Storing sensitive data like passwords or SSNs inside the JWT claims. **JWTs are not encrypted; they are only encoded and signed.** Anyone can paste a JWT into jwt.io and read the JSON payload.
*   **Pro Tip:** Token Revocation is the hardest part of JWTs. Because they are stateless, you cannot simply "delete the session" on the server. If an admin bans a user, their JWT remains valid until it expires! To solve this, keep JWT expiration times very short (15 mins), and use a stateful **Refresh Token** (stored in the DB) to issue new short-lived JWTs. If a user is banned, delete their Refresh Token from the DB.

### Level 2: Real-World
**Task:** Implement a custom `OncePerRequestFilter` named `JwtAuthFilter`. It should extract the token from the `Authorization: Bearer <token>` header, validate it using `JwtService`, extract the username and role, and manually set a `UsernamePasswordAuthenticationToken` in the `SecurityContextHolder`.
<details>
<summary>💡 Hint</summary>
Check if the header starts with "Bearer ". Use `jwtService.isTokenValid()`.
</details>

<details>
<summary>✅ Solution</summary>

```java
@Component
public class JwtAuthFilter extends OncePerRequestFilter {

    private final JwtService jwtService;
    public JwtAuthFilter(JwtService jwtService) { this.jwtService = jwtService; }

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain chain)
            throws ServletException, IOException {

        final String authHeader = request.getHeader("Authorization");

        if (authHeader == null || !authHeader.startsWith("Bearer ")) {
            chain.doFilter(request, response);
            return;
        }

        final String jwt = authHeader.substring(7);

        try {
            if (jwtService.isTokenValid(jwt)) {
                String username = jwtService.extractUsername(jwt);
                String role = jwtService.extractClaims(jwt).get("role", String.class);

                List<GrantedAuthority> authorities = List.of(new SimpleGrantedAuthority("ROLE_" + role));
                UsernamePasswordAuthenticationToken authToken =
                        new UsernamePasswordAuthenticationToken(username, null, authorities);

                SecurityContextHolder.getContext().setAuthentication(authToken);
            }
        } catch (Exception e) {
            // Token is invalid/expired. Leave SecurityContext empty. FilterChain will return 403/401.
        }

        chain.doFilter(request, response);
    }
}
```
</details>

### Level 3: Boss Level
**Task:** JWT Token Revocation via Redis Blacklist. A user clicks "Logout". Because we can't destroy the JWT, we want to add that specific token to a Redis cache (blacklist) with a Time-To-Live (TTL) equal to its remaining expiration time. Modify your filter to check this blacklist before trusting the token.
<details>
<summary>💡 Hint</summary>
Assume you have a `RedisTemplate<String, String>` available. Calculate the remaining time: `tokenExpirationDate.getTime() - System.currentTimeMillis()`.
</details>

<details>
<summary>✅ Solution Walkthrough</summary>

```java
@Service
public class AuthService {
    private final RedisTemplate<String, String> redisTemplate;
    private final JwtService jwtService;

    public AuthService(RedisTemplate<String, String> redis, JwtService jwt) {
        this.redisTemplate = redis; this.jwtService = jwt;
    }

    public void logout(String token) {
        Claims claims = jwtService.extractClaims(token);
        long remainingMillis = claims.getExpiration().getTime() - System.currentTimeMillis();

        if (remainingMillis > 0) {
            // Save token to Redis with TTL. It will auto-delete when it expires anyway!
            redisTemplate.opsForValue().set("BLACKLIST:" + token, "revoked",
                                            remainingMillis, TimeUnit.MILLISECONDS);
        }
    }
}
```

*Walkthrough:* This is the enterprise standard for immediate token revocation in stateless architectures. By storing the token in Redis *only until it expires naturally*, we keep the Redis memory footprint extremely small. The `JwtAuthFilter` does a blazing-fast O(1) cache lookup on every request. If the token is there, it's rejected. If not, it falls back to the stateless cryptographic signature check. This gives you the speed of stateless JWTs with the control of stateful sessions.
