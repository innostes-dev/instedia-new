# 2.2 ACID Transactions & Propagation

## Phase A: The Core Concept

### Real-World Pain Point (The Why)
Imagine an e-commerce checkout. The code first charges the customer's credit card ($100), then it attempts to deduct the inventory (1 Laptop). But right after the credit card is charged, the database connection drops or a `NullPointerException` occurs during the inventory deduction. The method crashes. The customer has been charged $100, but the system still thinks it has the laptop. You have partial, corrupted data.

### Plain English Metaphor (The What)
A Transaction is an all-or-nothing wrapper around a group of tasks. It's like signing a contract to buy a house. You don't hand over the money, *then wait a week*, then get the keys. Both actions must happen at the exact same time (Atomic). If the seller refuses to give the keys, you pull your money back (Rollback). If everything is good, the deal is finalized (Commit).

**Transaction Propagation** dictates how methods share transactions.
*   `REQUIRED` (Default): "If there is a contract already on the table, I'll sign it. If not, I'll write a new one."
*   `REQUIRES_NEW`: "I don't care about your contract. I'm writing my own, separate contract. If mine fails, yours might still succeed."

### Complete Runnable Code
Let's build an Atomic Order Checkout & Balance Deduction Service.

```java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Propagation;
import org.springframework.transaction.annotation.Transactional;

@Service
public class CheckoutService {

    private final InventoryService inventoryService;
    private final PaymentService paymentService;
    private final AuditService auditService;

    public CheckoutService(InventoryService inv, PaymentService pay, AuditService aud) {
        this.inventoryService = inv;
        this.paymentService = pay;
        this.auditService = aud;
    }

    // Default propagation is REQUIRED.
    // Rolls back on ANY unchecked Exception (RuntimeException).
    @Transactional
    public void processOrder(Long orderId, double amount) {

        // 1. Audit the attempt (We want this saved even if the order fails!)
        auditService.logAttempt(orderId);

        // 2. Charge the card (If this passes...)
        paymentService.charge(orderId, amount);

        // 3. Deduct inventory (...but this throws an exception)
        inventoryService.deductItem(orderId);

        // RESULT: Payment rolls back, Inventory rolls back, BUT Audit commits.
    }
}

@Service
class AuditService {
    // REQUIRES_NEW means this pauses the main transaction, starts a new one,
    // commits it immediately, and then resumes the main one.
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void logAttempt(Long orderId) {
        System.out.println("Saving audit log to DB...");
        // db.save(audit);
    }
}
```

### Progressive Step-by-Step Breakdown

**Step 1: The Main Transaction (@Transactional)**
```java
@Transactional
public void processOrder(Long orderId, double amount) { ... }
```
*Why this precedes the next step:* This creates our "wrapper." When a Controller calls this method, Spring intercepts the call, opens a database transaction, and wraps `charge` and `deductItem`. If `deductItem` throws a `RuntimeException`, Spring catches it, issues a SQL `ROLLBACK`, and re-throws the error. The payment is never committed.

**Step 2: The Nested Call with REQUIRES_NEW**
```java
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void logAttempt(Long orderId) { ... }
```
*Why this precedes the next step:* We have a business requirement: Even if a checkout fails (e.g., fraudulent card), we *must* log that the attempt happened. If `logAttempt` used the default `REQUIRED`, it would join the main `processOrder` transaction. When `deductItem` fails and triggers a rollback, the audit log would be rolled back too! `REQUIRES_NEW` forces it into an independent transaction that commits immediately before returning to `processOrder`.

**Step 3: Rollback Rules**
```java
// Spring defaults to ONLY rolling back on RuntimeExceptions.
// If you throw a checked Exception (e.g., IOException), IT WILL COMMIT by default!
@Transactional(rollbackFor = Exception.class)
```
*Why this is the final step:* This is a critical gotcha. If your method throws a custom checked exception (e.g., `InsufficientFundsException extends Exception`), Spring will silently commit the transaction unless you explicitly tell it to `rollbackFor = Exception.class`.

### ASCII Architecture Data Flow

```text
[ CheckoutService.processOrder() ] --> Starts TX 1
    |
    |-- Calls AuditService.logAttempt()
    |       --> Suspends TX 1
    |       --> Starts TX 2 (REQUIRES_NEW)
    |       --> INSERT Audit Log
    |       --> Commits TX 2
    |       --> Resumes TX 1
    |
    |-- Calls PaymentService.charge()
    |       --> Joins TX 1 (REQUIRED)
    |       --> UPDATE User Balance
    |
    |-- Calls InventoryService.deductItem()
            --> Joins TX 1 (REQUIRED)
            --> THROWS OutOfStockException (RuntimeException)
    |
<-- Spring Interceptor catches Exception
    --> Issues ROLLBACK for TX 1 (User Balance reverted)
    (Audit Log remains saved because TX 2 already committed)
```

### Noob Trap vs Pro Tip
*   **Noob Trap:** Calling a `@Transactional` method from *within the same class*. Spring's transaction management relies on AOP proxies. If `methodA()` calls `methodB()` in the same class, the proxy is bypassed, and `methodB`'s `@Transactional` annotation is entirely ignored.
*   **Pro Tip:** Always call `@Transactional` methods from *another bean* to ensure the proxy intercepts it. Also, prefer `rollbackFor = Exception.class` on your main entry points so you don't have to memorize which exception types trigger rollbacks and which don't.

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**Task:** Create a `UserService` with a `@Transactional` method `updateEmail(userId, newEmail)`. If the user is not found, throw a custom checked exception `UserNotFoundException extends Exception`. Ensure the transaction rolls back when this is thrown.
<details>
<summary>💡 Hint</summary>
You must use the `rollbackFor` attribute on the annotation.
</details>

<details>
<summary>✅ Solution</summary>

```java
@Service
public class UserService {

    @Transactional(rollbackFor = UserNotFoundException.class)
    public void updateEmail(Long userId, String newEmail) throws UserNotFoundException {
        // userRepo.update(...)
        throw new UserNotFoundException("User not found!");
        // Will correctly roll back
    }
}
```
</details>

### Level 2: Real-World
**Task:** You are building an email newsletter service. You loop through 100 users and call `emailService.sendNewsletter(user)`. If one email fails (e.g., bad address), you want to catch the error, log it, and *continue* sending to the other 99 users. If `sendNewsletter` is `@Transactional`, how do you prevent a failure from rolling back the entire batch?
<details>
<summary>💡 Hint</summary>
If the batch process has a transaction, and `sendNewsletter` fails, it will mark the batch transaction as "rollback-only". You need `sendNewsletter` to run in its own independent transaction so its failure doesn't infect the parent.
</details>

<details>
<summary>✅ Solution</summary>

```java
@Service
public class BatchEmailService {
    private final EmailService emailService;
    public BatchEmailService(EmailService emailService) { this.emailService = emailService; }

    @Transactional
    public void sendToAll(List<User> users) {
        for (User u : users) {
            try {
                // If this fails, the loop continues and the main TX is safe
                emailService.sendNewsletter(u);
            } catch (Exception e) {
                System.out.println("Failed for user: " + u.getId());
            }
        }
    }
}

@Service
class EmailService {
    // Isolates this transaction. A rollback here does NOT rollback BatchEmailService.
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void sendNewsletter(User u) {
        // db.save(emailLog);
        // if bad email -> throw new RuntimeException()
    }
}
```
</details>

### Level 3: Boss Level
**Task:** Fix the Self-Invocation Proxy bypass! You have a class with `public void orchestrate()` which calls `public void saveToDb()`. `saveToDb()` is `@Transactional`. You realize `saveToDb()` is not actually creating a transaction because `orchestrate()` is calling it directly from within the same class. Fix this without creating a second Service class.
<details>
<summary>💡 Hint</summary>
You need to call `saveToDb()` through the Spring proxy, not through `this`. You can actually inject the class into itself!
</details>

<details>
<summary>✅ Solution Walkthrough</summary>

```java
@Service
public class SelfReferencingService {

    // 1. Inject the class into ITSELF using ObjectProvider or @Autowired
    // We use @Lazy or ObjectProvider to prevent a Circular Dependency crash on startup
    private final ObjectProvider<SelfReferencingService> selfProvider;

    public SelfReferencingService(ObjectProvider<SelfReferencingService> selfProvider) {
        this.selfProvider = selfProvider;
    }

    public void orchestrate() {
        System.out.println("Doing non-transactional work...");

        // 2. Fetch the PROXY instance of this class, not 'this'
        SelfReferencingService proxy = selfProvider.getObject();

        // 3. Call the method via the proxy. Spring will now intercept it!
        proxy.saveToDb();
    }

    @Transactional
    public void saveToDb() {
        System.out.println("Saving to DB WITH a proper transaction!");
    }
}
```
*Walkthrough:* When Spring creates `SelfReferencingService`, it wraps it in an invisible proxy class that handles the `@Transactional` logic. When you use `this.saveToDb()`, you are inside the real object, completely bypassing the outer proxy shell. By injecting an `ObjectProvider` of the class into itself, we grab hold of that outer proxy shell. When we call `proxy.saveToDb()`, we hit the transaction interceptor first. (Note: While this works, moving `saveToDb` to a separate `DataService` class is generally a cleaner architectural pattern).
</details>
