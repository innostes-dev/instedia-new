# 2.3 Optimistic Locking & Concurrency

## Phase A: The Core Concept

### Real-World Pain Point (The Why)
You build a ticketing app for a massive Taylor Swift concert. There is exactly 1 VIP front-row seat left (Seat 1A). User Alice and User Bob both click "Buy" on Seat 1A at the exact same millisecond.
1. Thread A (Alice) reads Seat 1A from the database. Status: AVAILABLE.
2. Thread B (Bob) reads Seat 1A from the database. Status: AVAILABLE.
3. Thread A updates Seat 1A to "SOLD TO ALICE" and saves.
4. Thread B updates Seat 1A to "SOLD TO BOB" and saves (overwriting Alice).
You just double-booked the seat. Bob gets the ticket, Alice's money is taken, and you have a lawsuit. This is a classic "Lost Update" race condition.

### Plain English Metaphor (The What)
Optimistic Locking is like checking out a document from a shared library, but the librarian stamps it with a "Version Number" (e.g., v1).
Alice takes v1, crosses out a line, and brings it back. The librarian updates the master copy to v2.
Bob also took v1 at the same time. He crosses out a different line and brings it back. The librarian looks at Bob's document (stamped v1), looks at the master copy (now v2), and says: *"Sorry Bob, someone else updated this while you were looking at it. I'm rejecting your changes. Go get the newest version and try again."*

### Complete Runnable Code
Let's build a Flash-Sale Ticket Reservation Lock Engine.

```java
import jakarta.persistence.*;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

// 1. The Entity
@Entity
public class Ticket {
    @Id
    private Long id;
    private String seatNumber;
    private String owner;

    // The magic annotation! Hibernate manages this automatically.
    @Version
    private Integer version;

    public void setOwner(String owner) { this.owner = owner; }
    public String getOwner() { return this.owner; }
    // Getters/setters omitted for brevity
}

// 2. The Repository
public interface TicketRepository extends JpaRepository<Ticket, Long> {}

// 3. The Service
@Service
public class TicketingService {

    private final TicketRepository repo;
    public TicketingService(TicketRepository repo) { this.repo = repo; }

    @Transactional
    public void reserveSeat(Long ticketId, String username) {
        Ticket ticket = repo.findById(ticketId).orElseThrow();

        if (ticket.getOwner() != null) {
            throw new RuntimeException("Seat already taken!");
        }

        // Simulate some processing time so another thread can sneak in
        try { Thread.sleep(100); } catch (InterruptedException e) {}

        ticket.setOwner(username);

        // When Spring commits the transaction, Hibernate issues the UPDATE statement.
        // It checks if the version in the DB matches the version in Java memory.
    }
}
```

### Progressive Step-by-Step Breakdown

**Step 1: The @Version Column**
```java
@Version
private Integer version;
```
*Why this precedes the next step:* This is the core of Optimistic Locking. We add a simple Integer field to our entity and annotate it with `@Version`. We NEVER update this field manually. Hibernate will automatically set it to 0 on insert, and increment it by 1 on every successful update.

**Step 2: The Concurrent Reads**
```java
Ticket ticket = repo.findById(ticketId).orElseThrow();
```
*Why this precedes the next step:* When Alice and Bob both read the ticket, Hibernate pulls the version down too. Alice has `Ticket(id=1, owner=null, version=0)`. Bob has `Ticket(id=1, owner=null, version=0)`.

**Step 3: The Update and Exception**
```java
ticket.setOwner(username);
```
*Why this is the final step:* When the transaction ends, Hibernate flushes the changes to SQL. It doesn't just do `UPDATE ticket SET owner='Alice'`. It does:
`UPDATE ticket SET owner='Alice', version=1 WHERE id=1 AND version=0`.
Because the row with version=0 exists, it works.
Milliseconds later, Bob's thread flushes:
`UPDATE ticket SET owner='Bob', version=1 WHERE id=1 AND version=0`.
Because Alice already bumped the DB version to 1, Bob's `WHERE version=0` clause affects **0 rows**. Hibernate sees this, realizes a concurrent modification happened, and throws an `OptimisticLockException`! Bob's transaction rolls back. Alice keeps the seat.

### ASCII Architecture Data Flow

```text
DB State: Seat 1A (Owner: NULL, Version: 0)

[ Thread A (Alice) ]                        [ Thread B (Bob) ]
        |                                           |
  Reads: Ver 0                                Reads: Ver 0
        |                                           |
  Set Owner = "Alice"                         Set Owner = "Bob"
        |                                           |
  Save()                                            |
  SQL: UPDATE ... WHERE version = 0                 |
  (Success! DB now Version 1)                       |
                                                    |
                                              Save()
                                              SQL: UPDATE ... WHERE version = 0
                                              (FAILS! 0 rows updated)
                                              THROWS OptimisticLockException!
```

### Noob Trap vs Pro Tip
*   **Noob Trap:** Trying to fix concurrency by wrapping the method in Java's `synchronized` keyword. `synchronized` only works on a single JVM. If you have 5 instances of your Spring Boot microservice running behind a load balancer, `synchronized` is useless because Thread A is on Server 1 and Thread B is on Server 2.
*   **Pro Tip:** Use Optimistic Locking (`@Version`) for high-read/low-write contention (like updating a user profile). Use **Pessimistic Locking** (`SELECT ... FOR UPDATE`) for high-write contention (like deducting money from a bank account). Pessimistic locking locks the row at the database level the moment it is read, forcing other threads to wait, rather than throwing exceptions at the end.

### Level 2: Real-World
**Task:** In your `@RestController`, you call `TicketingService.reserveSeat()`. If two users collide, one gets an `OptimisticLockException` (which is wrapped by Spring as an `ObjectOptimisticLockingFailureException`). Write a `@ExceptionHandler` in a `@ControllerAdvice` class to catch this specifically and return a friendly HTTP 409 Conflict message to the user.
<details>
<summary>💡 Hint</summary>
Create a class annotated with `@RestControllerAdvice` and a method annotated with `@ExceptionHandler`.
</details>

<details>
<summary>✅ Solution</summary>

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(org.springframework.orm.ObjectOptimisticLockingFailureException.class)
    public ResponseEntity<String> handleConcurrencyFailure(Exception ex) {
        return ResponseEntity
                .status(HttpStatus.CONFLICT)
                .body("Sorry! Someone else updated this resource at the exact same time. Please refresh and try again.");
    }
}
```
</details>

### Level 3: Boss Level
**Task:** Automatic Retries! When an `ObjectOptimisticLockingFailureException` occurs, instead of failing and telling the user to click again, we want the server to automatically retry the transaction up to 3 times before finally giving up.
<details>
<summary>💡 Hint</summary>
You can use Spring Retry (`@Retryable`). You'll need to add the `@EnableRetry` annotation to your main class.
</details>

<details>
<summary>✅ Solution Walkthrough</summary>

```java
// 1. In your pom.xml/build.gradle, add spring-retry and spring-boot-starter-aop
// 2. Add @EnableRetry to your @SpringBootApplication class

import org.springframework.retry.annotation.Backoff;
import org.springframework.retry.annotation.Retryable;
import org.springframework.orm.ObjectOptimisticLockingFailureException;

@Service
public class TicketingService {

    private final TicketRepository repo;
    public TicketingService(TicketRepository repo) { this.repo = repo; }

    // This tells Spring: "If this specific exception is thrown, wait 500ms, and call this entire method again. Try 3 times total."
    @Retryable(
        retryFor = {ObjectOptimisticLockingFailureException.class},
        maxAttempts = 3,
        backoff = @Backoff(delay = 500)
    )
    @Transactional
    public void reserveSeatWithRetry(Long ticketId, String username) {
        System.out.println("Attempting to reserve seat...");
        Ticket ticket = repo.findById(ticketId).orElseThrow();

        if (ticket.getOwner() != null) {
            throw new RuntimeException("Seat already taken!");
        }

        ticket.setOwner(username);
    }
}
```
*Walkthrough:* This is how enterprise apps handle background collisions gracefully. If Thread A and Thread B collide, Thread B throws the exception. The `@Retryable` AOP proxy catches it, waits half a second, and invokes `reserveSeatWithRetry` again. This time, when `findById` runs, it pulls the fresh data (Version 1). If the seat is now taken by Alice, it hits our standard `RuntimeException` (which we aren't retrying). If the data was just a generic counter we were incrementing, the retry would successfully apply the increment on top of the new version.
</details>
