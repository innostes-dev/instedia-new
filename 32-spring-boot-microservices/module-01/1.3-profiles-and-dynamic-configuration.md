# 1.3 Profiles and Dynamic Configuration

## Phase A: The Core Concept

### Real-World Pain Point (The Why)
It’s Friday at 4 PM. You deploy the latest code to the Staging environment. Suddenly, thousands of real customer emails are sent out containing test data, and millions of dollars are charged to actual credit cards using fake test tokens. You accidentally hardcoded the Production Stripe API key and Production SMTP server into your `application.properties` and pushed it to Git. Managing configurations across Dev, Test, Staging, and Prod without modifying the actual `.jar` file is critical to survival.

### Plain English Metaphor (The What)
Spring Profiles are like having different "Modes" for your car.
*   **Eco Mode (Dev Profile):** Uses less power, connects to a local, in-memory database, prints a lot of debugging logs.
*   **Sport Mode (Prod Profile):** High performance, connects to massive cloud databases, suppresses verbose logs, enables strict security.
The car's engine (your code) never changes, but how it behaves changes based on the mode you activate.

`@ConfigurationProperties` is like a structured manual. Instead of looking up 50 different settings scattered across the car, they are grouped logically (e.g., `car.engine.horsepower`, `car.engine.cylinders`) into a single, type-safe Java object.

### Complete Runnable Code
Let's build a Multi-Environment Dynamic Cloud Config Engine.

```java
// 1. application.yml (The Base)
/*
spring:
  profiles:
    active: dev # Default profile

cloud:
  provider: "local-mock"
  timeout-ms: 5000
*/

// 2. application-prod.yml (Overrides Base when 'prod' profile is active)
/*
cloud:
  provider: "aws"
  timeout-ms: 1000
*/

// 3. The Type-Safe Configuration Properties Bean
import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.context.annotation.Configuration;

@Configuration
@ConfigurationProperties(prefix = "cloud")
public class CloudConfigProperties {
    private String provider;
    private int timeoutMs;

    // Getters and Setters are REQUIRED for Spring to bind the properties
    public String getProvider() { return provider; }
    public void setProvider(String provider) { this.provider = provider; }
    public int getTimeoutMs() { return timeoutMs; }
    public void setTimeoutMs(int timeoutMs) { this.timeoutMs = timeoutMs; }
}

// 4. A Profile-Specific Bean
import org.springframework.context.annotation.Profile;
import org.springframework.stereotype.Service;

@Service
@Profile("prod") // This bean ONLY exists if the 'prod' profile is active
public class ProductionCloudService {
    private final CloudConfigProperties config;

    public ProductionCloudService(CloudConfigProperties config) {
        this.config = config;
        System.out.println("Connecting to PROD Cloud: " + config.getProvider());
        System.out.println("Timeout set to: " + config.getTimeoutMs() + "ms");
    }
}
```

### Progressive Step-by-Step Breakdown

**Step 1: The YAML Hierarchy**
```yaml
# application-prod.yml
cloud:
  provider: "aws"
```
*Why this precedes the next step:* Spring uses a predictable naming convention: `application-{profile}.yml`. When you launch Spring with `--spring.profiles.active=prod`, it loads `application.yml` first, and then loads `application-prod.yml`, overriding any matching keys. This externalizes your configuration.

**Step 2: Type-Safe Binding (@ConfigurationProperties)**
```java
@ConfigurationProperties(prefix = "cloud")
public class CloudConfigProperties {
    private String provider;
```
*Why this precedes the next step:* Instead of scattering `@Value("${cloud.provider}")` across 20 different classes (which throws nasty runtime errors if you misspell a key), we bind the entire `cloud.*` tree into a strongly-typed Java object. If `timeout-ms` is accidentally set to "foo" in the YAML, the application fails to start immediately because "foo" cannot be cast to an `int`.

**Step 3: Conditional Bean Creation (@Profile)**
```java
@Service
@Profile("prod")
public class ProductionCloudService { ... }
```
*Why this is the final step:* Now that we have environment-specific properties, we can also conditionally create entire components. If we are running in `dev`, this `ProductionCloudService` bean will never be instantiated by the IoC container, preventing any accidental production connections.

### ASCII Architecture Data Flow

```text
[ Command Line / ENV Var ] --> SPRING_PROFILES_ACTIVE=prod
                                      |
                                      v
[ Spring Boot Startup Sequence ]
  |-- Loads application.yml (Base)
  |-- Loads application-prod.yml (Overrides Base)
  |
  |-- Binds YAML `cloud.*` ----> [ CloudConfigProperties Bean ]
  |
  |-- Scans for @Profile
      |-- @Profile("dev") MockCloudService -> IGNORED
      |-- @Profile("prod") ProductionCloudService -> CREATED & INJECTED WITH PROPERTIES
```

### Noob Trap vs Pro Tip
*   **Noob Trap:** Using `@Value("${my.property}")` everywhere. It creates brittle code, provides zero code completion in your IDE for properties, makes it hard to see all related configuration in one place, and defaults to null/runtime errors if missing.
*   **Pro Tip:** Always use `@ConfigurationProperties`. Furthermore, keep secrets (passwords, API keys) entirely out of your Git repository (even in `application-prod.yml`). Use environment variables on the server (e.g., `CLOUD_API_KEY=xyz`) and reference them in YAML like this: `api-key: ${CLOUD_API_KEY}`.

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**Task:** Create an `AppProperties` class that binds to a `server.max-threads` integer property.
<details>
<summary>💡 Hint</summary>
Use `@ConfigurationProperties(prefix = "server")` and create a `maxThreads` integer field with getters and setters. Spring automatically converts kebab-case (`max-threads`) to camelCase (`maxThreads`).
</details>

<details>
<summary>✅ Solution</summary>

```java
@Configuration
@ConfigurationProperties(prefix = "server")
public class AppProperties {
    private int maxThreads;

    public int getMaxThreads() { return maxThreads; }
    public void setMaxThreads(int maxThreads) { this.maxThreads = maxThreads; }
}
```
</details>

### Level 2: Real-World
**Task:** You need an `EmailSender` interface. Create a `DummyEmailSender` that is used when the `dev` profile is active, and a `SendGridEmailSender` used when the `prod` profile is active.
<details>
<summary>💡 Hint</summary>
Implement the interface twice. Annotate one with `@Component` + `@Profile("dev")` and the other with `@Component` + `@Profile("prod")`.
</details>

<details>
<summary>✅ Solution</summary>

```java
public interface EmailSender { void send(String msg); }

@Component
@Profile("dev")
public class DummyEmailSender implements EmailSender {
    public void send(String msg) { System.out.println("DEV (No Email Sent): " + msg); }
}

@Component
@Profile("prod")
public class SendGridEmailSender implements EmailSender {
    public void send(String msg) { System.out.println("PROD (Sent via SendGrid): " + msg); }
}

@Service
public class UserService {
    private final EmailSender emailSender; // Spring injects the correct one based on active profile!
    public UserService(EmailSender emailSender) { this.emailSender = emailSender; }
}
```
</details>

### Level 3: Boss Level
**Task:** Bind nested YAML properties and lists! Given the following YAML, create the corresponding `@ConfigurationProperties` structure.
```yaml
security:
  jwt:
    secret: "super-secret"
    expiration-mins: 60
  allowed-ips:
    - "192.168.1.1"
    - "10.0.0.1"
```
<details>
<summary>💡 Hint</summary>
You will need a nested inner class for `Jwt` and a `List<String>` for `allowedIps`.
</details>

<details>
<summary>✅ Solution Walkthrough</summary>

```java
@Configuration
@ConfigurationProperties(prefix = "security")
public class SecurityProperties {

    // Binds the list automatically
    private List<String> allowedIps;

    // Binds the nested 'jwt' block
    private Jwt jwt = new Jwt(); // Important to instantiate the inner class

    public List<String> getAllowedIps() { return allowedIps; }
    public void setAllowedIps(List<String> allowedIps) { this.allowedIps = allowedIps; }
    public Jwt getJwt() { return jwt; }
    public void setJwt(Jwt jwt) { this.jwt = jwt; }

    // Inner class for nested properties
    public static class Jwt {
        private String secret;
        private int expirationMins;

        public String getSecret() { return secret; }
        public void setSecret(String secret) { this.secret = secret; }
        public int getExpirationMins() { return expirationMins; }
        public void setExpirationMins(int expirationMins) { this.expirationMins = expirationMins; }
    }
}
```
*Walkthrough:* This is how enterprise applications manage complex configurations. By structuring it this way, when injected into a service, you access it fluently: `properties.getJwt().getSecret()`. It provides a clean, self-documenting, and type-safe approach to application configuration that survives refactoring.
</details>
