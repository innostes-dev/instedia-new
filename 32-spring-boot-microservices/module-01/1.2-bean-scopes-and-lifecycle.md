# 1.2 Bean Scopes and Lifecycle

## Phase A: The Core Concept

### Real-World Pain Point (The Why)
Imagine building a shopping cart application. You create a `ShoppingCart` service and annotate it with `@Service`. User A adds a laptop to their cart. Suddenly, User B logs in, checks their cart, and sees User A's laptop! This catastrophic data leak happens because Spring creates only **one instance** of a bean by default (Singleton scope) and shares it across all threads and requests.

### Plain English Metaphor (The What)
Bean Scopes dictate *how many copies* of an object Spring makes.
*   **Singleton (Default):** Like a public city fountain. Everyone drinks from the exact same water source. Great for stateless services.
*   **Prototype:** Like a disposable paper cup. Every time someone asks for a cup, they get a brand new, empty one.
*   **Request:** Like a temporary locker at a theme park. It belongs to you for exactly one visit (HTTP request), then it gets wiped clean.

The **Bean Lifecycle** is the birth-to-death process of that object. Sometimes you need to run specific setup code *after* Spring has injected dependencies, or cleanup code right before the application shuts down.

### Complete Runnable Code
Let's build a Tenant-Isolated Security Context Resolver to demonstrate Scopes and Lifecycle.

```java
import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;
import org.springframework.context.annotation.Scope;
import org.springframework.context.annotation.ScopedProxyMode;
import org.springframework.stereotype.Component;
import org.springframework.web.context.WebApplicationContext;

// We need a NEW instance of this context for every single HTTP Request
@Component
@Scope(value = WebApplicationContext.SCOPE_REQUEST, proxyMode = ScopedProxyMode.TARGET_CLASS)
public class TenantSecurityContext {

    private String currentTenantId;

    // Lifecycle Hook: Runs right after Spring injects dependencies
    @PostConstruct
    public void initialize() {
        System.out.println("TenantSecurityContext initialized for a new request.");
        this.currentTenantId = "UNAUTHENTICATED";
    }

    public void setTenantId(String tenantId) {
        this.currentTenantId = tenantId;
    }

    public String getTenantId() {
        return this.currentTenantId;
    }

    // Lifecycle Hook: Runs right before the bean is destroyed (end of request)
    @PreDestroy
    public void cleanup() {
        System.out.println("Wiping security context: " + this.currentTenantId);
        this.currentTenantId = null;
    }
}
```

### Progressive Step-by-Step Breakdown

**Step 1: Declare the Request Scope**
```java
@Component
@Scope(value = WebApplicationContext.SCOPE_REQUEST, proxyMode = ScopedProxyMode.TARGET_CLASS)
public class TenantSecurityContext { ... }
```
*Why this precedes the next step:* If we don't set this to `SCOPE_REQUEST`, this bean will be a Singleton. If User A sets the `tenantId` to "AcmeCorp", User B will inherit "AcmeCorp" as well. The `proxyMode` is required because Singletons (like a global Controller) will try to inject this Request-scoped bean at startup when no HTTP request exists. The proxy acts as a placeholder that connects to the *real* request-scoped object at runtime.

**Step 2: The Initialization Hook (@PostConstruct)**
```java
@PostConstruct
public void initialize() {
    this.currentTenantId = "UNAUTHENTICATED";
}
```
*Why this precedes the next step:* You cannot perform complex logic or access injected dependencies inside a standard Java constructor because Spring hasn't finished wiring the dependencies yet. `@PostConstruct` guarantees the bean is fully wired and ready for custom setup logic before any other code can use it.

**Step 3: The Cleanup Hook (@PreDestroy)**
```java
@PreDestroy
public void cleanup() {
    this.currentTenantId = null;
}
```
*Why this is the final step:* When the HTTP request ends, Spring destroys this specific instance of `TenantSecurityContext`. `@PreDestroy` allows us to cleanly release resources, close file handles, or clear out sensitive data (like wiping a tenant ID from memory) just before garbage collection.

### ASCII Architecture Data Flow

```text
HTTP Request 1 (User A) ---> [ Singleton Controller ]
                                     |
                                     v (Via Proxy)
                             [ TenantSecurityContext (Instance 1) ]
                                 1. @PostConstruct (Birth)
                                 2. setTenantId("Company_A")
                                 3. @PreDestroy (Death/End Request)

HTTP Request 2 (User B) ---> [ Singleton Controller ]
                                     |
                                     v (Via Proxy)
                             [ TenantSecurityContext (Instance 2) ]
                                 1. @PostConstruct (Birth)
                                 2. setTenantId("Company_B")
                                 3. @PreDestroy (Death/End Request)
```

### Noob Trap vs Pro Tip
*   **Noob Trap:** Putting state (like a `List<Order>` or `currentUser`) into a standard `@Service` bean. You will create severe race conditions and data leaks across threads in production.
*   **Pro Tip:** Keep your Singletons (Services, Controllers, Repositories) **100% stateless**. They should only contain methods and final dependency references. If you *must* hold state per request/user, use `SCOPE_REQUEST` or pass the state as method parameters.

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**Task:** Create a `CacheManager` bean. When it starts up, it should load some dummy data into a map. When the application stops, it should print "Flushing cache".
<details>
<summary>💡 Hint</summary>
Use a standard `@Component` (which is Singleton by default) and utilize `@PostConstruct` and `@PreDestroy`.
</details>

<details>
<summary>✅ Solution</summary>

```java
@Component
public class CacheManager {
    private Map<String, String> cache = new HashMap<>();

    @PostConstruct
    public void init() {
        cache.put("config", "loaded");
        System.out.println("Cache initialized.");
    }

    @PreDestroy
    public void shutdown() {
        System.out.println("Flushing cache to disk...");
        cache.clear();
    }
}
```
</details>

### Level 2: Real-World
**Task:** You are building an email batch processor. Every time you send a batch, you need a brand new instance of an `EmailJobTracker` to keep track of successes and failures for *that specific batch*.
<details>
<summary>💡 Hint</summary>
You cannot use Singleton. You need a new instance every time you ask Spring for one. Use `@Scope("prototype")`.
</details>

<details>
<summary>✅ Solution</summary>

```java
@Component
@Scope("prototype")
public class EmailJobTracker {
    private int successCount = 0;

    public void incrementSuccess() {
        this.successCount++;
    }
    public int getSuccessCount() { return this.successCount; }
}

@Service
public class EmailService {
    // You cannot just inject a prototype bean normally into a singleton,
    // it will only be injected once!
    // Use ObjectProvider or ApplicationContext to fetch a new one when needed.

    private final ObjectProvider<EmailJobTracker> trackerProvider;

    public EmailService(ObjectProvider<EmailJobTracker> trackerProvider) {
        this.trackerProvider = trackerProvider;
    }

    public void processBatch() {
        // Gets a BRAND NEW instance every time this is called
        EmailJobTracker tracker = trackerProvider.getObject();
        tracker.incrementSuccess();
    }
}
```
</details>

### Level 3: Boss Level
**Task:** Combine scopes! Build a `RequestLogger` (Request Scope) that depends on a `GlobalAuditService` (Singleton Scope). The RequestLogger should generate a unique trace ID on creation, log it, and send it to the GlobalAuditService when destroyed.
<details>
<summary>💡 Hint</summary>
Yes, Request scoped beans can safely have Singleton beans injected into them via constructor injection!
</details>

<details>
<summary>✅ Solution Walkthrough</summary>

```java
@Service
public class GlobalAuditService {
    public void saveAudit(String traceId) {
        System.out.println("Saved audit for trace: " + traceId);
    }
}

@Component
@Scope(value = WebApplicationContext.SCOPE_REQUEST, proxyMode = ScopedProxyMode.TARGET_CLASS)
public class RequestLogger {
    private final GlobalAuditService auditService;
    private String traceId;

    public RequestLogger(GlobalAuditService auditService) {
        // Safe: Injecting a Singleton into a Request-scoped bean
        this.auditService = auditService;
    }

    @PostConstruct
    public void init() {
        this.traceId = UUID.randomUUID().toString();
        System.out.println("Starting request with trace: " + traceId);
    }

    @PreDestroy
    public void finish() {
        System.out.println("Request ended. Auditing trace: " + traceId);
        auditService.saveAudit(this.traceId);
    }
}
```
*Walkthrough:* This perfectly demonstrates mixing scopes. It is safe for a short-lived bean (Request) to depend on a long-lived bean (Singleton). However, the reverse (Singleton depending on a Request bean) requires a `ScopedProxy` as seen in Phase A, because the Singleton outlives the Request bean and needs a proxy to fetch the *current* request instance dynamically.
</details>
