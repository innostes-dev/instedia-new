# 2.2 Offline-First Architecture: SQLite & WatermelonDB

## Phase A: Concept & Implementation

### 1. Real-World Pain Point (The Why)
Web apps often assume a constant, high-speed internet connection. When mobile users go through a tunnel, enter airplane mode, or have spotty 3G, traditional React Native apps that rely heavily on `fetch` or `axios` on every screen load will freeze, show infinite spinners, or crash to a white screen. Simple `AsyncStorage` is inadequate for complex relational data because it's a slow, string-based key-value store. You need a real database running locally on the phone.

### 2. Plain English Metaphor (The What)
Imagine you are a traveling salesperson. A traditional web app is like having to call headquarters on your cell phone every time you need to check a customer's file. If you lose signal, you can't work. An Offline-First app is like downloading all the filing cabinets into the trunk of your car (Local SQLite Database) before you leave. You can read, write, and update files instantly, regardless of your cell connection. When you get back to a Wi-Fi zone, an engine (WatermelonDB) quietly synchronizes your local changes back to headquarters.

### 3. Complete Runnable Code
*Example: Offline-First Mobile Note-Taking App (Using WatermelonDB)*

**Setup requirements:** Requires `@nozbe/watermelondb` and a SQLite adapter.

**`model/schema.ts` (Defining the Database)**
```ts
import { appSchema, tableSchema } from '@nozbe/watermelondb'

export const mySchema = appSchema({
  version: 1,
  tables: [
    tableSchema({
      name: 'notes',
      columns: [
        { name: 'title', type: 'string' },
        { name: 'body', type: 'string' },
        { name: 'is_pinned', type: 'boolean' },
        { name: 'created_at', type: 'number' }, // For syncing
        { name: 'updated_at', type: 'number' },
      ]
    })
  ]
})
```

**`model/Note.ts` (The Data Model)**
```ts
import { Model } from '@nozbe/watermelondb'
import { field, date, readonly } from '@nozbe/watermelondb/decorators'

export default class Note extends Model {
  static table = 'notes'

  @field('title') title
  @field('body') body
  @field('is_pinned') isPinned
  @readonly @date('created_at') createdAt
  @readonly @date('updated_at') updatedAt
}
```

**`database.ts` (Instantiating the DB)**
```ts
import { Database } from '@nozbe/watermelondb'
import SQLiteAdapter from '@nozbe/watermelondb/adapters/sqlite'
import { mySchema } from './schema'
import Note from './Note'

const adapter = new SQLiteAdapter({
  schema: mySchema,
  jsi: true, // Use fast C++ synchronous bindings
  onSetUpError: error => console.error(error)
})

export const database = new Database({
  adapter,
  modelClasses: [Note],
})
```

**`App.tsx` (Reactive UI)**
```tsx
import React, { useState } from 'react';
import { View, Text, TextInput, Button, FlatList, StyleSheet } from 'react-native';
import { withObservables } from '@nozbe/watermelondb/react';
import { database } from './database';
import Note from './model/Note';

// Component that purely renders the list of notes
const NoteList = ({ notes }: { notes: Note[] }) => (
  <FlatList
    data={notes}
    keyExtractor={item => item.id}
    renderItem={({ item }) => (
      <View style={styles.card}>
        <Text style={styles.title}>{item.title}</Text>
        <Text style={styles.body}>{item.body}</Text>
        <Button
          title={item.isPinned ? "Unpin" : "Pin"}
          onPress={async () => {
            // Update action wrapped in a DB transaction
            await database.write(async () => {
              await item.update(note => {
                note.isPinned = !note.isPinned;
              });
            });
          }}
        />
      </View>
    )}
  />
);

// HOC to auto-re-render NoteList when the DB changes
const EnhancedNoteList = withObservables([], () => ({
  notes: database.collections.get<Note>('notes').query().observe(),
}))(NoteList);

export default function OfflineApp() {
  const [title, setTitle] = useState('');

  const addNote = async () => {
    if (!title) return;

    // Write directly to local SQLite instantly
    await database.write(async () => {
      await database.collections.get<Note>('notes').create(note => {
        note.title = title;
        note.body = 'Offline content here...';
        note.isPinned = false;
      });
    });
    setTitle('');
  };

  return (
    <View style={styles.container}>
      <Text style={styles.header}>Offline Notebook</Text>
      <View style={styles.inputRow}>
        <TextInput
          style={styles.input}
          value={title}
          onChangeText={setTitle}
          placeholder="New Note Title"
        />
        <Button title="Add" onPress={addNote} />
      </View>
      <EnhancedNoteList />
    </View>
  );
}

const styles = StyleSheet.create({
  container: { flex: 1, padding: 20, paddingTop: 60, backgroundColor: '#f0f0f0' },
  header: { fontSize: 24, fontWeight: 'bold', marginBottom: 20 },
  inputRow: { flexDirection: 'row', marginBottom: 20 },
  input: { flex: 1, borderWidth: 1, borderColor: '#ccc', marginRight: 10, padding: 10, backgroundColor: 'white' },
  card: { backgroundColor: 'white', padding: 15, marginBottom: 10, borderRadius: 8 },
  title: { fontSize: 18, fontWeight: 'bold' },
  body: { color: '#666', marginTop: 5, marginBottom: 10 }
});
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: Schema and Models (The DB Shape)**
Why this precedes the next: SQLite requires strict types and tables before it can store data, unlike NoSQL document stores.
```ts
export const mySchema = appSchema({
  version: 1,
  tables: [ tableSchema({ name: 'notes', columns: [...] }) ]
})
```
*Rationale:* This defines the physical tables created on the device's storage. Versioning is critical; if you add a column later, you must bump the version and write a migration script, just like a backend database.

**Step 2: Database Instantiation with JSI**
Why this precedes the next: We must configure how the JS thread talks to the local database file.
```ts
const adapter = new SQLiteAdapter({
  schema: mySchema,
  jsi: true,
})
```
*Rationale:* `jsi: true` is crucial. Without it, reading 10,000 rows requires serializing massive JSON strings over the asynchronous React Native bridge. JSI allows synchronous C++ memory access, meaning querying 10,000 local notes takes milliseconds.

**Step 3: Reactive UI with Observables**
Why this precedes the next: Now that the DB exists, the UI needs a way to react instantly when data is created, avoiding manual state management.
```ts
const EnhancedNoteList = withObservables([], () => ({
  notes: database.collections.get('notes').query().observe(),
}))(NoteList);
```
*Rationale:* `withObservables` connects the React component directly to a SQLite query. When you call `database.write(...)` elsewhere in the app, this observable fires, and `NoteList` re-renders instantly. It functions like an ultra-fast, local-only Redux store backed by a hard drive.

### 5. ASCII / Architecture Data Flow
```text
[ React Native UI ] --> User types Note & taps "Save"
        |
        v
[ JS Thread: database.write() ]
        |
[ JSI C++ Bridge (Synchronous) ]
        |
[ SQLite Engine ] --> Writes to device disk (/data/data/com.app/databases/my.db)
        |
[ DB Observer Fires ]
        |
[ JS Thread: withObservables() ] --> Re-renders UI instantly (Offline First complete)

--- LATER (Background Thread) ---
[ Sync Engine ] --> Detects internet connection
        |
[ HTTP POST ] --> Pushes new Note to Backend API (Eventual Consistency)
```

### 6. Noob Trap vs Pro Tip
* **Noob Trap:** Using Redux-Persist + AsyncStorage for "offline capabilities". Loading a 50MB Redux store from AsyncStorage into RAM on app boot will cause massive memory spikes and UI freezing.
* **Pro Tip:** Always wrap DB modifications in `database.write(async () => { ... })`. This ensures atomic transactions. If the app crashes halfway through updating three related records, the transaction rolls back, preventing corrupt local data.

### Level 2: Real-World
**Challenge:** Implement a "Soft Delete" mechanism. Instead of permanently deleting a note, add a `deleted_at` column, and update the UI to filter out deleted notes.
<details>
<summary>Hint</summary>
1. Update `schema.ts` (add `deleted_at: number | null`).
2. Update `Note.ts` model.
3. Instead of `note.destroyPermanently()`, use `note.update(n => n.deletedAt = Date.now())`.
4. Update queries to use `Q.where('deleted_at', null)`.
</details>

<details>
<summary>Solution Walkthrough</summary>
Soft deletes are crucial for syncing. If you hard delete locally while offline, the sync engine won't know it needs to tell the server to delete it.
```ts
// Deletion function
await database.write(async () => {
  await item.update(note => {
    note.deletedAt = Date.now();
  });
});

// Query
.query(Q.where('deleted_at', null))
```
WatermelonDB actually has a built-in `markAsDeleted()` method that handles this standard sync protocol automatically.
</details>

### Level 3: Boss Level
**Challenge:** Write the skeleton for the actual Synchronization function using `synchronize` from `@nozbe/watermelondb/sync`. You must handle pulling changes from the server and pushing local changes up.
<details>
<summary>Hint</summary>
You need to provide `pullChanges` (fetches from API based on `lastPulledAt`) and `pushChanges` (sends `changes` object to API) to the `synchronize()` function.
</details>

<details>
<summary>Solution Walkthrough</summary>
This is the core of real-world offline-first architecture.

```ts
import { synchronize } from '@nozbe/watermelondb/sync';

async function syncWithBackend() {
  await synchronize({
    database,
    // 1. Pull changes from server since the last sync
    pullChanges: async ({ lastPulledAt, schemaVersion, migration }) => {
      const response = await fetch(`https://api.myapp.com/sync?last_pulled_at=${lastPulledAt || 0}`);
      if (!response.ok) throw new Error('Failed to pull sync');
      const { changes, timestamp } = await response.json();
      return { changes, timestamp };
    },
    // 2. Push offline modifications to the server
    pushChanges: async ({ changes, lastPulledAt }) => {
      const response = await fetch('https://api.myapp.com/sync', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ changes, lastPulledAt }),
      });
      if (!response.ok) throw new Error('Failed to push sync');
    },
    migrationsEnabledAtVersion: 1,
  });
}
```
You run `syncWithBackend()` on app startup, when returning from the background, or when a "Back Online" network listener fires.
