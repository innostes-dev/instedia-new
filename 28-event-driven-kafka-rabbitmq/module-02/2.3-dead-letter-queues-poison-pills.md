# 2.3 Dead Letter Queues & Poison Pills

## Phase A: Understanding the Concept

### 1. Real-World Pain Point (The Why)
You have a resilient Payment Processing pipeline reading from a Kafka topic. It reads an event, calls Stripe via HTTP, and if it fails, it throws an error. Kafka (or RabbitMQ) dutifully retries the message.

But what if the message itself is fundamentally flawed? For example, `amount: "negative five"` (a string instead of an integer). Stripe will reject this *every single time*. This is called a **Poison Pill**. If your consumer throws an error and retries infinitely, this single bad message will block the entire partition. All valid payments queue up behind it, causing a massive system outage! If you simply "skip" the error (as seen in the previous module), you lose track of the failed payment entirely.

### 2. Plain English Metaphor (The What)
Think of an assembly line checking apples. A robot arm (Consumer) picks up an apple (Message) and tries to put a sticker on it.
If the sticker machine jams temporarily (transient error), the robot should put the apple back and try again in 5 seconds.
But if the robot picks up a *rock* that got mixed in (Poison Pill), it can't put a sticker on it, no matter how many times it tries. If the robot keeps trying forever, the whole assembly line stops.

Instead, the robot should try a few times. If it fails 3 times, it throws the rock into a special "Reject Bin" (Dead Letter Queue) so human engineers can look at it later, and the robot moves on to the next apple.

### 3. Complete Runnable Code
*Note: This utilizes `kafkajs` in Node.js, building heavily on the manual commit structure from the previous module.*

```javascript
const { Kafka } = require('kafkajs');

const kafka = new Kafka({ clientId: 'payments-app', brokers: ['localhost:9092'] });
const producer = kafka.producer();

async function processPayment(consumerGroup) {
  const consumer = kafka.consumer({ groupId: consumerGroup });
  await consumer.connect();
  await producer.connect(); // We need a producer to send to the DLQ!

  await consumer.subscribe({ topic: 'payment-events' });

  // In-memory retry state (in production, use Redis or message headers)
  const retryCount = new Map();

  await consumer.run({
    autoCommit: false,
    eachBatchAutoResolve: false,
    eachBatch: async ({ batch, resolveOffset, commitOffsetsIfNecessary }) => {
      for (let message of batch.messages) {
        const offset = message.offset;

        try {
          // 1. Attempt Processing
          const data = JSON.parse(message.value.toString());
          console.log(`[Processor] Charging $${data.amount} for user ${data.user}...`);

          if (data.amount < 0) {
            throw new Error("Validation Failed: Negative Amount");
          }

          // Simulate successful network call
          await new Promise(res => setTimeout(res, 50));
          console.log(`[Processor] Success: ${data.user}`);

          resolveOffset(offset); // Done!
          retryCount.delete(offset); // Clear state

        } catch (error) {
          // 2. Handle Failure
          let attempts = (retryCount.get(offset) || 0) + 1;
          retryCount.set(offset, attempts);

          if (attempts >= 3) {
            console.error(`[Processor] ❌ Max retries reached for offset ${offset}. Moving to DLQ!`);

            // Send to DLQ Topic
            await producer.send({
              topic: 'payment-events-dlq',
              messages: [
                {
                  key: message.key,
                  value: message.value,
                  headers: {
                    error_message: error.message,
                    original_topic: batch.topic
                  }
                }
              ]
            });

            // Mark as resolved in the MAIN topic so we can move on!
            resolveOffset(offset);
            retryCount.delete(offset);
          } else {
            console.warn(`[Processor] ⚠️ Failed offset ${offset}. Attempt ${attempts}/3.`);
            // Throwing the error aborts the batch. Kafka will deliver it again on next poll.
            throw error;
          }
        }
      }
      await commitOffsetsIfNecessary();
    }
  });
}

// startProducer to test: send { amount: -5 }
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: The Retry State (`retryCount`)**
We need to know how many times a specific message has failed. We use the message `offset` as a unique identifier.

**Step 2: The Retry Loop**
If a failure occurs and `attempts < 3`, we log a warning and **throw the error**. Throwing the error aborts the `eachBatch` loop. Because we haven't resolved the offset, Kafka will give us this exact same batch of messages again in a few seconds.

**Step 3: The DLQ Route**
If `attempts >= 3`, we realize this is a Poison Pill. We instantiate our `producer` and write the exact same raw message into a *different* topic: `payment-events-dlq`. We also attach useful metadata in the `headers` (like why it failed).

**Step 4: Moving On (`resolveOffset`)**
Crucially, after writing to the DLQ, we call `resolveOffset(offset)`. Even though processing failed, we have "handled" the failure by moving it to the DLQ. We must tell Kafka to move the bookmark forward, otherwise the partition remains blocked.

### 5. ASCII Data Flow

```text
[ Producer ] -> (Normal Event) -> [ Topic: "payments" ] -> (Consumer) -> [ DB ]
                                                               |
(Poison Pill arrives!)                                         |
                                                               v
                                                      (Error thrown 3x)
                                                               |
                                                               v
                                       (Produce raw message + Error Headers)
                                                               |
                                                               v
                                                 [ Topic: "payments-dlq" ]
                                                               |
                                                               v
                                                 [ Alerts / Manual Review ]
```

### 6. Noob Trap vs Pro Tip
**Noob Trap:** Using a local in-memory `Map` (like `retryCount`) for retries in a distributed system. If the Node.js process crashes on attempt 2, the container restarts, the memory is wiped, and the retry count goes back to 0.
**Pro Tip:** For RabbitMQ, use built-in DLX (Dead Letter Exchange) and `x-death` headers which track retry counts automatically on the broker side. For Kafka, store the retry state in a fast, external datastore like Redis, OR use a specialized "Retry Topic" architecture (e.g., `topic-retry-1`, `topic-retry-2`, `topic-dlq`).

### Level 1: Warm-Up

</details>

### Level 2: Real-World
**Challenge:** Exponential Backoff. Currently, if an external API is down, we retry 3 times instantly, bombarding the down API, and then instantly send valid messages to the DLQ.
Modify the catch block so that before it throws the error (to trigger a Kafka retry), it physically pauses the consumer execution for `attempts * 1000` milliseconds (1s, then 2s, then 3s).
<details>
<summary><strong>Hint</strong></summary>
Inside the `catch` block, in the `else` statement (where `attempts < 3`), add an `await new Promise(res => setTimeout(res, attempts * 1000));` before throwing the error.
</details>

<details>
<summary><strong>Solution Walkthrough</strong></summary>
```javascript
          if (attempts >= 3) {
            // ... DLQ Logic ...
          } else {
            console.warn(`[Processor] ⚠️ Failed. Backing off for ${attempts} seconds...`);

            // Exponential Backoff pause
            await new Promise(resolve => setTimeout(resolve, attempts * 1000));

            // Now throw to trigger Kafka retry loop
            throw error;
          }
```
This gives transient issues (like a restarting database or a momentary network blip) time to recover before you permanently DLQ the message.
</details>


### Level 3: Boss Level
**Challenge:** Build the DLQ Reprocessor.
The engineers fixed the bug that was rejecting negative amounts (turns out, refunds are negative amounts!). Now you have 500 valid refund messages sitting in the `payment-events-dlq` topic.
Write a script `reprocessDLQ()` that consumes from the DLQ topic, reads the original payload, and produces those messages *back* into the main `payment-events` topic so they can be processed by the main workers.
<details>
<summary><strong>Hint</strong></summary>
Create a new consumer connected to `groupId: dlq-reprocessor-group`. Subscribe to `payment-events-dlq`. In `eachMessage`, use a producer to send `message.value` to `payment-events`. Don't forget to remove the error headers so they don't pollute the main topic!
</details>

<details>
<summary><strong>Solution Walkthrough</strong></summary>
```javascript
async function reprocessDLQ() {
  const consumer = kafka.consumer({ groupId: 'dlq-recovery-tool' });
  await consumer.connect();
  await producer.connect();

  await consumer.subscribe({ topic: 'payment-events-dlq', fromBeginning: true });

  await consumer.run({
    eachMessage: async ({ message }) => {
      console.log(`[Recovery Tool] Re-queueing message to main topic...`);

      await producer.send({
        topic: 'payment-events',
        messages: [
          {
            key: message.key,
            value: message.value,
            // Clean slate: do not copy the error headers!
          }
        ]
      });
    }
  });
}
```
This completes the lifecycle of event-driven resilience. A bug caused data to be rejected, it was saved securely in the DLQ, the code was fixed, and the data was replayed back into the system without the user ever having to click "Submit" again!
</details>
