# 2.2 Scaling with Consumer Groups & Partitioning

## Phase A: Understanding the Concept

### 1. Real-World Pain Point (The Why)
Your e-commerce platform is growing. Your single Fraud Detection server is processing 500 events per second. But on Black Friday, traffic spikes to 50,000 events per second! The single server maxes out its CPU and starts falling behind.

If you just spin up two more Fraud Detection servers and point them all at the same Kafka topic, what happens? **They all read the exact same messages!** Because Kafka is a broadcast log, every independent consumer gets every message. You don't want three servers doing fraud checks on the *same* order; you want the three servers to *divide the work* (Server A handles 1/3, Server B handles 1/3, etc.). How do you achieve load balancing in a broadcast log?

### 2. Plain English Metaphor (The What)
Think of a massive library (Kafka) with an enormous multi-volume encyclopedia set (a Topic split into Partitions).
You hire a team of researchers (a Consumer Group) to read the entire set.

If you have one researcher, they have to read Volume 1, then Volume 2, then Volume 3. It takes forever.
If you hire three researchers *and tell them they are in the same team* (Consumer Group), the librarian will coordinate them: "Alice, you read Volume 1. Bob, you read Volume 2. Charlie, you read Volume 3." They work in parallel, processing the data three times as fast.
If Bob gets sick and goes home, the librarian (Kafka Coordinator) notices and reassigns Volume 2 to Alice or Charlie so no data is missed (Rebalancing).

### 3. Complete Runnable Code
*Note: This utilizes `kafkajs` in Node.js. It assumes a Kafka broker is running, but demonstrates the core syntax of consumer groups.*

```javascript
const { Kafka } = require('kafkajs');

const kafka = new Kafka({
  clientId: 'fraud-app',
  brokers: ['localhost:9092']
});

// --- PRODUCER ---
async function startProducer() {
  const producer = kafka.producer();
  await producer.connect();

  setInterval(async () => {
    const userId = `user_${Math.floor(Math.random() * 100)}`;
    const event = { amount: Math.random() * 1000, user: userId };

    await producer.send({
      topic: 'transactions',
      messages: [
        // The key is CRITICAL for partitioning!
        { key: userId, value: JSON.stringify(event) }
      ],
    });
    console.log(`[Producer] Sent tx for ${userId}`);
  }, 500);
}

// --- CONSUMER GROUP WORKER ---
async function startFraudWorker(workerName) {
  // All workers share the same groupId to divide the work!
  const consumer = kafka.consumer({ groupId: 'fraud-detection-group' });
  await consumer.connect();

  // fromBeginning: false means only read new messages
  await consumer.subscribe({ topic: 'transactions', fromBeginning: false });

  await consumer.run({
    eachMessage: async ({ topic, partition, message }) => {
      const data = JSON.parse(message.value.toString());
      console.log(`[${workerName}] Partition: ${partition} | Processing tx for ${data.user} - $${data.amount.toFixed(2)}`);

      // Simulate processing time
      await new Promise(res => setTimeout(res, 100));

      // kafkajs automatically commits offsets back to Kafka in the background by default
    },
  });
}
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: Partitions (The Volumes of the Encyclopedia)**
When you create a Kafka topic, you must specify how many *Partitions* it has. If a topic has 3 partitions, it is essentially 3 separate logs running in parallel.

**Step 2: Message Keys (`key: userId`)**
How does Kafka know which partition to put a message in? It hashes the `key`. If `user_123` hashes to Partition 1, *every single transaction* for `user_123` will go to Partition 1. This guarantees that messages for a specific user are processed strictly in order!

**Step 3: Consumer Groups (`groupId: 'fraud-detection-group'`)**
When `Worker-A` starts, Kafka assigns it all 3 partitions.
When `Worker-B` joins 5 seconds later with the *same* `groupId`, Kafka triggers a **Rebalance**. It pauses `Worker-A`, recalculates, and says: "Worker A, take Partitions 0 and 1. Worker B, take Partition 2." They are now sharing the load.

**Step 4: Offset Commits**
Unlike our simple arrays in the previous module, real Kafka stores the consumer's offset *inside Kafka itself* (in a hidden topic called `__consumer_offsets`). When `Worker-B` takes over Partition 2, it knows exactly where `Worker-A` left off because the offset was committed globally!

### 5. ASCII Data Flow

```text
[ Producer ] --(hash("user_99"))--> [ Partition 0 ] ---> (Worker A)
                                                           |
[ Producer ] --(hash("user_12"))--> [ Partition 1 ] ---> (Worker A)
                                                           | (fraud-group)
[ Producer ] --(hash("user_55"))--> [ Partition 2 ] ---> (Worker B)
```

### 6. Noob Trap vs Pro Tip
**Noob Trap:** Creating a topic with 1 Partition, but spinning up 5 workers in a Consumer Group.
**Result:** 1 worker does all the work, and the other 4 sit completely idle. A partition can only be read by *one* consumer in a group at a time.
**Pro Tip:** Over-partition your topics slightly from day one. If you think you need 3 servers, create the topic with 12 partitions. That way, as you scale, you can add up to 12 servers before you hit the Kafka concurrency limit. Changing partition counts later breaks message key ordering!

```javascript
async function startFraudWorker(workerName) {
  const consumer = kafka.consumer({ groupId: 'fraud-detection-group' });
  await consumer.connect();
  await consumer.subscribe({ topic: 'transactions' });

  if (workerName === 'Worker-B') {
    setTimeout(async () => {
      console.log(`[${workerName}] CRASHING!`);
      await consumer.disconnect();
    }, 10000);
  }
  // ... run logic ...
}
```
When `Worker-B` disconnects (or misses its heartbeat timeout if the server physically died), Kafka coordinator notices. It triggers another Rebalance. It takes Partition 2 away from the dead worker and gives it back to `Worker-A`. High availability achieved!
</details>


### Level 2: Real-World
**Challenge:** Switch from Auto-Commit to Manual Commit.
By default, KafkaJS auto-commits offsets every few seconds. If your worker pulls a message, starts processing it, and crashes 1 second later *before* the auto-commit fires, what happens? The next worker will replay that message.
Update the consumer to disable auto-commit and manually commit the offset *only after* the transaction is successfully written to your local database (simulated).
<details>
<summary><strong>Hint</strong></summary>
In `consumer.run()`, set `autoCommit: false`.
KafkaJS provides the `commitOffsetsIfNecessary` or you can use the `resolveOffset(message.offset)` function provided in `eachBatch` (if using batch processing). For `eachMessage`, you must use a slightly different pattern or switch to `eachBatch`.
</details>

<details>
<summary><strong>Solution Walkthrough</strong></summary>
*Note: KafkaJS handles offsets elegantly in `eachMessage`—if your async function throws an error, it does not commit. But to be strictly explicit with manual commits, developers often use `eachBatch`.*
```javascript
  await consumer.run({
    autoCommit: false,
    eachBatchAutoResolve: false, // Don't auto resolve the batch
    eachBatch: async ({ batch, resolveOffset, heartbeat, commitOffsetsIfNecessary }) => {
      for (let message of batch.messages) {
        const data = JSON.parse(message.value.toString());

        try {
          // 1. Process Message
          console.log(`Processing: ${data.user}`);
          await new Promise(res => setTimeout(res, 50)); // Sim DB write

          // 2. Mark as done locally
          resolveOffset(message.offset);

          // 3. Heartbeat to keep Kafka from thinking we died during long processing
          await heartbeat();
        } catch (error) {
          // If we fail here, the offset is never resolved.
          // Next time we poll, we get this message again!
          console.error(`Failed! Halting batch.`);
          throw error;
        }
      }
      // 4. Commit all resolved offsets in this batch to Kafka
      await commitOffsetsIfNecessary();
    },
  });
```
This guarantees "At-Least-Once" delivery. Messages are only committed when safely processed.
</details>


### Level 3: Boss Level
**Challenge:** Handle the "Poison Pill" (Malformed Data) without blocking the partition.
In Level 2, if a message has invalid JSON, `JSON.parse` will throw an error. The batch halts, the offset is not committed. The consumer retries. It fails again. It retries infinitely. The entire partition is now **blocked** because of one bad message!
Modify the code to catch parsing errors, log them, skip the message (by resolving its offset), and move on to the next one so traffic keeps flowing.
<details>
<summary><strong>Hint</strong></summary>
Wrap `JSON.parse` in a `try/catch`. If it catches a `SyntaxError`, log "Skipping invalid message", call `resolveOffset(message.offset)`, and `continue` to the next iteration of the loop.
</details>

<details>
<summary><strong>Solution Walkthrough</strong></summary>
```javascript
    eachBatch: async ({ batch, resolveOffset, heartbeat, commitOffsetsIfNecessary }) => {
      for (let message of batch.messages) {
        let data;
        try {
          // Potential Poison Pill!
          data = JSON.parse(message.value.toString());
        } catch (parseError) {
          console.error(`[Poison Pill] Bad JSON at offset ${message.offset}. Skipping!`);
          resolveOffset(message.offset); // Mark as "done" so we don't get stuck
          continue; // Move to next message in batch
        }

        // ... Normal Processing ...
        console.log(`Processing: ${data.user}`);
        resolveOffset(message.offset);
      }
      await commitOffsetsIfNecessary();
    }
```
This is a critical distributed systems concept. In a real system, instead of just logging the poison pill, you would publish that exact raw message to a Dead Letter Queue (DLQ) Kafka topic so engineers can inspect it later, which leads us perfectly into Module 2.3!
</details>
