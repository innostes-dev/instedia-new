# 2.2 Authentication Guards and RBAC (Role-Based Access Control)

## Phase A: Concept & Implementation

### Real-World Pain Point (The Why)
In standard Node.js applications, authorization often looks like middleware soup. You write an `isAdmin` middleware, an `isSuperAdmin` middleware, and attach them manually to routes. Soon, you need to check if a user is an admin *or* a manager. You start putting role checks directly inside controller logic: `if (req.user.role !== 'admin') return res.status(403)`. This violates the Single Responsibility Principle, makes controllers unreadable, and makes it impossible to view a route's security constraints at a glance.

### Plain English Metaphor (The What)
If the ValidationPipe is the bouncer checking the dress code, the **Guard** is the security guard checking your VIP badge. Before you even get to the door, the Guard asks, "Are you allowed to be here?" The Guard reads metadata (like a VIP list) attached to the route. If you don't have the right clearance, the Guard stops you immediately. Guards separate *who is allowed to do something* from *what the application actually does*.

### Complete Runnable Code
```typescript
import {
  Injectable, CanActivate, ExecutionContext,
  Controller, Get, UseGuards, SetMetadata
} from '@nestjs/common';
import { Reflector } from '@nestjs/core';

// 1. Custom Decorator for assigning roles to routes
export const Roles = (...roles: string[]) => SetMetadata('roles', roles);

// 2. The Auth Guard (Checks if user is logged in)
@Injectable()
export class AuthGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const request = context.switchToHttp().getRequest();
    // Simulate finding a user from a token
    const authHeader = request.headers.authorization;
    if (authHeader === 'Bearer secret-token') {
      // Attach mock user to request
      request.user = { id: 1, role: 'admin' };
      return true;
    }
    return false; // Automatically throws 403 Forbidden
  }
}

// 3. The RBAC Guard (Checks if logged-in user has the right role)
@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}

  canActivate(context: ExecutionContext): boolean {
    // Read the required roles from the route's metadata
    const requiredRoles = this.reflector.get<string[]>('roles', context.getHandler());

    // If no roles are required, allow access
    if (!requiredRoles) {
      return true;
    }

    const request = context.switchToHttp().getRequest();
    const user = request.user;

    // Check if the user exists and has a role included in requiredRoles
    if (!user) return false;
    return requiredRoles.includes(user.role);
  }
}

// 4. Controller using Guards and Decorators
@Controller('dashboard')
// Apply AuthGuard globally to this controller
@UseGuards(AuthGuard, RolesGuard)
export class DashboardController {

  @Get('public-stats')
  // No @Roles() metadata, so RolesGuard allows it (AuthGuard still runs)
  getPublicStats() {
    return { data: 'Basic Stats' };
  }

  @Get('financials')
  @Roles('admin', 'finance') // Attach metadata
  getFinancials() {
    return { money: '$1,000,000' };
  }
}
```

### Progressive Step-by-Step Breakdown

**Step 1: Implementing `CanActivate`**
```typescript
export class AuthGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    // Return true to allow, false to deny
  }
}
```
*Rationale:* Every Guard must implement the `CanActivate` interface. It provides an `ExecutionContext`, which abstracts the underlying platform (HTTP, WebSockets, gRPC). You return a boolean (or a Promise resolving to a boolean).

**Step 2: Attaching Metadata**
```typescript
export const Roles = (...roles: string[]) => SetMetadata('roles', roles);
```
*Rationale:* We need a way to tell the Guard *which* roles are allowed for a specific route. `SetMetadata` creates a custom decorator (`@Roles`) that simply attaches key-value pairs (`'roles': ['admin']`) to the route handler.

**Step 3: Reading Metadata with `Reflector`**
```typescript
const requiredRoles = this.reflector.get<string[]>('roles', context.getHandler());
```
*Rationale:* Inside the `RolesGuard`, we use NestJS's `Reflector` utility to read the metadata that was attached by `@Roles()`. We compare this required list against the `request.user.role` (which was populated earlier by the `AuthGuard`).

### ASCII / Architecture Data Flow
```text
[HTTP GET /dashboard/financials]
       │
       ▼
┌──────────────┐
│  AuthGuard   │ -> Checks Headers -> Attaches `req.user = { role: 'admin' }`
└──────┬───────┘
       │ (Proceeds)
       ▼
┌──────────────┐
│  RolesGuard  │ -> Reads Route Metadata: ['admin', 'finance']
│ (Reflector)  │ -> Compares to `req.user.role`
└──────┬───────┘
       │ (Match Found, Proceeds)
       ▼
┌──────────────┐
│  Controller  │ -> Returns Financial Data
└──────────────┘
```

### Noob Trap vs Pro Tip
* **Noob Trap:** Putting complex database queries directly inside a Guard to look up a user. Guards execute before Pipes and Interceptors. If your Guard fails, the request dies. Keep Guards fast. Use them to verify tokens (JWTs) and use the token payload for roles.
* **Pro Tip:** Execution order matters! In `@UseGuards(AuthGuard, RolesGuard)`, they run left-to-right. `AuthGuard` *must* run first to populate `req.user` so that `RolesGuard` has a user to check.

### Level 1 Warm-Up
**Task:** Create an `ApiKeyGuard` that checks if the `x-api-key` header exactly matches `'super-secret'`. Protect a `ConfigController` with it.
<details>
<summary>Hint</summary>
Implement `CanActivate`. Extract the header using `context.switchToHttp().getRequest().headers['x-api-key']`.
</details>
<details>
<summary>Solution</summary>

```typescript
import { Injectable, CanActivate, ExecutionContext, Controller, Get, UseGuards } from '@nestjs/common';

@Injectable()
export class ApiKeyGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const request = context.switchToHttp().getRequest();
    return request.headers['x-api-key'] === 'super-secret';
  }
}

@Controller('config')
@UseGuards(ApiKeyGuard)
export class ConfigController {
  @Get()
  getConfig() { return { dbUrl: 'localhost' }; }
}
```

### Level 2 Real-World
**Task:** Create a `RequirePermissions` decorator and a `PermissionsGuard`. The Guard should deny access if the user (mocked as having `permissions: ['read:users']`) doesn't have the permissions defined by the decorator.
<details>
<summary>Hint</summary>
Create `const RequirePermissions = (...perms: string[]) => SetMetadata('permissions', perms);`. Use `Reflector` in the guard to read `'permissions'`.
</details>
<details>
<summary>Solution</summary>

```typescript
import { Injectable, CanActivate, ExecutionContext, SetMetadata, Controller, Get, UseGuards } from '@nestjs/common';
import { Reflector } from '@nestjs/core';

export const RequirePermissions = (...perms: string[]) => SetMetadata('permissions', perms);

@Injectable()
export class PermissionsGuard implements CanActivate {
  constructor(private reflector: Reflector) {}

  canActivate(context: ExecutionContext): boolean {
    const required = this.reflector.get<string[]>('permissions', context.getHandler());
    if (!required) return true;

    // Mock user
    const user = { id: 1, permissions: ['read:users'] };

    // Check if user has ALL required permissions
    return required.every(p => user.permissions.includes(p));
  }
}

@Controller('users')
@UseGuards(PermissionsGuard)
export class UserController {

  @Get()
  @RequirePermissions('read:users')
  getUsers() { return [{ name: 'Alice' }]; }

  @Get('delete')
  @RequirePermissions('delete:users') // Will fail
  deleteUser() { return { status: 'Deleted' }; }
}
```
</details>

### Level 3 Boss Level
**Task:** Build an Enterprise Multi-Tier RBAC system. You have a `JwtAuthGuard` that sets `req.user = { id: 1, role: 'editor', isBanned: false }`. You need a `BanGuard` (blocks banned users) and a `RolesGuard`. Combine them so that a route requires the user to be logged in, NOT banned, and have the `'admin'` role.
<details>
<summary>Hint</summary>
Create all three guards. Apply them in order: `@UseGuards(JwtAuthGuard, BanGuard, RolesGuard)`.
</details>
<details>
<summary>Solution</summary>

```typescript
import { Injectable, CanActivate, ExecutionContext, Controller, Post, UseGuards, SetMetadata } from '@nestjs/common';
import { Reflector } from '@nestjs/core';

export const Roles = (...roles: string[]) => SetMetadata('roles', roles);

@Injectable()
export class JwtAuthGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const req = context.switchToHttp().getRequest();
    // Simulate JWT extraction
    req.user = { id: 1, role: 'editor', isBanned: false };
    return true;
  }
}

@Injectable()
export class BanGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const req = context.switchToHttp().getRequest();
    return req.user && !req.user.isBanned; // Deny if banned
  }
}

@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}
  canActivate(context: ExecutionContext): boolean {
    const roles = this.reflector.get<string[]>('roles', context.getHandler());
    if (!roles) return true;
    const req = context.switchToHttp().getRequest();
    return req.user && roles.includes(req.user.role);
  }
}

@Controller('system')
export class SystemController {
  @Post('wipe-database')
  @Roles('admin')
  // Execution order guarantees user exists and isn't banned before checking roles
  @UseGuards(JwtAuthGuard, BanGuard, RolesGuard)
  wipeDb() {
    return { status: 'DB Wiped' }; // Will fail because user is 'editor'
  }
}
```
</details>
