# 1.1 Inversion of Control & Constructor-Based DI

## Phase A: Concept & Implementation

### Real-World Pain Point (The Why)
Imagine an Express application where a `PaymentService` instantiates a `StripeClient` directly inside its methods. As the app grows, you realize you need to pass a configuration object into `StripeClient`. Suddenly, you have to find and modify every place `StripeClient` is initialized. Worse, testing becomes impossible without complex mocking because the `PaymentService` is tightly coupled to the exact implementation of `StripeClient`. This un-structured callback spaghetti and tight coupling makes the system brittle and unmaintainable.

### Plain English Metaphor (The What)
Think of building a car. Instead of the engine manufacturing its own spark plugs, the factory (the IoC container) manufactures the spark plugs, the engine, and the chassis. When the engine is being assembled, the factory *injects* the ready-made spark plugs into it. This is **Dependency Injection (DI)**. The engine doesn't care how the spark plugs were made; it just needs them to work. **Inversion of Control (IoC)** means the car parts have given up control over creating their dependencies and handed that responsibility to the factory.

### Complete Runnable Code
```typescript
import { Module, Injectable, Controller, Post, Body } from '@nestjs/common';
import { NestFactory } from '@nestjs/core';

// 1. Define the Dependency
@Injectable()
export class StripeGateway {
  processPayment(amount: number): string {
    return `Processed $${amount} via Stripe.`;
  }
}

// 2. Inject the Dependency via Constructor
@Injectable()
export class PaymentService {
  constructor(private readonly stripeGateway: StripeGateway) {}

  executeCheckout(cartTotal: number): string {
    return this.stripeGateway.processPayment(cartTotal);
  }
}

// 3. Expose via Controller
@Controller('payments')
export class PaymentController {
  constructor(private readonly paymentService: PaymentService) {}

  @Post('checkout')
  checkout(@Body() body: { amount: number }): { result: string } {
    return { result: this.paymentService.executeCheckout(body.amount) };
  }
}

// 4. Register in a Module
@Module({
  controllers: [PaymentController],
  providers: [StripeGateway, PaymentService],
})
export class PaymentModule {}

// 5. Bootstrap
async function bootstrap() {
  const app = await NestFactory.create(PaymentModule);
  await app.listen(3000);
}
bootstrap();
```

### Progressive Step-by-Step Breakdown

**Step 1: The `@Injectable()` Decorator**
```typescript
@Injectable()
export class StripeGateway {
  processPayment(amount: number): string {
    return `Processed $${amount} via Stripe.`;
  }
}
```
*Rationale:* Before a class can be injected, it needs to be recognized by NestJS's IoC container. The `@Injectable()` decorator attaches metadata to the class, telling NestJS that this class can be managed as a provider.

**Step 2: Constructor Dependency Injection**
```typescript
@Injectable()
export class PaymentService {
  constructor(private readonly stripeGateway: StripeGateway) {}
}
```
*Rationale:* Instead of creating `new StripeGateway()`, we declare it in the constructor. NestJS reads the TypeScript type (`StripeGateway`), finds the corresponding provider in the container, and automatically passes it when creating `PaymentService`. The `private readonly` shorthand automatically creates a class property.

**Step 3: The `@Module()` Decorator**
```typescript
@Module({
  controllers: [PaymentController],
  providers: [StripeGateway, PaymentService],
})
export class PaymentModule {}
```
*Rationale:* The module is the wiring center. It tells NestJS exactly which controllers handle routes and which providers (services) belong to this module's context. Without this, NestJS won't know how to resolve dependencies.

```text
[HTTP Request]

└──────────────┘
```

### Noob Trap vs Pro Tip
* **Noob Trap:** Using `new Service()` inside another service. This defeats the entire purpose of the IoC container, making testing harder and breaking singleton instances (you'll end up with multiple instances of a service that was meant to be shared).
* **Pro Tip:** Always mark injected dependencies as `private readonly` in the constructor. It prevents accidental reassignment, makes the code cleaner, and adheres to strict TypeScript practices for dependency safety.

## Phase B: Engineering Challenges

### Level 1 Warm-Up
**Task:** Create an `EmailService` and inject it into a `NotificationController`.
<details>
<summary>Hint</summary>
Use `@Injectable()` on the `EmailService` and add it to the `providers` array in your Module.
</details>
<details>
<summary>Solution</summary>

```typescript
import { Injectable, Controller, Post, Module } from '@nestjs/common';

@Injectable()
export class EmailService {
  send(msg: string) { return `Sent: ${msg}`; }
}

@Controller('notify')
export class NotificationController {
  constructor(private readonly emailService: EmailService) {}

  @Post()
  notify() { return this.emailService.send("Hello"); }
}

@Module({
  controllers: [NotificationController],
  providers: [EmailService]
})
export class NotificationModule {}
```
</details>

### Level 2 Real-World
**Task:** Build a `ReportService` that depends on both a `DataFetchService` and a `PdfFormatService`. Ensure all three are properly wired in a `ReportModule`.
<details>
<summary>Hint</summary>
The `ReportService` constructor will have two parameters. Both dependencies need to be in the `providers` array of the Module.
</details>
<details>
<summary>Solution</summary>

```typescript
import { Injectable, Module } from '@nestjs/common';

@Injectable()
export class DataFetchService {
  getData() { return { sales: 100 }; }
}

@Injectable()
export class PdfFormatService {
  format(data: any) { return Buffer.from(JSON.stringify(data)); }
}

@Injectable()
export class ReportService {
  constructor(
    private readonly dataFetcher: DataFetchService,
    private readonly formatter: PdfFormatService
  ) {}

  generate() {
    const data = this.dataFetcher.getData();
    return this.formatter.format(data);
  }
}

@Module({
  providers: [DataFetchService, PdfFormatService, ReportService]
})
export class ReportModule {}
```
</details>

### Level 3 Boss Level
**Task:** Construct a `MultiProviderPaymentEngine` that takes a standard `PaymentProvider` interface. Use constructor DI to inject the specific provider (e.g., `PaypalGateway`) into the Engine based on standard NestJS DI mechanics.
<details>
<summary>Hint</summary>
Define an abstract class (which works as an interface that also generates a JS token) and bind it in the module using `provide` and `useClass`.
</details>
<details>
<summary>Solution</summary>

```typescript
import { Injectable, Module, Controller, Post } from '@nestjs/common';

// 1. Abstract class acts as both an Interface and an Injection Token
export abstract class PaymentGateway {
  abstract process(amount: number): boolean;
}

// 2. Concrete Implementation
@Injectable()
export class PaypalGateway extends PaymentGateway {
  process(amount: number): boolean {
    console.log(`Processing ${amount} through PayPal`);
    return true;
  }
}

// 3. Engine relies on Abstraction
@Injectable()
export class MultiProviderPaymentEngine {
  constructor(private readonly gateway: PaymentGateway) {}

  checkout(cartTotal: number) {
    return this.gateway.process(cartTotal);
  }
}

@Controller('checkout')
export class CheckoutController {
  constructor(private readonly engine: MultiProviderPaymentEngine) {}

  @Post()
  run() { return this.engine.checkout(50); }
}

// 4. Wiring: Bind Token to Concrete Class
@Module({
  controllers: [CheckoutController],
  providers: [
    MultiProviderPaymentEngine,
    {
      provide: PaymentGateway,
      useClass: PaypalGateway, // Can swap with StripeGateway easily!
    }
  ]
})
export class PaymentEngineModule {}
```
</details>
