# 1.2 Writing a Clean Dockerfile

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
**The Scenario:** You've built an Express.js API. You tell a new developer, "Just clone the repo, run `npm install`, and then `npm start`." They do it, and it crashes because they are on an old version of Node, and they don't have the global `nodemon` package installed that your script relies on. You spend 3 hours debugging their environment.

**The Pain:** Manually configuring environments is error-prone, undocumented, and doesn't scale. You need a way to script the *exact* steps required to build and run your application, completely independent of the host machine.

### 2. Plain English Metaphor (The What)
Think of a **Dockerfile** as a recipe for a very specific cake.
The base image (e.g., `node:18`) is the flour and eggs.
The instructions (e.g., `COPY`, `RUN npm install`) are the steps to mix in your specific ingredients (your code).
When Docker reads this recipe, it bakes a cake (the Docker Image). Once baked, you can't change the ingredients, but you can slice it up and serve it (run Containers from it) anywhere, and it will always taste exactly the same.

### 3. Complete Runnable Code
Here is a production-ready Dockerfile for a Node.js Express application.

```dockerfile
# 1. Start from a lightweight base image
FROM node:18-alpine

# 2. Set the working directory inside the container
WORKDIR /app

# 3. Copy ONLY package.json and package-lock.json first
COPY package*.json ./

# 4. Install dependencies
RUN npm ci

# 5. Copy the rest of the application code
COPY . .

# 6. Document the port the app listens on
EXPOSE 3000

# 7. Define the command to start the app
CMD ["node", "server.js"]
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: The Base Image (`FROM`)**
Every Dockerfile must start with `FROM`. `node:18-alpine` pulls a tiny version of Linux (Alpine) that already has Node.js 18 installed. Alpine keeps our final image size under 150MB instead of 1GB+.

**Step 2: The Setup (`WORKDIR` & `COPY`)**
`WORKDIR /app` creates a directory named `/app` inside the container and CD's into it.
We then `COPY package*.json ./` to bring our dependency definitions into the container *before* our source code.

**Step 3: The Cache Trick (`RUN` & `COPY`)**
Why do we copy `package.json`, run `npm ci` (clean install), and *then* copy the rest of our code (`COPY . .`)? **Layer Caching.** Docker caches each step. If you change a single line in `server.js`, Docker sees the code changed, but the `package.json` didn't. It will use the cached `npm ci` step, making your build take 1 second instead of 60 seconds!

**Step 4: The Execution (`EXPOSE` & `CMD`)**
`EXPOSE 3000` does *not* actually publish the port (we do that at runtime). It is purely documentation for other developers.
`CMD ["node", "server.js"]` is the default command that runs when a container is started from this image. Unlike `RUN` (which happens during the *build* phase), `CMD` happens during the *run* phase.

### 5. ASCII Data Flow

```text
Host Machine Code       Dockerfile Instructions         Docker Image Layers
+---------------+       +---------------------+       +-----------------------+
| server.js     |       | FROM node:18-alpine | --->  | Layer 1: OS + Node    |
| package.json  |       | WORKDIR /app        | --->  | Layer 2: Dir Setup    |
| node_modules/ |       | COPY package*.json  | --->  | Layer 3: Pkg files    |
+---------------+       | RUN npm ci          | --->  | Layer 4: Dependencies |
                        | COPY . .            | --->  | Layer 5: App Source   |
                        | CMD ["node"...]     | --->  | Metadata: Entrypoint  |
                        +---------------------+       +-----------------------+
```

### 6. Noob Trap vs Pro Tip
**Noob Trap:** Using `RUN apt-get update && apt-get install ...` on multiple different lines. Each `RUN` creates a new, immutable layer in the image. If you update the package list in layer 1, and install a package in layer 2, layer 2 might use a stale, cached version of layer 1! Always combine them: `RUN apt-get update && apt-get install -y <package>`.

**Pro Tip:** Always create a `.dockerignore` file (similar to `.gitignore`). If you don't ignore `node_modules`, `COPY . .` will copy your host machine's heavy, OS-specific `node_modules` folder into the Linux container, overwriting the clean ones you just installed with `npm ci`, and causing catastrophic crashes.

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**Objective:** Write a one-line `.dockerignore` file to prevent the scenario described in the Pro Tip above.

<details>
<summary><b>Click for Hint</b></summary>
It uses the exact same syntax as a `.gitignore` file.
</details>

<details>
<summary><b>Click for Solution Walkthrough</b></summary>

Create a file named `.dockerignore` in the same directory as your Dockerfile:
```text
node_modules
```
That's it. Now when `COPY . .` runs, the massive `node_modules` folder on your host machine will be ignored, keeping your image small and preventing cross-OS binary conflicts.
</details>

### Level 2: Real-World
**Objective:** You are given a simple Python script `app.py` that requires the `requests` library. Write a Dockerfile that uses python:3.9-slim, installs the requirements, and runs the script. Assume you have a `requirements.txt` file.

<details>
<summary><b>Click for Hint</b></summary>
Use the same caching trick we used for Node.js! Copy `requirements.txt` first, run `pip install -r requirements.txt`, then copy the rest of the code.
</details>

<details>
<summary><b>Click for Solution Walkthrough</b></summary>

```dockerfile
FROM python:3.9-slim

WORKDIR /app

# Copy requirements first for caching
COPY requirements.txt .

# Install dependencies
RUN pip install --no-cache-dir -r requirements.txt

# Copy the rest of the application code (e.g., app.py)
COPY . .

# Run the script
CMD ["python", "app.py"]
```
</details>

### Level 3: Boss Level
**Objective:** Build and run the image!
1. Create a `Dockerfile` for an Nginx web server.
2. The base image must be `nginx:alpine`.
3. Create an `index.html` file with the text "Hello Docker Boss!".
4. The Dockerfile must copy this `index.html` to the default Nginx html directory: `/usr/share/nginx/html`.
5. Build the image and tag it as `my-website`.

<details>
<summary><b>Click for Hint</b></summary>
To build an image, use the `docker build -t <tag-name> .` command. The `.` tells Docker to look for the Dockerfile in the current directory.
</details>

<details>
<summary><b>Click for Solution Walkthrough</b></summary>

**1. Create the files:**
```bash
echo "<h1>Hello Docker Boss!</h1>" > index.html
```

Create `Dockerfile`:
```dockerfile
FROM nginx:alpine
COPY index.html /usr/share/nginx/html/index.html
EXPOSE 80
```

**2. Build the image:**
```bash
docker build -t my-website .
```

*Note: Nginx images already have a CMD built-in to start the server, so we don't need to specify one in our Dockerfile!*
</details>
