# 2.1 Persistent Data: Volumes and Bind Mounts

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
**The Scenario:** You set up a pristine PostgreSQL database inside a Docker container. You spend an hour running migrations, seeding the database with dummy user data, and testing your application. You stop the container for the night. The next day, you start a new Postgres container from the same image, and the database is completely empty.

**The Pain:** Containers are **ephemeral** by design. When a container is deleted, its writable layer (where all new data is stored) is destroyed with it. If you run a database, upload user avatars, or generate log files inside a container without configuring storage, that data will vanish the moment the container goes away.

### 2. Plain English Metaphor (The What)
Imagine you rent a hotel room (the Container). You unpack your clothes into the dresser and write notes on the notepad on the desk. When you check out, housekeeping comes in, throws away your notes, empties the dresser, and resets the room to exactly how it was (the Base Image) for the next guest.

If you want to keep your stuff, you have two options:
1. **Named Volumes (A Storage Locker):** You rent a secure storage locker in the hotel basement managed by the hotel staff. When you return, you ask them to bring your locker up to your new room. (Best for databases in production).
2. **Bind Mounts (A USB Drive):** You bring your own USB drive from home and plug it into the hotel room's computer. The files stay on your personal drive. (Best for live-reloading code during development).

### 3. Complete Runnable Code
Let's run a persistent PostgreSQL database using a Docker Named Volume.

```bash
# 1. Create a Named Volume (the storage locker)
docker volume create pg_data

# 2. Run the database container, attaching the volume to the container's internal data directory
docker run -d \
  --name persistent-db \
  -e POSTGRES_PASSWORD=secret \
  -v pg_data:/var/lib/postgresql/data \
  postgres:15-alpine

# (You can now write data to this DB. If you delete the container and start a new one
# with the exact same -v command, your data will still be there!)
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: Container Ephemerality**
By default, Docker uses a "Union File System." The image layers are read-only. When a container starts, Docker slaps a thin read/write layer on top. Everything the container writes goes here. When the container dies, this layer dies.

**Step 2: `-v` Syntax (Volume Mapping)**
The syntax is `-v <SOURCE>:<TARGET>`.
- `<TARGET>` is always the absolute path *inside* the container where the app expects to read/write data (for Postgres, this is `/var/lib/postgresql/data`).
- `<SOURCE>` can be one of two things...

**Step 3: Named Volumes vs Bind Mounts**
- **Named Volume:** If `<SOURCE>` is just a name (like `pg_data`), Docker creates and manages a folder on your host machine in a hidden, protected Docker directory. You don't interact with these files directly. This is the safest way to persist database data.
- **Bind Mount:** If `<SOURCE>` is an absolute path on your host (like `/Users/jules/my-code`), Docker directly maps that exact folder into the container. When you hit `CTRL+S` in VS Code on your host, the container sees the file change instantly.

### 5. ASCII Data Flow

```text
Host Machine File System                             Docker Container
+------------------------------------+             +----------------------------------+
|                                    |             |                                  |
|   /var/lib/docker/volumes/pg_data  | <=========> |   /var/lib/postgresql/data       |
|   (Named Volume managed by Docker) |             |   (Postgres writes data here)    |
|                                    |             |                                  |
+------------------------------------+             +----------------------------------+
                                                             |
+------------------------------------+                       |
|                                    |                       |
|   /home/user/my-node-app/src       | <=========>           |  /app/src                |
|   (Bind Mount: Your actual code)   |             |   (Node.js reads code from here) |
|                                    |             |                                  |
+------------------------------------+             +----------------------------------+
```

### 6. Noob Trap vs Pro Tip
**Noob Trap:** Using Bind Mounts for database data on Windows/Mac. If you try to map Postgres data to a local folder like `-v $(pwd)/db_data:/var/lib/postgresql/data`, file permission errors and massive performance degradation will ruin your day, because Docker Desktop has to translate file lock signals across the VM boundary. Always use Named Volumes for databases.

**Pro Tip:** Use Bind Mounts heavily in development to achieve "Live Reload" without rebuilding your image. Map your local `./src` directory to the container's `/app/src` directory, and run `nodemon` or `webpack-dev-server` inside the container!

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**Objective:** Create a named volume called `web_logs`. Run an Nginx container and map this volume to `/var/log/nginx` inside the container.

<details>
<summary><b>Click for Hint</b></summary>
Use `docker volume create`, then `docker run` with the `-v` flag using the `source:target` syntax.
</details>

<details>
<summary><b>Click for Solution Walkthrough</b></summary>

```bash
# 1. Create the volume
docker volume create web_logs

# 2. Run Nginx, attaching the volume
docker run -d --name nginx-logger -v web_logs:/var/log/nginx nginx:alpine
```
Now, even if `nginx-logger` is deleted, the access and error logs are safely stored in the `web_logs` volume!
</details>

### Level 2: Real-World
**Objective:** You are developing a Node.js app. You have an `index.js` file in your current directory. Use a **Bind Mount** to map your current working directory (`$(pwd)` on Linux/Mac, or `${PWD}` on Windows PowerShell) to `/app` inside a `node:18` container, and run `node index.js`.

<details>
<summary><b>Click for Hint</b></summary>
The source path for a bind mount must be absolute. Using `$(pwd)` automatically injects your current absolute path.
</details>

<details>
<summary><b>Click for Solution Walkthrough</b></summary>

```bash
# 1. Create a quick script
echo "console.log('Running from a Bind Mount!');" > index.js

# 2. Run the container with a Bind Mount
docker run --rm -v $(pwd):/app -w /app node:18 node index.js
```
*Note: We used `-w /app` to set the Working Directory for the command, so `node index.js` looks in `/app` instead of the root folder.*
</details>

### Level 3: Boss Level
**Objective:** Prove that Named Volumes persist data.
1. Run a Postgres container with a named volume `my_pg_data` mapped to `/var/lib/postgresql/data`. Set the password to `admin`.
2. Connect to the container and create a table with one row of data.
3. Completely stop and `docker rm` the container.
4. Start a brand new Postgres container using the *same* volume.
5. Connect to the new container and prove the data is still there.

<details>
<summary><b>Click for Hint</b></summary>
To run a command inside a running database container, use `docker exec -it <container_name> psql -U postgres`.
</details>

<details>
<summary><b>Click for Solution Walkthrough</b></summary>

**1. Start the first container:**
```bash
docker run -d --name db1 -e POSTGRES_PASSWORD=admin -v my_pg_data:/var/lib/postgresql/data postgres:15-alpine

# Wait a few seconds for Postgres to boot up...
```

**2. Add data:**
```bash
# Execute psql inside the container
docker exec -it db1 psql -U postgres -c "CREATE TABLE users (name VARCHAR(50)); INSERT INTO users VALUES ('Jules');"
```

**3. Destroy the container:**
```bash
docker stop db1
docker rm db1
# The container is gone, but the volume my_pg_data remains!
```

**4. Start a new container with the same volume:**
```bash
docker run -d --name db2 -e POSTGRES_PASSWORD=admin -v my_pg_data:/var/lib/postgresql/data postgres:15-alpine
```

**5. Verify the data survived:**
```bash
docker exec -it db2 psql -U postgres -c "SELECT * FROM users;"
# Output:
#  name
# -------
#  Jules
```
</details>
