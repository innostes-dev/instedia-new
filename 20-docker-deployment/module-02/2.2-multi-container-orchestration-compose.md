# 2.2 Multi-Container Orchestration with Docker Compose

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
**The Scenario:** You are building a modern web application. It requires a React frontend, a FastAPI backend, a PostgreSQL database, and a Redis cache. To start your development environment, you have to open 4 terminal windows and run 4 massive, hard-to-remember `docker run` commands with dozens of `-p`, `-v`, and `-e` flags, making sure to start them in the exact right order.

**The Pain:** Managing multiple containers using raw Docker CLI commands is tedious, unscalable, and impossible to share cleanly with teammates. Furthermore, containers started with separate `docker run` commands cannot easily talk to each other without manually creating complex Docker Networks.

### 2. Plain English Metaphor (The What)
If a `Dockerfile` is a recipe to bake a single cake (an Image)...
A `docker-compose.yml` file is the **Manager of a Restaurant**.

The Manager knows exactly what needs to happen to open the restaurant for the day. They know the Database Chef needs to arrive before the Backend Chef (`depends_on`). They know exactly which ingredients to hand to which Chef (Environment Variables). They ensure all the Chefs are in the same Kitchen so they can yell to each other (Docker Network). Instead of you running around screaming 20 different instructions, you just look at the Manager and say, `"Compose, bring it up."` (`docker-compose up`).

### 3. Complete Runnable Code
Here is a complete `docker-compose.yml` for a 3-tier architecture (Database, Backend, Frontend).

```yaml
version: '3.8'

services:
  # 1. The Database
  db:
    image: postgres:15-alpine
    environment:
      POSTGRES_USER: admin
      POSTGRES_PASSWORD: secretpassword
    volumes:
      - pg_data:/var/lib/postgresql/data
    ports:
      - "5432:5432"

  # 2. The Backend API
  api:
    image: my-fastapi-backend:latest
    build: ./backend # Tells compose to build the Dockerfile in the ./backend folder
    ports:
      - "8000:8000"
    environment:
      DATABASE_URL: postgresql://admin:secretpassword@db:5432/postgres
    depends_on:
      - db # Wait for the db service to start before starting the api

  # 3. The Frontend Web App
  web:
    image: my-nextjs-frontend:latest
    build: ./frontend
    ports:
      - "3000:3000"
    environment:
      NEXT_PUBLIC_API_URL: http://localhost:8000
    depends_on:
      - api

# 4. Declare the Volumes
volumes:
  pg_data:
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: Services and Images**
Under the `services` block, we define our containers. We named them `db`, `api`, and `web`. For `db`, we use a pre-built image from Docker Hub. For `api` and `web`, we use the `build: ./path` directive, telling Compose: "Look in this folder for a Dockerfile, build it, and tag it with the `image` name."

**Step 2: Service Discovery (The Magic of Compose Networks)**
Notice the `DATABASE_URL` in the `api` service: `postgresql://.../postgres@db:5432/...`
Notice the hostname is just `db`! When you run `docker-compose up`, Docker automatically creates a custom Network and attaches all these containers to it. It also sets up internal DNS. The `api` container can literally just ping `db` or `web`, and Docker automatically routes the traffic to the correct container's internal IP address. No IP hardcoding required!

**Step 3: `depends_on` and `volumes`**
`depends_on: - db` ensures Docker starts the database container before it attempts to start the API container.
At the very bottom, we must explicitly declare any Named Volumes (like `pg_data`) that our services use in the top-level `volumes:` block.

### 5. ASCII Data Flow

```text
                     Docker Compose Custom Network
+-------------------------------------------------------------------------+
|                                                                         |
|  +----------------+        +----------------+        +---------------+  |
|  | Web (Frontend) |        | API (Backend)  |        | DB (Postgres) |  |
|  | Hostname: web  | <----> | Hostname: api  | <----> | Hostname: db  |  |
|  +-------+--------+        +-------+--------+        +-------+-------+  |
|          |                         |                         |          |
+----------|-------------------------|-------------------------|----------+
           |                         |                         |
      Port 3000                 Port 8000                 Port 5432
           |                         |                         |
+----------v-------------------------v-------------------------v----------+
|                            Host Machine (Your Laptop)                   |
+-------------------------------------------------------------------------+
```

### 6. Noob Trap vs Pro Tip
**Noob Trap:** Assuming `depends_on: - db` waits for the database to be *ready to accept connections*. It doesn't! It only waits for the container process to *start*. Postgres takes a few seconds to boot up. If your API immediately crashes because the DB isn't ready, you need a retry mechanism in your application code, or you need to use `depends_on` with `condition: service_healthy` and define healthchecks.

**Pro Tip:** Use `docker-compose down -v` to completely destroy the stack **and** delete all associated Named Volumes. This is the fastest way to "factory reset" your entire local development environment if your database gets corrupted.

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**Objective:** Write a `docker-compose.yml` that starts two services: a `redis` container (using image `redis:alpine`) and an `nginx` container (using `nginx:alpine`). Map the nginx port to 8080 on the host.

<details>
<summary><b>Click for Hint</b></summary>
Define `version: '3.8'`, `services:`, and then define your two services under it. Only the nginx service needs a `ports:` array.
</details>

<details>
<summary><b>Click for Solution Walkthrough</b></summary>

Create a `docker-compose.yml` file:
```yaml
version: '3.8'
services:
  cache:
    image: redis:alpine

  web:
    image: nginx:alpine
    ports:
      - "8080:80"
```
Run it with `docker-compose up -d`.
</details>

### Level 2: Real-World

### Level 3: Boss Level
**Objective:** Prove Internal Service Discovery works.
1. Create a compose file with two services.
2. Service 1: `cache` using `redis:alpine`.
3. Service 2: `app` using `node:18-alpine`. Set its `command` to `sleep 10000` so it stays alive.
4. Bring the stack up.
5. Use `docker exec` to open a shell inside the `app` container.
6. Install the `ping` utility (Alpine uses `apk add --no-cache iputils`).
7. Ping the `cache` container by its hostname!

<details>
<summary><b>Click for Hint</b></summary>
You don't need to expose any ports to the host machine for containers to talk to each other internally.
</details>

<details>
<summary><b>Click for Solution Walkthrough</b></summary>

**1 & 2 & 3. Create `docker-compose.yml`:**
```yaml
version: '3.8'
services:
  cache:
    image: redis:alpine

  app:
    image: node:18-alpine
    command: sleep 10000
```

**4. Bring it up:**
```bash
docker-compose up -d
```

**5 & 6. Exec and Install Ping:**
```bash
# Assuming the folder is named 'my-project', compose prepends it to the container name
docker exec -it my-project-app-1 sh
apk add --no-cache iputils
```

**7. Ping the cache by hostname:**
```bash
ping cache
# Output:
# PING cache (172.20.0.2) 56(84) bytes of data.
# 64 bytes from my-project-cache-1.my-project_default (172.20.0.2): icmp_seq=1 ttl=64 time=0.123 ms
```
*Notice how Docker automatically resolved the hostname `cache` to the internal IP `172.20.0.2`!*
</details>
