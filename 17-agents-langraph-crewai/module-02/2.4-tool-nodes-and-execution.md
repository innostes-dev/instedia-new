# 2.4 Tool Nodes and Execution

## Phase A: Core Concept

### 1. Real-World Pain Point (The Why)
In Module 1, we used `initialize_agent` and let LangChain handle tool execution implicitly. In LangGraph, *you* control the graph. If an LLM decides it wants to use a tool, it outputs a "Tool Call" request. If you don't have a node specifically designed to execute that tool and return the observation, the agent crashes. Manually writing a node to parse the tool call, run the python function, and format the result is tedious. We need a standardized way to execute tools within a graph.

### 2. Plain English Metaphor (The What)
Think of the LLM as a Manager and the `ToolNode` as the Intern.
1. The Manager (LLM Node) writes a sticky note: "Hey, look up the weather in Chicago." (This is a `tool_call`).
2. The sticky note goes to the Intern (`ToolNode`).
3. The Intern actually opens the weather app, types in Chicago, gets the result, writes "It's raining" on a new sticky note (the `tool_message`), and hands it back to the Manager.

### 3. Complete Runnable Code

```python
import os
from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode, tools_condition
from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage
from langchain.tools import tool

os.environ["OPENAI_API_KEY"] = "your-api-key"

# 1. Define the Tool
@tool
def get_weather(location: str) -> str:
    """Gets the weather for a location."""
    if location.lower() == "chicago":
        return "Raining and 50F."
    return "Sunny and 75F."

tools = [get_weather]

# 2. Bind tools to the LLM (Tells LLM the tools exist)
llm = ChatOpenAI(model="gpt-3.5-turbo").bind_tools(tools)

# 3. State
class AgentState(TypedDict):
    messages: Annotated[list, add_messages]

# 4. Nodes
def agent_node(state: AgentState):
    """The LLM decides whether to respond or call a tool."""
    response = llm.invoke(state["messages"])
    return {"messages": [response]}

# 5. Build Graph
builder = StateGraph(AgentState)

builder.add_node("agent", agent_node)
# ToolNode automatically handles parsing and executing the tools!
builder.add_node("tools", ToolNode(tools))

builder.set_entry_point("agent")

# tools_condition is a built-in router.
# If LLM outputs a tool call -> goes to "tools"
# If LLM outputs a normal text response -> goes to END
builder.add_conditional_edges("agent", tools_condition)

# After tools run, ALWAYS go back to the agent to interpret the result
builder.add_edge("tools", "agent")

app = builder.compile()

if __name__ == "__main__":
    result = app.invoke({"messages": [HumanMessage(content="What's the weather in Chicago?")]})

    print("--- Conversation Log ---")
    for msg in result["messages"]:
        msg_type = type(msg).__name__
        print(f"[{msg_type}]: {msg.content or 'Tool Call Requested'}")
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: `.bind_tools(tools)`**
Before the LLM can use tools, it needs to know they exist. `bind_tools` converts your Python functions into JSON schema and passes them to the OpenAI API so the model knows what arguments are required.

**Step 2: `ToolNode(tools)`**
This is a pre-built node from LangGraph. When the state enters this node, `ToolNode` looks at the last message in `state["messages"]`. If it's an `AIMessage` containing a `tool_calls` list, it automatically extracts the arguments, runs your Python function (`get_weather`), creates a `ToolMessage` with the result, and appends it to the state.

**Step 3: `tools_condition` (The Built-in Router)**
You don't have to write the routing logic! `tools_condition` looks at the last message. Does it have `tool_calls`? Yes -> route to the `"tools"` node. No -> route to `END`.

### 5. ASCII Data Flow

```text
       User: "Weather in Chicago?"
                   │
                   ▼
         ┌───────────────────┐
         │   NODE: agent     │
         └───────────────────┘
                   │ LLM output: tool_call(get_weather("Chicago"))
                   ▼
     [ ROUTER: tools_condition ]──(If no tools)──► END
                   │
           (If tool_calls exist)
                   │
                   ▼
         ┌───────────────────┐
         │   NODE: tools     │ Executes function.
         └───────────────────┘ Returns ToolMessage: "Raining"
                   │
                   └─────────────────┐
                                     │ loops back
                                     ▼
                             ┌───────────────┐
                             │  NODE: agent  │ Reads ToolMessage.
                             └───────────────┘ Formats final answer.
                                     │
                                     ▼
                          [ ROUTER: tools_condition ]
                                     │ (No tool calls)
                                     ▼
                                    END
```

### 6. Noob Trap vs Pro Tip
**Noob Trap:** Forgetting `bind_tools`. If you create a `ToolNode` but don't bind the tools to the LLM, the LLM won't know the tools exist, will never output a `tool_call`, and the `ToolNode` will never execute.
**Pro Tip:** Tool Execution Exceptions. If your Python tool throws an error (e.g. division by zero), `ToolNode` will crash the graph. You can wrap your tools in try/except blocks and return the error message as a string. The LLM will read the error and can try again!

from langgraph.graph import StateGraph

llm = ChatOpenAI(temperature=0).bind_tools(tools)

```python
from langchain.tools import tool
# The rest of the setup is identical to Level 1.
@tool
def fetch_user(user_id: int) -> str:
    """Fetches user data."""
    try:
        raise ValueError("Database timeout")
    except Exception as e:
        return f"Error: {e}"

# If you run the graph asking to fetch a user, the LLM will receive the Error string
# and format a polite response like "I'm sorry, I couldn't fetch the user due to a database timeout."
```

### Level 3 Boss Level (Cumulative)
**Task:** GitHub Issue Manager Agent.
Tool 1: `search_issues(keyword)` -> Returns list of issue IDs.
Tool 2: `close_issue(issue_id)` -> Closes the issue.
User Prompt: "Find issues about 'login bug' and close them."
The agent must use Tool 1, read the observation, and then use Tool 2.
<details>
<summary>Hint</summary>
The beauty of LangGraph's loop (`agent` -> `tools_condition` -> `tools` -> `agent`) is that it naturally handles sequential tool calls. Just define both tools, bind them, and pass the prompt. The LLM will loop twice!
</details>

<details>
<summary>Solution</summary>
```python
from langgraph.graph import StateGraph
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode, tools_condition
from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage
from langchain.tools import tool
from typing import TypedDict, Annotated

@tool
def search_issues(keyword: str) -> str:
    """Finds issue IDs for a keyword."""
    return "Found issue #404"

@tool
def close_issue(issue_id: str) -> str:
    """Closes a specific issue by ID."""
    return f"Issue {issue_id} closed."

tools = [search_issues, close_issue]
llm = ChatOpenAI(temperature=0).bind_tools(tools)

class S(TypedDict): messages: Annotated[list, add_messages]
def agent(state): return {"messages": [llm.invoke(state["messages"])]}

b = StateGraph(S)
b.add_node("agent", agent)
b.add_node("tools", ToolNode(tools))
b.set_entry_point("agent")
b.add_conditional_edges("agent", tools_condition)
b.add_edge("tools", "agent")
app = b.compile()

res = app.invoke({"messages": [HumanMessage(content="Find issues about 'login bug' and close them.")]})
for m in res["messages"]:
    print(m.content or m.additional_kwargs)
```
</details>
