# 2.1 HashMap Internals: Hash Buckets & Treeification

## Phase A: Understanding the Mechanics

### 1. Real-World Pain Point (The Why)
Your high-frequency trading platform caches account balances in memory using a `HashMap<String, Account>`. Everything is lightning fast (O(1) lookups) until a malicious user registers thousands of accounts with strategically chosen account IDs. Suddenly, your O(1) lookups degrade into O(N) linear searches, your CPU pegs at 100%, and the trading engine grinds to a halt. You are the victim of a Hash Collision Denial of Service (DoS) attack. You need to understand exactly how `HashMap` routes data internally, what the `equals()` and `hashCode()` contract really means, and how Java 8+ defends against this attack using Red-Black Trees.

### 2. Plain English Metaphor (The What)
Imagine a massive post office with an infinite number of mailboxes (Buckets).
- **hashCode()** is the zip code on the envelope. It tells the postal worker *exactly* which mailbox to drop the letter into.
- **equals()** is checking the exact name on the envelope once you look inside that specific mailbox, to make sure you hand it to the right person.
- A **Hash Collision** happens when 50 people all live in the same zip code. The postal worker dumps 50 letters into one mailbox. Now, when finding your letter, you have to dig through a linked list of 50 envelopes one by one.
- **Treeification** (Java 8+) is an automated upgrade. If a mailbox gets stuffed with more than 8 letters, the post office replaces that messy pile with a highly organized filing cabinet (a Red-Black Tree), dropping the search time from O(N) to O(log N).

### 3. Complete Runnable Code
Here is a complete, runnable example demonstrating the `equals`/`hashCode` contract, hash collisions, and how `HashMap` structure adapts.

```java
import java.util.HashMap;
import java.util.Map;
import java.util.Objects;

public class HashMapInternalsDemo {

    // A poorly designed key that causes intentional Hash Collisions
    static class BadKey {
        private final String accountId;

        public BadKey(String accountId) {
            this.accountId = accountId;
        }

        @Override
        public boolean equals(Object o) {
            if (this == o) return true;
            if (o == null || getClass() != o.getClass()) return false;
            BadKey badKey = (BadKey) o;
            return Objects.equals(accountId, badKey.accountId);
        }

        @Override
        public int hashCode() {
            // DISASTER: Forces every single key into the exact same bucket!
            return 42;
        }
    }

    // A properly designed key that distributes evenly
    static class GoodKey implements Comparable<GoodKey> {
        private final String accountId;

        public GoodKey(String accountId) {
            this.accountId = accountId;
        }

        @Override
        public boolean equals(Object o) {
            if (this == o) return true;
            if (o == null || getClass() != o.getClass()) return false;
            GoodKey goodKey = (GoodKey) o;
            return Objects.equals(accountId, goodKey.accountId);
        }

        @Override
        public int hashCode() {
            // Distributes keys across many different buckets
            return Objects.hash(accountId);
        }

        // REQUIRED for Java 8 Treeification to work efficiently!
        @Override
        public int compareTo(GoodKey other) {
            return this.accountId.compareTo(other.accountId);
        }
    }

    public static void main(String[] args) {
        System.out.println("Starting HashMap internals simulation...");

        // 1. The Collision Disaster (Linked List degradation)
        Map<BadKey, String> badMap = new HashMap<>();
        long start = System.nanoTime();
        for (int i = 0; i < 20_000; i++) {
            badMap.put(new BadKey("ACC-" + i), "Balance-" + i);
        }
        long badTime = System.nanoTime() - start;
        System.out.println("Time to insert 20,000 BadKeys (Collisions): " + (badTime / 1_000_000) + "ms");

        // 2. The Proper Distribution (O(1) performance)
        Map<GoodKey, String> goodMap = new HashMap<>();
        start = System.nanoTime();
        for (int i = 0; i < 20_000; i++) {
            goodMap.put(new GoodKey("ACC-" + i), "Balance-" + i);
        }
        long goodTime = System.nanoTime() - start;
        System.out.println("Time to insert 20,000 GoodKeys (Distributed): " + (goodTime / 1_000_000) + "ms");

        System.out.println("Performance Difference: GoodKey was " + (badTime / goodTime) + "x faster.");
    }
}
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: The Bucket Routing (`hashCode`)**
```java
public int hashCode() { return Objects.hash(accountId); }
```
*Rationale:* When you call `map.put(key, value)`, `HashMap` first calls `key.hashCode()`. It then runs this integer through a bitwise math operation (`(n - 1) & hash`) to figure out which slot in its internal array (the Bucket array) this entry belongs in. A good `hashCode()` returns wildly different numbers for different keys, spreading data evenly across the array.

**Step 2: Resolving Collisions (`equals`)**
```java
public boolean equals(Object o) { ... }
```
*Rationale:* What happens if two different keys result in the same bucket? `HashMap` stores them in a Linked List in that bucket. When you call `map.get(key)`, it finds the bucket, then iterates through the Linked List, calling `equals()` on each item until it finds the exact match. This is why if you override `equals()`, you MUST override `hashCode()`. If two objects are equal, they MUST go into the same bucket.

**Step 3: Treeification (The Java 8 Savior)**
```java
static class GoodKey implements Comparable<GoodKey> { ... }
```
*Rationale:* If a malicious attacker sends data that intentionally collides in the same bucket (e.g., thousands of items in one Linked List), lookups degrade from O(1) to O(N). To prevent this, Java 8 introduced Treeification. If a single bucket hits 8 items (`TREEIFY_THRESHOLD`), the JVM transforms that Linked List into a Red-Black Tree. However, to build a tree, the objects must be ordered. Therefore, for Treeification to work properly, your Key class *should* implement `Comparable`.

### 6. Noob Trap vs Pro Tip
- **Noob Trap:** Using a mutable object as a `HashMap` key. If you put an object in a map, and then later change a field that alters its `hashCode()`, the map will be completely broken. It will look for the object in the *new* bucket, but the object is permanently lost in the *old* bucket. Always use immutable classes (like Records or Strings) for Keys.
- **Pro Tip:** Set the initial capacity! A `HashMap` has a Load Factor (default 0.75). When the map is 75% full, it creates a brand new array double the size and re-hashes *every single item*. If you know you are inserting 10,000 items, initialize it via `new HashMap<>(13334)` (10000 / 0.75) to prevent expensive array resizing operations entirely.

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**The Challenge:** You have a `HashMap<User, String>`. Explain why the following code prints `null` instead of "Admin", and fix the `User` class so it works correctly.
```java
class User {
    String name;
    User(String name) { this.name = name; }
}

Map<User, String> map = new HashMap<>();
map.put(new User("Alice"), "Admin");
System.out.println(map.get(new User("Alice"))); // Prints: null
```
<details>
<summary><b>Hint</b></summary>
If you don't override `hashCode()` and `equals()`, Java uses object memory addresses. The second `new User("Alice")` has a different memory address, so it looks in the wrong bucket.
</details>
<details>
<summary><b>Solution Walkthrough</b></summary>
You must override `equals` and `hashCode`. The modern and safest way to do this is to simply use a Record, which implements them automatically based on the fields.

```java
record User(String name) {}

Map<User, String> map = new HashMap<>();
map.put(new User("Alice"), "Admin");
System.out.println(map.get(new User("Alice"))); // Now prints: Admin
```
</details>

### Level 2: Real-World
**The Challenge:** Build a `HighFrequencyAccountCache`. We need to avoid resizing delays. We expect exactly 1,000,000 accounts to be cached. Initialize the `HashMap` correctly so that it never undergoes a resize operation, and write a Key class that guarantees it will safely treeify if a collision attack occurs.
<details>
<summary><b>Hint</b></summary>
Capacity = Expected Elements / Load Factor (0.75). To allow treeification, the Key must implement `Comparable`.
</details>
<details>
<summary><b>Solution Walkthrough</b></summary>

```java
import java.util.HashMap;
import java.util.Map;

public class HighFrequencyAccountCache {

    // Key MUST be immutable and implement Comparable for Red-Black tree fallback
    public record AccountKey(String accountId) implements Comparable<AccountKey> {
        @Override
        public int compareTo(AccountKey other) {
            return this.accountId.compareTo(other.accountId);
        }
    }

    private final Map<AccountKey, String> cache;

    public HighFrequencyAccountCache() {
        // Expected: 1,000,000. Load Factor: 0.75.
        // 1,000,000 / 0.75 = 1,333,333.33 (Round up)
        int initialCapacity = 1_333_334;

        // This map will store 1 million items without ever resizing or rehashing
        this.cache = new HashMap<>(initialCapacity);
    }
}
```
</details>

### Level 3: Boss Level
**The Challenge:** The "Mutable Key Disaster". Write an application that demonstrates a memory leak caused entirely by mutating a key after it has been placed in a `HashSet` (which is backed by a `HashMap`). You must insert an object, mutate it, and prove that `contains()` returns false, yet the object is permanently stuck in the set.
<details>
<summary><b>Hint</b></summary>
Create a class with a mutable field. Insert it. Change the field. The `hashCode` will change. When you ask the set to remove it, it will look in the wrong bucket, fail to find it, and leave it there forever.
</details>
<details>
<summary><b>Solution Walkthrough</b></summary>

```java
import java.util.HashSet;
import java.util.Objects;
import java.util.Set;

public class MutableKeyDisaster {

    static class MutableKey {
        int id;

        MutableKey(int id) { this.id = id; }

        @Override
        public boolean equals(Object o) {
            if (this == o) return true;
            if (o == null || getClass() != o.getClass()) return false;
            MutableKey that = (MutableKey) o;
            return id == that.id;
        }

        @Override
        public int hashCode() {
            return Objects.hash(id);
        }
    }

    public static void main(String[] args) {
        Set<MutableKey> leakedSet = new HashSet<>();

        MutableKey key1 = new MutableKey(1);

        // Step 1: Insert into the Set (goes into Bucket A)
        leakedSet.add(key1);
        System.out.println("Set size: " + leakedSet.size()); // 1
        System.out.println("Contains key1? " + leakedSet.contains(key1)); // true

        // Step 2: Mutate the Key (Disaster strikes)
        key1.id = 999;

        // Step 3: Prove the leak
        // The HashSet recalculates hash(999), looks in Bucket B, and finds nothing.
        System.out.println("Contains key1 after mutation? " + leakedSet.contains(key1)); // FALSE

        // We try to remove it...
        leakedSet.remove(key1); // Fails to find it in Bucket B

        // The object is permanently stuck in Bucket A! Memory leak!
        System.out.println("Set size after remove attempt: " + leakedSet.size()); // STILL 1!
    }
}
```
This is why modern Java heavily promotes `record` types—they physically prevent this exact class of enterprise memory leak.
</details>
