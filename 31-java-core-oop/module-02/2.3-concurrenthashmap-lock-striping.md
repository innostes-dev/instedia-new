# 2.3 ConcurrentHashMap: Lock Striping & CAS

## Phase A: Understanding the Mechanics

### 1. Real-World Pain Point (The Why)
You are building an in-memory Session Store for a multi-tenant web application. Because multiple threads are handling HTTP requests, you know a standard `HashMap` isn't thread-safe (it can enter an infinite loop during resizing). You wrap it with `Collections.synchronizedMap()`. Suddenly, your throughput plummets. Under high load, Thread 1 updating User A's session blocks Thread 2 from updating User B's session. You have created a massive bottleneck because the entire Map is locked for every single operation. You need a way to allow thousands of concurrent reads and writes without locking the whole data structure.

### 2. Plain English Metaphor (The What)
- **SynchronizedMap / Hashtable:** Imagine a giant warehouse with thousands of storage bins, but there is only ONE door and ONE padlock. If Alice goes in to get something from bin 1, she locks the entire warehouse. Bob, who just wants something from bin 9000, has to wait outside until Alice is done.
- **ConcurrentHashMap (Lock Striping - Java 7):** Instead of one door, the warehouse is divided into 16 independent sectors, each with its own door and padlock. Alice goes into Sector 1 and locks it. Bob goes into Sector 9, locks it, and does his work at the exact same time. Throughput goes up 16x.
- **ConcurrentHashMap (Node Locking & CAS - Java 8+):** The warehouse removes the doors entirely. Instead, there is a tiny padlock on *every single bin*. Furthermore, for simple actions (like tossing a box into an empty bin), workers don't even use locks—they use ninja-like speed (Compare-And-Swap) to slide the box in. If two workers aim for the exact same bin at the exact same millisecond, only then does one lock that specific bin.

### 3. Complete Runnable Code
Here is a complete, runnable example demonstrating the bottleneck of `synchronizedMap` versus the massive throughput of `ConcurrentHashMap`.

```java
import java.util.Collections;
import java.util.HashMap;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class ConcurrentMapPerformance {

    public static void main(String[] args) throws InterruptedException {
        int threads = 10;
        int operations = 100_000;

        System.out.println("--- 1. Testing SynchronizedMap (Global Lock) ---");
        Map<String, Integer> syncMap = Collections.synchronizedMap(new HashMap<>());
        long syncTime = testMapPerformance(syncMap, threads, operations);
        System.out.println("SynchronizedMap Time: " + syncTime + "ms\n");

        System.out.println("--- 2. Testing ConcurrentHashMap (Node Locking / CAS) ---");
        Map<String, Integer> concurrentMap = new ConcurrentHashMap<>();
        long concurrentTime = testMapPerformance(concurrentMap, threads, operations);
        System.out.println("ConcurrentHashMap Time: " + concurrentTime + "ms\n");

        System.out.println("Performance Difference: ConcurrentHashMap is roughly "
            + (syncTime / (concurrentTime == 0 ? 1 : concurrentTime)) + "x faster.");
    }

    private static long testMapPerformance(Map<String, Integer> map, int threadCount, int operationsPerThread)
            throws InterruptedException {

        ExecutorService pool = Executors.newFixedThreadPool(threadCount);
        CountDownLatch latch = new CountDownLatch(threadCount);
        long start = System.currentTimeMillis();

        for (int i = 0; i < threadCount; i++) {
            final int threadId = i;
            pool.submit(() -> {
                for (int j = 0; j < operationsPerThread; j++) {
                    // Simulating heavy concurrent writes across different keys
                    String key = "Key-" + threadId + "-" + j;
                    map.put(key, j);

                    // Simulating heavy concurrent reads
                    map.get(key);
                }
                latch.countDown();
            });
        }

        latch.await();
        long end = System.currentTimeMillis();
        pool.shutdown();

        return end - start;
    }
}
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: The Global Lock Bottleneck**
```java
Map<String, Integer> syncMap = Collections.synchronizedMap(new HashMap<>());
```
*Rationale:* When you use `synchronizedMap`, Java wraps every method (`put`, `get`, `size`) in a `synchronized(mutex)` block. This means Thread A calling `put` and Thread B calling `get` cannot happen at the same time, even if they are accessing completely different keys. It serializes all access, destroying the benefits of multi-core processors.

**Step 2: Compare-And-Swap (CAS) in Java 8+**
```java
Map<String, Integer> concurrentMap = new ConcurrentHashMap<>();
concurrentMap.put("Key-1", 100);
```
*Rationale:* In Java 8, `ConcurrentHashMap` was completely rewritten. When you `put` an item, the map hashes the key and finds the bucket (array index). If the bucket is *empty*, it doesn't use a lock. It uses an OS-level hardware instruction called Compare-And-Swap (CAS). It says to the CPU: "If this bucket is still empty, put my node here." This is lock-free and blisteringly fast.

**Step 3: Node-Level Locking (The `synchronized` node)**
*Rationale:* What if the bucket isn't empty (a hash collision)? The thread must add the item to the Linked List or Red-Black Tree in that specific bucket. It does this by synchronizing on the *first node* (the head) of that specific bucket.
```java
// Conceptual representation of ConcurrentHashMap internal put:
Node head = table[index];
synchronized(head) {
    // Append to linked list or tree
}
```
This means Thread A updating Bucket 5 and Thread B updating Bucket 12 run completely in parallel with zero contention.

### 5. ASCII / Architecture Data Flow

```text
+-------------------------------------------------------------+
|                ConcurrentHashMap Internal Array             |
+-------+-------+-------+-------+-------+-------+-------+-----+
| Bkt 0 | Bkt 1 | Bkt 2 | Bkt 3 | Bkt 4 | Bkt 5 | Bkt 6 | ... |
+-------+-------+-------+-------+-------+-------+-------+-----+
    |               |                       |
 [Node]          [Node] <--- LOCK X      [Node] <--- LOCK Y
                 (Thread 1               (Thread 2
                  updates list)           updates tree)

** Thread 3 writes to Bkt 4 (Empty): Uses CAS! No Locks! **
** Thread 4 reads from Bkt 2: Volatile read! No Locks! **
```

### 6. Noob Trap vs Pro Tip
- **Noob Trap:** Using `ConcurrentHashMap` for aggregate operations like `size()`. Because the map is constantly changing, by the time `size()` finishes counting, the answer is already wrong. `ConcurrentHashMap` guarantees thread-safety for *individual operations* (like `put` or `get`), but it does not guarantee atomic snapshots across the whole map unless you lock it externally (which defeats the purpose).
- **Pro Tip:** Use `computeIfAbsent` instead of `get` then `put`.
  *BAD:* `if (!map.containsKey("A")) map.put("A", 1);` (Thread unsafe, race condition).
  *GOOD:* `map.computeIfAbsent("A", key -> 1);` (Atomic, thread-safe, ensures the lambda runs exactly once).

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**The Challenge:** The following code tries to implement a thread-safe hit counter using a `ConcurrentHashMap`, but under high concurrency, it loses counts. Why? Fix it using the correct atomic method.
```java
ConcurrentHashMap<String, Integer> hits = new ConcurrentHashMap<>();

public void recordHit(String pageId) {
    Integer current = hits.get(pageId); // Race Condition!
    if (current == null) {
        hits.put(pageId, 1);
    } else {
        hits.put(pageId, current + 1); // Race Condition!
    }
}
```
<details>
<summary><b>Hint</b></summary>
The map itself is thread-safe, but your sequence of operations (Read, then Modify, then Write) is not atomic. Use `merge()` or `compute()`.
</details>
<details>
<summary><b>Solution Walkthrough</b></summary>

```java
ConcurrentHashMap<String, Integer> hits = new ConcurrentHashMap<>();

public void recordHit(String pageId) {
    // Atomic operation!
    // If "pageId" doesn't exist, puts 1.
    // If it exists, applies the lambda (oldVal + 1).
    hits.merge(pageId, 1, (oldVal, increment) -> oldVal + increment);
}
```
</details>

### Level 2: Real-World
**The Challenge:** Build a `ConcurrentSessionStore`. When a user requests their `UserSession`, check the map. If it doesn't exist, simulate a slow database call (e.g., `Thread.sleep(500)`) to load it. You must ensure that if 10 threads request the same user concurrently, the slow DB call only happens *once*, and the other 9 threads wait and receive the result of the first call.
<details>
<summary><b>Hint</b></summary>
`computeIfAbsent` guarantees that the mapping function (the lambda) is executed at most once per key.
</details>
<details>
<summary><b>Solution Walkthrough</b></summary>

```java
import java.util.concurrent.ConcurrentHashMap;

public class ConcurrentSessionStore {

    private final ConcurrentHashMap<String, String> store = new ConcurrentHashMap<>();

    public String getSession(String userId) {
        // computeIfAbsent is atomic. The first thread locks the bucket and runs the lambda.
        // Threads 2-10 will block until the lambda finishes, then receive the cached result.
        return store.computeIfAbsent(userId, this::loadFromDatabase);
    }

    private String loadFromDatabase(String userId) {
        System.out.println("Cache miss! Executing slow DB call for " + userId);
        try {
            Thread.sleep(500); // Simulate slow I/O
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
        return "SessionDataFor-" + userId;
    }
}
```
</details>

### Level 3: Boss Level
**The Challenge:** A multi-tenant Analytics Engine groups incoming metrics by `TenantId`. Each tenant has an `ArrayList` of metrics. You must build a `TenantMetricRouter` that concurrently receives metrics and adds them to the correct tenant's list safely. You cannot use `CopyOnWriteArrayList` (too slow for writes). You must use `ConcurrentHashMap` combined with targeted synchronization.
<details>
<summary><b>Hint</b></summary>
The Map should store `TenantId` -> `ArrayList`. Use `computeIfAbsent` to safely initialize the list if it's the first metric. Then, `synchronized` on the specific `ArrayList` instance to safely append to it without locking other tenants.
</details>
<details>
<summary><b>Solution Walkthrough</b></summary>

```java
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.ConcurrentHashMap;

public class TenantMetricRouter {

    // Maps TenantId to a standard ArrayList of metrics
    private final ConcurrentHashMap<String, List<String>> tenantMetrics = new ConcurrentHashMap<>();

    public void routeMetric(String tenantId, String metricPayload) {

        // 1. Get the list for this tenant.
        // If it doesn't exist, safely create it ONCE using computeIfAbsent.
        List<String> metricsList = tenantMetrics.computeIfAbsent(
            tenantId,
            key -> new ArrayList<>()
        );

        // 2. We now have a reference to the specific ArrayList for this tenant.
        // Standard ArrayList is not thread-safe, so we must synchronize on IT.
        // This locks Tenant A's list, but allows Tenant B's list to be updated simultaneously!
        synchronized (metricsList) {
            metricsList.add(metricPayload);
        }
    }

    // For demonstration purposes
    public int getMetricCount(String tenantId) {
        List<String> list = tenantMetrics.get(tenantId);
        if (list == null) return 0;

        synchronized (list) {
            return list.size();
        }
    }
}
```
This pattern is critical in enterprise systems: granular, targeted locking instead of global locks.
</details>
