# 3.1 Race Conditions & Intrinsic Monitors (synchronized)

## Phase A: Understanding the Mechanics

### 1. Real-World Pain Point (The Why)
You are building the core ledger for a Banking application. A husband and wife both share a joint checking account with a balance of $100. At the exact same millisecond, the husband buys a coffee for $5, and the wife buys a bagel for $5. The transactions process on two separate server threads. Both threads read the balance as $100. Both threads subtract $5, calculating a new balance of $95. Both threads save $95 back to the database. The bank just lost $5 because of a "Lost Update" anomaly. You need a way to ensure that critical sections of code are executed by only one thread at a time.

### 2. Plain English Metaphor (The What)
Imagine a single airplane bathroom (the shared resource).
- A **Race Condition** happens if the bathroom has no lock. Two people walk in at the exact same time, bumping into each other and causing chaos (corrupted data).
- The **Intrinsic Monitor (synchronized)** is the physical lock on the bathroom door. When Thread A walks in, they turn the lock (`synchronized`). If Thread B tries to enter, the door won't budge. Thread B enters a `BLOCKED` state and simply stands outside waiting. When Thread A finishes and turns the lock back (`unlock`), the OS wakes up Thread B and says, "Your turn." Every single Java object has exactly one of these invisible locks built into it.

### 3. Complete Runnable Code
Here is a complete, runnable example demonstrating a race condition destroying a bank balance, and how `synchronized` fixes it.

```java
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class RaceConditionDemo {

    // The shared resource
    static class BankAccount {
        private int balance = 1000;

        // UNSAFE: Vulnerable to race conditions
        public void withdrawUnsafe(int amount) {
            int currentBalance = this.balance; // Read
            // Small pause to force the race condition to happen consistently
            try { Thread.sleep(1); } catch (InterruptedException e) {}
            this.balance = currentBalance - amount; // Write
        }

        // SAFE: Protected by intrinsic monitor lock
        // 'synchronized' on an instance method locks 'this' object
        public synchronized void withdrawSafe(int amount) {
            int currentBalance = this.balance; // Read
            try { Thread.sleep(1); } catch (InterruptedException e) {}
            this.balance = currentBalance - amount; // Write
        }

        public int getBalance() { return balance; }
    }

    public static void main(String[] args) throws InterruptedException {
        System.out.println("--- 1. The Race Condition ---");
        runSimulation(false);

        System.out.println("\n--- 2. The Synchronized Fix ---");
        runSimulation(true);
    }

    private static void runSimulation(boolean useSafeMethod) throws InterruptedException {
        BankAccount account = new BankAccount();
        int threads = 100;
        int withdrawAmount = 10;

        ExecutorService pool = Executors.newFixedThreadPool(threads);
        CountDownLatch latch = new CountDownLatch(threads);

        for (int i = 0; i < threads; i++) {
            pool.submit(() -> {
                if (useSafeMethod) {
                    account.withdrawSafe(withdrawAmount);
                } else {
                    account.withdrawUnsafe(withdrawAmount);
                }
                latch.countDown();
            });
        }

        latch.await();
        pool.shutdown();

        // Expected: 1000 - (100 * 10) = 0
        System.out.println("Expected Balance : 0");
        System.out.println("Actual Balance   : " + account.getBalance());
        if (account.getBalance() != 0) {
            System.err.println("CRITICAL DATA LOSS DETECTED!");
        }
    }
}
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: The Anatomy of a Lost Update**
```java
int currentBalance = this.balance; // Step 1: Read
this.balance = currentBalance - amount; // Step 2: Write
```
*Rationale:* Why does the unsafe method fail? Because modifying a variable is not an "atomic" (single, indivisible) operation. It happens in steps: Read, Calculate, Write. If Thread 1 reads $1000, but gets paused by the CPU before writing, Thread 2 can also read $1000. They both calculate $990, and both write $990. One deduction is permanently lost.

**Step 2: The Instance Monitor Lock**
```java
public synchronized void withdrawSafe(int amount) { ... }
```
*Rationale:* Adding `synchronized` to an instance method implicitly uses `this` (the specific object instance) as the lock. If Thread A calls `withdrawSafe` on `account1`, it acquires the lock for `account1`. If Thread B tries to call `withdrawSafe` on `account1`, it blocks. However, if Thread C calls `withdrawSafe` on `account2`, it proceeds immediately because `account2` has a completely different lock!

**Step 3: The Thread State Transition**
*Rationale:* When Thread B hits a `synchronized` block and the lock is already held by Thread A, Thread B enters the `BLOCKED` state. It is removed from the CPU completely, consuming 0% CPU cycles, until the OS wakes it up.

### 5. ASCII / Architecture Data Flow

```text
+---------------------------------------------------+
|               INTRINSIC MONITOR LOCK              |
|                                                   |
|                BankAccount Instance               |
|            +-------------------------+            |
|            | Lock Owner: Thread 1    |            |
|            |                         |            |
| Thread 1 ->| [EXECUTING withdrawSafe]|            |
|            |                         |            |
|            +-------------------------+            |
|                         ^                         |
|                         |  (Waiting for unlock)   |
|            +-------------------------+            |
| Thread 2 ->| BLOCKED QUEUE           |            |
| Thread 3 ->|                         |            |
|            +-------------------------+            |
+---------------------------------------------------+
```

### 6. Noob Trap vs Pro Tip
- **Noob Trap:** Using `synchronized` on the method signature when you only need to protect a tiny portion of the code. If a method does 5 seconds of slow database reads and then 1 millisecond of updating a shared variable, synchronizing the whole method blocks other threads for 5 seconds unnecessarily!
- **Pro Tip:** Use `synchronized(this) { ... }` or `synchronized(customLock) { ... }` blocks to create tight "Critical Sections." Only wrap the exact lines of code that actually modify the shared state. Keep locks held for the absolute minimum time possible.

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**The Challenge:** The following static counter is losing counts under heavy load. Fix it using synchronization.
```java
public class HitCounter {
    private static int totalHits = 0;

    public static void increment() {
        totalHits++; // Not atomic!
    }
}
```
<details>
<summary><b>Hint</b></summary>
Because the variable and method are `static`, you cannot lock on `this` (there is no instance). You must lock on the Class object itself.
</details>
<details>
<summary><b>Solution Walkthrough</b></summary>

```java
public class HitCounter {
    private static int totalHits = 0;

    // Synchronizing a static method locks the Class object (HitCounter.class)
    public static synchronized void increment() {
        totalHits++;
    }

    // Equivalent to:
    // public static void increment() {
    //     synchronized(HitCounter.class) { totalHits++; }
    // }
}
```
</details>

### Level 2: Real-World
**The Challenge:** You are building a `TransferService` to move money between two accounts. You write `synchronized (fromAccount) { synchronized (toAccount) { ... } }`. During testing, Thread 1 transfers $10 from A to B. Simultaneously, Thread 2 transfers $10 from B to A. The entire application freezes permanently. Why? Fix the Deadlock.
<details>
<summary><b>Hint</b></summary>
This is a classic Deadlock. Thread 1 locks A and waits for B. Thread 2 locks B and waits for A. Neither can ever proceed. To fix a deadlock, locks must always be acquired in a *consistent, global order*.
</details>
<details>
<summary><b>Solution Walkthrough</b></summary>

```java
public class TransferService {

    static class Account {
        final String accountId;
        int balance;
        Account(String id) { this.accountId = id; }
    }

    public void transfer(Account from, Account to, int amount) {
        // Fix: Enforce a global lock ordering using the accountId strings
        Account firstLock = from;
        Account secondLock = to;

        // String.compareTo returns negative, 0, or positive based on alphabetical order
        if (from.accountId.compareTo(to.accountId) > 0) {
            firstLock = to;
            secondLock = from;
        }

        // Now, regardless of the transfer direction, if A and B are involved,
        // ALL threads will ALWAYS attempt to lock A first, then B. Deadlock impossible.
        synchronized (firstLock) {
            synchronized (secondLock) {
                from.balance -= amount;
                to.balance += amount;
            }
        }
    }
}
```
</details>

### Level 3: Boss Level
**The Challenge:** Build a `ThreadSafeBankingLedgerSystem`. Instead of simple balances, accounts maintain a `List<Transaction>`. You must write a `deposit` and `getRecentTransactions` method. `deposit` modifies the list. `getRecentTransactions` reads it. If you synchronize both methods on `this`, readers will block other readers! Implement it using explicit locking (`ReentrantReadWriteLock`) so that multiple threads can read the ledger concurrently, but writers get exclusive access.
<details>
<summary><b>Hint</b></summary>
Create a `ReentrantReadWriteLock`. Use `lock.readLock().lock()` for the getter, and `lock.writeLock().lock()` for the depositor. Remember to use `try...finally` to ensure `unlock()` is always called, even if an exception occurs.
</details>
<details>
<summary><b>Solution Walkthrough</b></summary>

```java
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.locks.ReadWriteLock;
import java.util.concurrent.locks.ReentrantReadWriteLock;

public class ThreadSafeBankingLedger {

    private final List<String> ledger = new ArrayList<>();

    // Replaces the intrinsic 'synchronized' with a highly tunable explicit lock
    private final ReadWriteLock lock = new ReentrantReadWriteLock();

    public void deposit(String transactionDetail) {
        // Exclusive lock. Blocks all other writers AND all readers.
        lock.writeLock().lock();
        try {
            ledger.add(transactionDetail);
        } finally {
            // CRITICAL: Always unlock in a finally block
            lock.writeLock().unlock();
        }
    }

    public List<String> getRecentTransactions() {
        // Shared lock. Multiple threads can hold this lock simultaneously,
        // ensuring high throughput for reads. Only blocks if a writer holds the lock.
        lock.readLock().lock();
        try {
            // Return a defensive copy so callers can't modify the internal list later
            return new ArrayList<>(ledger);
        } finally {
            lock.readLock().unlock();
        }
    }
}
```
This is the standard enterprise approach for read-heavy, write-rarely critical sections where `synchronized` would cause severe contention.
</details>
