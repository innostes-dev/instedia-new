# 3.4 Thread Pools, Executors & Rejection Policies

## Phase A: Understanding the Mechanics

### 1. Real-World Pain Point (The Why)
You are building an e-commerce checkout service. For every order submitted, you need to send a confirmation email. Because sending an email takes 2 seconds over SMTP, you don't want to block the HTTP response, so you do what seems logical: `new Thread(() -> sendEmail()).start();`. Everything works perfectly in QA. On Black Friday, you get 10,000 orders in one minute. Your server crashes completely with `java.lang.OutOfMemoryError: unable to create new native thread`. You realize that every Java thread consumes 1MB of native OS memory just for its stack. 10,000 threads equals 10GB of RAM instantly requested from Linux. The OS panicked and killed your app. You need a way to process background tasks asynchronously without ever exceeding a safe limit of system resources.

### 2. Plain English Metaphor (The What)
Imagine a busy restaurant kitchen.
- **`new Thread().start()`:** Every time an order comes in, the manager goes to the street, hires a brand new chef, trains them, gives them one ticket, and as soon as they finish cooking that one meal, fires them. This is insane overhead.
- **A Thread Pool:** The manager hires exactly 10 professional chefs. When an order comes in, it goes on a spinning ticket wheel (a Queue). The chefs pull tickets from the wheel one by one. If 100 orders come in at once, the 10 chefs just work through them at maximum capacity. No chefs are hired or fired.
- **Rejection Policies:** What happens if the ticket wheel is completely full and 50 more customers walk in? The manager needs a rule. Do they throw the tickets in the trash (`Discard`)? Do they scream at the customer to cook it themselves (`CallerRuns`)? Or do they throw an error (`Abort`)?

### 3. Complete Runnable Code
Here is a complete, runnable example demonstrating why unbounded thread creation crashes systems, and how a properly tuned `ThreadPoolExecutor` safely buffers spikes in traffic.

```java
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

public class ThreadPoolTuningDemo {

    public static void main(String[] args) throws InterruptedException {
        System.out.println("--- Starting Thread Pool Demo ---");

        // 1. Create a custom ThreadPoolExecutor
        // Core Pool Size: 2 (Always keep 2 threads alive)
        // Max Pool Size: 4 (Can scale to 4 threads if queue is full)
        // Queue: ArrayBlockingQueue of size 5 (Buffer for pending tasks)
        // Rejection Policy: CallerRunsPolicy (If full, the thread submitting the task does the work!)
        ThreadPoolExecutor pool = new ThreadPoolExecutor(
            2, 4,
            60L, TimeUnit.SECONDS,
            new ArrayBlockingQueue<>(5),
            new ThreadPoolExecutor.CallerRunsPolicy()
        );

        AtomicInteger taskCounter = new AtomicInteger(1);

        // We submit 12 tasks to a system that can only handle 4 active + 5 queued (Total capacity 9)
        // What happens to the other 3 tasks?
        for (int i = 0; i < 12; i++) {
            int taskId = taskCounter.getAndIncrement();

            System.out.println("Main thread submitting Task " + taskId);

            pool.submit(() -> {
                System.out.println("   [Start] Task " + taskId + " executing on " + Thread.currentThread().getName());
                try {
                    // Simulate heavy 1-second workload
                    Thread.sleep(1000);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
                System.out.println("   [End] Task " + taskId + " finished.");
            });

            // Tiny delay to watch the pool scale up
            Thread.sleep(50);
        }

        pool.shutdown();
        pool.awaitTermination(10, TimeUnit.SECONDS);
        System.out.println("All tasks finished.");
    }
}
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: The Core Pool and Queue**
```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(2, 4, 60L, TimeUnit.SECONDS, new ArrayBlockingQueue<>(5), ...);
```
*Rationale:* How does a Thread Pool decide when to scale? It's counter-intuitive.
1. When Tasks 1 and 2 arrive, the pool creates 2 threads (Core Size).
2. When Task 3 arrives, *it does NOT create a 3rd thread*. It puts Task 3 in the Queue.
3. It keeps putting tasks in the Queue until the Queue is FULL (5 items).
4. Only when the Queue is completely full (at Task 8), will it create Thread 3 and Thread 4 (up to Max Size) to help drain the queue faster.

**Step 2: The Rejection Policy**
```java
new ThreadPoolExecutor.CallerRunsPolicy()
```
*Rationale:* What happens at Task 10? The 4 threads are busy, and the queue (size 5) is full. The pool *rejects* the task. The default policy is `AbortPolicy` (throws `RejectedExecutionException`). But we used `CallerRunsPolicy`. This tells the `main` thread: "I'm full. If you want this done, do it yourself." The `main` thread is forced to run Task 10 synchronously. This acts as a natural "backpressure" mechanism, slowing down the incoming flood of traffic until the pool can recover!

**Step 3: Keep-Alive Time**
```java
60L, TimeUnit.SECONDS
```
*Rationale:* If the traffic spike dies down, Threads 3 and 4 will sit idle. After 60 seconds of doing nothing, the pool will terminate them, shrinking back down to the Core Size of 2 to save system resources.

### 6. Noob Trap vs Pro Tip
- **Noob Trap:** Using `Executors.newCachedThreadPool()` in production. Under the hood, this sets Core Size to 0, Max Size to `Integer.MAX_VALUE`, and uses a `SynchronousQueue` (queue size 0). If 10,000 tasks arrive simultaneously, it creates 10,000 native threads, immediately causing the exact `OutOfMemoryError` you were trying to avoid.
- **Pro Tip:** For CPU-intensive workloads (math, parsing), set Core Pool Size to `Number of CPU Cores + 1`. For I/O-intensive workloads (database calls, HTTP requests), set it much higher (e.g., `Cores * 10`) because the threads spend most of their time asleep waiting for network responses.

### Level 1: Warm-Up
**The Challenge:** You need to run a database cleanup script every night at 3:00 AM, and also ping a health endpoint every 5 seconds. You don't want to use heavy external schedulers like Quartz. Implement this using Java's built-in concurrency tools.
<details>
<summary><b>Hint</b></summary>
Use `ScheduledExecutorService`. It is specifically designed to handle delayed and periodic task execution efficiently.
</details>
<details>
<summary><b>Solution Walkthrough</b></summary>

```java
import java.util.concurrent.Executors;
import java.util.concurrent.ScheduledExecutorService;
import java.util.concurrent.TimeUnit;

public class ScheduledTasks {
    public static void main(String[] args) {
        // A pool optimized for scheduled tasks
        ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(2);

        // Run immediately, then repeat every 5 seconds
        scheduler.scheduleAtFixedRate(
            () -> System.out.println("Pinging health endpoint..."),
            0, 5, TimeUnit.SECONDS
        );

        // Note: Real 3 AM scheduling requires calculating initial delay.
        // For simplicity, we delay by 10 minutes here.
        scheduler.schedule(
            () -> System.out.println("Running one-time DB cleanup..."),
            10, TimeUnit.MINUTES
        );
    }
}
```

### Level 2: Real-World
**The Challenge:** Build an `AsynchronousOrderBatchProcessor`. You receive individual `Order` objects. You want to submit them to a ThreadPool, but you don't want them executed immediately. You want a single worker thread to wake up, pull up to 100 pending orders from the queue at once, process them in a single batch database `INSERT`, and go back to sleep.
<details>
<summary><b>Hint</b></summary>
Don't submit tasks directly to the ThreadPool. Instead, put the raw `Order` data into a concurrent queue (like `ConcurrentLinkedQueue`). Have a single scheduled task that wakes up every 1 second, drains the queue, and executes the batch.
</details>
<details>
<summary><b>Solution Walkthrough</b></summary>

```java
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.ConcurrentLinkedQueue;
import java.util.concurrent.Executors;
import java.util.concurrent.ScheduledExecutorService;
import java.util.concurrent.TimeUnit;

public class AsyncOrderBatchProcessor {

    // Lock-free queue for high-throughput injest
    private final ConcurrentLinkedQueue<String> orderBuffer = new ConcurrentLinkedQueue<>();
    private final ScheduledExecutorService batchWorker = Executors.newSingleThreadScheduledExecutor();

    public AsyncOrderBatchProcessor() {
        // Wake up every 1 second to process whatever is in the buffer
        batchWorker.scheduleAtFixedRate(this::processBatch, 1, 1, TimeUnit.SECONDS);
    }

    // Called heavily by HTTP threads
    public void submitOrder(String orderData) {
        orderBuffer.add(orderData); // Lightning fast, no blocking
    }

    private void processBatch() {
        List<String> batch = new ArrayList<>();
        String order;

        // Drain up to 100 items from the queue
        while (batch.size() < 100 && (order = orderBuffer.poll()) != null) {
            batch.add(order);
        }

        if (!batch.isEmpty()) {
            System.out.println("Processing database batch insert of " + batch.size() + " orders.");
            // simulateDbBatchInsert(batch);
        }
    }
}
```
This pattern is critical for converting high-frequency individual requests into efficient database batch operations.

### Level 3: Boss Level
**The Challenge:** A legacy system uses an `ExecutorService` and submits tasks using `.submit(Runnable)`. You notice that when a task throws a `NullPointerException`, the application doesn't crash, but the error completely vanishes. It isn't printed to the console, it isn't in the logs. The thread just dies silently. Why does this happen, and how do you build a `RobustThreadPoolFactory` that guarantees all unhandled exceptions in background threads are caught and logged?
<details>
<summary><b>Hint</b></summary>
When you use `submit()`, the pool wraps your task in a `Future`. If an exception occurs, the `Future` catches it and holds it internally. If you never call `future.get()`, the exception is swallowed forever. To fix this globally, you must use a custom `ThreadFactory` that sets an `UncaughtExceptionHandler` on the threads, AND you should override the `afterExecute` method of `ThreadPoolExecutor`.
</details>
<details>
<summary><b>Solution Walkthrough</b></summary>

```java
import java.util.concurrent.*;

public class RobustThreadPoolFactory {

    public static ThreadPoolExecutor createRobustPool() {

        // 1. Custom Thread Factory (Names threads and catches raw Thread deaths)
        ThreadFactory customFactory = runnable -> {
            Thread t = new Thread(runnable, "Robust-Worker-Thread");
            t.setUncaughtExceptionHandler((thread, exception) -> {
                System.err.println("CRITICAL: Thread " + thread.getName() + " died!");
                exception.printStackTrace();
            });
            return t;
        };

        // 2. Override afterExecute to extract Exceptions swallowed by Futures
        return new ThreadPoolExecutor(
            2, 4, 60L, TimeUnit.SECONDS,
            new ArrayBlockingQueue<>(10),
            customFactory
        ) {
            @Override
            protected void afterExecute(Runnable r, Throwable t) {
                super.afterExecute(r, t);

                // If the task was submitted via submit(), the exception is hidden in the Future
                if (t == null && r instanceof Future<?>) {
                    try {
                        // isDone() is true, get() will instantly throw if an error occurred
                        ((Future<?>) r).get();
                    } catch (CancellationException ce) {
                        t = ce;
                    } catch (ExecutionException ee) {
                        t = ee.getCause(); // The actual exception thrown by the task!
                    } catch (InterruptedException ie) {
                        Thread.currentThread().interrupt();
                    }
                }

                // Now we can globally log the swallowed exception
                if (t != null) {
                    System.err.println("BACKGROUND TASK FAILED: " + t.getMessage());
                }
            }
        };
    }

    public static void main(String[] args) {
        ThreadPoolExecutor pool = createRobustPool();

        // This NPE will be caught and printed by our custom afterExecute!
        pool.submit(() -> {
            String nullString = null;
            nullString.length();
        });

        pool.shutdown();
    }
}
```
This is a mandatory configuration for enterprise ThreadPools to ensure observability and prevent silent failures in asynchronous jobs.
</details>
