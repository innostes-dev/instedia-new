# 1.3 Modern Data Modeling: Records, Sealed Types & Pattern Matching

## Phase A: Understanding the Mechanics

### 1. Real-World Pain Point (The Why)
You are building a financial payment gateway that processes Credit Cards, Bank Transfers, and Crypto payments. In traditional Java, creating a simple `PaymentTransaction` class required 50 lines of boilerplate (getters, `equals()`, `hashCode()`, `toString()`). When a new developer added a `cryptoWallet` field but forgot to update the `hashCode()` method, it caused a subtle bug where duplicate transactions weren't caught in a `HashSet`. Furthermore, you have a `processPayment(Payment p)` method, but there is no way to enforce at compile-time that you have handled *every* possible payment type. If someone adds a `GiftCard` payment type later, your system might just crash at runtime with an `UnsupportedOperationException`.

### 2. Plain English Metaphor (The What)
- **Records** are like standardized shipping containers. You declare the dimensions once (the fields), and the factory automatically builds the doors, locks, and labels (`getters`, `equals`, `hashCode`, `toString`) exactly to standard, every single time. No human error possible.
- **Sealed Interfaces** are like an exclusive VIP club list. The club (Interface) explicitly lists the exact names of the people (Classes/Records) who are allowed inside. Nobody else can just show up and claim they are part of the club.
- **Pattern Matching (with Switch)** is like a sorting facility that knows the VIP list. Because it knows *exactly* who is on the list, it can guarantee that every single VIP has been checked in, refusing to start the event (compile) if someone was forgotten.

### 3. Complete Runnable Code
Here is a complete, runnable example of modern Java (17/21+) combining Records, Sealed Types, and Pattern Matching.

```java
import java.math.BigDecimal;

public class ModernDataModeling {

    // 1. Sealed Interface: Exhaustively defines permitted subclasses
    public sealed interface PaymentMethod
        permits CreditCard, BankTransfer, CryptoWallet {}

    // 2. Records: Immutable data carriers (no boilerplate)
    public record CreditCard(String cardNumber, String expiryDate) implements PaymentMethod {
        // Compact constructor for validation
        public CreditCard {
            if (cardNumber == null || cardNumber.length() != 16) {
                throw new IllegalArgumentException("Invalid card number");
            }
        }
    }

    public record BankTransfer(String routingNumber, String accountNumber) implements PaymentMethod {}

    public record CryptoWallet(String walletAddress, String network) implements PaymentMethod {}

    // 3. Pattern Matching with Switch (Java 21)
    public static void processPayment(PaymentMethod method, BigDecimal amount) {
        // The compiler GUARANTEES all cases are handled. No 'default' branch needed!
        String confirmation = switch (method) {
            case CreditCard cc ->
                "Charging Card ending in " + cc.cardNumber().substring(12) + " for $" + amount;

            case BankTransfer bt ->
                "Routing transfer to account " + bt.accountNumber() + " for $" + amount;

            case CryptoWallet cw when cw.network().equals("BTC") ->
                "Processing Bitcoin transaction to " + cw.walletAddress();

            case CryptoWallet cw ->
                "Processing Altcoin transaction to " + cw.walletAddress();
        };

        System.out.println(confirmation);
    }

    public static void main(String[] args) {
        PaymentMethod card = new CreditCard("1234567890123456", "12/25");
        PaymentMethod bank = new BankTransfer("123456789", "987654321");
        PaymentMethod cryptoBtc = new CryptoWallet("bc1qxy2kgdygjrsqtzq2n0yrf2493p83kkfjhx0wlh", "BTC");

        processPayment(card, new BigDecimal("99.99"));
        processPayment(bank, new BigDecimal("500.00"));
        processPayment(cryptoBtc, new BigDecimal("0.05"));

        // Testing Record's built-in equals/toString
        PaymentMethod card2 = new CreditCard("1234567890123456", "12/25");
        System.out.println("\nRecords automatically implement equals(): " + card.equals(card2));
        System.out.println("Records automatically implement toString(): " + card.toString());
    }
}
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: The Record Declaration**
```java
public record CreditCard(String cardNumber, String expiryDate) implements PaymentMethod {
    public CreditCard {
        if (cardNumber == null || cardNumber.length() != 16) {
            throw new IllegalArgumentException("Invalid card number");
        }
    }
}
```
*Rationale:* Why start with Records? Because they solve the boilerplate problem. The compiler automatically generates `cardNumber()` and `expiryDate()` accessors, plus perfect `equals`, `hashCode`, and `toString` methods. The "Compact Constructor" (the block without arguments) allows you to inject validation logic *before* the immutable fields are finalized, ensuring illegal states are impossible.

**Step 2: The Sealed Hierarchy**
```java
public sealed interface PaymentMethod
    permits CreditCard, BankTransfer, CryptoWallet {}
```
*Rationale:* Next, we secure the domain model. By declaring `PaymentMethod` as `sealed`, we explicitly list (`permits`) the allowed implementations. This prevents random developers from creating a `GiftCard implements PaymentMethod` in another package, which would silently break domain assumptions.

**Step 3: Pattern Matching and Exhaustiveness**
```java
String confirmation = switch (method) {
    case CreditCard cc -> "Charging Card...";
    // ...
};
```
*Rationale:* Finally, the payoff. Because the interface is sealed, the `switch` statement is "exhaustive." The compiler checks the `permits` clause and knows there are exactly three types. If you handle all three, you do *not* need a `default` case. If someone later adds `GiftCard` to the `permits` clause, this `switch` statement will instantly fail to compile, immediately alerting the developer that they need to add a `case GiftCard` branch. This transforms a runtime crash into a compile-time guarantee.

### 6. Noob Trap vs Pro Tip
- **Noob Trap:** Trying to use Records for entities that change over time (like JPA/Hibernate Entities). Records are strictly **immutable**. Their fields are `final`. They are designed for Data Transfer Objects (DTOs), events, messages, and configurations, *not* mutable database rows.
- **Pro Tip:** Combine Records with "Guards" (the `when` keyword) in switch statements to handle complex business logic right at the routing layer, e.g., `case CryptoWallet cw when cw.network().equals("ETH") -> handleEth()`.

Then write a method that takes an `ApiResponse` and returns a formatted JSON string using an exhaustive switch.

<details>
<summary><b>Solution Walkthrough</b></summary>

```java
public sealed interface ApiResponse<T> permits Success, Failure {
}

public record Success<T>(T data) implements ApiResponse<T> {}

public record Failure<T>(String errorMessage, int statusCode) implements ApiResponse<T> {}

public class ApiHandler {
    public static <T> String formatResponse(ApiResponse<T> response) {
        return switch (response) {
            case Success<T> s ->
                "{ \"status\": \"ok\", \"data\": \"" + s.data() + "\" }";
            case Failure<T> f ->
                "{ \"status\": \"error\", \"code\": " + f.statusCode() +
                ", \"message\": \"" + f.errorMessage() + "\" }";
        };
    }
}
```

### Level 3: Boss Level
**The Challenge:** Build a Type-Safe Financial Payment Message Model. You receive raw JSON-like Maps. You need to parse them into a sealed `Event` hierarchy (`UserCreated`, `TransactionProcessed`, `AccountSuspended`). Use a factory method with an enhanced switch (using `yield`) to parse the Map into the correct Record. If the event type is unknown, throw a custom exception.
<details>
<summary><b>Hint</b></summary>
A `switch` expression can be used inside a method to `yield` a constructed Record back to the caller.
</details>
<details>
<summary><b>Solution Walkthrough</b></summary>

```java
import java.util.Map;

public class EventProcessor {

    public sealed interface DomainEvent permits UserCreated, TransactionProcessed, AccountSuspended {}

    public record UserCreated(String userId, String email) implements DomainEvent {}
    public record TransactionProcessed(String txId, double amount) implements DomainEvent {}
    public record AccountSuspended(String userId, String reason) implements DomainEvent {}

    // Factory method parsing raw data into our strictly typed sealed hierarchy
    public static DomainEvent parseEvent(Map<String, String> rawData) {
        String eventType = rawData.get("type");

        // Java 14+ Switch Expression (yielding a value)
        return switch (eventType) {
            case "USER_CREATED" -> {
                String id = rawData.get("userId");
                String email = rawData.get("email");
                yield new UserCreated(id, email);
            }
            case "TX_PROCESSED" -> {
                String txId = rawData.get("txId");
                double amount = Double.parseDouble(rawData.get("amount"));
                yield new TransactionProcessed(txId, amount);
            }
            case "ACCT_SUSPENDED" ->
                new AccountSuspended(rawData.get("userId"), rawData.get("reason"));

            default -> throw new IllegalArgumentException("Unknown event type: " + eventType);
        };
    }

    public static void main(String[] args) {
        Map<String, String> payload = Map.of(
            "type", "TX_PROCESSED",
            "txId", "TX-999",
            "amount", "150.50"
        );

        DomainEvent event = parseEvent(payload);

        // Exhaustive routing based on the parsed event
        switch (event) {
            case UserCreated u -> System.out.println("Welcome " + u.email());
            case TransactionProcessed t -> System.out.println("Processing $" + t.amount());
            case AccountSuspended s -> System.out.println("Suspended: " + s.reason());
        }
    }
}
```
This pattern (often called Algebraic Data Types or ADTs) is incredibly powerful for building robust, compiler-checked domain models in modern Java.
</details>
