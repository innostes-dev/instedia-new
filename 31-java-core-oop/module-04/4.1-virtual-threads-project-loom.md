# 4.1 Virtual Threads (Project Loom)

## Phase A: Understanding the Mechanics

### 1. Real-World Pain Point (The Why)
You are building a Real-Time Chat Gateway. You expect 500,000 users to be connected simultaneously. Your code architecture is standard: "Thread-per-request" (each connected user gets a thread to read messages from the socket). You start the server. At exactly 8,000 users, the server crashes with `OutOfMemoryError`. Why? Because standard Java Threads are wrappers around underlying Linux/OS Threads. Each OS thread requires a massive 1MB memory stack. 8,000 threads * 1MB = 8GB of RAM just to *hold* the threads, completely ignoring the actual application memory. You cannot scale. Historically, to fix this, developers had to rewrite their entire application using complex Reactive Programming (RxJava, Project Reactor) filled with confusing callbacks (`.subscribe(..).flatMap(..)`). You want the simplicity of standard blocking code, but the scalability of Reactive code.

### 2. Plain English Metaphor (The What)
Imagine a massive hotel with 500,000 guests, but only 10 Elevators.
- **Platform (OS) Threads:** Every time a guest (Task) gets into an Elevator (Thread), they lock the doors. If they need to wait 5 minutes for their wife to come out of the room (blocking I/O), they *keep the Elevator locked* and sit inside it. The hotel grinds to a halt. You'd need to buy 500,000 physical Elevators (which is impossible/too expensive).
- **Virtual Threads (Project Loom):** The hotel changes the rules. If a guest gets into an Elevator and realizes they have to wait for something (blocking I/O), the hotel staff instantly grabs them, pulls them out of the Elevator, and sits them in a tiny chair in the hallway (unmounting). The Elevator is instantly freed up for another guest. When the guest's wife is finally ready, the staff grabs the guest, throws them back into the next available Elevator (mounting), and sends them on their way. 10 Elevators (Carrier Threads) can now service 500,000 guests (Virtual Threads) seamlessly.

### 3. Complete Runnable Code
Here is a complete, runnable example demonstrating how standard OS threads crash the JVM, while Java 21 Virtual threads can spawn 100,000 concurrent tasks effortlessly.

```java
import java.time.Duration;
import java.time.Instant;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.atomic.AtomicInteger;

public class VirtualThreadsDemo {

    public static void main(String[] args) {
        int taskCount = 100_000;

        System.out.println("--- Starting Project Loom Simulation ---");

        // WARNING: If you try to run this with standard Platform Threads,
        // your OS will likely kill the JVM process!
        // testPlatformThreads(taskCount);

        System.out.println("\nExecuting 100,000 blocking tasks using Virtual Threads...");
        testVirtualThreads(taskCount);
    }

    private static void testPlatformThreads(int taskCount) {
        // Creates a heavy 1MB OS thread for EVERY single task.
        try (ExecutorService pool = Executors.newCachedThreadPool()) {
            executeTasks(pool, taskCount, "Platform");
        }
    }

    private static void testVirtualThreads(int taskCount) {
        // Java 21: Creates a Virtual Thread for every task.
        // Virtual Threads share a small pool of underlying OS Carrier Threads.
        try (ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor()) {
            executeTasks(pool, taskCount, "Virtual");
        }
    }

    private static void executeTasks(ExecutorService pool, int taskCount, String type) {
        AtomicInteger completedTasks = new AtomicInteger(0);
        Instant start = Instant.now();

        for (int i = 0; i < taskCount; i++) {
            pool.submit(() -> {
                try {
                    // Simulate a blocking I/O operation (e.g., waiting for Database or Network)
                    // In a Virtual Thread, this DOES NOT block the underlying OS thread!
                    Thread.sleep(1000);
                    completedTasks.incrementAndGet();
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            });
        }

        // ExecutorService implements AutoCloseable in Java 19+
        // The try-with-resources block automatically waits for all tasks to finish!
        System.out.println("All tasks submitted. Waiting for completion...");
    }
}
```
*(Note: To compile and run this code, you must use Java 21)*

### 4. Progressive Step-by-Step Breakdown

**Step 1: The Heavy OS Thread**
```java
Executors.newCachedThreadPool()
```
*Rationale:* Why does this fail? The JVM requests a new Thread from the Linux kernel. Linux allocates a 1MB memory stack. When the Java code calls `Thread.sleep(1000)` or `socket.read()`, the Linux thread enters the `BLOCKED` state. That 1MB of memory, and that CPU scheduling slot, is completely dead and unusable for an entire second.

**Step 2: The Virtual Thread Executor**
```java
Executors.newVirtualThreadPerTaskExecutor()
```
*Rationale:* Virtual Threads are managed by the JVM, not the OS. They are incredibly cheap (consuming only a few hundred *bytes* of RAM). Under the hood, the JVM creates a standard `ForkJoinPool` of OS threads (Carrier Threads) equal to your CPU core count (e.g., 8 threads). When you submit 100,000 tasks, the JVM creates 100,000 Virtual Threads.

**Step 3: Mounting and Unmounting**
```java
Thread.sleep(1000); // Or Database I/O, or HTTP call
```
*Rationale:* The magic happens here. A Carrier Thread executes Virtual Thread #1. It hits the `sleep()` command. Instead of blocking the Carrier Thread, the JVM intercepts the call. It copies the tiny stack of Virtual Thread #1 to the Java Heap (unmounting) and tells the OS Carrier Thread to immediately pick up Virtual Thread #2. This Carrier Thread operates at 100% CPU utilization, constantly swapping Virtual Threads in and out whenever they hit a blocking I/O wall.

### 5. ASCII / Architecture Data Flow

```text
+-------------------------------------------------------------+
|                     JAVA 21 VIRTUAL THREADS                 |
|                                                             |
|   100,000 Virtual Threads (Cheap, Heap-Allocated)           |
|   [VT1] [VT2] [VT3] [VT4] ... [VT99999]                     |
|     |     |     |     |                                     |
|     |     |     |     v                                     |
|     |     |     +--> [Blocked on I/O -> UNMOUNTED to Heap]  |
|     |     |                                                 |
|     v     v                                                 |
|   +-----------------------------------------------------+   |
|   |         JVM CARRIER THREAD POOL (ForkJoinPool)      |   |
|   |   [OS Thread 1]   [OS Thread 2]   [OS Thread 3]     |   |
|   +-----------------------------------------------------+   |
|                                                             |
| * When VT1 makes a DB call, JVM unmounts it from OS Thd 1.  |
| * OS Thd 1 immediately grabs VT3 to keep working.           |
| * When DB responds, VT1 is mounted back onto any open OS Thd|
+-------------------------------------------------------------+
```

### 6. Noob Trap vs Pro Tip
- **Noob Trap:** Using Thread Pools for Virtual Threads (e.g., `Executors.newFixedThreadPool(10, Thread.ofVirtual().factory())`). Virtual threads are so cheap that pooling them is an anti-pattern. You should create a brand new Virtual Thread for *every single task* and let it die when the task is done. The JVM handles the pooling of the Carrier Threads automatically.
- **Pro Tip ("Thread Pinning"):** If a Virtual Thread enters a `synchronized` block, or calls a native C++ method (JNI), the JVM *cannot* unmount it. The Virtual Thread becomes "Pinned" to the Carrier Thread. If it does blocking I/O while pinned, the entire OS Carrier Thread blocks! In Java 21, replace `synchronized` blocks with `ReentrantLock` when doing blocking I/O inside Virtual Threads to prevent pinning.

### Level 1: Warm-Up
**The Challenge:** You want to execute three HTTP calls concurrently and wait for all three to finish. In the past, you used `CompletableFuture`. Rewrite this to use simple, blocking, imperative code with Virtual Threads.
<details>
<summary><b>Hint</b></summary>
Use `Executors.newVirtualThreadPerTaskExecutor()` in a `try-with-resources` block. Submit all three tasks. The block will automatically wait for all of them to complete.
</details>
<details>
<summary><b>Solution Walkthrough</b></summary>

```java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class ConcurrentFetcher {
    public void fetchAllData() {
        // try-with-resources acts as an automatic concurrency barrier
        try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {

            executor.submit(() -> fetchFrom("https://api.github.com"));
            executor.submit(() -> fetchFrom("https://api.stripe.com"));
            executor.submit(() -> fetchFrom("https://api.twilio.com"));

        } // The main thread blocks right here until all 3 Virtual Threads finish!

        System.out.println("All data fetched concurrently!");
    }

    private void fetchFrom(String url) {
        // Standard blocking I/O code (e.g., Java HttpClient)
        // Under the hood, the Virtual Thread unmounts while waiting for the network
    }
}
```
</details>

### Level 2: Real-World
**The Challenge:** You are building a Million-Connection Chat Gateway. Every time a user connects via Socket, you need to spin up a thread to read from that socket indefinitely. Implement the server loop safely so it can scale to a million users.
<details>
<summary><b>Hint</b></summary>
Do not use a standard Thread. Do not use an ExecutorService. Use the static factory method `Thread.ofVirtual().start()`.
</details>
<details>
<summary><b>Solution Walkthrough</b></summary>

```java
import java.io.IOException;
import java.net.ServerSocket;
import java.net.Socket;

public class ChatGateway {

    public void startServer() throws IOException {
        try (ServerSocket serverSocket = new ServerSocket(8080)) {
            System.out.println("Listening for million connections...");

            while (true) {
                // Blocks until a new user connects
                Socket clientSocket = serverSocket.accept();

                // Extremely cheap. We can do this 1,000,000 times!
                Thread.ofVirtual().start(() -> handleClient(clientSocket));
            }
        }
    }

    private void handleClient(Socket socket) {
        try {
            // Blocking read operations.
            // The VT unmounts whenever the socket is silent.
            byte[] buffer = new byte[1024];
            while (socket.getInputStream().read(buffer) != -1) {
                System.out.println("Received message.");
            }
        } catch (IOException e) {
            System.err.println("Client disconnected.");
        }
    }
}
```
</details>

### Level 3: Boss Level
**The Challenge:** The "Pinning" Trap. Write an application that intentionally causes a complete JVM deadlock by spinning up 10 Virtual Threads (assuming your computer has 8 CPU cores). Each Virtual Thread must acquire a lock, and then perform a slow blocking task (like `Thread.sleep(5000)`). First, write it using `synchronized` to prove that it pins the carrier threads and deadlocks the system. Then, fix it using `ReentrantLock` to show how to correctly write concurrent I/O with Virtual Threads.
<details>
<summary><b>Hint</b></summary>
If you have 8 CPU cores, the Carrier Thread pool size is 8. If you spawn 10 Virtual Threads that all execute `Thread.sleep()` inside a `synchronized` block, the first 8 VTs will "pin" all 8 Carrier Threads. The last 2 VTs will be stuck in the queue forever, and the application halts. `ReentrantLock` allows the JVM to unmount the VT correctly.
</details>
<details>
<summary><b>Solution Walkthrough</b></summary>

```java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.locks.ReentrantLock;

public class PinningDisaster {

    // Simulating a shared resource
    private static final Object intrinsicLock = new Object();
    private static final ReentrantLock explicitLock = new ReentrantLock();

    public static void main(String[] args) {
        System.out.println("--- 1. The Pinning Disaster (synchronized) ---");
        // Warning: This will severely degrade performance because it blocks OS threads
        runTest(true);

        System.out.println("\n--- 2. The Correct Way (ReentrantLock) ---");
        // This will run perfectly, unmounting VTs and freeing OS threads
        runTest(false);
    }

    private static void runTest(boolean useBadLocking) {
        long start = System.currentTimeMillis();

        try (ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor()) {
            // Assuming an 8-core machine, submitting 20 tasks
            for (int i = 0; i < 20; i++) {
                final int taskId = i;
                pool.submit(() -> {
                    if (useBadLocking) {
                        badDatabaseCall(taskId);
                    } else {
                        goodDatabaseCall(taskId);
                    }
                });
            }
        } // Blocks until all 20 finish

        System.out.println("Finished in " + (System.currentTimeMillis() - start) + "ms");
    }

    private static void badDatabaseCall(int id) {
        // SYNCHRONIZED PINS THE CARRIER THREAD!
        // The JVM cannot unmount this Virtual Thread.
        synchronized (intrinsicLock) {
            try {
                // The underlying OS Carrier Thread is now blocked for 1 second!
                Thread.sleep(1000);
            } catch (InterruptedException e) {}
        }
    }

    private static void goodDatabaseCall(int id) {
        // REENTRANT LOCK ALLOWS UNMOUNTING!
        explicitLock.lock();
        try {
            // The Virtual Thread unmounts. The OS Carrier Thread is completely free
            // to go execute other tasks while we sleep!
            Thread.sleep(1000);
        } catch (InterruptedException e) {
        } finally {
            explicitLock.unlock();
        }
    }
}
```
*Rule of thumb for Java 21+: If a block of code contains Blocking I/O (File, Network, DB), NEVER wrap it in `synchronized`. Always use `ReentrantLock`.*
</details>
