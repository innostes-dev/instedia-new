# Module 02: Networking & Ingress (Connecting to the Internet)
## 2.1 Kubernetes Services & ClusterIP

### Phase A: Core Concept

#### 1. Real-World Pain Point (The Why)
You have a frontend React app trying to communicate with a Node.js backend. In Kubernetes, every time a backend Pod crashes and is restarted by a Deployment, it gets a completely new, random IP address. If your frontend is hardcoded to talk to IP `10.4.2.14`, and that Pod dies, the new Pod might be at `10.4.5.99`. Your frontend instantly breaks. You need a stable, static address that never changes, even if the underlying Pods are constantly dying and being recreated.

#### 2. Plain English Metaphor (The What)
Imagine you are calling a large call center to speak to Customer Support. You don't memorize the personal desk phone numbers of all 50 support agents—those agents take breaks, end shifts, or quit (Pods dying).

Instead, you call a single **1-800 Number (The Service)**. The 1-800 number never changes. When you dial it, an automated switchboard (The Kubernetes proxy) routes your call to whatever agent is currently sitting at a desk (a healthy Pod).

A Kubernetes **Service** provides a stable IP address and DNS name. A **ClusterIP** Service provides an internal 1-800 number (only reachable from *inside* the cluster), while a **NodePort** or **LoadBalancer** provides an external number (reachable from the outside world).

#### 3. Complete Runnable Code
Let's create an Internal Microservice Communication Service. We will deploy 3 backend Pods and put a Service in front of them.

**backend-service.yaml**
```yaml
# 1. The Deployment (The Agents)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-backend
spec:
  replicas: 3
  selector:
    matchLabels:
      app: order-api
  template:
    metadata:
      labels:
        app: order-api
    spec:
      containers:
      - name: api
        image: nginx:1.25-alpine # Using nginx to simulate an API
        ports:
        - containerPort: 80

---
# 2. The Service (The 1-800 Number)
apiVersion: v1
kind: Service
metadata:
  name: order-service
spec:
  type: ClusterIP
  selector:
    app: order-api
  ports:
  - port: 80
    targetPort: 80
```

To run this:
```bash
kubectl apply -f backend-service.yaml
kubectl get svc
```

#### 4. Progressive Step-by-Step Breakdown

**Step 1: Multiple Resources in One File**
Notice the `---`. In Kubernetes YAML, this separates distinct resources. We are creating both a Deployment and a Service in a single file.

**Step 2: Service Metadata**
```yaml
apiVersion: v1
kind: Service
metadata:
  name: order-service
```
The `name` of the Service is critical. In Kubernetes, an internal DNS record is automatically created using this name. Other Pods in the cluster can simply make an HTTP request to `http://order-service` and Kubernetes will resolve it!

**Step 3: The Type and Selector**
```yaml
spec:
  type: ClusterIP
  selector:
    app: order-api
```
`type: ClusterIP` means this service is internal-only. The `selector` is how the Service knows which Pods to route traffic to. It constantly scans the cluster for Pods that have the label `app: order-api`. Notice how this perfectly matches the `labels` in the Deployment template.

**Step 4: Port Mapping**
```yaml
  ports:
  - port: 80
    targetPort: 80
```
- `port`: The port the Service listens on (e.g., the port you hit when requesting `http://order-service:80`).
- `targetPort`: The port the actual Container is listening on inside the Pod.

#### 5. ASCII Data Flow
```
[ Frontend Pod wants to fetch Orders ]

Request -> HTTP GET http://order-service:80
                     |
                     v
           [ order-service (ClusterIP) ]
           (Stable IP: 10.96.0.50)
                     |
        (Load balances round-robin)
        /            |             \
       v             v              v
[Pod 1 (10.1.1.2)] [Pod 2 (10.1.1.3)] [Pod 3 (10.2.1.8)]
 (If Pod 2 dies, Service stops sending traffic there)
```

#### 6. Noob Trap vs Pro Tip
**Noob Trap:** Using `NodePort` to expose your web application to the public internet in production. NodePorts open a high-numbered port (30000-32767) directly on your physical servers, bypassing advanced routing and causing security risks.
**Pro Tip:** Use `ClusterIP` for 99% of your microservices. Only expose apps to the internet using an `Ingress` controller (covered in the next lesson), which acts as a secure, smart reverse-proxy at the edge of your cluster.

### Phase B: Challenges

#### Level 1: Warm-Up
**Task:** Create a Service named `inventory-svc` of type `ClusterIP` that listens on port `8080` but routes traffic to targetPort `3000`. It should route traffic to Pods with the label `component: inventory-db`.
<details>
<summary>Hint</summary>
Define <code>apiVersion: v1</code> and <code>kind: Service</code>. Set the <code>type</code>, <code>selector</code>, <code>port</code>, and <code>targetPort</code> as requested.
</details>

<details>
<summary>Solution Walkthrough</summary>

```yaml
apiVersion: v1
kind: Service
metadata:
  name: inventory-svc
spec:
  type: ClusterIP
  selector:
    component: inventory-db
  ports:
  - port: 8080
    targetPort: 3000
```
Any Pod in the cluster can now make a request to `http://inventory-svc:8080`.
</details>

#### Level 2: Real-World
**Task:** You are debugging a connection issue. You have a Service named `cache-service` selecting label `db: redis`. How can you verify that the Service has successfully found and linked to the underlying Pods?
<details>
<summary>Hint</summary>
Services route traffic to "Endpoints". You can inspect the endpoints created by a service using a `kubectl get` command.
</details>

<details>
<summary>Solution Walkthrough</summary>
Run <code>kubectl get endpoints cache-service</code> or <code>kubectl describe svc cache-service</code>.
If the `Endpoints` list is `<none>`, it means your Service's `selector` labels do not match the labels on any running Pods. This is the #1 cause of networking issues in K8s!
</details>

#### Level 3: Boss Level (Cumulative)
**Task:** Combine Deployments and Services. Create a Deployment named `cart-api` running `2` replicas of `nginx:alpine` with the label `app: shopping-cart`. Then, create a `NodePort` Service named `cart-ext-svc` that exposes the `cart-api` Pods to the outside world. The Service should listen on port `80`, target port `80`, and force the NodePort to be exactly `30050`.
<details>
<summary>Hint</summary>
Use `---` to put both resources in one file. For the Service, change the `type` to `NodePort`. Under the `ports` array, add a `nodePort: 30050` field alongside `port` and `targetPort`.
</details>

<details>
<summary>Solution Walkthrough</summary>

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: cart-api
spec:
  replicas: 2
  selector:
    matchLabels:
      app: shopping-cart
  template:
    metadata:
      labels:
        app: shopping-cart
    spec:
      containers:
      - name: web
        image: nginx:alpine
        ports:
        - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: cart-ext-svc
spec:
  type: NodePort
  selector:
    app: shopping-cart
  ports:
  - port: 80
    targetPort: 80
    nodePort: 30050
```
By accessing `http://<ANY-NODE-IP>:30050` from your web browser, K8s will accept the traffic on that high port and route it internally to the Service, which load balances it to one of your two Nginx Pods.
</details>
