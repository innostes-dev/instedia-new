# Module 02: Networking & Ingress (Connecting to the Internet)
## 2.2 Ingress Controllers and TLS

### Phase A: Core Concept

#### 1. Real-World Pain Point (The Why)
You have three different microservices: a React frontend, a Node API, and a Python reporting service. You want them all accessible under one domain:
- `mycompany.com/` routes to React.
- `mycompany.com/api` routes to Node.
- `mycompany.com/reports` routes to Python.
If you use standard Kubernetes LoadBalancer Services, you have to provision a separate, expensive cloud Load Balancer (with a separate IP) for *each* service. Managing multiple IPs, routing rules, and SSL/TLS certificates across different Load Balancers is a nightmare and highly cost-inefficient.

#### 2. Plain English Metaphor (The What)
Imagine a massive office building. A Service (LoadBalancer type) is like giving every single department in the building its own dedicated front door and security guard facing the street. It's expensive and chaotic.

An **Ingress Controller** is the grand main lobby of the building. It has one single front door (one IP address) and a smart receptionist. When a visitor walks in and says, "I'm looking for the Sales department" (`/api`), the receptionist checks their directory (The **Ingress Resource**) and points them to the correct internal hallway (a ClusterIP Service). Furthermore, the receptionist checks everyone's ID and handles security (SSL/TLS termination) at the front door, so the internal departments don't have to worry about it.

#### 3. Complete Runnable Code
Let's create a Production Domain Routing Ingress.
*Note: This requires an Ingress Controller (like Nginx) installed on your cluster to function.*

**production-ingress.yaml**
```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: company-main-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
  - host: www.mycompany.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: node-api-service
            port:
              number: 80
      - path: /
        pathType: Prefix
        backend:
          service:
            name: react-frontend-service
            port:
              number: 80
```

#### 4. Progressive Step-by-Step Breakdown

**Step 1: The API Group and Annotations**
```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: company-main-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
```
Ingress belongs to the `networking.k8s.io` API. We use `annotations` to pass specific configurations to the underlying controller (e.g., Nginx). Here, `rewrite-target` tells Nginx to strip the `/api` prefix before sending the request to the backend service.

**Step 2: Defining the Host and Paths**
```yaml
spec:
  ingressClassName: nginx
  rules:
  - host: www.mycompany.com
    http:
      paths:
```
We specify which controller to use (`nginx`). The `rules` array defines routing based on the `host` (domain name). We tell it to intercept HTTP traffic destined for `www.mycompany.com`.

**Step 3: Routing to Backends**
```yaml
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: node-api-service
            port:
              number: 80
```
For traffic hitting the `/api` path, route it to a standard ClusterIP Service named `node-api-service` on port 80. The Ingress acts as the smart bridge between the public internet and your internal `ClusterIP` services.

#### 5. ASCII Data Flow
```
Internet User -> HTTPS GET www.mycompany.com/api/users
                         |
                (Public Load Balancer IP)
                         v
            [ NGINX Ingress Controller ]
            (Terminates SSL, Reads Rules)
                         |
        Matches `/api` -> Routes to `node-api-service`
                         |
                         v
       [ node-api-service (ClusterIP: 10.96.x.x) ]
                         |
                         v
              [ Node.js Backend Pod ]
```

#### 6. Noob Trap vs Pro Tip
**Noob Trap:** Hardcoding SSL certificates into your Docker images or individual Pods. Managing expiration dates this way guarantees an eventual outage.
**Pro Tip:** Use **Cert-Manager** alongside your Ingress Controller. You can add a few lines to your Ingress YAML, and Cert-Manager will automatically talk to Let's Encrypt, fetch a free TLS certificate, mount it to your Ingress Controller, and renew it 30 days before it expires—completely hands-free!

#### Level 2: Real-World
**Task:** You have two domains: `api.startup.io` and `admin.startup.io`. Create an Ingress that routes `api.startup.io/v1` to `core-api-svc` (port 80) and `admin.startup.io/` to `admin-dashboard-svc` (port 3000).
<details>
<summary>Hint</summary>
The `rules` array can contain multiple items. Create one item for `host: api.startup.io` and a second distinct item for `host: admin.startup.io`.
</details>

<details>
<summary>Solution Walkthrough</summary>

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: multi-domain-ingress
spec:
  ingressClassName: nginx
  rules:
  - host: api.startup.io
    http:
      paths:
      - path: /v1
        pathType: Prefix
        backend:
          service:
            name: core-api-svc
            port:
              number: 80
  - host: admin.startup.io
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: admin-dashboard-svc
            port:
              number: 3000
```
</details>

#### Level 3: Boss Level (Cumulative)
**Task:** Secure the `blog-ingress` from Level 1 using TLS. You have a Kubernetes Secret named `blog-tls-cert` that contains your SSL certificate and private key. Modify the Ingress manifest to apply this TLS certificate to the `blog.example.com` host.
<details>
<summary>Hint</summary>
Add a `tls` array at the top level of the `spec` block (same level as `rules`). The `tls` block requires `hosts` (an array) and a `secretName`.
</details>

<details>
<summary>Solution Walkthrough</summary>

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: blog-ingress
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - blog.example.com
    secretName: blog-tls-cert
  rules:
  - host: blog.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: wordpress-svc
            port:
              number: 8080
```
By adding the `tls` block, the Ingress Controller will intercept HTTPS traffic on port 443, decrypt it using the provided secret, and forward plain HTTP to your internal `wordpress-svc`.
</details>
