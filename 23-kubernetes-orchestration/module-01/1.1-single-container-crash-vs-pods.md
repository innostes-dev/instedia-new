# Module 01: When Docker is Not Enough (Why K8s Exists)
## 1.1 Single Container Crash vs Pods

### Phase A: Core Concept

#### 1. Real-World Pain Point (The Why)
Imagine this: It’s 3:00 AM on Black Friday. You're running your e-commerce API inside a single Docker container. A sudden spike in traffic causes a memory leak, and the container crashes. Your site goes down, and you lose thousands of dollars per minute while you manually SSH into the server to run `docker restart my-api`. Docker alone doesn't automatically heal itself or reschedule failed containers on other healthy machines. You need something that constantly watches your application and brings it back to life instantly.

#### 2. Plain English Metaphor (The What)
Think of a single Docker container like a musician playing in the subway. If they get sick, the music stops.

Kubernetes is like a **Symphony Conductor (The Control Plane)**. The conductor doesn't play the instruments, but they manage the orchestra. If a musician (a container) stops playing, the conductor notices immediately and brings in a replacement. In Kubernetes, the conductor manages **Pods**. A Pod is the smallest deployable unit—think of it as a small soundproof room that holds one or more musicians (containers) playing together.

#### 3. Complete Runnable Code
Let's create our first self-healing Pod using a simple Nginx web server.

**nginx-pod.yaml**
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: self-healing-web-pod
  labels:
    app: web-store
spec:
  containers:
  - name: nginx-server
    image: nginx:1.25-alpine
    ports:
    - containerPort: 80
```

To run this on a Kubernetes cluster:
```bash
# Apply the configuration
kubectl apply -f nginx-pod.yaml

# Verify the pod is running
kubectl get pods
```

#### 4. Progressive Step-by-Step Breakdown

**Step 1: The API Version and Kind**
```yaml
apiVersion: v1
kind: Pod
```
Every Kubernetes manifest starts by telling the API server what type of resource we want to create. Here, we are explicitly stating we want to create a `Pod` using the core `v1` API.

**Step 2: Metadata (Who am I?)**
```yaml
metadata:
  name: self-healing-web-pod
  labels:
    app: web-store
```
We give our Pod a unique `name`. The `labels` act like sticky notes; later, other resources (like Services or Deployments) will use these labels to find and manage this specific Pod.

**Step 3: Specification (What should it do?)**
```yaml
spec:
  containers:
  - name: nginx-server
    image: nginx:1.25-alpine
    ports:
    - containerPort: 80
```
The `spec` defines the desired state. We define a list of `containers` that live inside this Pod. We name the container, specify the exact image version (`nginx:1.25-alpine` is better than `latest`), and expose port 80 where the server listens.

#### 5. ASCII Data Flow
```
[ 3:00 AM Crash Scenario ]

Without K8s:
Traffic --> [ Docker Container (CRASH!) ]
Result: ❌ 502 Bad Gateway (Until manual restart)

With K8s:
Traffic --> [ Kubernetes Cluster ]
                 |
                 v
         [ K8s Control Plane ] (Constantly watching)
                 | (Detects Crash)
                 v
         [ Node 1: Pod (CRASH!) ] ---> Control Plane kills and reschedules
                 |
                 v
         [ Node 2: New Pod (Running) ]
Result: ✅ Minimal downtime, automatic recovery
```

#### 6. Noob Trap vs Pro Tip
**Noob Trap:** Using raw Pods in production. If a Node (the physical server running the Pod) dies, a raw Pod will NOT automatically be rescheduled to another Node.
**Pro Tip:** Never deploy raw Pods in production. Always wrap them in higher-level controllers like `Deployments` (which we will learn next), which guarantee that if a Node dies, the Pod is recreated elsewhere.

### Phase B: Challenges

#### Level 1: Warm-Up
**Task:** Write a `Pod` manifest named `cache-pod` running a `redis:7.0` container. Expose port `6379`.
<details>
<summary>Hint</summary>
Use the <code>nginx-pod.yaml</code> as a template. Change the <code>metadata.name</code>, <code>container.name</code>, <code>image</code>, and <code>containerPort</code>.
</details>

<details>
<summary>Solution Walkthrough</summary>
Create a file named <code>redis-pod.yaml</code>:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: cache-pod
spec:
  containers:
  - name: redis-cache
    image: redis:7.0
    ports:
    - containerPort: 6379
```
Apply with <code>kubectl apply -f redis-pod.yaml</code>.
</details>

#### Level 2: Real-World
**Task:** In the real world, you sometimes need two containers tightly coupled in one Pod (e.g., a web server and a log forwarder). Create a Pod named `multi-container-pod` containing an `nginx:alpine` container and a `busybox` container that just sleeps (simulate a sidecar).
<details>
<summary>Hint</summary>
The <code>containers</code> field under <code>spec</code> is a list (array). You can define multiple items starting with a hyphen <code>-</code>. For the busybox container, use <code>command: ["sleep", "3600"]</code>.
</details>

<details>
<summary>Solution Walkthrough</summary>

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: multi-container-pod
spec:
  containers:
  - name: web-server
    image: nginx:alpine
    ports:
    - containerPort: 80
  - name: sidecar-logger
    image: busybox
    command: ["sleep", "3600"]
```
This demonstrates the Sidecar Pattern. The busybox container represents a sidecar that could share a volume and read logs from the nginx container.
</details>

#### Level 3: Boss Level
**Task:** Create a Pod named `secure-db-pod` running `postgres:15`. You must set an environment variable `POSTGRES_PASSWORD=supersecret` to allow the container to start, otherwise it will crash in a `CrashLoopBackOff`.
<details>
<summary>Hint</summary>
Add an <code>env</code> array to your container spec. Each item needs a <code>name</code> and a <code>value</code>.
</details>

<details>
<summary>Solution Walkthrough</summary>

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: secure-db-pod
spec:
  containers:
  - name: postgres-db
    image: postgres:15
    env:
    - name: POSTGRES_PASSWORD
      value: "supersecret"
    ports:
    - containerPort: 5432
```
If you forget the environment variable, the Postgres image immediately exits, and Kubernetes will constantly try to restart it, causing a `CrashLoopBackOff` state. Adding the `env` block fixes this.
</details>
