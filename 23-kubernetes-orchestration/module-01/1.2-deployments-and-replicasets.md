# Module 01: When Docker is Not Enough (Why K8s Exists)
## 1.2 Deployments and ReplicaSets

### Phase A: Core Concept

#### 1. Real-World Pain Point (The Why)
In the previous lesson, we learned that a raw Pod won't survive a complete server (Node) failure. Imagine your Black Friday sale is booming, and your single Node loses power. The raw Pod goes down with it. Furthermore, a single Pod can only handle so much traffic. What happens when you need to run 5 copies of your API to handle the load? Manually writing 5 Pod manifests and applying them is tedious and error-prone. And what if one of those 5 crashes? You need a system that ensures exactly 5 copies are running at all times.

#### 2. Plain English Metaphor (The What)
If a Pod is a single musician, a **ReplicaSet** is an HR manager whose only job is ensuring there are exactly 5 musicians on stage at all times. If one faints, HR hires another instantly.

A **Deployment** is the CEO who commands the HR manager. You tell the CEO, "I want 5 musicians playing Version 1 of the song." The CEO tells HR (the ReplicaSet) to make it happen. Later, you say, "Actually, switch to Version 2." The CEO manages the transition gracefully, bringing down Version 1 musicians while bringing up Version 2 musicians.

**Desired State vs. Actual State:** You declare the Desired State (e.g., "5 replicas"). The Kubernetes Control Plane constantly compares the Actual State to your Desired State and takes action to correct any drift.

#### 3. Complete Runnable Code
Let's create a Resilient High-Availability API Deployment.

**api-deployment.yaml**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api-deployment
  labels:
    app: payment-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: payment-api
  template:
    metadata:
      labels:
        app: payment-api
    spec:
      containers:
      - name: payment-api-container
        image: nginx:1.25-alpine
        ports:
        - containerPort: 80
```

To run this:
```bash
kubectl apply -f api-deployment.yaml
kubectl get deployments
kubectl get pods
```

#### 4. Progressive Step-by-Step Breakdown

**Step 1: Deployment Metadata**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api-deployment
  labels:
    app: payment-api
```
Unlike Pods (which use `v1`), Deployments belong to the `apps/v1` API group. We name our deployment `payment-api-deployment`.

**Step 2: Desired State & Selector**
```yaml
spec:
  replicas: 3
  selector:
    matchLabels:
      app: payment-api
```
Here is the magic. `replicas: 3` defines our Desired State. The `selector` tells the Deployment *how* to find the Pods it is supposed to manage. It will look for any Pods with the label `app: payment-api`.

**Step 3: The Pod Template**
```yaml
  template:
    metadata:
      labels:
        app: payment-api
    spec:
      containers:
      - name: payment-api-container
        image: nginx:1.25-alpine
        ports:
        - containerPort: 80
```
The `template` is essentially a nested Pod manifest (notice it lacks `apiVersion` and `kind` because those are implied). Crucially, the `labels` here (`app: payment-api`) MUST match the `selector.matchLabels` defined above, or the Deployment won't recognize the Pods it just created!

#### 5. ASCII Data Flow
```
[ Defining Desired State ]

User -> `kubectl apply -f deployment.yaml` (Desired: 3 Replicas)
                 |
                 v
[ K8s Control Plane (Deployment Controller) ]
                 | Creates
                 v
      [ ReplicaSet Controller ]
                 | Spawns
    ----------------------------
    |            |             |
 [ Pod 1 ]    [ Pod 2 ]     [ Pod 3 ]
 (Node A)     (Node A)      (Node B)

*If Node A crashes, destroying Pod 1 & 2:*
Actual State: 1 Pod. Desired State: 3 Pods.
Control Plane detects drift -> Spawns 2 new Pods on Node B.
```

#### 6. Noob Trap vs Pro Tip
**Noob Trap:** Using the `latest` image tag (e.g., `image: my-app:latest`). If a Pod restarts, Kubernetes might pull a completely new version of your code unexpectedly, breaking production.
**Pro Tip:** Always pin specific image versions (e.g., `nginx:1.25.3`). Furthermore, if you edit a Deployment to change the image version, Kubernetes automatically handles a rolling update, meaning zero downtime!

### Phase B: Challenges

#### Level 1: Warm-Up
**Task:** Create a Deployment named `frontend-deploy` that runs `2` replicas of an `httpd:2.4` image.
<details>
<summary>Hint</summary>
Change the <code>kind</code> to <code>Deployment</code>. Ensure your <code>matchLabels</code> matches the labels in your Pod <code>template</code>. Set <code>replicas: 2</code>.
</details>

<details>
<summary>Solution Walkthrough</summary>

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend-deploy
spec:
  replicas: 2
  selector:
    matchLabels:
      tier: frontend
  template:
    metadata:
      labels:
        tier: frontend
    spec:
      containers:
      - name: apache-server
        image: httpd:2.4
        ports:
        - containerPort: 80
```
</details>

#### Level 2: Real-World
**Task:** Scale the `frontend-deploy` from 2 replicas to 5 without modifying the original YAML file, using an imperative kubectl command. Then, simulate a crash by deleting one of the pods manually. What happens?
<details>
<summary>Hint</summary>
Look up the <code>kubectl scale</code> command. To delete a pod, use <code>kubectl delete pod &lt;pod-name&gt;</code>.
</details>

<details>
<summary>Solution Walkthrough</summary>
1. Scale the deployment: <code>kubectl scale deployment frontend-deploy --replicas=5</code>
2. View pods: <code>kubectl get pods</code>. You will see 5 pods running.
3. Simulate crash: <code>kubectl delete pod &lt;frontend-pod-name&gt;</code>
4. Immediately run <code>kubectl get pods</code>. You will see Kubernetes terminating the deleted pod, but instantly starting a new one to maintain the desired state of 5.
</details>

#### Level 3: Boss Level (Cumulative)
**Task:** Create a Deployment named `backend-worker`. It should run `4` replicas. The Pod template should use the Sidecar Pattern we learned in the previous lesson: one container running `node:18` (simulating a worker, use `command: ["sleep", "3600"]`) and a second container running `busybox` (simulating a log parser, use `command: ["sleep", "3600"]`). If the deployment is applied, 4 Pods should be created, each containing 2 containers.
<details>
<summary>Hint</summary>
Combine the Deployment structure (replicas, selector, template) with the multi-container spec from Module 1.1 Level 2.
</details>

<details>
<summary>Solution Walkthrough</summary>

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend-worker
spec:
  replicas: 4
  selector:
    matchLabels:
      app: worker
  template:
    metadata:
      labels:
        app: worker
    spec:
      containers:
      - name: node-worker
        image: node:18
        command: ["sleep", "3600"]
      - name: log-parser
        image: busybox
        command: ["sleep", "3600"]
```
When you run <code>kubectl get pods</code>, you will see 4 pods. Under the <code>READY</code> column, it will show <code>2/2</code>, indicating both containers in each Pod are running successfully.
</details>
