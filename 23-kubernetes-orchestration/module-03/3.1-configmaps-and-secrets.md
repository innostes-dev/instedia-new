# Module 03: Storage, Configs & Auto-Scaling
## 3.1 ConfigMaps and Secrets

### Phase A: Core Concept

#### 1. Real-World Pain Point (The Why)
You have a Node.js microservice. In development, it connects to `localhost:5432` for the database. In production, it connects to `prod-db.aws.com:5432` with a complex password. If you hardcode these values into your Docker image, you have to build and maintain multiple images for every environment (Dev, QA, Prod). Worse, if you hardcode the password, anyone who can pull your image can steal your database credentials. You need a way to inject environment-specific configuration and sensitive passwords into your Pods at runtime, without altering the container image itself.

#### 2. Plain English Metaphor (The What)
Imagine you are building a generic coffee machine (the Container Image). The machine knows *how* to make coffee, but it doesn't know *what kind* of coffee you want today.

A **ConfigMap** is like a post-it note stuck to the machine that says "Make it a medium roast, no sugar." It holds non-sensitive configuration data (URLs, feature flags, UI themes).

A **Secret** is a locked safe next to the machine containing the special key to access the premium coffee beans. It holds sensitive data (Passwords, API Tokens, SSH keys).

You can inject both into your Pods either as Environment Variables or as physical files mounted on a Virtual Volume.

#### 3. Complete Runnable Code
Let's inject configuration and a secret password into a backend Pod.

**config-and-secret.yaml**
```yaml
# 1. The ConfigMap (Non-Sensitive)
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  DB_HOST: "prod-db.internal.cloud"
  LOG_LEVEL: "INFO"

---
# 2. The Secret (Sensitive - values MUST be base64 encoded)
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
type: Opaque
data:
  # echo -n "supersecret" | base64
  DB_PASSWORD: c3VwZXJzZWNyZXQ=

---
# 3. The Pod consuming them
apiVersion: v1
kind: Pod
metadata:
  name: backend-api
spec:
  containers:
  - name: api
    image: node:18-alpine
    command: ["node", "-e", "console.log(process.env.DB_HOST, process.env.DB_PASSWORD); setInterval(() => {}, 1000);"]
    envFrom:
    - configMapRef:
        name: app-config
    - secretRef:
        name: db-credentials
```

#### 4. Progressive Step-by-Step Breakdown

**Step 1: Creating the ConfigMap**
```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  DB_HOST: "prod-db.internal.cloud"
```
We define a ConfigMap named `app-config`. The `data` block is a simple key-value store. These are plain text strings.

**Step 2: Creating the Secret**
```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
type: Opaque
data:
  DB_PASSWORD: c3VwZXJzZWNyZXQ=
```
Secrets look similar, but `type: Opaque` indicates generic secret data. **Crucially**, values in the `data` block of a Secret MUST be base64 encoded. Base64 is not encryption; it's just encoding to handle special characters.

**Step 3: Injecting via envFrom**
```yaml
    envFrom:
    - configMapRef:
        name: app-config
    - secretRef:
        name: db-credentials
```
Inside the Pod spec, instead of defining `env` one by one, we use `envFrom`. This tells Kubernetes: "Take every single key-value pair from `app-config` and `db-credentials` and inject them as Environment Variables into this container."

#### 5. ASCII Data Flow
```
[ K8s etcd Database ]
      |
      |-- Holds ConfigMap (DB_HOST)
      |-- Holds Secret (DB_PASSWORD)
      |
      v
[ Kubelet on Node ]
      | (Reads configs, decrypts secrets)
      v
[ Container Runtime ]
      | (Injects as Environment Variables)
      v
[ Pod: backend-api ]
Process runs with:
$DB_HOST = "prod-db.internal.cloud"
$DB_PASSWORD = "supersecret"
```

#### 6. Noob Trap vs Pro Tip
**Noob Trap:** Assuming base64 encoding makes a Secret secure. Anyone with `kubectl get secret` permissions can read the base64 string and decode it instantly.
**Pro Tip:** Use a tool like **SealedSecrets** or integrate with **HashiCorp Vault / AWS Secrets Manager** in production. These tools encrypt the secret at rest and only decrypt it inside the Kubernetes cluster, allowing you to safely store your YAML files in Git (GitOps).

### Phase B: Challenges

#### Level 1: Warm-Up
**Task:** Create a ConfigMap named `ui-theme` with a key `THEME_COLOR` and value `dark-mode`. Create a Pod named `frontend` (image `nginx:alpine`) that loads this specific key as an environment variable named `COLOR`.
<details>
<summary>Hint</summary>
Instead of `envFrom`, use the `env` array. For the `valueFrom` property, use `configMapKeyRef`.
</details>

<details>
<summary>Solution Walkthrough</summary>

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: ui-theme
data:
  THEME_COLOR: "dark-mode"
---
apiVersion: v1
kind: Pod
metadata:
  name: frontend
spec:
  containers:
  - name: web
    image: nginx:alpine
    env:
    - name: COLOR
      valueFrom:
        configMapKeyRef:
          name: ui-theme
          key: THEME_COLOR
```
</details>

#### Level 2: Real-World
**Task:** Create a Secret named `api-key` containing a key `token` with the base64 encoded value of `my-secret-token`.
<details>
<summary>Hint</summary>
Run `echo -n "my-secret-token" | base64` in your terminal to get the encoded value.

apiVersion: v1

#### Level 3: Boss Level (Cumulative)
**Task:** Environment variables are great, but some apps expect a physical configuration file (like `nginx.conf`). Create a ConfigMap named `nginx-config` with a key `default.conf` containing basic nginx config text. Create a Deployment of 2 Nginx pods. Use a **Volume** and a **VolumeMount** to mount that ConfigMap as a file at the path `/etc/nginx/conf.d/default.conf` inside the containers.
<details>
<summary>Hint</summary>
In the Pod template `spec`, add a `volumes` array mapping to the ConfigMap. In the `containers` array, add a `volumeMounts` array referencing the volume by name and setting the `mountPath` and `subPath`.
</details>

<details>
<summary>Solution Walkthrough</summary>

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: nginx-config
data:
  default.conf: |
    server {
        listen       80;
        server_name  localhost;
        location / {
            return 200 'ConfigMap Loaded Successfully!';
            add_header Content-Type text/plain;
        }
    }
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: custom-nginx
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx:alpine
        volumeMounts:
        - name: config-volume
          mountPath: /etc/nginx/conf.d/default.conf
          subPath: default.conf
      volumes:
      - name: config-volume
        configMap:
          name: nginx-config
```
This is how you dynamically inject files (like configurations or TLS certificates) into running pods!
</details>
