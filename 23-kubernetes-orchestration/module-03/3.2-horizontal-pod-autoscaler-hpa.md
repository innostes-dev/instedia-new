# Module 03: Storage, Configs & Auto-Scaling
## 3.2 Horizontal Pod Autoscaler (HPA)

### Phase A: Core Concept

#### 1. Real-World Pain Point (The Why)
Your AI Inference API normally receives 10 requests per minute, so 2 Pods handle it perfectly. Suddenly, a tech influencer tweets about your app, and traffic spikes to 10,000 requests per minute. The 2 Pods max out their CPU, requests start timing out, and the system crashes.
You could manually run `kubectl scale deployment ai-api --replicas=30`, but you were asleep. When the traffic dies down 3 hours later, you are now paying for 30 Pods doing nothing. You need a system that automatically adds Pods when CPU/Memory is high, and removes them when it's low.

#### 2. Plain English Metaphor (The What)
Imagine you manage a grocery store checkout area (The Deployment).
Normally, you have 2 cashiers working (2 Pods).
The **Metrics Server** is a camera watching the cashiers, noting how fast they are scanning items (measuring CPU usage).
The **Horizontal Pod Autoscaler (HPA)** is the Store Manager. You tell the manager: "If the cashiers are ever working at 80% of their maximum speed, page another cashier from the back room (Scale Up). If they drop below 50% speed for a few minutes, send someone on break (Scale Down). Never exceed 10 cashiers, and never drop below 2."

#### 3. Complete Runnable Code
Let's create an Auto-Scaling AI Inference Pod Fleet.
*Note: This requires a Metrics Server installed on your cluster.*

**hpa-deployment.yaml**
```yaml
# 1. The Deployment MUST have resource requests defined!
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ai-inference-api
spec:
  replicas: 2
  selector:
    matchLabels:
      app: ai-api
  template:
    metadata:
      labels:
        app: ai-api
    spec:
      containers:
      - name: inference-engine
        image: python:3.9-slim
        command: ["python", "-c", "while True: pass"] # Simulates high CPU load
        resources:
          requests:
            cpu: "100m" # 100 millicores (0.1 CPU)
          limits:
            cpu: "200m"

---
# 2. The Horizontal Pod Autoscaler
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: ai-api-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: ai-inference-api
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50
```

#### 4. Progressive Step-by-Step Breakdown

**Step 1: Resource Requests (The Prerequisite)**
```yaml
        resources:
          requests:
            cpu: "100m"
          limits:
            cpu: "200m"
```
The HPA **cannot function** unless the underlying Pods declare their CPU/Memory requirements. `requests` is what the Pod needs to start (the HPA calculates percentages based on this number). `limits` is the absolute maximum it is allowed to use before being throttled.

**Step 2: Linking HPA to Deployment**
```yaml
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: ai-inference-api
```
The `scaleTargetRef` points the HPA to the specific Deployment it is supposed to manage.

**Step 3: Defining the Rules**
```yaml
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50
```
We set boundaries (`min 2`, `max 10`). The metric rule states: "Keep the average CPU utilization across all Pods at 50%." If the average hits 75%, the HPA will add Pods until the average drops back down to 50%.

#### 5. ASCII Data Flow
```
[ High Traffic Arrives ]
        |
        v
[ Pod 1 (CPU: 90%) ]  [ Pod 2 (CPU: 90%) ]
        |
[ Metrics Server notices Average CPU is 90% ]
        |
[ HPA compares 90% to Target 50% ]
        |
[ HPA calculates: Need more Pods! ] -> HPA updates Deployment Replicas to 4
        |
[ Deployment spawns Pod 3 & Pod 4 ]
        |
(Traffic spreads out via Service)
        |
[ Pod 1 (45%) ] [ Pod 2 (45%) ] [ Pod 3 (45%) ] [ Pod 4 (45%) ]
(System is stable)
```

#### 6. Noob Trap vs Pro Tip
**Noob Trap:** Setting HPA but forgetting to set CPU `requests` on your Pod template. The HPA will show `CPU: <unknown>/50%` and will never scale.
**Pro Tip:** Auto-scaling takes time (often 1-2 minutes for new Pods to start). If your traffic spikes instantly (e.g., flash sales), HPA might be too slow. In those cases, schedule a manual scale-up *before* the event, or use advanced event-driven autoscalers like KEDA.

#### Level 3: Boss Level (Cumulative)
**Task:** Combine HPA with ConfigMaps. Create a deployment `app-engine` that mounts a ConfigMap `app-settings` as an environment variable `MAX_THREADS`. Ensure the deployment requests `100m` CPU. Then, use an imperative `kubectl` command to generate an HPA that targets 60% CPU and scales from 1 to 5 replicas for this deployment.
<details>
<summary>Hint</summary>
Write the YAML for the ConfigMap and Deployment. Then look up the `kubectl autoscale` command.
</details>

<details>
<summary>Solution Walkthrough</summary>
First, apply the YAML:
```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-settings
data:
  MAX_THREADS: "4"
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app-engine
spec:
  replicas: 1
  selector:
    matchLabels:
      app: engine
  template:
    metadata:
      labels:
        app: engine
    spec:
      containers:
      - name: main
        image: nginx
        resources:
          requests:
            cpu: 100m
        envFrom:
        - configMapRef:
            name: app-settings
```
After applying the YAML, run:
`kubectl autoscale deployment app-engine --cpu-percent=60 --min=1 --max=5`
This imperative command creates the HPA without needing a YAML file!
</details>
