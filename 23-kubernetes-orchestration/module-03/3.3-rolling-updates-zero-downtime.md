# Module 03: Storage, Configs & Auto-Scaling
## 3.3 Rolling Updates & Zero Downtime

### Phase A: Core Concept

#### 1. Real-World Pain Point (The Why)
Your company just released v2 of the frontend app. To deploy it, you delete the v1 Pods and start the v2 Pods. For about 30 seconds, there are no Pods running. Every user currently on your site gets a "502 Bad Gateway" error and loses their shopping cart. In a modern cloud environment, downtime for deployments is unacceptable. You need a way to gradually replace old Pods with new Pods, ensuring that traffic is never dropped and only routed to Pods that are fully ready to accept it.

#### 2. Plain English Metaphor (The What)
Imagine an airplane in mid-flight (Production Traffic) that needs its 4 engines (Pods) replaced with newer models.
If you turn off all 4 engines at once, the plane crashes (Downtime).

A **Rolling Update** is like turning off Engine 1, and attaching the new V2 Engine 1. You wait for the new engine to spin up and prove it works. Once it's running perfectly, you move to Engine 2, then Engine 3. The plane keeps flying the entire time.

**Liveness & Readiness Probes** are the mechanic's checklist. A **Liveness Probe** checks "Is the engine on fire?" (If yes, kill it and restart). A **Readiness Probe** checks "Is the engine providing thrust?" (If yes, start sending fuel/traffic to it). A Deployment won't shut down an old Pod until the new Pod passes its Readiness Probe.

#### 3. Complete Runnable Code
Let's create a Zero-Downtime Rolling Update Pipeline.

**rolling-update.yaml**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend-rolling
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1 # Never take down more than 1 pod at a time
      maxSurge: 1       # Never build more than 1 extra pod over the desired 4
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: ui
        image: nginx:1.24 # Imagine we want to upgrade this to 1.25 later
        ports:
        - containerPort: 80
        # Check if the app is frozen/dead
        livenessProbe:
          httpGet:
            path: /
            port: 80
          initialDelaySeconds: 5
          periodSeconds: 10
        # Check if the app is ready to receive traffic
        readinessProbe:
          httpGet:
            path: /
            port: 80
          initialDelaySeconds: 5
          periodSeconds: 5
```

#### 4. Progressive Step-by-Step Breakdown

**Step 1: The RollingUpdate Strategy**
```yaml
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1
      maxSurge: 1
```
We define *how* the update happens.
`maxUnavailable: 1` guarantees that out of 4 replicas, at least 3 will always be up during an update.
`maxSurge: 1` means K8s is allowed to temporarily run 5 pods (4 desired + 1 surge) while swapping versions.

**Step 2: Liveness Probe (Survival)**
```yaml
        livenessProbe:
          httpGet:
            path: /
            port: 80
          initialDelaySeconds: 5
          periodSeconds: 10
```
Kubernetes will ping `http://pod-ip:80/` every 10 seconds. If the app returns a 500 error or hangs, Kubernetes assumes the app is deadlocked, kills the container, and restarts it.

**Step 3: Readiness Probe (Traffic Control)**
```yaml
        readinessProbe:
          httpGet:
            path: /
            port: 80
          initialDelaySeconds: 5
          periodSeconds: 5
```
Kubernetes will ping this endpoint every 5 seconds. If it returns 200 OK, the Pod is marked `READY`, and the Service starts sending user traffic to it. **During a Rolling Update, Kubernetes waits for the new v2 Pod to pass this check before it terminates the old v1 Pod.**

#### 5. ASCII Data Flow
```
[ Trigger Update: kubectl set image deployment frontend-rolling ui=nginx:1.25 ]

[ V1 Pod ] [ V1 Pod ] [ V1 Pod ] [ V1 Pod ] (4/4 Ready)
       | (maxSurge kicks in)
       v
[ V2 Pod ] (Starts up) -> (Fails Readiness Probe initially)
(Traffic still flows ONLY to the 4 V1 Pods)
       |
       v
[ V2 Pod ] (Passes Readiness Probe!) -> (Now 5 Pods total)
       |
[ K8s terminates one V1 Pod ]
       |
[ V1 Pod ] [ V1 Pod ] [ V1 Pod ] [ V2 Pod ] (Back to 4/4)
       |
(Repeats until all Pods are V2)
```

#### 6. Noob Trap vs Pro Tip
**Noob Trap:** Using only Liveness Probes without Readiness Probes. A Pod might be alive (not crashed) but still loading a massive dataset into memory. Without a Readiness probe, K8s will send traffic to it immediately, resulting in errors for users while the app boots.
**Pro Tip:** Your Readiness probe should ideally check a dedicated health endpoint (e.g., `/healthz`) that checks connections to databases or caches. If the database drops, the Readiness probe fails, and K8s temporarily stops sending user traffic to that Pod until the DB recovers, saving users from seeing errors.

### Phase B: Challenges

#### Level 1: Warm-Up
**Task:** Write a Liveness probe for a container that runs a bash script. Instead of an `httpGet`, use an `exec` command to run `cat /tmp/healthy`. If the file exists, the probe passes.
<details>
<summary>Hint</summary>
Replace `httpGet` with an `exec` block containing a `command` array.
</details>

<details>
<summary>Solution Walkthrough</summary>

```yaml
        livenessProbe:
          exec:
            command:
            - cat
            - /tmp/healthy
          initialDelaySeconds: 5
          periodSeconds: 5
```
If the script inside the container deletes `/tmp/healthy`, the `cat` command will return an error code, the probe will fail, and K8s will restart the container.
</details>

#### Level 2: Real-World
**Task:** You are deploying a massive Java application that takes exactly 45 seconds to boot up and initialize. Write a `readinessProbe` (hitting `/health` on port 8080) that ensures Kubernetes waits long enough before deciding the Pod is ready.
<details>
<summary>Hint</summary>
Use the `initialDelaySeconds` property to give the Java app a head start before checking.
</details>

<details>
<summary>Solution Walkthrough</summary>

```yaml
        readinessProbe:
          httpGet:
            path: /health
            port: 8080
          initialDelaySeconds: 50 # Wait 50s before the first check
          periodSeconds: 10
```
Alternatively, in newer K8s versions, you can use a `startupProbe` which disables liveness/readiness checks until it succeeds, specifically designed for slow-starting apps.
</details>

#### Level 3: Boss Level (Cumulative)
**Task:** Create a Deployment named `api-gateway`. It must use a RollingUpdate strategy that updates 25% of pods at a time (`maxSurge: 25%`, `maxUnavailable: 25%`). It must run 4 replicas. Include a Readiness probe on port 3000 `/ping`.
How would you initiate the rolling update to a new image `gateway:v2`, and how would you watch the rollout happen in real-time using `kubectl`?
<details>
<summary>Hint</summary>
Use strings like `"25%"` in the strategy configuration. The commands are `kubectl set image` and `kubectl rollout status`.
</details>

<details>
<summary>Solution Walkthrough</summary>
The YAML:
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-gateway
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%
      maxUnavailable: 25%
  selector:
    matchLabels:
      app: gateway
  template:
    metadata:
      labels:
        app: gateway
    spec:
      containers:
      - name: proxy
        image: gateway:v1
        ports:
        - containerPort: 3000
        readinessProbe:
          httpGet:
            path: /ping
            port: 3000
          initialDelaySeconds: 2
```
To trigger the update: `kubectl set image deployment/api-gateway proxy=gateway:v2`
To watch it: `kubectl rollout status deployment/api-gateway`
You will see output like "Waiting for deployment to finish: 1 out of 4 new replicas have been updated..."
</details>
