# 3.1 Database Sessions and Cleanup (Depends)

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
In many frameworks, managing database connections is a nightmare. You open a connection in a route, do some work, and then an exception happens. The function exits, but the database connection was never closed! Over time, your app leaks connections until the database crashes with "Too many connections." Trying to wrap every single route in `try...finally` is repetitive and messy.

### 2. Plain English Metaphor (The What)
Managing connections manually is like checking out a library book. If you get into a car crash on the way home, you forget to return the book, and eventually, the library runs out of books.
FastAPI's `Depends` with `yield` is like a magical librarian who physically hands you the book, follows you around silently, and the millisecond you are done (or if you crash), they snatch the book back and put it on the shelf automatically.

### 3. Complete Runnable Code
```python
from fastapi import FastAPI, Depends, HTTPException

app = FastAPI()

# Simulated Database Connection
class DBSession:
    def __init__(self):
        self.is_active = True
    def query(self):
        return "data"
    def close(self):
        self.is_active = False

# The Dependency
def get_db():
    db = DBSession()
    try:
        print("Opening DB Connection")
        yield db
    finally:
        print("Closing DB Connection (Cleanup)")
        db.close()

@app.get("/data")
async def get_data(db: DBSession = Depends(get_db)):
    result = db.query()
    return {"result": result}

@app.get("/error")
async def error_route(db: DBSession = Depends(get_db)):
    raise HTTPException(status_code=400, detail="Boom")
    # Even though we crash here, the finally block in get_db STILL runs!
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: The Generator Dependency**
```python
def get_db():
    db = DBSession()
    try:
        yield db
```
Instead of `return`, we use `yield`. This pauses the execution of this function. FastAPI takes the yielded `db` object and passes it into the endpoint.

**Step 2: Injection via Depends**
```python
async def get_data(db: DBSession = Depends(get_db)):
```
FastAPI sees `Depends(get_db)`. Before running `get_data`, it executes `get_db` up to the `yield`. It injects the result into the `db` variable.

**Step 3: Guaranteed Cleanup**
```python
    finally:
        db.close()
```
After the endpoint finishes, returns data, OR raises an exception, FastAPI goes back to the dependency and resumes execution right after the `yield`. The `finally` block guarantees that `db.close()` runs 100% of the time.

### 5. ASCII Data Flow
```text
Client Request
      |
[FastAPI Calls get_db()] -> Initializes Connection -> (Yields 'db')
      |                                                |
[Endpoint Executes] <---- (Injects 'db') <-------------|
      |
(Returns JSON or Crashes)
      |
[FastAPI Resumes get_db()] -> Executes 'finally: db.close()'
      |
Response Sent to Client
```

### 6. Noob Trap vs Pro Tip
**Noob Trap:** Calling the dependency directly inside the function: `db = get_db()`. This bypasses FastAPI's injection system, so the generator never yields, and cleanup never happens.
**Pro Tip:** You can chain dependencies! Dependency A can `Depend` on Dependency B. FastAPI resolves the entire graph and cleans them all up in reverse order.

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**Challenge:** Create a dependency `get_temp_file()` that yields a string `"/tmp/file.txt"` and prints "Deleting file" in the `finally` block. Inject it into a `GET /read` endpoint.
<details>
<summary><b>Hint</b></summary>
Write a generator function with <code>try...yield...finally</code>. Use <code>Depends(get_temp_file)</code> in the route signature.
</details>
<details>
<summary><b>Solution</b></summary>

```python
from fastapi import FastAPI, Depends

app = FastAPI()

def get_temp_file():
    file_path = "/tmp/file.txt"
    try:
        yield file_path
    finally:
        print(f"Deleting {file_path}")

@app.get("/read")
async def read_file(path: str = Depends(get_temp_file)):
    return {"reading_from": path}
```
</details>

### Level 2: Real-World
**Challenge:** Database Session Rollback. Create a dependency `get_session()` that yields a mock `Session` object. The `Session` has a `.commit()` and `.rollback()` method. If the endpoint succeeds, it should just clean up. But simulate a scenario where the dependency catches an exception, calls `.rollback()`, and then re-raises the exception.
<details>
<summary><b>Hint</b></summary>
Use <code>try: yield db; db.commit() except Exception: db.rollback(); raise finally: db.close()</code>.
</details>
<details>
<summary><b>Solution</b></summary>

```python
from fastapi import FastAPI, Depends

app = FastAPI()

class Session:
    def commit(self): print("Committed")
    def rollback(self): print("Rolled back")
    def close(self): print("Closed")

def get_session():
    session = Session()
    try:
        yield session
        session.commit()
    except Exception:
        session.rollback()
        raise
    finally:
        session.close()

@app.get("/save")
async def save_data(db: Session = Depends(get_session)):
    return {"status": "saved"}

@app.get("/fail")
async def fail_data(db: Session = Depends(get_session)):
    raise ValueError("Something broke")
```
</details>

### Level 3: Boss Level
**Challenge:** Dependency Chaining.
1. Create `get_db_pool()` that yields a pool name "PG_POOL".
2. Create `get_connection(pool: str = Depends(get_db_pool))` that yields a connection string `"Conn from PG_POOL"`.
3. Create `GET /status` that depends on `get_connection`.
Prove that FastAPI resolves nested dependencies automatically!
<details>
<summary><b>Hint</b></summary>
Dependencies can take <code>Depends()</code> in their own arguments, just like route functions.
</details>
<details>
<summary><b>Solution Walkthrough</b></summary>

```python
from fastapi import FastAPI, Depends

app = FastAPI()

def get_db_pool():
    yield "PG_POOL"

def get_connection(pool: str = Depends(get_db_pool)):
    yield f"Connection from {pool}"

@app.get("/status")
async def status(conn: str = Depends(get_connection)):
    return {"active_connection": conn}
```
*Walkthrough:* This is Clean Architecture at its finest. The `/status` endpoint knows absolutely nothing about database pools. It just asks for a connection. FastAPI sees that `get_connection` needs `get_db_pool`, resolves it first, injects the pool into the connection generator, and then injects the connection into the endpoint.
</details>
