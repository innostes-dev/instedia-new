# 2.2 Outbound Response Models & Security

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
You query a database for a User object, which contains `id`, `email`, `hashed_password`, and `is_superuser`. You accidentally return the whole object in your API: `return user_record`. Now, hackers have password hashes and administrative status information, resulting in a critical data breach.

### 2. Plain English Metaphor (The What)
Returning raw database records is like handing a customer the master recipe book when they ask for the menu.
`response_model` is like a strict editor. Before the menu is handed to the customer, the editor crosses out all the secret ingredients, ensuring the customer only sees what they are explicitly allowed to see.

### 3. Complete Runnable Code
```python
from fastapi import FastAPI
from pydantic import BaseModel, EmailStr

app = FastAPI()

# What the DB returns
class UserInDB(BaseModel):
    id: int
    email: EmailStr
    hashed_password: str
    is_admin: bool

# What the client is ALLOWED to see
class UserPublic(BaseModel):
    id: int
    email: EmailStr

# Fake Database Record
fake_db_user = UserInDB(
    id=1,
    email="alice@ai.com",
    hashed_password="bcrypt_hashed_secret!",
    is_admin=True
)

@app.get("/users/me", response_model=UserPublic)
async def get_current_user():
    # We return the FULL internal object...
    return fake_db_user
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: The Internal Model**
```python
class UserInDB(BaseModel):
    ...
    hashed_password: str
```
This represents your internal data structure, usually mapped to an ORM (like SQLAlchemy). It contains sensitive information.

**Step 2: The Public Model**
```python
class UserPublic(BaseModel):
    id: int
    email: EmailStr
```
This is the outbound contract. It strictly defines only the fields that are safe for the public API.

**Step 3: The response_model Decorator**
```python
@app.get("/users/me", response_model=UserPublic)
async def get_current_user():
    return fake_db_user
```
Notice we return the full `fake_db_user` inside the function. But because of `response_model=UserPublic`, FastAPI intercepts the data just before it leaves the server, strips away `hashed_password` and `is_admin`, and serializes only `id` and `email`.

### 5. ASCII Data Flow
```text
[Database Object] -> {id: 1, email: "a@a.com", pass: "secret"}
                                |
                   [FastAPI response_model Filter]
                                |
                          (Strips pass)
                                |
[Client Receives] -> {id: 1, email: "a@a.com"}
```

### 6. Noob Trap vs Pro Tip
**Noob Trap:** Manually constructing dictionaries to return: `return {"id": user.id, "email": user.email}`. It's tedious and if you add a field later, you have to update 10 different endpoints.
**Pro Tip:** Use `response_model_exclude_unset=True` in the decorator if you want to avoid returning fields that have `None` values, saving bandwidth.

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**Challenge:** You have an internal `OrderInDB` with `order_id`, `item`, `cost`, and `supplier_margin`. Create a route `GET /order` that uses a `response_model` to only return `order_id` and `item` to the client.
<details>
<summary><b>Hint</b></summary>
Create an <code>OrderPublic</code> model with only those two fields. Set <code>response_model=OrderPublic</code> on the route.
</details>
<details>
<summary><b>Solution</b></summary>

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class OrderInDB(BaseModel):
    order_id: int
    item: str
    cost: float
    supplier_margin: float

class OrderPublic(BaseModel):
    order_id: int
    item: str

@app.get("/order", response_model=OrderPublic)
async def get_order():
    return OrderInDB(order_id=99, item="GPU", cost=5000.0, supplier_margin=0.2)
```
</details>

### Level 2: Real-World
**Challenge:** List of objects. Create a route `GET /users` that returns a *list* of `UserPublic` objects. Return a list of 2 dummy database records.
<details>
<summary><b>Hint</b></summary>
Use <code>from typing import List</code> and set <code>response_model=List[UserPublic]</code>.
</details>
<details>
<summary><b>Solution</b></summary>

```python
from typing import List
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class UserInDB(BaseModel):
    name: str
    secret: str

class UserPublic(BaseModel):
    name: str

@app.get("/users", response_model=List[UserPublic])
async def list_users():
    users = [
        UserInDB(name="Alice", secret="A"),
        UserInDB(name="Bob", secret="B")
    ]
    return users
```
</details>

### Level 3: Boss Level
**Challenge:** Create a generic `GET /profile` endpoint.
It should return a user's details. However, use `response_model_exclude={"admin_notes"}` directly in the decorator to filter out a field without creating a whole new Pydantic model.
<details>
<summary><b>Hint</b></summary>
Define only ONE model with all fields. Use <code>@app.get(..., response_model=YourModel, response_model_exclude={"admin_notes"})</code>.
</details>
<details>
<summary><b>Solution Walkthrough</b></summary>

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class UserProfile(BaseModel):
    username: str
    bio: str
    admin_notes: str

@app.get("/profile", response_model=UserProfile, response_model_exclude={"admin_notes"})
async def view_profile():
    return UserProfile(
        username="hacker",
        bio="I love coding",
        admin_notes="Flagged for suspicious activity"
    )
```
*Walkthrough:* Sometimes creating a completely separate `Public` model is overkill for just hiding a single field. By using `response_model_exclude`, we instruct FastAPI's serializer to dynamically drop the `admin_notes` field during the final JSON serialization step, ensuring it never hits the network.
</details>
