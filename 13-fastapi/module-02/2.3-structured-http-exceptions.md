# 2.3 Structured HTTP Exceptions & Handlers

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
When something goes wrong (e.g., item not found, invalid state), developers often just `return {"error": "not found"}`, which yields an HTTP 200 OK status! Or worse, an unhandled exception causes a messy HTTP 500 Internal Server Error with a full traceback leaked to the user. Client applications need proper HTTP status codes (404, 403, 400) to behave correctly.

### 2. Plain English Metaphor (The What)
Returning a 200 OK with an error message in the payload is like a doctor smiling and handing you a clean bill of health, but scribbled on the back it says "You have 3 days to live."
`HTTPException` is the standard medical alert system. It immediately stops the flow, sounds the alarm (the correct status code), and provides a clean, standardized diagnosis to the patient.

### 3. Complete Runnable Code
```python
from fastapi import FastAPI, HTTPException, Request
from fastapi.responses import JSONResponse

app = FastAPI()

# Database mock
ITEMS = {"item_1": "Nvidia A100", "item_2": "Nvidia H100"}

@app.get("/items/{item_id}")
async def get_item(item_id: str):
    if item_id not in ITEMS:
        raise HTTPException(
            status_code=404,
            detail=f"Item {item_id} not found in inventory."
        )
    return {"item": ITEMS[item_id]}

# A custom global exception handler
class InsufficientFundsException(Exception):
    pass

@app.exception_handler(InsufficientFundsException)
async def funds_exception_handler(request: Request, exc: InsufficientFundsException):
    return JSONResponse(
        status_code=402,
        content={"message": "Payment Required. Please top up your API credits."},
    )

@app.get("/generate")
async def generate():
    raise InsufficientFundsException()
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: Raising HTTPException**
```python
    if item_id not in ITEMS:
        raise HTTPException(
            status_code=404,
            detail=f"Item {item_id} not found in inventory."
        )
```
By raising `HTTPException`, we immediately abort the endpoint execution. FastAPI catches this and formats a proper JSON response: `{"detail": "..."}` with the 404 HTTP status code.

**Step 2: Custom Exceptions**
```python
class InsufficientFundsException(Exception):
    pass
```
For complex business logic, polluting your code with HTTP knowledge is bad practice. Deep in your service layer, you just raise a standard Python exception.

**Step 3: Global Handlers**
```python
@app.exception_handler(InsufficientFundsException)
async def funds_exception_handler(request: Request, exc: InsufficientFundsException):
    return JSONResponse(status_code=402, ...)
```
FastAPI registers this handler globally. Anytime, anywhere in the app, if `InsufficientFundsException` is raised, FastAPI catches it here and maps it to an HTTP 402 status code automatically.

### 5. ASCII Data Flow
```text
GET /generate -> [Endpoint Business Logic]
                       |
             (Raises CustomException)
                       |
               [FastAPI Router]
                       |
           [Global Exception Handler]
                       |
<-- HTTP 402 {"message": "Payment Required"} -- Client
```

### 6. Noob Trap vs Pro Tip
**Noob Trap:** Using `try...except` in every single route just to return a 500 JSON response. Let FastAPI handle unhandled exceptions globally.
**Pro Tip:** You can pass a dictionary to the `detail` parameter of `HTTPException`, not just a string, allowing you to return highly structured error payloads.

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**Challenge:** Create an endpoint `GET /divide` that takes `a: int` and `b: int`. If `b == 0`, raise an `HTTPException` with status 400 and detail "Cannot divide by zero". Otherwise return the result.
<details>
<summary><b>Hint</b></summary>
Use <code>raise HTTPException(status_code=400, detail="...")</code>.
</details>
<details>
<summary><b>Solution</b></summary>

```python
from fastapi import FastAPI, HTTPException

app = FastAPI()

@app.get("/divide")
async def divide(a: int, b: int):
    if b == 0:
        raise HTTPException(status_code=400, detail="Cannot divide by zero")
    return {"result": a / b}
```
</details>

### Level 2: Real-World
**Challenge:** Override the default 422 Unprocessable Entity handler. When Pydantic validation fails, it raises `RequestValidationError`. Write an exception handler for it that returns a 400 status code instead, with a simpler message: `{"error": "Bad data submitted"}`.
<details>
<summary><b>Hint</b></summary>
Import <code>RequestValidationError</code> from <code>fastapi.exceptions</code>. Use <code>@app.exception_handler(RequestValidationError)</code> returning a <code>JSONResponse(status_code=400)</code>.
</details>
<details>
<summary><b>Solution</b></summary>

```python
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse
from fastapi.exceptions import RequestValidationError
from pydantic import BaseModel

app = FastAPI()

class User(BaseModel):
    name: str

@app.exception_handler(RequestValidationError)
async def validation_exception_handler(request: Request, exc: RequestValidationError):
    return JSONResponse(
        status_code=400,
        content={"error": "Bad data submitted"}
    )

@app.post("/test")
async def test(user: User):
    return {"ok": True}
```
</details>

### Level 3: Boss Level
**Challenge:** Build an API Rate Limiter simulation.
1. Create a custom exception `RateLimitExceeded`.
2. Create a global handler for it that returns HTTP 429 and includes a custom header `Retry-After: 60`.
3. Create an endpoint that randomly either returns data or raises the rate limit exception based on a random number.
<details>
<summary><b>Hint</b></summary>
In <code>JSONResponse</code>, you can pass a <code>headers={"Retry-After": "60"}</code> argument.
</details>
<details>
<summary><b>Solution Walkthrough</b></summary>

```python
import random
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

app = FastAPI()

class RateLimitExceeded(Exception):
    pass

@app.exception_handler(RateLimitExceeded)
async def rate_limit_handler(request: Request, exc: RateLimitExceeded):
    return JSONResponse(
        status_code=429,
        content={"error": "Too many requests. Calm down."},
        headers={"Retry-After": "60"}
    )

@app.get("/data")
async def get_data():
    # Simulate a 50% chance of being rate limited
    if random.choice([True, False]):
        raise RateLimitExceeded()
    return {"data": "Here is your precious data"}
```
*Walkthrough:* This pattern is incredibly powerful for clean architecture. By separating the business logic (raising an exception) from the transport logic (setting HTTP status codes and specific headers), your core application logic remains completely agnostic to the fact that it is running inside a web framework.
</details>
