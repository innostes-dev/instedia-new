# 3.3 Pull Requests and Code Reviews: The Gatekeeper

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
In a junior environment, everyone on the team has administrative access to push directly to the `main` branch on GitHub. A tired developer types `git push origin main` on a Friday at 4 PM, pushing broken code that completely takes down the production server.
We need a way to **protect** the `main` branch, ensuring no one can push directly to it, and forcing all new code to be reviewed and approved by another human before it is allowed in.

### 2. Plain English Metaphor (The What)
Think of the `main` branch as a VIP nightclub.
- **Branch Protection Rules:** The giant bouncer at the door. He refuses entry to anyone trying to walk directly in (direct pushes).
- **Pull Request (PR):** You stand outside the club and fill out an application form asking to be let in. The application includes exactly what code you changed, why you changed it, and evidence that it works.
- **Code Review:** A senior manager inside the club reads your application, inspects your code, maybe asks you to fix a few things, and finally stamps it "Approved." Only then does the bouncer let your code merge into the club.

### 3. Complete Runnable Code
*(Note: Pull Requests are a GitHub/Cloud concept, not a native Git command-line feature, though you can use the `gh` CLI to create them).*

```bash
# 1. You cannot push to main directly anymore!
git switch main
git push origin main
# error: GH006: Protected branch update failed.

# 2. Work on a feature branch instead
git switch -c feature/stripe-integration
echo "stripe code" > billing.js
git add billing.js
git commit -m "feat: add stripe billing"

# 3. Push the feature branch to GitHub
git push -u origin feature/stripe-integration

# 4. Create the PR using GitHub CLI (or the web UI)
gh pr create --title "Feature: Stripe Integration" --body "Adds Stripe to the billing page. Fixes #42."

# 5. Reviewer approves and merges it on GitHub
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: Enable Branch Protection (GitHub UI)**
As an admin, go to Repo Settings -> Branches -> Add branch protection rule. Target `main`. Check "Require a pull request before merging" and "Require approvals". Now, direct pushes are banned.

**Step 2: Push a Feature Branch**
Developers must create a local branch (`git switch -c feature`), commit their work, and push that branch to GitHub (`git push -u origin feature`).

**Step 3: Open the Pull Request**
On GitHub, click "Compare & pull request". Fill out the PR Template. A good PR description includes:
- **What:** What does this PR do?
- **Why:** Why is this necessary?
- **How to Test:** Steps for the reviewer to verify it works.

**Step 4: The Review Loop**
A reviewer leaves comments. You modify your local branch, make a new commit, and `git push` again. The PR on GitHub updates automatically. Once approved, click "Merge pull request" on GitHub.

### 5. ASCII Data Flow
```text
[ Local ]                      [ GitHub ]
 (feature) --(git push)--> (origin/feature)
                                  |
                               (Open PR)
                                  |
                            [ Review Loop ] <--- Comments/Approvals
                                  |
                              (Merge PR)
                                  |
                             [ origin/main ] (Protected)
```

### 6. Noob Trap vs Pro Tip
**Noob Trap:** Opening a massive PR that changes 4,000 lines of code across 50 files. Reviewers will gloss over it ("Looks good to me") because it's too painful to read, and critical bugs will slip through.
**Pro Tip:** Keep PRs under 400 lines of code. Small, atomic PRs are reviewed faster and more thoroughly. If you are building a massive feature, break it down (e.g., PR 1: Database schema, PR 2: API routes, PR 3: Frontend UI).

## Phase B: Engineering Challenges

### Level 1 Warm-Up
**Objective:** Understand the purpose of a PR.
**Instructions:** Explain why a company would disable direct pushes to `main`.

<details>
<summary>Hint</summary>
Think about quality control, testing, and human error.
</details>

<details>
<summary>Solution Walkthrough</summary>
Disabling direct pushes prevents developers from accidentally (or intentionally) deploying unreviewed, broken, or malicious code directly to production. It forces a pause for automated tests to run and humans to review the logic, ensuring high code quality and shared team knowledge.
</details>

### Level 2 Real-World
**Objective:** Simulate the PR update loop.
**Instructions:** You opened a PR for `feature/auth`. The reviewer says, "Please add comments to the login function." You are already on the `feature/auth` branch locally. What commands do you run to update the PR?

<details>
<summary>Hint</summary>
You just need to change the file, commit, and push again. The PR will absorb the new push automatically.
</details>

<details>
<summary>Solution Walkthrough</summary>

```bash
# Add comments to the file in your editor
git add auth.js
git commit -m "docs: add comments to login function per review"
git push origin feature/auth
# The GitHub PR will instantly update with this new commit.
```
</details>

### Level 3 Boss Level (Cumulative)
**Objective:** End-to-end Feature PR Workflow.
**Instructions:**
1. Your team uses branch protection on `main`.
2. Ensure your local `main` is up to date with the cloud.
3. Create a branch `feature/stripe`.
4. Create `stripe.js` and commit it.
5. Push it to the cloud.
6. A reviewer approves it and merges it via the GitHub UI.
7. Your local `main` is now outdated. Sync your local `main` to reflect the newly merged code, and clean up your local machine by deleting the old feature branch.

<details>
<summary>Hint</summary>
Checkout `main`, `git pull`, then `git branch -d` to delete the local branch.
</details>

<details>
<summary>Solution Walkthrough</summary>

```bash
# 2. Sync main
git switch main
git pull origin main

# 3 & 4. Create feature
git switch -c feature/stripe
echo "stripe api" > stripe.js
git add stripe.js
git commit -m "feat: stripe integration"

# 5. Push to cloud
git push -u origin feature/stripe

# 6. (Assume PR is created and merged on GitHub Web UI)

# 7. Sync local main and cleanup
git switch main
git pull origin main
# main now has the stripe.js file!

# Safely delete the local feature branch since it is merged
git branch -d feature/stripe
```
</details>
