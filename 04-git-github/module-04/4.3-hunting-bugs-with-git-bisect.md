# 4.3 Hunting Bugs with Binary Search: `git bisect`

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
A critical bug is reported in production: "Users cannot log in."
You check out the current `main` branch, and sure enough, the login button is totally broken.
You know it worked two weeks ago when version v1.0 was released. However, since v1.0, your team has merged 250 commits. You have absolutely no idea which of those 250 commits introduced the bug. If you manually checkout and test each commit one by one, it will take you hours.

### 2. Plain English Metaphor (The What)
Think of a dictionary. If you need to find the word "Mango", you don't read page 1, page 2, page 3... that takes too long.
You open the book exactly in the middle. Is "Mango" before or after the middle? It's before. You rip the back half of the book off and throw it away. You open the remaining half in the middle. Is it before or after?
This is **binary search**. `git bisect` is an automated assistant that does this dictionary trick through your Git history. It checks out the exact middle commit, asks you "Is it broken here?", and based on your answer, cuts the search space in half until it pinpoints the exact bad commit.

### 3. Complete Runnable Code
```bash
# We know the current commit is bad
git bisect start
git bisect bad

# We know the v1.0 tag (or a specific past commit) was good
git bisect good v1.0

# Git automatically checks out a commit in the middle!
# Output: "Bisecting: 125 revisions left to test after this (roughly 7 steps)"

# You test the app...
# If it's broken:
git bisect bad

# Git checks out a new commit in the middle of the new range.
# You test again... If it works:
git bisect good

# ... repeat until Git says:
# "abc1234 is the first bad commit"

# When you are done hunting, reset your working directory to normal
git bisect reset
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: Start the Hunt**
```bash
git bisect start
git bisect bad     # Mark the current state as broken
git bisect good <commit-hash> # Tell Git when it last worked
```
Git calculates the commits between the 'good' and 'bad' points and checks out the commit exactly in the middle.

**Step 2: Test and Report**
Run your tests (e.g., click the button, run `npm test`).
If the bug exists, tell Git: `git bisect bad`.
If the bug does not exist (the app works), tell Git: `git bisect good`.
Git will instantly jump to the next halfway point based on your answer.

**Step 3: End the Hunt**
Eventually, Git will narrow it down to one commit and print: `<hash> is the first bad commit`. You can read that commit (`git show <hash>`) to see exactly what code broke the app.
Always remember to run `git bisect reset` to end the session and return to your original branch.

### 5. ASCII Data Flow
```text
(Good) 1 -- 2 -- 3 -- 4 -- 5 -- 6 -- 7 -- 8 -- 9 (Bad)
                     ^
           Git checks out #5
           You say "Good!" -> Bug must be between 6 and 9

                          (Good) 5 -- 6 -- 7 -- 8 -- 9 (Bad)
                                           ^
                                 Git checks out #7
                                 You say "Bad!" -> Bug must be 6 or 7
```

### 6. Noob Trap vs Pro Tip
**Noob Trap:** Forgetting to run `git bisect reset` when you finish or abort the search. You will be left in a "detached HEAD" state on a random old commit, and if you start writing code, you will lose it.
**Pro Tip:** You can fully automate this! If you have a script that tests for the bug (e.g., `npm run test:login`), you can run `git bisect run npm run test:login`. Git will automatically run the script on every step, use the exit code (0 for good, 1 for bad) to answer itself, and find the bug in seconds while you drink coffee.

## Phase B: Engineering Challenges

### Level 1 Warm-Up
**Objective:** Initiate a bisect session.
**Instructions:** In an existing repo, start a bisect session. Mark `HEAD` as bad. Mark `HEAD~10` as good. Observe Git checking out a middle commit. Then abort the session.

<details>
<summary>Hint</summary>
Use `git bisect start`, `git bisect bad`, `git bisect good HEAD~10`, then `git bisect reset`.
</details>

<details>
<summary>Solution Walkthrough</summary>

```bash
# (Assuming a repo with at least 10 commits exists)
git bisect start
git bisect bad
git bisect good HEAD~10
# Git says "Bisecting..."
git bisect reset
# Back to normal
```
</details>

### Level 2 Real-World
**Objective:** Hunt down a specific bug manually.
**Instructions:**
1. Create a script that generates 5 commits. (Commit 1, 2, 3, 4, 5).
2. In Commit 3, inject a bug (e.g., write "BUG" into a file).
3. Start bisecting. You know Commit 5 is bad, and Commit 1 is good.
4. Manually inspect the file at each step and tell Git if it's good or bad until it finds Commit 3.

<details>
<summary>Hint</summary>
Use `cat file` to check for "BUG". If present, `git bisect bad`. If absent, `git bisect good`.
</details>

<details>
<summary>Solution Walkthrough</summary>

```bash
git init
echo "1" > app.txt && git add app.txt && git commit -m "c1"
echo "2" > app.txt && git commit -am "c2"
echo "BUG" > app.txt && git commit -am "c3"
echo "4" >> app.txt && git commit -am "c4"
echo "5" >> app.txt && git commit -am "c5"

git bisect start
git bisect bad
git bisect good HEAD~4 # Points to c1

# Git checks out c3 or c4.
cat app.txt
# If it contains BUG -> git bisect bad
# If it does not -> git bisect good
# Repeat until Git identifies c3 as the bad commit.
git bisect reset
```
</details>

### Level 3 Boss Level (Cumulative)
**Objective:** Automate the hunt using `git bisect run`.
**Instructions:**
1. Use a bash script to generate 20 commits in a file `math.js`.
2. In the 14th commit, change a correct function `return a + b;` to a broken function `return a - b;`.
3. Write a tiny test script `test.sh` that checks if `math.js` contains the broken string. It should exit 0 if good, and exit 1 if broken.
4. Use `git bisect run ./test.sh` to find the 14th commit automatically.

<details>
<summary>Hint</summary>
A simple test script: `grep "return a + b" math.js > /dev/null`. This exits 0 if the string is found (good), and 1 if it is missing (bad).
</details>

<details>
<summary>Solution Walkthrough</summary>

```bash
# 1 & 2. Setup (Simulation)
git init
for i in {1..13}; do
  echo "function add(a,b) { return a + b; } // $i" > math.js
  git add math.js && git commit -m "commit $i"
done

# The Bug (Commit 14)
echo "function add(a,b) { return a - b; } // 14" > math.js
git commit -am "commit 14"

for i in {15..20}; do
  echo "function add(a,b) { return a - b; } // $i" > math.js
  git commit -am "commit $i"
done

# 3. Write Test Script
echo 'grep "a + b" math.js > /dev/null' > test.sh
chmod +x test.sh

# 4. Automate Bisect
git bisect start
git bisect bad HEAD
git bisect good HEAD~19 # Commit 1

git bisect run ./test.sh
# Watch Git fly through the history and automatically find Commit 14!

git bisect reset
```
</details>
