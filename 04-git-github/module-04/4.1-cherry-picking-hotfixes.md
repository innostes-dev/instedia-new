# 4.1 Cherry-Picking Hotfixes: `git cherry-pick`

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
You just merged a massive feature branch into `main` (which goes to the staging environment). Included in that branch was a tiny, critical fix for a payment authentication bug. Your manager says, "We can't deploy the massive feature to production yet, but we *need* that payment auth bug fix in the `production` branch immediately."
You can't merge `main` into `production` because you'll drag the unfinished feature code with it. You need a way to surgically extract that single bug-fix commit from `main` and transplant it onto `production` without taking anything else.

### 2. Plain English Metaphor (The What)
Think of Git commits as pieces of fruit on a tree branch.
Merging is like taking an entire branch and grafting it onto another tree.
Cherry-picking is exactly what it sounds like. You walk up to the `main` tree, find the exact single piece of fruit (the commit) that fixes the bug, pluck it off, walk over to the `production` tree, and tape that single piece of fruit onto the tip of the branch.

### 3. Complete Runnable Code
```bash
# Setup timelines
git init
echo "production ready" > auth.js
git add auth.js && git commit -m "base commit"

# Create a production branch
git branch production

# Advance main with mixed feature and fix commits
git switch main
echo "feature code" > feature.js
git add feature.js && git commit -m "feat: new giant feature"

echo "fix payment auth" >> auth.js
git add auth.js && git commit -m "fix: resolve payment auth bug"
# Let's find the ID of this specific commit
git log --oneline
# Assuming the ID is 'abc1234'

echo "more feature code" >> feature.js
git commit -am "feat: part 2 of giant feature"

# We ONLY want the fix on production!
git switch production

# Pluck the specific commit by its hash
git cherry-pick abc1234

# Check production
git log --oneline
# You will see the base commit, and ONLY the fix commit!
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: Find the Commit Hash**
You must identify the exact commit you want to copy. Use `git log --oneline` on the branch that has the commit and copy the short alphanumeric hash (e.g., `a1b2c3d`).

**Step 2: Switch to the Target Branch**
Move to the universe where you want the code to arrive (e.g., `git switch production`).

**Step 3: Cherry-Pick**
```bash
git cherry-pick <commit-hash>
```
Git will grab the changes introduced by that specific commit and replay them as a *brand new commit* at the tip of your current branch. It will have the exact same commit message, but a different commit hash (because it's a clone in a new universe).

### 5. ASCII Data Flow
```text
[main]
  (A) --- (B: feature) --- (C: FIX) --- (D: feature)

[production]
  (A) --------------------------------- (C': FIX clone)
                                           ^
                                     git cherry-pick (C)
```

### 6. Noob Trap vs Pro Tip
**Noob Trap:** Cherry-picking a commit that relies on code from previous commits that you *aren't* cherry-picking. If Commit C modifies a variable created in Commit B, and you only cherry-pick Commit C, you will get a massive merge conflict.
**Pro Tip:** Cherry-picking is highly effective for isolated atomic commits. This is the exact reason we learned Atomic Commits in Module 1.2! If your bug fix is perfectly isolated in one file, cherry-picking is seamless.

## Phase B: Engineering Challenges

### Level 1 Warm-Up
**Objective:** Perform a basic cherry-pick.
**Instructions:** Create a repo with a `base` commit. Branch to `dev`. Make a commit on `dev` ("dev work"). Make a second commit on `dev` ("urgent fix"). Switch back to `main`. Use `git cherry-pick` to pull *only* the "urgent fix" into `main`.

<details>
<summary>Hint</summary>
Use `git log --oneline` while on `dev` to get the hash of the urgent fix, then switch to `main` and run `git cherry-pick <hash>`.
</details>

<details>
<summary>Solution Walkthrough</summary>

```bash
git init
touch base.txt && git add base.txt && git commit -m "base"

git switch -c dev
touch dev.txt && git add dev.txt && git commit -m "dev work"
touch fix.txt && git add fix.txt && git commit -m "urgent fix"

# Get hash
git log --oneline
# (Assume urgent fix is hash 8888888)

git switch main
git cherry-pick 8888888
ls
# Output shows base.txt and fix.txt, but NOT dev.txt
```
</details>

### Level 2 Real-World
**Objective:** Cherry-pick multiple commits at once.
**Instructions:** You are maintaining an older version of software on a `release-v1` branch. On `main`, developers made commits A, B, C, D, E. You realize commits C and E contain security patches that must be backported to `release-v1`. Cherry-pick both C and E in a single command.

<details>
<summary>Hint</summary>
You can pass multiple hashes to the command separated by spaces: `git cherry-pick <hash1> <hash2>`.
</details>

<details>
<summary>Solution Walkthrough</summary>

```bash
# Setup
git init && touch 1 && git add 1 && git commit -m "A"
git branch release-v1
touch 2 && git add 2 && git commit -m "B"
touch 3 && git add 3 && git commit -m "C" # Need this
touch 4 && git add 4 && git commit -m "D"
touch 5 && git add 5 && git commit -m "E" # Need this

# Note the hashes for C and E. Let's assume ccc333 and eee555.

git switch release-v1
git cherry-pick ccc333 eee555

git log --oneline
# Shows A, C, and E.
```
</details>

### Level 3 Boss Level (Cumulative)
**Objective:** Cherry-pick an atomic commit across branches, resolve a conflict during the pick, and verify linear history.
**Instructions:**
1. On `main`, commit `config.json` with `{"port": 80}`.
2. Branch `release`.
3. On `main`, change port to `8080`, commit as `feat: update port`.
4. On `main`, add a new key `{"port": 8080, "timeout": 500}`, commit as `fix: add timeout constraint`.
5. On `release`, a hotfix happened! Change port to `443`, commit as `hotfix: secure port`.
6. You must transplant the `timeout` fix from `main` to `release`.
7. Execute the cherry-pick. It will conflict because the port lines differ.
8. Resolve the conflict to keep `443` and add the `timeout`.
9. Finalize the cherry-pick.

<details>
<summary>Hint</summary>
A cherry-pick is essentially a tiny merge. If it conflicts, you resolve the markers in the file, `git add`, and then `git cherry-pick --continue`.
</details>

<details>
<summary>Solution Walkthrough</summary>

```bash
git init
echo '{"port": 80}' > config.json
git add config.json && git commit -m "base"

git branch release

# Main advances
echo '{"port": 8080}' > config.json
git commit -am "feat: update port"
echo '{"port": 8080, "timeout": 500}' > config.json
git commit -am "fix: add timeout constraint"
# Assume this commit hash is 999aaaa

# Release advances
git switch release
echo '{"port": 443}' > config.json
git commit -am "hotfix: secure port"

# Cherry-pick the fix
git cherry-pick 999aaaa
# CONFLICT!

# Resolve in editor:
# Change to: {"port": 443, "timeout": 500}

git add config.json
# Finalize the process
git cherry-pick --continue
```
</details>
