# 5.1 GitHub Actions: The Automated CI Pipeline

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
You have branch protection on `main` and require Pull Requests (PRs). However, human reviewers are lazy. When a developer submits a PR, the reviewer might say "Looks good to me" without actually running the code on their machine to see if the tests pass or if the code formatting is correct.
A broken PR gets merged, and production breaks again. We need a robot that automatically runs our test suite and code linters every single time someone opens a PR, and we need this robot to mathematically block the PR from merging if the tests fail, removing human error entirely.

### 2. Plain English Metaphor (The What)
Think of GitHub Actions as a factory assembly line robot you rent in the cloud.
Every time an event happens on GitHub (like "a new PR is opened"), the robot wakes up. It reads an instruction manual (a `.yaml` file) that you wrote for it.
The manual says: "1. Download the code. 2. Install dependencies. 3. Run tests."
The robot provisions a brand new, clean server in the cloud, executes your instructions step-by-step, and reports back a Green Checkmark (Success) or a Red X (Failure) directly on the PR page.

### 3. Complete Runnable Code
```yaml
# Place this file in your repo exactly at:
# .github/workflows/ci.yml

name: Node.js CI Pipeline

# Trigger the robot on PRs pointing to main
on:
  pull_request:
    branches: [ "main" ]

jobs:
  test:
    runs-on: ubuntu-latest # The server OS the robot provisions

    steps:
    - name: Download repository code
      uses: actions/checkout@v3

    - name: Set up Node.js
      uses: actions/setup-node@v3
      with:
        node-version: '18'

    - name: Install dependencies
      run: npm ci

    - name: Run code linter
      run: npm run lint

    - name: Run unit tests
      run: npm test
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: The Trigger (`on:`)**
You must tell the robot *when* to wake up. Common triggers are `push` (every time code is pushed to a branch) or `pull_request` (when a PR is opened or updated).

**Step 2: The Environment (`runs-on:`)**
You specify the virtual machine that GitHub will boot up for you. `ubuntu-latest` is standard, but you can request Windows or macOS if you are compiling desktop apps.

**Step 3: The Steps**
A job is a sequence of steps.
- `uses:` calls pre-built community actions (like `actions/checkout`, which simply runs `git clone` on the robot's server so it has your code).
- `run:` executes basic shell commands exactly as you would type them on your local laptop (`npm install`, `pytest`, `cargo build`).

### 5. ASCII Data Flow
```text
[ Developer Pushes Code ] -> [ GitHub PR Opens ]
                                     |
                             (Triggers GitHub Action)
                                     |
                          [ Boot Ubuntu Cloud Server ]
                                     |
                     [ Clone Code -> Install -> Run Tests ]
                                     |
                       (Success) /       \ (Failure)
                                /         \
                   [ Green Checkmark ]   [ Red X (Blocks Merge) ]
```

### 6. Noob Trap vs Pro Tip
**Noob Trap:** Putting your secret API keys (like `AWS_ACCESS_KEY`) directly into the `.yml` file in plain text. Since this file is tracked by Git, anyone who reads your code can steal your cloud infrastructure.
**Pro Tip:** Use GitHub Secrets. Go to Repo Settings -> Secrets, and add a secret named `API_KEY`. In your `.yml` file, securely inject it into the environment using `${{ secrets.API_KEY }}`.

## Phase B: Engineering Challenges

### Level 1 Warm-Up
**Objective:** Create the workflow file structure.
**Instructions:** In a local repository, create the exact directory structure required for GitHub Actions and add a file named `lint.yml` inside it.

<details>
<summary>Hint</summary>
The path must be exactly `.github/workflows/lint.yml`. Note the dot in `.github` and the 's' in `workflows`.
</details>

<details>
<summary>Solution Walkthrough</summary>

```bash
mkdir -p .github/workflows
touch .github/workflows/lint.yml
# This is now ready to be committed and pushed.
```
</details>

### Level 2 Real-World
**Objective:** Write a basic action that prints the Git version on the server.
**Instructions:** Write a GitHub Actions YAML file named `version-check.yml` that triggers on any `push`. It should run on `ubuntu-latest`, check out the code, and run `git --version`.

<details>
<summary>Hint</summary>
Use `on: push`, `runs-on: ubuntu-latest`, `actions/checkout@v3`, and a `run` step.
</details>

<details>
<summary>Solution Walkthrough</summary>

```yaml
# .github/workflows/version-check.yml
name: Git Version Check
on: push
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Print Version
        run: git --version
```
</details>

### Level 3 Boss Level (Cumulative)
**Objective:** Setup an Automated Linter & Unit Test CI Pipeline for a Python project.
**Instructions:**
1. Create `.github/workflows/python-ci.yml`.
2. Trigger it on `pull_request` to `main`.
3. Use `ubuntu-latest`.
4. Check out the code.
5. Setup Python 3.10 (Hint: `uses: actions/setup-python@v4` with `python-version: '3.10'`).
6. Install `flake8` and `pytest` using pip.
7. Run `flake8 .`
8. Run `pytest`
9. Commit this file to a branch and simulate pushing it.

<details>
<summary>Hint</summary>
Combine the YAML syntax from the Core Concept with the Python-specific setup steps.
</details>

<details>
<summary>Solution Walkthrough</summary>

```yaml
# .github/workflows/python-ci.yml
name: Python CI Pipeline

on:
  pull_request:
    branches: [ "main" ]

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
    - name: Checkout code
      uses: actions/checkout@v3

    - name: Set up Python
      uses: actions/setup-python@v4
      with:
        python-version: '3.10'

    - name: Install dependencies
      run: |
        python -m pip install --upgrade pip
        pip install flake8 pytest

    - name: Run Linter
      run: flake8 .

    - name: Run Tests
      run: pytest
```
*Note: In reality, you commit this and push to GitHub, and watch the Actions tab light up!*
</details>
