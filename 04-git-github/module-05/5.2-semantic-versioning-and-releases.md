# 5.2 Semantic Versioning and Automated Releases

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
Your team merges dozens of PRs into `main` every week. How do you know exactly which commit is currently running in production? How do you package all these changes into a neat, downloadable zip file or Docker container for your customers?
If you just say "Production is on whatever commit was merged yesterday," rolling back a broken production environment becomes a nightmare of searching through raw commit hashes. You need permanent, human-readable labels for specific points in history.

### 2. Plain English Metaphor (The What)
Think of commits as pages in a book.
- **Git Tag:** A permanent bookmark placed on a very specific page. Unlike a branch (which constantly moves forward as new pages are written), a tag never moves. It is stuck to that specific page forever.
- **Semantic Versioning (SemVer):** The naming convention for those bookmarks (e.g., `v1.2.4`).
  - `1` (Major): We completely rewrote the book, old readers will be confused.
  - `2` (Minor): We added a new chapter, but old chapters are the same.
  - `4` (Patch): We fixed a typo in a paragraph.
- **GitHub Release:** You take the bookmarked page (Tag), wrap it in a pretty cover, attach binary files (like a compiled `.exe` or PDF), and publish it on the GitHub Releases page for users to download.

### 3. Complete Runnable Code
```bash
# Setup a repository with some code
git init
echo "app code v1.0.0" > main.go
git add main.go && git commit -m "feat: initial release"

# 1. Create an annotated tag (bookmark the commit)
git tag -a v1.0.0 -m "Release version 1.0.0"

# 2. Push the tag to GitHub
# (Normal git push does NOT push tags!)
git push origin v1.0.0

# Or push all tags at once
git push origin --tags

# 3. View your tags
git tag -l
git show v1.0.0
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: Determine the Version Number (SemVer)**
Analyze the commits since your last release.
- Did you fix a bug? Increment Patch (`v1.0.0` -> `v1.0.1`).
- Did you add a backwards-compatible feature? Increment Minor (`v1.0.0` -> `v1.1.0`).
- Did you introduce a breaking change to the API? Increment Major (`v1.0.0` -> `v2.0.0`).

**Step 2: Create the Tag (`git tag -a`)**
```bash
git tag -a v2.1.0 -m "Add user dashboard"
```
The `-a` creates an *annotated* tag, which stores the date, the tagger's name, and a message (unlike a lightweight tag, which is just a silent pointer).

**Step 3: Push the Tag (`git push --tags`)**
Tags exist only locally until explicitly pushed to the cloud.

**Step 4: Automate the Release (GitHub Actions)**
You can instruct GitHub Actions to listen for new tags being pushed, automatically compile the code, and publish a GitHub Release.

### 5. ASCII Data Flow
```text
  (Commit A) --- (Commit B) --- (Commit C) <- [main]
                                    ^
                             (Tag: v1.0.0)
                                    |
                             (git push --tags)
                                    |
                           [ GitHub Action triggers ]
                                    |
                    [ Compiles Code -> Creates GitHub Release ]
```

### 6. Noob Trap vs Pro Tip
**Noob Trap:** Creating a tag, realizing there was a typo in the code, fixing the typo with a new commit, and trying to move the tag. Moving tags that have already been pushed to the cloud breaks the fundamental rule of release management (immutability).
**Pro Tip:** If a release is broken, leave the broken tag alone. Make a fix, commit it, and cut a *new* tag (e.g., `v1.0.1`). Releases must be immutable artifacts.

## Phase B: Engineering Challenges

### Level 1 Warm-Up
**Objective:** Create and list an annotated tag.
**Instructions:** In a repo, make a commit. Create an annotated tag named `v0.1.0` with the message "Alpha release". List all tags to verify.

<details>
<summary>Hint</summary>
Use `git tag -a <name> -m <msg>` and `git tag -l`.
</details>

<details>
<summary>Solution Walkthrough</summary>

```bash
git init
git commit --allow-empty -m "base"
git tag -a v0.1.0 -m "Alpha release"
git tag -l
# Output: v0.1.0
```
</details>

### Level 2 Real-World
**Objective:** Apply Semantic Versioning logic.
**Instructions:** Your current app is on `v2.4.1`.
1. You merge a PR that adds a new "Dark Mode" toggle (backwards compatible). What should the new version be? Tag it.
2. You then merge a PR that completely deletes the old REST API and replaces it with GraphQL, breaking all existing clients. What should the new version be? Tag it.

<details>
<summary>Hint</summary>
New feature = Minor bump (increment middle number, reset patch to 0). Breaking change = Major bump (increment first number, reset minor and patch to 0).
</details>

<details>
<summary>Solution Walkthrough</summary>

```bash
# 1. New Feature -> Minor bump
# Current: 2.4.1 -> New: 2.5.0
git commit --allow-empty -m "feat: dark mode"
git tag -a v2.5.0 -m "Release v2.5.0"

# 2. Breaking Change -> Major bump
# Current: 2.5.0 -> New: 3.0.0
git commit --allow-empty -m "BREAKING CHANGE: replace REST with GraphQL"
git tag -a v3.0.0 -m "Release v3.0.0"
```
</details>

### Level 3 Boss Level (Cumulative)
**Objective:** Create an Automated Production Release Pipeline.
**Instructions:**
1. Write a GitHub Actions YAML file (`release.yml`) that triggers *only* when a tag starting with `v` is pushed (e.g., `v1.0.0`). *(Hint: `on: push: tags: - 'v*'`)*.
2. The job should run on Ubuntu, checkout the code.
3. Add a step that simply echoes "Building release for $GITHUB_REF_NAME".
4. Add a step that uses the official `softprops/action-gh-release@v1` to automatically generate a GitHub Release based on the pushed tag.

<details>
<summary>Hint</summary>
This combines Action triggers from 5.1 with Tags from 5.2.
</details>

<details>
<summary>Solution Walkthrough</summary>

```yaml
# .github/workflows/release.yml
name: Automated Release

on:
  push:
    tags:
      - 'v*' # Trigger on tags like v1.0.0, v2.1.3

jobs:
  build-and-release:
    runs-on: ubuntu-latest

    steps:
    - name: Checkout Code
      uses: actions/checkout@v3

    - name: Build Artifacts
      run: |
        echo "Building release for ${{ github.ref_name }}..."
        # (Imagine we run `npm run build` or `go build` here)
        echo "compile successful" > binary.txt

    - name: Create GitHub Release
      uses: softprops/action-gh-release@v1
      with:
        generate_release_notes: true
        files: |
          binary.txt
      env:
        GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }} # Provided automatically by GitHub
```
*When you push `git push origin v1.0.0`, this robot wakes up, builds the code, and creates the official Release page!*
</details>
