# 2.4 Emergency Stashing: `git stash`

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
You are deep into writing a complex database migration on your `feature-db` branch. It's broken, it doesn't compile, and it's definitely not ready for a commit (even a WIP one).
Suddenly, your boss asks you to switch back to `main` to test a quick hotfix someone else just pushed.
If you try to `git switch main`, Git will stop you: "Your local changes would be overwritten by checkout. Please commit your changes or stash them before you switch branches." You can't commit broken code, but you must switch branches immediately.

### 2. Plain English Metaphor (The What)
Think of `git stash` as a magical desk drawer.
Your working directory is the top of your desk. It's covered in half-finished blueprints.
When you run `git stash`, you sweep all those unfinished blueprints into the drawer. Your desk is now perfectly clean and matches the last recorded snapshot. You can now safely switch universes.
Later, when you return to this universe, you can open the drawer (`git stash pop`) and put the messy blueprints exactly back where they were on your desk to resume working.

### 3. Complete Runnable Code
```bash
# Setup
git init
echo "baseline" > index.js
git add index.js && git commit -m "base"

# Start messy, unfinishable work
echo "half-written code..." >> index.js

# Boss: "Switch to main NOW!"
# Git says: error! You must stash!
git stash

# Your desk is now clean!
git status # "nothing to commit, working tree clean"

# (Pretend you switch branches, do work, switch back)

# Resume your messy work
git stash pop
cat index.js
# "half-written code..." is back!
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: Stash the Mess (`git stash`)**
```bash
git stash
```
This takes all modified, tracked files and saves them on a stack of unfinished work, reverting your working directory to match the HEAD commit. *(Note: By default, it does not stash untracked/new files unless you use `git stash -u`).*

**Step 2: Check Stashed Items (`git stash list`)**
```bash
git stash list
```
You can stash multiple times! This shows you all the messy desk drawers you've created, labeled `stash@{0}`, `stash@{1}`, etc.

**Step 3: Retrieve the Mess (`git stash pop`)**
```bash
git stash pop
```
This takes the most recent stash (`stash@{0}`), applies it back to your working directory, and then deletes it from the stash drawer. (If you want to apply it but keep the copy in the drawer, use `git stash apply`).

### 5. ASCII Data Flow
```text
Working Directory (Messy)
      |
 (git stash) ---------->  Stash Stack (Drawer)
      |                     - stash@{0}: WIP on main...
Working Directory (Clean)
      |
 (git switch, do things)
      |
 (git stash pop) <------  Stash Stack (Drawer)
      |                     (Empty)
Working Directory (Messy again)
```

### 6. Noob Trap vs Pro Tip
**Noob Trap:** Using `git stash` dozens of times over a month without ever popping them. You end up with a massive graveyard of lost code in `git stash list` and no idea what `stash@{14}` does.
**Pro Tip:** Treat the stash as highly temporary (minutes or hours, not days). If you need to put work aside for days, it is much better to just `git commit -m "WIP: database migration"` and then fix that commit later (using techniques we'll learn in Module 3) rather than relying on the invisible stash drawer.

## Phase B: Engineering Challenges

### Level 1 Warm-Up
**Objective:** Stash and pop changes.
**Instructions:** Create a repo with one committed file. Modify the file. Stash the changes, verify the working directory is clean, then pop the changes back.

<details>
<summary>Hint</summary>
Use `git stash`, `git status`, and `git stash pop`.
</details>

<details>
<summary>Solution Walkthrough</summary>

```bash
git init
echo "stable" > config.txt
git add config.txt && git commit -m "base"

echo "messy" >> config.txt
git stash
git status # Shows working tree clean

git stash pop
cat config.txt # Shows both lines again
```
</details>

### Level 2 Real-World
**Objective:** Include untracked files in a stash.
**Instructions:** You modified a tracked file `app.js` and created a *new* file `helpers.js`. Use the correct stash command to sweep BOTH files into the drawer so your working directory is completely empty.

<details>
<summary>Hint</summary>
Standard `git stash` ignores untracked files. Use `git stash -u` (include untracked).
</details>

<details>
<summary>Solution Walkthrough</summary>

```bash
git init
touch app.js && git add app.js && git commit -m "base"

echo "edit" > app.js
touch helpers.js

git stash -u
ls
# helpers.js is gone (stashed)! Working tree is completely clean.

git stash pop
# helpers.js and app.js modifications return.
```
</details>

### Level 3 Boss Level (Cumulative)
**Objective:** Handle an emergency branch switch while managing untracked files and conflicts upon popping.
**Instructions:**
1. Init repo, add `search.js` ("v1"), commit.
2. Branch to `feature-search`.
3. Modify `search.js` ("v1 - filtering added"), create new untracked file `styles.css`.
4. Emergency! You must switch to `main` immediately to deploy.
5. Stash EVERYTHING (including untracked files).
6. Switch to `main`. Modify `search.js` ("v1 - hotfix applied"), commit.
7. Switch back to `feature-search`.
8. Pop your stash. Observe what Git does.

<details>
<summary>Hint</summary>
Because the hotfix modified the same file you stashed, Git might warn you or create a conflict when popping. Use `git stash -u` to capture the CSS file.
</details>

<details>
<summary>Solution Walkthrough</summary>

```bash
git init
echo "v1" > search.js
git add search.js && git commit -m "base"

git switch -c feature-search
echo "v1 - filtering added" > search.js
touch styles.css

# Emergency stash
git stash -u

# Hotfix on main
git switch main
echo "v1 - hotfix applied" > search.js
git commit -am "hotfix"

# Back to feature
git switch feature-search

# Pop the stash
git stash pop
# Git successfully restores styles.css, but warns:
# "Needs merge... error: Your local changes to the following files would be overwritten by merge"
# NOTE: Because we branched *before* the hotfix, our branch doesn't have the hotfix yet.
# In this specific universe, `search.js` is still "v1". The pop succeeds without conflict!
```
</details>
