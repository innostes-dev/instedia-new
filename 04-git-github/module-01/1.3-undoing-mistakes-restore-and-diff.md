# 1.3 Undoing Mistakes: `git restore` & `git diff`

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
You are experimenting with a new sorting algorithm in `data.js`. After 30 minutes of tweaking, everything is completely broken, and you don't remember what the file looked like before you started typing. If you were just using basic OS files, you'd have to aggressively hit `Ctrl+Z` and pray, or manually rewrite the old logic from memory.

### 2. Plain English Metaphor (The What)
Think of `git restore` like an "Undo" button that pulls the pristine, untouched version of a file straight from the last recorded snapshot (the last commit) and overwrites your messy workbench.
Think of `git diff` as putting on x-ray glasses. It highlights exactly what lines you added (in green) and what lines you deleted (in red) compared to the last snapshot, so you can review your changes before committing.

### 3. Complete Runnable Code
```bash
# Setup: We have a tracked file
echo "initial good code" > script.js
git add script.js
git commit -m "initial commit"

# Oh no, we messed it up!
echo "broken experimental garbage" > script.js

# Let's see exactly what we broke
git diff script.js

# Discard the changes and go back to the safe version
git restore script.js

# File is back to "initial good code"
cat script.js
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: Check the Differences (`git diff`)**
Before saving or discarding changes, you should review them.
```bash
git diff script.js
```
This shows the difference between your *Working Directory* and the *Staging Area* (or the last commit if staging is empty).
Lines starting with `-` (red) were removed. Lines starting with `+` (green) were added.

**Step 2: Discard Unstaged Changes (`git restore`)**
If you decide the changes are terrible:
```bash
git restore script.js
```
This takes the file from the last commit and forcefully overwrites the version in your working directory. **Warning:** This destroys your uncommitted work in that file permanently.

**Step 3: Review History (`git log`)**
If you need to see what previous snapshots look like to understand *why* the old code was written that way:
```bash
git log --oneline
```
This shows a concise history of commits.

### 5. ASCII Data Flow
```text
Working Directory        Local Repository (Last Commit)
 (Messy Changes)          (Safe Snapshot)

   script.js (broken) <--- git restore script.js --- [ Commit: "initial good code" ]
        |
    (Overwrites with safe version)
```

### 6. Noob Trap vs Pro Tip
**Noob Trap:** Using `git checkout -- <file>` to undo changes. While this works in older versions of Git, it is an overloaded command that also switches branches, confusing beginners.
**Pro Tip:** Always use the newer `git restore` command explicitly designed for undoing changes in the working directory or staging area. Always run `git diff` *before* `git restore` to ensure you aren't throwing away good code accidentally.

## Phase B: Engineering Challenges

### Level 1 Warm-Up
**Objective:** View differences before committing.
**Instructions:** Create a repo, add `app.txt` with text "v1", and commit. Change the text to "v2". Use a Git command to show the exact line changed.

<details>
<summary>Hint</summary>
After modifying the file, use <code>git diff</code>.
</details>

<details>
<summary>Solution Walkthrough</summary>

```bash
git init
echo "v1" > app.txt
git add app.txt
git commit -m "add v1"
echo "v2" > app.txt
git diff
# You will see -v1 in red and +v2 in green.
```
</details>

### Level 2 Real-World
**Objective:** Restore a file that you accidentally broke.
**Instructions:** Continuing from Level 1, realize that "v2" is a mistake. Revert `app.txt` back to the state it was in at the last commit without making a new commit.

<details>
<summary>Hint</summary>
Use <code>git restore &lt;filename&gt;</code> to overwrite the working directory changes.
</details>

<details>
<summary>Solution Walkthrough</summary>

```bash
git restore app.txt
cat app.txt
# Output is back to "v1"
```
</details>

### Level 3 Boss Level (Cumulative)
**Objective:** Discard broken experimental code while keeping a successful atomic commit, reviewing history to confirm.
**Instructions:**
1. Initialize a repo.
2. Create and commit a working function in `math.js`.
3. You start working on a complex `divide` function in `math.js`, and simultaneously start drafting `readme.md`.
4. You finish `readme.md` successfully, but your `divide` function in `math.js` is totally broken.
5. Stage and commit ONLY `readme.md`.
6. Discard the broken changes in `math.js` to return it to the state of the first commit.
7. Use a log command to view the clean history.

<details>
<summary>Hint</summary>
Remember how to stage specific files from Module 1.2. Then use <code>git restore</code> on the file you want to revert.
</details>

<details>
<summary>Solution Walkthrough</summary>

```bash
git init
echo "function add(a,b) { return a+b; }" > math.js
git add math.js
git commit -m "feat: add function"

# Simultaneous work
echo "function divide() { syntax error!! }" >> math.js
echo "Documentation" > readme.md

# Commit the good work
git add readme.md
git commit -m "docs: add readme"

# Review the bad work
git diff math.js

# Discard the bad work
git restore math.js

# Verify the file is fixed
cat math.js

# Check clean history
git log --oneline
```
</details>
