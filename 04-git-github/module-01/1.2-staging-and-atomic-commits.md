# 1.2 Staging and Atomic Commits: `git add` & `git commit`

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
You've spent the last 4 hours fixing a bug in the billing service, but you also tweaked the UI colors and added a new dependency. If you save all of this as one massive "Fixed stuff" checkpoint, a colleague reviewing the billing bug fix will be confused by the UI color changes. If they need to revert the UI colors, they also accidentally revert the billing fix! We need a way to group related changes together precisely before permanently saving them.

### 2. Plain English Metaphor (The What)
Think of Git like a photography studio.
Your working folder is the chaotic backstage.
`git add` is moving items onto the photography stage (the Staging Area). You arrange exactly what you want in the shot.
`git commit` is pressing the shutter button on the camera, taking a permanent snapshot of whatever is on the stage, along with a caption (the commit message).

### 3. Complete Runnable Code
```bash
# Create files for different features
echo "function login() {}" > auth.js
echo "body { color: blue; }" > style.css

# Check what changed
git status

# Stage ONLY the auth feature (move to stage)
git add auth.js

# Commit the auth feature (take the snapshot)
git commit -m "feat: implement basic login function"

# The CSS is still untracked/modified in the working directory
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: Make Changes (Working Directory)**
You edit or create files. Git notices these files have changed compared to the last snapshot, but it doesn't automatically prep them for the next snapshot.

**Step 2: Stage Specific Changes (`git add`)**
```bash
git add auth.js
```
This tells Git, "Include this specific file's current state in the next commit." This is the Staging Area (or Index). You can stage files one by one to ensure only related changes go together.

**Step 3: Commit the Staged Changes (`git commit`)**
```bash
git commit -m "feat: implement basic login function"
```
This creates a permanent checkpoint in history containing *only* what was staged. The `-m` flag allows you to write a descriptive message. A good commit message explains *why* the change was made.

### 5. ASCII Data Flow
```text
Working Directory        Staging Area              Local Repository
 (Unstaged Files)         (Prepped for Commit)      (Permanent History)

   auth.js (modified) ----> git add auth.js ------> git commit -m "..."
   style.css (modified) -|  (auth.js is staged)     (auth.js saved in history)
                            (style.css stays behind)
```

### 6. Noob Trap vs Pro Tip
**Noob Trap:** Using `git commit -a -m "updates"` or `git add .` blindly every time. This creates "monster commits" that bundle unrelated bug fixes, feature work, and accidental typos into a single, un-revertable mess.
**Pro Tip:** Use `git status` frequently to see what is modified vs staged. Make "Atomic Commits" — commits that do one single logical thing (e.g., one commit for the bug fix, one for the UI change).

## Phase B: Engineering Challenges

### Level 1 Warm-Up
**Objective:** Stage and commit a single file.
**Instructions:** Create a file `config.json`. Stage it, and commit it with a message indicating it's the initial configuration.

<details>
<summary>Hint</summary>
Use <code>git add config.json</code> and <code>git commit -m "..."</code>.
</details>

<details>
<summary>Solution Walkthrough</summary>

```bash
echo "{}" > config.json
git add config.json
git commit -m "chore: add initial config.json"
```
</details>

### Level 2 Real-World
**Objective:** Separate unrelated changes into atomic commits.
**Instructions:** You modified `app.js` to fix a crash, and created `readme.md` to update documentation. Commit the bug fix first, then commit the documentation update separately.

<details>
<summary>Hint</summary>
Do not use <code>git add .</code>. Add and commit the files individually.
</details>

<details>
<summary>Solution Walkthrough</summary>

```bash
echo "console.log('fixed')" > app.js
echo "# Docs" > readme.md

# Commit 1: Bug fix
git add app.js
git commit -m "fix: resolve crash in app.js"

# Commit 2: Docs
git add readme.md
git commit -m "docs: update readme"
```
</details>

### Level 3 Boss Level (Cumulative)
**Objective:** Initialize a repository, create multiple features, and execute atomic commits for a Login Screen feature while leaving experimental work behind.
**Instructions:**
1. Initialize a new repo `login-module`.
2. Create `login.html`, `login.css`, and `experimental-api.js`.
3. You realize `experimental-api.js` is broken and shouldn't be committed yet.
4. Stage and commit only the HTML and CSS files together as a single feature commit.
5. Verify the history shows one commit, and the working directory still holds the experimental file.

<details>
<summary>Hint</summary>
Initialize first. Then create files. You can pass multiple files to <code>git add</code> separated by spaces. Use <code>git log</code> and <code>git status</code> to verify.
</details>

<details>
<summary>Solution Walkthrough</summary>

```bash
mkdir login-module
cd login-module
git init

touch login.html login.css experimental-api.js

# Stage only the login feature files
git add login.html login.css

# Commit the cohesive feature
git commit -m "feat: basic login UI structure and styling"

# Verify
git status
# Shows experimental-api.js as untracked

git log
# Shows the single commit we just made
```
</details>
