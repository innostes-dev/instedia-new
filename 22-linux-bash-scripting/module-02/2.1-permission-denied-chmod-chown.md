# 2.1 Security & Permissions (chmod, chown, sudo)

## Phase A: Core Concepts

### 1. Real-World Pain Point (The Why)
You deployed a web server and uploaded your files. But when you visit the website, you get a "403 Forbidden - Permission Denied" error. The web server process doesn't have the authority to read the files you just uploaded because they are owned by your user account, not the web server. If you just grant "read/write/execute to everyone" to fix it quickly, a hacker can execute a malicious script on your server and take over.

### 2. Plain English Metaphor (The What)
- **Permissions (`rwx`)** are like rules on a house. Can you Read (look inside), Write (rearrange furniture), or Execute (run a business from the house)?
- `chmod` (Change Mode) is like giving out keys. You can give a key to the Owner, the Group, or Others (the public).
- `chown` (Change Owner) is like selling the house to someone else entirely.
- `sudo` (Superuser Do) is like putting on a police badge that grants you absolute authority to bypass all standard rules temporarily.

### 3. Complete Runnable Code
Here is a Secure Production Web Directory Permission Lock script.

```bash
#!/usr/bin/env bash

# Setup dummy web directory for the example
sudo mkdir -p /var/www/my-secure-site
sudo touch /var/www/my-secure-site/index.html

echo "Setting ownership to the web server user (www-data)..."
sudo chown -R www-data:www-data /var/www/my-secure-site

echo "Setting strict directory permissions (755)..."
# Directories need execute (x) to be entered
sudo find /var/www/my-secure-site -type d -exec chmod 755 {} \;

echo "Setting strict file permissions (644)..."
# Files only need read (r) and write (w), not execute (x)
sudo find /var/www/my-secure-site -type f -exec chmod 644 {} \;

echo "Verifying permissions:"
ls -la /var/www/my-secure-site
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: Changing Ownership**
```bash
sudo chown -R www-data:www-data /var/www/my-secure-site
```
`chown` changes the owner and group of the files. The `-R` flag applies it recursively to everything inside. `www-data:www-data` sets the user to `www-data` and the group to `www-data` (the standard Nginx/Apache user).

**Step 2: Securing Directories**
```bash
sudo find /var/www/my-secure-site -type d -exec chmod 755 {} \;
```
`chmod 755` means:
- `7` (Owner): Read (4) + Write (2) + Execute (1) = 7. Owner can do everything.
- `5` (Group): Read (4) + Execute (1) = 5. Group can read and enter.
- `5` (Public): Read (4) + Execute (1) = 5. Public can read and enter.
Directories *must* have the Execute bit set, otherwise you cannot `cd` into them.

**Step 3: Securing Files**
```bash
sudo find /var/www/my-secure-site -type f -exec chmod 644 {} \;
```
`chmod 644` means:
- `6` (Owner): Read (4) + Write (2) = 6. Owner can read and edit.
- `4` (Group): Read (4). Group can only read.
- `4` (Public): Read (4). Public can only read.
Never give execute permissions (the `1`) to standard web files like HTML or images.

### 5. ASCII Data Flow

```text
[ File: index.html ]
Permissions: 644 (rw-r--r--)
Owner: www-data

[Web Request (Public)] ---> Tries to Read ---> Granted (Matches '4' Others)
[Hacker (Public)]      ---> Tries to Write --> DENIED (Missing '2' Others)
[Root User (sudo)]     ---> Tries to Write --> Granted (sudo bypasses all)
```

### 6. Noob Trap vs Pro Tip
**Noob Trap:** Using `chmod 777` to fix permission errors. This gives read, write, and execute permissions to *everyone on the planet*. It is a massive security vulnerability.
**Pro Tip:** Use numeric modes (like `755` or `644`) instead of symbolic modes (like `u+rwx,g+rx,o+rx`) in scripts because they force absolute permissions rather than just appending to existing ones.

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**Task:** Create a file named `secret.txt` and ensure only the owner can read or write to it, and no one else can do anything.
<details>
<summary>Hint</summary>
Use <code>touch</code> to create the file and <code>chmod 600</code>.
</details>
<details>
<summary>Solution Walkthrough</summary>
1. <code>touch secret.txt</code>
2. <code>chmod 600 secret.txt</code>
The `6` gives Read(4)+Write(2) to the owner. The `0` gives nothing to the Group, and the other `0` gives nothing to the Public.
</details>

### Level 2: Real-World
**Task:** You wrote a bash script `deploy.sh`. Make it executable, then run it using `sudo`.
<details>
<summary>Hint</summary>
Use <code>chmod +x</code> to make it executable.
</details>
<details>
<summary>Solution Walkthrough</summary>
1. <code>chmod +x deploy.sh</code> (or <code>chmod 755 deploy.sh</code>)
2. <code>sudo ./deploy.sh</code>
The `+x` flag specifically adds the execute bit without modifying the read/write bits.
</details>

### Level 3: Boss Level
**Task:** Create a directory `/opt/app-data`. Make a user named `appuser`. Assign ownership of the directory to `appuser`. Ensure that `appuser` has full rights, the group has read/execute, and others have zero access whatsoever.
<details>
<summary>Hint</summary>
You need <code>sudo useradd</code>, <code>sudo chown</code>, and <code>sudo chmod 750</code>.
</details>
<details>
<summary>Solution Walkthrough</summary>

```bash
# 1. Create the user
sudo useradd appuser

# 2. Create the directory
sudo mkdir -p /opt/app-data

# 3. Assign ownership to appuser
sudo chown appuser:appuser /opt/app-data

# 4. Set strict permissions (Owner: 7, Group: 5, Others: 0)
sudo chmod 750 /opt/app-data

# Verify
ls -ld /opt/app-data
# Output should look like: drwxr-x--- appuser appuser ...
```
Using `750` blocks any other user on the server (except root) from even seeing what is inside the directory.
</details>
