# 3.2 Scheduled Cron Jobs

## Phase A: Core Concepts

### 1. Real-World Pain Point (The Why)
You wrote a brilliant backup script that saves your database every time you run it. But you have to remember to run it manually every night at midnight. If you go on vacation or simply forget, and the server crashes the next day, you lose a day's worth of data. You need a robot that executes your script on a precise schedule, forever, without human intervention.

### 2. Plain English Metaphor (The What)
- **Cron daemon (`crond`):** The server's built-in alarm clock. It wakes up every single minute, checks its list of alarms, and goes back to sleep.
- **Crontab (`crontab -e`):** The actual list of alarms. It's a text file where you define *when* to wake up and *what* to do.
- **Cron syntax (`* * * * *`):** The language used to set the alarm clock, representing Minute, Hour, Day of Month, Month, and Day of Week.

### 3. Complete Runnable Code
Here is how you set up an Automated Midnight Database Backup & Rotation Cron.

First, the script (`/opt/scripts/db_backup.sh`):
```bash
#!/usr/bin/env bash
set -e

# Backup PostgreSQL database to a file with today's date
BACKUP_FILE="/backups/db-$(date +\%F).sql"
echo "[$(date)] Starting backup to $BACKUP_FILE..."

# (Simulated database dump)
echo "Dumping database data..." > "$BACKUP_FILE"

# Delete backups older than 7 days to save disk space (Rotation)
find /backups/ -name "db-*.sql" -type f -mtime +7 -exec rm {} \;

echo "[$(date)] Backup and rotation complete."
```

Then, the crontab configuration (run `crontab -e` and paste this):
```bash
# Minute Hour DayOfMonth Month DayOfWeek Command
# Run every day at midnight (00:00) and append output to a log file
0 0 * * * /opt/scripts/db_backup.sh >> /var/log/db_backup.log 2>&1
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: The Backup and Rotation Script**
```bash
find /backups/ -name "db-*.sql" -type f -mtime +7 -exec rm {} \;
```
In the script, we create a backup, but backups pile up and eat disk space. The `find` command is used here for log rotation. `-mtime +7` finds files modified more than 7 days ago. `-exec rm {} \;` executes the remove command on every file found.

**Step 2: Understanding Cron Syntax**
```bash
0 0 * * *
```
The five stars represent: `[Minute] [Hour] [Day of Month] [Month] [Day of Week]`.
`0 0 * * *` means: Minute 0, Hour 0 (Midnight), Every Day, Every Month, Every Day of Week.
Another example: `30 14 * * 5` means 2:30 PM every Friday.

**Step 3: Logging Cron Output**
```bash
... >> /var/log/db_backup.log 2>&1
```
Cron jobs run in the background with no terminal attached. If they print errors, you will never see them. `>> /var/log/...` captures standard output. `2>&1` takes standard errors (2) and redirects them to wherever standard output (1) is going. This ensures all logs and errors are safely recorded.

### 5. ASCII Data Flow

```text
[System Clock] ---> Hits 00:00 ---> [Cron Daemon]
                                          |
                                          v
                                 Reads Crontab File
                                          |
                                          v
                              Executes /opt/scripts/db_backup.sh
                                          |
                        (stdout/stderr)   v
                           [ /var/log/db_backup.log ]
```

### 6. Noob Trap vs Pro Tip
**Noob Trap:** Using relative paths like `cd myapp` or relying on environment variables inside a cron script. Cron runs with an extremely limited environment (a minimal `$PATH`). Always use absolute paths (e.g., `/usr/bin/node` instead of `node`, `/opt/app` instead of `app`).
**Pro Tip:** If you want a script to run every 5 minutes, you use a slash step value: `*/5 * * * *`. If you want to use the `%` character in a cron command, you must escape it like `\%`, because cron interprets `%` as a newline.

### Level 2: Real-World
**Task:** You want a health-check script (`/usr/local/bin/healthcheck.sh`) to run every 10 minutes. Set up the crontab entry so that its output is entirely discarded (sent to the black hole) so it doesn't create massive log files over time.
<details>
<summary>Hint</summary>
Use the <code>*/10</code> step syntax and redirect to <code>/dev/null</code>.
</details>
<details>
<summary>Solution Walkthrough</summary>
<code>*/10 * * * * /usr/local/bin/healthcheck.sh > /dev/null 2>&1</code>
The `*/10` means "every 10 minutes". The `> /dev/null 2>&1` throws away both standard output and standard error.
</details>

### Level 3: Boss Level
**Task:** Create a script that checks if your web server (Nginx) is running. If it's not running, it starts it and logs the event. Then, write the crontab entry to run this "watchdog" script every minute.
<details>
<summary>Hint</summary>
You can use <code>pgrep nginx</code> to check if it's running. Use <code>systemctl start nginx</code> to start it.
</details>
<details>
<summary>Solution Walkthrough</summary>

First, the script `/opt/watchdog.sh`:
```bash
#!/usr/bin/env bash

# Check if nginx process is running silently
if ! pgrep -x "nginx" > /dev/null; then
    echo "[$(date)] Nginx is down! Attempting to restart..." >> /var/log/watchdog.log
    # Requires sudo privileges if not run as root
    systemctl start nginx
fi
```

Then, make it executable:
```bash
chmod +x /opt/watchdog.sh
```

Finally, the crontab entry (run via `sudo crontab -e` so it has permissions to restart services):
```bash
* * * * * /opt/watchdog.sh
```
`* * * * *` means run every single minute of every single day.
</details>
