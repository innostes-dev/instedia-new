# 2.1 Redis Power Structures: Sorted Sets & Leaderboards

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
You are building a live multiplayer battle royale game. You need a real-time leaderboard showing the top 10 players globally. Every time a player scores a kill, their score updates, and the leaderboard must instantly recalculate ranks. In a relational database (SQL), you would have to run `SELECT user_id, score FROM users ORDER BY score DESC LIMIT 10;`. Doing this sorting operation thousands of times a second on millions of rows will completely destroy your database CPU.

### 2. Plain English Metaphor (The What)
Think of a SQL database like a massive stack of ungraded test papers. To find the highest score, you have to read through every single paper, write down the scores, sort them on a separate piece of paper, and then find the top 10.
A Redis **Sorted Set** is like a specialized filing cabinet that *automatically keeps files in alphabetical (or numerical) order the exact moment you insert them*. You just reach into the front of the cabinet and grab the first 10 files instantly, because the sorting work was already done during insertion.

### 3. Complete Runnable Code: Real-Time Live Gaming Score Leaderboard

Here is a Node.js Express example using Redis Sorted Sets to manage a leaderboard.

```javascript
const express = require('express');
const { createClient } = require('redis');
const app = express();
app.use(express.json());

const initLeaderboard = async () => {
    const redisClient = createClient();
    await redisClient.connect();

    const LEADERBOARD_KEY = 'game:global:leaderboard';

    // 1. Submit or Update a Score
    app.post('/api/score', async (req, res) => {
        const { username, points } = req.body; // e.g. points = 100 (points to add)

        // ZINCRBY: Increments the score of a member in a sorted set.
        // If the member does not exist, they are added with the score.
        const newTotalScore = await redisClient.zIncrBy(LEADERBOARD_KEY, points, username);

        res.json({ username, totalScore: newTotalScore, message: 'Score updated!' });
    });

    // 2. Get Top 10 Leaderboard
    app.get('/api/leaderboard/top10', async (req, res) => {
        // ZRANGE: Returns a range of members in a sorted set, by index.
        // REV: Reverse order (highest to lowest).
        // WITHSCORES: Return the score along with the member name.
        const topPlayers = await redisClient.zRangeWithScores(
            LEADERBOARD_KEY,
            0, // Start index (Rank 1)
            9, // End index (Rank 10)
            { REV: true }
        );

        // Map Redis output [{value: 'Player1', score: 500}, ...]
        const formattedLeaderboard = topPlayers.map((p, index) => ({
            rank: index + 1,
            username: p.value,
            score: p.score
        }));

        res.json({ leaderboard: formattedLeaderboard });
    });

    // 3. Get Specific User Rank
    app.get('/api/leaderboard/rank/:username', async (req, res) => {
        const username = req.params.username;

        // ZREVRANK: Determine the index of a member, with scores ordered from high to low.
        const rankIndex = await redisClient.zRevRank(LEADERBOARD_KEY, username);

        if (rankIndex === null) {
            return res.status(404).json({ message: 'User not on leaderboard' });
        }

        // Ranks are 0-indexed, so we add 1
        const actualRank = rankIndex + 1;

        res.json({ username, rank: actualRank });
    });

    app.listen(3000, () => console.log('Leaderboard API running on 3000'));
};

initLeaderboard();
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: Adding/Updating Scores (ZINCRBY)**
```javascript
const newTotalScore = await redisClient.zIncrBy(LEADERBOARD_KEY, points, username);
```
Instead of fetching the current score, adding to it, and saving it back (which causes race conditions), `ZINCRBY` atomically increments the score for `username`. Under the hood, Redis instantly adjusts the user's position in the balanced tree data structure (Skip List) to keep the set sorted perfectly.

**Step 2: Fetching the Top Players (ZRANGE)**
```javascript
const topPlayers = await redisClient.zRangeWithScores(LEADERBOARD_KEY, 0, 9, { REV: true });
```
Because the list is already sorted, fetching the top 10 is an O(log(N) + M) operation, which is incredibly fast. We use `REV: true` because by default, Redis sorts from lowest score to highest, and we want highest to lowest.

**Step 3: Finding a Specific Rank (ZREVRANK)**
```javascript
const rankIndex = await redisClient.zRevRank(LEADERBOARD_KEY, username);
```
Finding out that player 'NoobMaster69' is rank #4,231 out of 5 million players takes fractions of a millisecond. In a SQL database, this would require calculating the count of all users who have a score higher than NoobMaster69, which is a very heavy query.

### 5. ASCII Data Flow

```text
 [ Player Scores +100 ]
          |
          v
 [ ZINCRBY 'leaderboard' 100 'PlayerX' ]
          |
+------------------------------------+
| Redis Sorted Set (Auto-sorting!)   |
| 1. ProGamer  : 9500                |
| 2. PlayerX   : 8100  <-- Jumped up |
| 3. NoobGuy   : 8000                |
+------------------------------------+
          |
[ ZRANGE 0 9 REV ] -> Instantly returns top 10
```

### 6. Noob Trap vs Pro Tip

**Noob Trap:** Storing massive JSON objects as the "member" string in the Sorted Set. For example: `ZADD leaderboard 500 '{"id":1, "name":"Player1", "avatar":"url"}'`. If the user changes their avatar, you have to delete the old JSON string from the set and re-insert the new one because the string *is* the unique identifier.

**Pro Tip:** Only store unique IDs (like `user:123`) in the Sorted Set. Store the user's metadata (Name, Avatar) in a separate Redis Hash (`HSET`). When you pull the top 10 IDs from the Sorted Set, execute a quick pipeline of `HGETALL` commands to fetch the associated display data.

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**Task:** Players often have exactly the same score. When a tie happens, you want the first person who achieved that score to be ranked higher. However, standard Redis Sorted Sets resolve ties based on lexicographical (alphabetical) order of the member names. How can you modify the score you insert to naturally handle time-based tie-breakers?

<details>
<summary><b>Hint</b></summary>
You can use floating-point numbers in Sorted Sets. Combine the actual score with a timestamp fraction. For example, if score is 100, make the Redis score `100.9999999999999` minus the current timestamp.
</details>

<details>
<summary><b>Full Solution Walkthrough</b></summary>
To resolve ties by time (older is better), you append a time-derived fraction to the integer score.
Because we want the *oldest* time to be ranked *highest* in a tie, we subtract the timestamp from a large maximum value.

```javascript
// Function to generate a tie-breaking score
function generateScore(baseScore) {
    // Get current time in milliseconds
    const now = Date.now();
    // Max timestamp we care about (e.g. year 2100)
    const MAX_TIME = 4102444800000;

    // Create a tiny fraction where older timestamps result in a larger fraction
    const timeFraction = (MAX_TIME - now) / MAX_TIME;

    // e.g., 500.9998273
    return baseScore + timeFraction;
}

// When displaying to user, just Math.floor() it!
const displayScore = Math.floor(redisScore);
```
</details>

### Level 2: Real-World
**Task:** Implement the "Pro Tip". You have a Sorted Set containing only user IDs (`user:1`, `user:2`). Write the code to fetch the Top 5 IDs, and then look up their corresponding usernames and avatars stored in Redis Hashes (e.g., key `user:1:profile`), returning a fully combined JSON array to the client.

<details>
<summary><b>Hint</b></summary>
Use `ZREVRANGE` (or `ZRANGE` with `REV`) to get the top 5 IDs. Then map over those IDs to create an array of `redisClient.hGetAll(profileKey)` promises. Use `Promise.all()` to resolve them concurrently.
</details>

<details>
<summary><b>Full Solution Walkthrough</b></summary>

```javascript
app.get('/api/leaderboard/rich', async (req, res) => {
    // 1. Get Top 5 IDs and Scores
    const topIds = await redisClient.zRangeWithScores(
        LEADERBOARD_KEY, 0, 4, { REV: true }
    );

    // 2. Prepare parallel fetches for Hash data
    const profilePromises = topIds.map(async (item) => {
        const userId = item.value;
        const score = item.score;

        // Fetch metadata stored via HSET
        const profileKey = `profile:${userId}`;
        const profileData = await redisClient.hGetAll(profileKey);

        return {
            id: userId,
            score: score,
            username: profileData.username || 'Unknown',
            avatar: profileData.avatar || 'default.png'
        };
    });

    // 3. Execute all HGETALLs concurrently
    const richLeaderboard = await Promise.all(profilePromises);

    res.json({ leaderboard: richLeaderboard });
});
```
This is the standard production pattern for separating sorting indexes from data storage.
</details>

### Level 3: Boss Level
**Task:** You need to maintain an "All-Time" leaderboard AND a "Weekly" leaderboard. Furthermore, at midnight on Sunday, the Weekly leaderboard must reset. How do you structure this without losing data during the reset?

<details>
<summary><b>Hint</b></summary>
Include the ISO week number in the Redis key name (e.g., `leaderboard:weekly:2023-W41`). When adding a score, use a Redis Pipeline/Multi to increment BOTH the All-Time key and the current week's key simultaneously. You don't need a chron job to "reset" the weekly board; next week, the app will just start writing to `2023-W42`.
</details>

<details>
<summary><b>Full Solution Walkthrough</b></summary>

```javascript
const { getISOWeek, getYear } = require('date-fns'); // Utility for weeks

app.post('/api/score/multi', async (req, res) => {
    const { userId, points } = req.body;

    // Calculate current week string (e.g., '2023-W41')
    const now = new Date();
    const weekString = `${getYear(now)}-W${getISOWeek(now)}`;

    const allTimeKey = 'leaderboard:alltime';
    const weeklyKey = `leaderboard:weekly:${weekString}`;

    // Use a transaction (MULTI) to ensure both update together
    const multi = redisClient.multi();

    multi.zIncrBy(allTimeKey, points, userId);
    multi.zIncrBy(weeklyKey, points, userId);

    // Optional: Set a TTL on the weekly key so old weeks purge automatically after a month
    multi.expire(weeklyKey, 60 * 60 * 24 * 30);

    await multi.exec();

    res.json({ message: 'Both leaderboards updated successfully' });
});

// To fetch the current weekly leaderboard:
app.get('/api/leaderboard/current-week', async (req, res) => {
    const now = new Date();
    const weekString = `${getYear(now)}-W${getISOWeek(now)}`;
    const weeklyKey = `leaderboard:weekly:${weekString}`;

    const top = await redisClient.zRangeWithScores(weeklyKey, 0, 9, { REV: true });
    res.json(top);
});
```
This time-bucketing strategy is highly scalable and completely eliminates the need for expensive, locking "reset" scripts running on a schedule.
</details>
