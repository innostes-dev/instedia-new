# 2.3 Distributed Locks and Redlock

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
A user clicks the "Checkout" button on your e-commerce site. Because the site is slightly slow, they angrily double-click the button. Two separate HTTP POST requests hit your API simultaneously. They get routed by a load balancer to two different Node.js servers. Both servers check the database: "Does user have enough balance?" Yes. Both deduct the balance. Both ship an expensive laptop. You just double-charged the user and shipped two laptops for the price of one. This is a severe Race Condition. You need a way to ensure only *one* server processes a checkout for a specific user at a given time.

### 2. Plain English Metaphor (The What)
Imagine a bank with 5 different tellers (your servers) but only one central safety deposit box (the user's account). If two tellers try to put their hand in the box at the same time, money goes missing.
A Distributed Lock is a single padlock on the box. Teller 1 runs up, puts their padlock on it, and takes the key. When Teller 2 arrives a second later, they see the padlock and have to wait. Once Teller 1 finishes their transaction, they remove the padlock, allowing Teller 2 to take a turn. Redis acts as the central manager handing out these padlocks.

### 3. Complete Runnable Code: High-Security Payment Deduplication Lock

Here is a Node.js Express example demonstrating a simple Distributed Lock using Redis `SET` with the `NX` flag.

```javascript
const express = require('express');
const { createClient } = require('redis');
const { v4: uuidv4 } = require('uuid'); // for unique lock values
const app = express();
app.use(express.json());

const initApp = async () => {
    const redisClient = createClient();
    await redisClient.connect();

    app.post('/api/checkout', async (req, res) => {
        const userId = req.body.userId;
        const lockKey = `lock:checkout:${userId}`;
        const lockValue = uuidv4(); // Unique ID for this specific server/process

        try {
            // 1. Acquire Lock
            // NX: Only set the key if it does NOT already exist.
            // PX: Auto-expire the lock in 5000ms (5s) in case this server crashes.
            const lockAcquired = await redisClient.set(lockKey, lockValue, {
                NX: true,
                PX: 5000
            });

            if (!lockAcquired) {
                // Another server is already processing this user's checkout
                return res.status(409).json({
                    error: 'Conflict',
                    message: 'A checkout is already in progress. Please wait.'
                });
            }

            console.log(`[LOCKED] Processing checkout for user ${userId}...`);

            // 2. Perform Critical Section (e.g., charge credit card, deduct inventory)
            await new Promise(resolve => setTimeout(resolve, 2000)); // Simulate work
            console.log(`[SUCCESS] Checkout complete for user ${userId}.`);

            // 3. Safe Release Lock (Only release if WE hold the lock)
            // We use a simple Lua script to ensure atomicity during deletion
            const luaScript = `
                if redis.call("get", KEYS[1]) == ARGV[1] then
                    return redis.call("del", KEYS[1])
                else
                    return 0
                end
            `;
            await redisClient.eval(luaScript, {
                keys: [lockKey],
                arguments: [lockValue]
            });

            res.json({ message: 'Checkout successful!' });

        } catch (err) {
            console.error(err);
            res.status(500).send('Server error');
        }
    });

    app.listen(3000, () => console.log('Payment API running on 3000'));
};

initApp();
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: The Atomic NX Set**
```javascript
const lockAcquired = await redisClient.set(lockKey, lockValue, { NX: true, PX: 5000 });
```
This is the core of distributed locking. `NX` guarantees that if two servers attempt this command at the exact same millisecond, only ONE will succeed. Redis acts as the ultimate arbiter. We *must* include `PX` (Expiration) because if Server A acquires the lock and then immediately crashes (Out of Memory), the lock would be held forever (a Deadlock). The 5-second TTL ensures the lock automatically frees itself if things go wrong.

**Step 2: Blocking Concurrent Requests**
```javascript
if (!lockAcquired) return res.status(409).json(...);
```
If the lock wasn't acquired, it means another process is currently checking out this user. We instantly return a 409 Conflict (or we could choose to write a loop that waits and retries).

**Step 3: The Safe Release (Lua Script)**
```lua
if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("del", KEYS[1]) else return 0 end
```
Why a Lua script? Imagine Server A gets the lock (5s TTL). Server A experiences a huge Garbage Collection pause and takes 6 seconds to process the checkout. At 5 seconds, the lock auto-expires. Server B clicks checkout, acquires the lock, and starts processing. Then, Server A finally finishes and executes `redisClient.del(lockKey)`. Server A just deleted **Server B's lock**!
By checking that the `lockValue` (the UUID we generated) matches before deleting, we ensure a server only deletes its *own* lock.

### 5. ASCII Data Flow

```text
Server A (User clicks Checkout)       Server B (User double-clicks Checkout)
        |                                      |
[ SET NX PX 5000 ]                     [ SET NX PX 5000 ]
        |                                      |
        v                                      v
    [ Redis Executes A first ] -> OK       [ Redis Executes B second ] -> null
        |                                      |
[ Begins Checkout logic ]              [ Returns 409 Conflict ]
        |
[ EVAL (Delete if value matches) ]
```

### 6. Noob Trap vs Pro Tip

**Noob Trap:** Using `GET` to check if a lock exists, and then `SET` to create it. `if (!await redis.get('lock')) { await redis.set('lock', '1') }`. This is entirely broken. Two servers will run `GET` simultaneously, both see it doesn't exist, and both run `SET`. They both think they have the lock.

**Pro Tip:** For 99% of applications, the single-node Redis lock shown above is perfect. However, if your Redis node crashes entirely, you lose all locks. For highly critical financial systems across multi-node Redis clusters, use the **Redlock algorithm**, which involves acquiring locks on a majority of independent Redis nodes (e.g., 3 out of 5) to guarantee safety even during network partitions.

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**Task:** In the current implementation, if a user gets a 409 Conflict, they have to manually click the button again. Modify the code to implement a simple "Spin Lock". If the lock isn't acquired, wait 100ms and try again, up to a maximum of 10 retries, before finally returning an error to the user.

<details>
<summary><b>Hint</b></summary>
Create a recursive function or a `while` loop. Inside the loop, try to acquire the lock. If it fails, use `await new Promise(resolve => setTimeout(resolve, 100));`. Keep track of the loop count.
</details>

<details>
<summary><b>Full Solution Walkthrough</b></summary>

```javascript
const acquireLockWithRetry = async (redisClient, key, value, retries = 10, delay = 100) => {
    for (let i = 0; i < retries; i++) {
        const acquired = await redisClient.set(key, value, { NX: true, PX: 5000 });
        if (acquired) return true;

        // Wait and retry
        console.log(`Lock busy. Retrying... (${i+1}/${retries})`);
        await new Promise(resolve => setTimeout(resolve, delay));
    }
    return false; // Failed after all retries
};

// Inside route:
const lockAcquired = await acquireLockWithRetry(redisClient, lockKey, lockValue);
if (!lockAcquired) {
    return res.status(503).json({ error: 'Service Unavailable', message: 'System busy.' });
}
```
This massively improves User Experience, as the system handles the waiting transparently.
</details>

### Level 2: Real-World
**Task:** You need to perform a database migration script across your architecture, but you want to ensure only *one* cron job container runs it at midnight, even though you have 5 cron containers scaled up. You have an Express endpoint `/api/trigger-migration`. Wrap this in a Redis lock, but this time, wrap the lock acquisition and release logic into a clean, reusable Higher-Order Function so you don't clutter your business logic.

<details>
<summary><b>Hint</b></summary>
Create a function `withLock(lockKeyName, workerFunction)`. Inside `withLock`, acquire the lock, `try { await workerFunction() }`, and in the `finally` block, execute the safe release Lua script.
</details>

<details>
<summary><b>Full Solution Walkthrough</b></summary>

```javascript
// Generic Lock Wrapper
const withLock = async (redisClient, lockKey, ttlMs, worker) => {
    const lockValue = uuidv4();
    const acquired = await redisClient.set(lockKey, lockValue, { NX: true, PX: ttlMs });

    if (!acquired) {
        throw new Error('Could not acquire lock');
    }

    try {
        // Execute the business logic
        return await worker();
    } finally {
        // Guarantee release regardless of success or failure
        const luaScript = `
            if redis.call("get", KEYS[1]) == ARGV[1] then
                return redis.call("del", KEYS[1])
            else return 0 end
        `;
        await redisClient.eval(luaScript, { keys: [lockKey], arguments: [lockValue] });
    }
};

// Usage
app.post('/api/trigger-migration', async (req, res) => {
    try {
        await withLock(redisClient, 'lock:db:migration', 30000, async () => {
            console.log('Running heavy database migration...');
            await runMigrationQueries();
            console.log('Migration complete.');
        });
        res.send('Migration triggered successfully');
    } catch (err) {
        res.status(409).send('Migration is already running elsewhere.');
    }
});
```
This is a standard pattern in production codebases to keep locking logic entirely decoupled from domain logic.
</details>

### Level 3: Boss Level
**Task:** Implement the "Lock Extension" (Watchdog) pattern. You set your lock TTL to 5 seconds. But what if your worker function occasionally takes 8 seconds due to database latency? If it takes 8 seconds, the lock expires at 5 seconds, and another server will grab the lock, causing the dreaded double-execution.
You need to write a background process that runs *while* the worker is running, checking the lock every 2 seconds, and if the worker isn't finished, it extends the TTL by another 5 seconds.

<details>
<summary><b>Hint</b></summary>
Inside your `withLock` function, before starting the `worker()`, start a `setInterval`. The interval should execute `redisClient.pExpire(lockKey, ttlMs)` (but ideally only if the lock value still matches, via Lua). When the `worker()` finishes (in the `finally` block), immediately `clearInterval(intervalId)`.
</details>

<details>
<summary><b>Full Solution Walkthrough</b></summary>

```javascript
const withLockAndWatchdog = async (redisClient, lockKey, ttlMs, worker) => {
    const lockValue = uuidv4();
    const acquired = await redisClient.set(lockKey, lockValue, { NX: true, PX: ttlMs });

    if (!acquired) throw new Error('Lock busy');

    let watchdogInterval;

    try {
        // Start the watchdog to extend TTL periodically
        // Run it every (TTL / 2) milliseconds
        watchdogInterval = setInterval(async () => {
            const extendLua = `
                if redis.call("get", KEYS[1]) == ARGV[1] then
                    return redis.call("pexpire", KEYS[1], ARGV[2])
                else return 0 end
            `;
            const extended = await redisClient.eval(extendLua, {
                keys: [lockKey],
                arguments: [lockValue, ttlMs.toString()]
            });
            if (extended) console.log(`[Watchdog] Extended lock ${lockKey}`);
        }, Math.floor(ttlMs / 2));

        // Run the actual slow work
        return await worker();

    } finally {
        // Stop extending the lock
        clearInterval(watchdogInterval);

        // Safely delete the lock
        const delLua = `
            if redis.call("get", KEYS[1]) == ARGV[1] then
                return redis.call("del", KEYS[1])
            else return 0 end
        `;
        await redisClient.eval(delLua, { keys: [lockKey], arguments: [lockValue] });
    }
};

// Usage
await withLockAndWatchdog(redisClient, 'lock:long-task', 5000, async () => {
    // Even if this takes 15 seconds, the watchdog will keep extending the 5s TTL
    // ensuring no other process can grab it.
    await new Promise(resolve => setTimeout(resolve, 15000));
});
```
This mechanism (often called a "Watchdog Timer" or "Lease Extension") is exactly how robust production locking libraries (like `redisson` in Java or `redlock` in Node) guarantee safety during unpredictable workloads.
</details>
