# 2.2 Distributed Rate Limiting

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
You have a public API endpoint for User Login. A malicious botnet starts hitting it 5,000 times a second, trying to brute-force passwords. You add an in-memory rate limiter to your Express server (`req.ip` counter in an array) to allow only 10 requests per minute. But your backend is scaled across 10 different servers behind a load balancer! The bot hits all 10 servers round-robin. Because each server's memory is isolated, the bot gets $10 \times 10 = 100$ requests per minute. You need a centralized, blazing-fast place to count requests across your entire distributed architecture.

### 2. Plain English Metaphor (The What)
Imagine a theme park with 10 different entrance gates (Your API servers). You only want to allow 100 VIPs into the park per hour total. If every gatekeeper uses their own clicker, they might accidentally let in 1,000 VIPs total.
Instead, you give all 10 gatekeepers walkie-talkies connected to a single central boss (Redis). Every time a VIP arrives at *any* gate, the gatekeeper asks the boss, "Can I let one in?" The boss increments a single master whiteboard counter. If the boss sees 100, they tell all gatekeepers over the walkie-talkie: "Stop, park is full for this hour."

### 3. Complete Runnable Code: Production Anti-Abuse API Rate Limiter

Here is a Node.js Express middleware using the Redis atomic `INCR` and `EXPIRE` commands to implement a Fixed Window Rate Limiter.

```javascript
const express = require('express');
const { createClient } = require('redis');
const app = express();

let redisClient;

const initApp = async () => {
    redisClient = createClient();
    await redisClient.connect();

    // Rate Limiting Middleware
    const rateLimiter = (limit, windowSeconds) => async (req, res, next) => {
        // Use IP address as the identifier (can also use API Key or User ID)
        const userIp = req.ip;

        // Use a time-bucketed key: e.g., "ratelimit:192.168.1.1:2023-10-31T14:30"
        // This rounds the current time down to the current minute
        const currentMinute = Math.floor(Date.now() / 1000 / windowSeconds);
        const key = `ratelimit:${userIp}:${currentMinute}`;

        try {
            // INCR is atomic. If key doesn't exist, it creates it and sets to 1.
            const requestCount = await redisClient.incr(key);

            // If this is the very first request in this window, set the TTL
            if (requestCount === 1) {
                // Expire the key safely after the window passes
                await redisClient.expire(key, windowSeconds + 10);
            }

            if (requestCount > limit) {
                return res.status(429).json({
                    error: 'Too Many Requests',
                    message: `You have exceeded the ${limit} requests per ${windowSeconds}s limit.`
                });
            }

            // Optional: Send rate limit info in headers (Pro-tip!)
            res.setHeader('X-RateLimit-Limit', limit);
            res.setHeader('X-RateLimit-Remaining', Math.max(0, limit - requestCount));

            next();
        } catch (error) {
            console.error('Redis error', error);
            // Fail open: If Redis crashes, don't break the whole app
            next();
        }
    };

    // Apply to a sensitive route
    app.post('/api/login', rateLimiter(5, 60), (req, res) => {
        res.json({ message: 'Login attempt processed.' });
    });

    app.listen(3000, () => console.log('Server running on 3000'));
};

initApp();
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: Identifying the Client and Time Window**
```javascript
const currentMinute = Math.floor(Date.now() / 1000 / windowSeconds);
const key = `ratelimit:${userIp}:${currentMinute}`;
```
We combine the user's IP with a mathematical string representing the current minute (e.g., minute `28,234,441`). When the clock rolls over to the next minute, the key completely changes, granting the user a fresh bucket of requests.

**Step 2: Atomic Increment (INCR)**
```javascript
const requestCount = await redisClient.incr(key);
```
`INCR` is the magic here. It is *atomic*. Even if 50 Node.js servers receive a request from the same IP at the exact same millisecond, Redis executes `INCR` commands one by one sequentially in its single-threaded event loop. There are no race conditions. `requestCount` will definitively be 1, 2, 3... 50.

**Step 3: Setting the TTL and Enforcement**
```javascript
if (requestCount === 1) await redisClient.expire(key, windowSeconds + 10);
if (requestCount > limit) return res.status(429).send(...);
```
We set an `EXPIRE` only on the very first increment to clean up memory later. If the atomic increment returns a number higher than our limit, we instantly block the request with HTTP Status 429.

### 5. ASCII Data Flow

```text
    Botnet (IP: 1.1.1.1)
    fires 3 concurrent requests
          |  |  |
    +-----+--+--+-----+
    |                 |
[Server 1]       [Server 2]
    |                 |
 INCR key          INCR key
    |                 |
    +--------+--------+
             v
       [ Redis ] (Processes sequentially)
       1. INCR -> returns 1
       2. INCR -> returns 2
       3. INCR -> returns 3 (Exceeds limit of 2!)
             |
             v
Server 1: OK  |  Server 2: 429 Too Many Requests
```

### 6. Noob Trap vs Pro Tip

**Noob Trap:** Using `GET` followed by `SET` in application code.
```javascript
let count = await redisClient.get(key); // returns 9
count++;
await redisClient.set(key, count); // saves 10
```
If two requests happen at the same time, they both `GET` 9, both increment to 10, and both `SET` 10. You missed a request, allowing attackers to bypass your limits by sending parallel requests.

**Pro Tip:** Always use Redis atomic operations like `INCR`. Also, notice the `catch (error) { next(); }` in the code. If your rate-limiting Redis cluster crashes, your API should "Fail Open" (allow requests through) rather than taking your entire business offline.

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**Task:** The current fixed-window rate limiter has a flaw called the "boundary problem." If the limit is 10 requests per minute, a bot can send 10 requests at 1:59:59 and 10 more requests at 2:00:01. They successfully made 20 requests in just 2 seconds!
To mitigate this slightly without completely changing algorithms, implement a secondary, tighter rate limit on the same route. E.g., Max 10 per minute, AND max 2 per second.

<details>
<summary><b>Hint</b></summary>
You can chain multiple middleware functions in Express. Apply the `rateLimiter` function twice to the route array.
</details>

<details>
<summary><b>Full Solution Walkthrough</b></summary>

```javascript
// Apply strict per-second limit AND looser per-minute limit
app.post('/api/login',
    rateLimiter(2, 1),   // Max 2 requests per 1 second window
    rateLimiter(10, 60), // Max 10 requests per 60 second window
    (req, res) => {
        res.json({ message: 'Login attempt processed.' });
    }
);
```
This forces the bot to spread out their 10 requests over at least 5 seconds, heavily mitigating the boundary spike.
</details>

### Level 2: Real-World
**Task:** Switch from the Fixed Window algorithm to the **Sliding Window Log** algorithm to perfectly solve the boundary problem.
Instead of incrementing a simple counter, store a timestamp for every single request in a Redis Sorted Set (`ZADD`). To check the limit, remove all timestamps older than 60 seconds (`ZREMRANGEBYSCORE`), then count the remaining items (`ZCARD`). If the count > limit, block.

<details>
<summary><b>Hint</b></summary>
Use a `MULTI` block to execute `ZREMRANGEBYSCORE`, `ZADD`, `ZCARD`, and `EXPIRE` atomically. The score for the Sorted Set is `Date.now()`, and the value should be a unique string (like a UUID or timestamp + random string) since Sorted Sets require unique members.
</details>

<details>
<summary><b>Full Solution Walkthrough</b></summary>

```javascript
const { v4: uuidv4 } = require('uuid');

const slidingWindowLimiter = (limit, windowSeconds) => async (req, res, next) => {
    const key = `sliding:${req.ip}`;
    const now = Date.now();
    const windowStart = now - (windowSeconds * 1000);

    // Member must be unique. Score is the timestamp.
    const member = uuidv4();

    const multi = redisClient.multi();
    // 1. Remove requests outside the current sliding window
    multi.zRemRangeByScore(key, 0, windowStart);
    // 2. Add current request
    multi.zAdd(key, { score: now, value: member });
    // 3. Get total count in the window
    multi.zCard(key);
    // 4. Set expiry to clean up memory if IP stops requesting
    multi.expire(key, windowSeconds);

    try {
        const results = await multi.exec();
        const requestCount = results[2]; // Result of ZCARD

        if (requestCount > limit) {
            return res.status(429).send('Too Many Requests');
        }
        next();
    } catch (err) {
        next();
    }
};
```
This algorithm is 100% accurate down to the millisecond, completely destroying the boundary problem.
</details>

### Level 3: Boss Level
**Task:** The Sliding Window Log is perfect, but it consumes a lot of RAM because it stores every single request ID as a string in the Sorted Set. For massive scale, write a custom Lua Script that executes a **Token Bucket** algorithm entirely inside Redis. The script should deduct tokens on request, and automatically refill tokens based on the time elapsed since the last request.

<details>
<summary><b>Hint</b></summary>
You can use `redisClient.eval(luaScript, ...)` or the newer `redisClient.executeIsolated` functions. A Lua script in Redis is fully atomic. The script needs to read current tokens, check `redis.call("TIME")`, calculate how many tokens to add based on the time delta, update the bucket, deduct 1, and return 1 (allow) or 0 (deny).
</details>

<details>
<summary><b>Full Solution Walkthrough</b></summary>

```javascript
const LUA_SCRIPT = `
    local key = KEYS[1]
    local capacity = tonumber(ARGV[1])
    local refillRatePerSecond = tonumber(ARGV[2])

    local currentTime = redis.call('TIME')
    local now = tonumber(currentTime[1]) -- Seconds

    local bucket = redis.call('HMGET', key, 'tokens', 'lastRefill')
    local tokens = tonumber(bucket[1])
    local lastRefill = tonumber(bucket[2])

    -- Initialize if it doesn't exist
    if not tokens then
        tokens = capacity
        lastRefill = now
    end

    -- Calculate refill
    local elapsedTime = math.max(0, now - lastRefill)
    local tokensToAdd = elapsedTime * refillRatePerSecond

    tokens = math.min(capacity, tokens + tokensToAdd)

    -- Check if we have enough tokens to process request
    if tokens >= 1 then
        tokens = tokens - 1
        -- Save updated state
        redis.call('HMSET', key, 'tokens', tokens, 'lastRefill', now)
        redis.call('EXPIRE', key, capacity / refillRatePerSecond * 2) -- Cleanup
        return 1 -- ALLOW
    else
        -- Save state just for refill timestamp, but don't deduct
        redis.call('HMSET', key, 'tokens', tokens, 'lastRefill', now)
        return 0 -- DENY
    end
`;

const tokenBucketLimiter = (capacity, refillRate) => async (req, res, next) => {
    const key = `bucket:${req.ip}`;

    try {
        // eval(script, numberOfKeys, key1, argv1, argv2)
        const result = await redisClient.eval(
            LUA_SCRIPT,
            {
                keys: [key],
                arguments: [capacity.toString(), refillRate.toString()]
            }
        );

        if (result === 1) {
            next();
        } else {
            res.status(429).send('Rate limit exceeded (Token Bucket Empty)');
        }
    } catch (err) {
        next(); // fail open
    }
};
```
This is the ultimate rate limiting implementation used by massive APIs like Stripe and Twitter. It uses minimal memory (just two integers per user) and executes atomically inside Redis.
</details>
