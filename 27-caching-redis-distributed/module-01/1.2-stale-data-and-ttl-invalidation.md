# 1.2 Stale Data, TTL, and Cache Invalidation

## Phase A: The Core Concept

### 1. Real-World Pain Point (The Why)
You successfully cached your product catalog. The database is saved! But an hour later, the marketing team updates the price of the sneaker from $299 to $199 for a Flash Sale. Users refresh the page, but they still see $299. Why? Because the Express server is happily returning the cached copy from Redis and completely ignoring the database. This is **Stale Data**. The hardest problem in computer science is cache invalidation: knowing when to throw away the old copy.

### 2. Plain English Metaphor (The What)
Imagine you write today's weather forecast on a whiteboard (Redis) in your office so colleagues don't have to look at their phones (Database). At 9 AM, it says "Sunny."
If you never erase it, colleagues leaving at 6 PM will think it's sunny, even if it's pouring rain outside.
A **TTL (Time-To-Live)** is like writing "Sunny (Valid until 12:00 PM)" on the board. At 12:01 PM, you automatically erase it, forcing you to look at your phone again for the latest update.

### 3. Complete Runnable Code: Self-Expiring Flash Sale Price Cache

Here is a Node.js Express example demonstrating TTL (Time-To-Live) and a Write-Through invalidation strategy.

```javascript
const express = require('express');
const { createClient } = require('redis');
const app = express();
app.use(express.json());

// Mock DB
const database = {
    '123': { id: '123', name: 'Flash Sneaker', price: 299.99 }
};

const initApp = async () => {
    const redisClient = createClient();
    await redisClient.connect();

    // READ Endpoint (Cache-Aside pattern)
    app.get('/api/products/:id', async (req, res) => {
        const cacheKey = `product:${req.params.id}`;

        // 1. Check Cache
        const cachedProduct = await redisClient.get(cacheKey);
        if (cachedProduct) {
            return res.json({ source: 'cache', data: JSON.parse(cachedProduct) });
        }

        // 2. Fetch from DB
        const product = database[req.params.id];

        // 3. Save to Redis WITH A TTL (EX: 60 seconds)
        if (product) {
            await redisClient.set(cacheKey, JSON.stringify(product), {
                EX: 60 // Expires in 60 seconds
            });
        }

        return res.json({ source: 'database', data: product });
    });

    // WRITE Endpoint (Cache Invalidation / Write-Through)
    app.put('/api/products/:id', async (req, res) => {
        const productId = req.params.id;
        const newPrice = req.body.price;
        const cacheKey = `product:${productId}`;

        // 1. Update the actual Database
        if (database[productId]) {
            database[productId].price = newPrice;
        }

        // 2. Invalidate (Delete) the stale cache entry IMMEDIATELY
        await redisClient.del(cacheKey);

        /*
           Alternative (Write-Through):
           await redisClient.set(cacheKey, JSON.stringify(database[productId]), { EX: 60 });
        */

        res.json({ message: 'Product updated and cache invalidated' });
    });

    app.listen(3000, () => console.log('Server running on 3000'));
};

initApp();
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: Setting a Time-To-Live (TTL)**
```javascript
await redisClient.set(cacheKey, JSON.stringify(product), {
    EX: 60 // Expires in 60 seconds
});
```
When storing data, we use the `EX` option (Expire in seconds). Redis will automatically delete this key after 60 seconds. This acts as a safety net ensuring data never stays stale forever.

**Step 2: Updating the Source of Truth (Database)**
```javascript
database[productId].price = newPrice;
```
When a PUT/POST request comes in to update data, we must always update the primary database first. The database is the persistent source of truth.

**Step 3: Active Cache Invalidation**
```javascript
await redisClient.del(cacheKey);
```
Even with a 60-second TTL, serving wrong prices during a Flash Sale for up to 59 seconds is unacceptable. Therefore, during the write operation, we proactively `DEL` (delete) the key from Redis. The next `GET` request will experience a Cache Miss, query the database for the new price, and cache the fresh data.

### 5. ASCII Data Flow

```text
  [ Client PUT (Update Price) ]
            |
            v
     [ Express API ]
      |          |
 (1) Update     (2) Delete Key (Invalidate)
   Database      |
      |          v
 [ SQL DB ]   [ Redis Cache ]
```

### 6. Noob Trap vs Pro Tip

**Noob Trap:** Using the "Write-Back" (or Write-Behind) pattern for critical data. This is where you write updates *only* to the Redis cache and asynchronously save to the database later. If the Redis server crashes before the sync, you permanently lose the user's data.

**Pro Tip:** Stick to **Cache-Aside** (lazy loading on reads) combined with active invalidation on writes for 95% of use cases. Always add a TTL as a fallback mechanism, even if you actively delete keys on writes. If your delete logic fails due to a network blip, the TTL guarantees the stale data will eventually purge itself.

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**Task:** Instead of deleting the cache key when a product is updated, modify the PUT endpoint to use the **Write-Through** pattern. This means updating the database AND immediately updating the Redis cache with the new value so the very next read is a Cache Hit.

<details>
<summary><b>Hint</b></summary>
Instead of `redisClient.del(cacheKey)`, use `redisClient.set(...)` with the newly updated product object, maintaining the `{ EX: 60 }` TTL.
</details>

<details>
<summary><b>Full Solution Walkthrough</b></summary>
Replace the `.del` call in the PUT route with a `.set` call.

```javascript
app.put('/api/products/:id', async (req, res) => {
    const productId = req.params.id;
    const newPrice = req.body.price;
    const cacheKey = `product:${productId}`;

    // 1. Update Database
    if (database[productId]) {
        database[productId].price = newPrice;
    }

    // 2. Write-Through: Update Cache directly
    await redisClient.set(cacheKey, JSON.stringify(database[productId]), {
        EX: 60
    });

    res.json({ message: 'Product updated and cache updated (Write-Through)' });
});
```
This improves read performance immediately following a write, as the cache is pre-warmed.
</details>

### Level 2: Real-World
**Task:** Your marketing team updates an entire "Category" of products (e.g., all 50 'Nike' shoes go on sale). You need to invalidate all 50 cached products. How do you handle invalidating a group of keys efficiently without knowing all 50 exact IDs in advance?

<details>
<summary><b>Hint</b></summary>
Redis does not support deleting by wildcard patterns efficiently in production (`KEYS *` blocks the server). Instead, you should cache the entire category response under one key (e.g., `category:nike:products`), OR use a technique called "Cache Tagging" / namespacing using a version number. For this level, implement the single-key category invalidation.
</details>

<details>
<summary><b>Full Solution Walkthrough</b></summary>
When users request a category page, cache the whole array:
`redisClient.set('category:nike:products', JSON.stringify(allNikeProducts), { EX: 300 })`

When any Nike shoe is updated, delete the specific shoe AND the category key:
```javascript
app.put('/api/products/:id', async (req, res) => {
    // ... update DB ...
    const product = database[req.params.id];

    // Delete individual product cache
    await redisClient.del(`product:${product.id}`);

    // Delete the overarching category cache
    await redisClient.del(`category:${product.brand}:products`);

    res.send('Updated');
});
```
This ensures the category listing page never shows the old price.
</details>

### Level 3: Boss Level
**Task:** Prevent **Thundering Herd (Cache Stampede)**. Imagine the TTL on a highly popular product (10,000 QPS) expires. For the 500 milliseconds it takes to query the database and rebuild the cache, 5,000 concurrent requests all experience a Cache Miss simultaneously. They all hit the database at the exact same time, crashing it. Implement a mechanism to ensure only *one* request goes to the database when the cache expires, while the others wait or return slightly stale data.

<details>
<summary><b>Hint</b></summary>
You need a "Mutex" (Mutual Exclusion Lock). You can use Redis `SET` with the `NX` (Not Exists) flag. When a cache miss happens, try to acquire a lock key (e.g., `lock:product:123`). Only the request that successfully sets the lock queries the DB. Other requests should wait and retry fetching from the cache after a brief delay.
</details>

<details>
<summary><b>Full Solution Walkthrough</b></summary>

```javascript
const fetchWithStampedeProtection = async (productId, res) => {
    const cacheKey = `product:${productId}`;
    const lockKey = `lock:product:${productId}`;

    // 1. Try to get data
    let cachedData = await redisClient.get(cacheKey);
    if (cachedData) {
        return res.json(JSON.parse(cachedData));
    }

    // 2. Cache Miss! Try to acquire a lock to query the DB
    // NX: Set only if it doesn't exist. PX 5000: Lock expires in 5s (safety against crashes)
    const acquiredLock = await redisClient.set(lockKey, 'locked', {
        NX: true,
        PX: 5000
    });

    if (acquiredLock) {
        // WE ARE THE CHOSEN ONE. We query the database.
        try {
            const product = await slowDatabaseQuery(productId);
            // Save to cache with normal TTL
            await redisClient.set(cacheKey, JSON.stringify(product), { EX: 60 });
            return res.json(product);
        } finally {
            // Always release the lock when done
            await redisClient.del(lockKey);
        }
    } else {
        // WE DID NOT GET THE LOCK. Someone else is querying the DB.
        // Wait 50ms and try reading the cache again.
        console.log('Stampede prevented. Waiting for other process to fill cache...');
        setTimeout(async () => {
            const retryData = await redisClient.get(cacheKey);
            if (retryData) {
                return res.json(JSON.parse(retryData));
            } else {
                return res.status(500).send('Timeout waiting for cache');
            }
        }, 50);
    }
};
```
This is a professional-grade caching layer. Only one database query is executed, completely protecting the database from stampedes when a popular cache key expires.
</details>
