# 2.1 Parsing Complex Unstructured Documents

## Phase A: Core Concept

### 1. Real-World Pain Point (The Why)
In enterprise environments, the most valuable knowledge isn't sitting in neat JSON APIs—it's locked inside messy, unstructured PDFs like financial 10-K reports, legal contracts, or medical records. If you just naively extract all text from a PDF, you lose the layout: a two-column financial table turns into a randomized string of numbers. When an LLM reads this garbled text, it hallucinates earnings or fails to answer basic financial questions.

### 2. Plain English Metaphor (The What)
Imagine taking a beautifully formatted magazine page with a main article, a sidebar, and a table of statistics, and throwing it into a blender. That's naive PDF parsing.
**Structured Parsing** is like carefully cutting out the main article, the sidebar, and the table with scissors, labeling them, and putting them into separate, organized folders so a reader can easily understand the flow of information.

### 3. Complete Runnable Code

    print("--- Structured Table Extraction (pdfplumber) ---")

### 4. Progressive Step-by-Step Breakdown

**Step 1: The Naive Blender**
Libraries like PyPDF2 scan the document purely by text placement left-to-right, top-to-bottom. If a PDF has a table or columns, the extraction reads across the columns, mashing headers and data rows together into a meaningless string.

**Step 2: Structured Bounding Boxes**
Libraries like `pdfplumber` (or advanced OCR like Unstructured.io / AWS Textract) analyze the visual layout, looking for lines, rectangles, and whitespace gaps. They identify a bounding box as a "Table".

**Step 3: Conversion to LLM-Friendly Formats**
Once a table is identified as a 2D array, we convert it into Markdown format (using pandas). LLMs are heavily trained on GitHub markdown data, making Markdown tables the absolute best way to pass tabular data into a prompt for accurate RAG.

### 5. ASCII Data Flow

```text
[ Financial PDF (Visual Layout) ]
      |
      |--> (Naive Parser) --> Text: "Year 2022 2023 Revenue 10M 15M" --> LLM: Confused.
      |
      |--> (Layout-Aware Parser)
           |
           |--> Bounding Box: Text Paragraph
           |--> Bounding Box: Table Grid -> [ ["Year", "Revenue"], ["2022", "$10M"] ]
           |
           |--> Conversion to Markdown --> LLM: Perfectly understands year over year growth.
```

### 6. Noob Trap vs Pro Tip
- **Noob Trap:** Using PyPDF2 to ingest a 100-page SEC 10-K report and chunking it by every 500 characters. Tables will be split in half, headers separated from data, and financial queries will fail spectacularly.
- **Pro Tip:** Use multimodal models (like GPT-4o-Vision) to bypass PDF text parsing entirely for complex pages. Convert the PDF page to an image, and ask the Vision LLM to return the page content directly as strict Markdown.

```python
def fallback_ocr(page_id):
    print(f"[WARN] Page {page_id} contains no text layer. Sending to OCR/Vision pipeline...")
    return "OCR Extracted Content: ... "

pages = [
    {"id": 1, "text": "This is a normal page with plenty of text describing the product."},
    {"id": 2, "text": "  \n  "}, # Scanned image page, no readable text
]

for page in pages:
    if len(page["text"].strip()) < 50:
        content = fallback_ocr(page["id"])
        print(content)
    else:
        print(f"Page {page['id']} parsed normally.")
```
This is the standard architecture for resilient enterprise document ingestion pipelines.
