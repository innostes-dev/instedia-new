# 2.5 Adding Rich Metadata to Chunks

## Phase A: Core Concept

### 1. Real-World Pain Point (The Why)
Imagine a Multi-Tenant SaaS application (like Notion or Slack) where thousands of companies share the same Vector Database. If User A from Company X asks a question, the vector similarity search might retrieve highly relevant chunks from Company Y's private documents, causing a massive data breach. Furthermore, if a user wants to search *only* within documents updated in 2024, pure vector similarity cannot do date filtering. Vector embeddings only understand "meaning," not exact boolean logic or permissions.

### 2. Plain English Metaphor (The What)
Vector Embeddings are the **text** of a book.
Metadata is the **library catalog card** (Author, Year, Genre, Access Level).
If you want a book about "Space Travel" (Vector Search), but you *only* want books written after 2010 that are in the Children's section (Metadata Filter), you apply a pre-filter using the catalog card before reading any text.

### 3. Complete Runnable Code
Let's see how attaching JSON metadata to chunks enables powerful pre-filtering in vector databases.

```python
# pip install chromadb
import chromadb

# 1. Initialize an in-memory vector database
client = chromadb.Client()
collection = client.create_collection("enterprise_knowledge_base")

# 2. Document Chunks with Metadata
# Notice how we decouple the raw text from strict attributes
documents = [
    "Q3 Financials show a 20% increase in revenue.",
    "Project Alpha is delayed until next month.",
    "Employee Bob has a salary of $90,000."
]

# Crucial: Metadata dictionary for each chunk
metadatas = [
    {"tenant_id": "org_apple", "doc_type": "finance", "year": 2023, "access_level": "public"},
    {"tenant_id": "org_apple", "doc_type": "engineering", "year": 2024, "access_level": "public"},
    {"tenant_id": "org_google", "doc_type": "hr", "year": 2024, "access_level": "confidential"}
]

ids = ["doc1", "doc2", "doc3"]

# Add to database (Chroma automatically embeds the text)
collection.add(
    documents=documents,
    metadatas=metadatas,
    ids=ids
)

# 3. Querying with Metadata Pre-Filtering
print("--- Scenario: User from org_apple searching for 2024 updates ---")
# The query is semantic, but we apply strict boolean filters FIRST.
results = collection.query(
    query_texts=["What is the status of our projects?"],
    n_results=2,
    where={
        "$and": [
            {"tenant_id": "org_apple"}, # Multi-tenant isolation!
            {"year": 2024}              # Time filtering!
        ]
    }
)

for doc, meta in zip(results['documents'][0], results['metadatas'][0]):
    print(f"Retrieved: '{doc}'")
    print(f"Metadata: {meta}\n")

# Notice how it completely ignores org_google's data, preventing a breach.
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: Defining the Schema**
We separate the text (which will be converted to dense vectors) from the structured facts (which remain exact strings/integers). We define critical fields: `tenant_id` for security, `doc_type` for categorization, and `year` for temporal filtering.

**Step 2: Ingestion**
When saving to the Vector DB, we pass the text, the metadata dicts, and unique IDs. The DB indexes the text in HNSW/IVF (Vector space) and indexes the metadata in a standard B-Tree/Inverted index (like Postgres).

**Step 3: Pre-Filtering (Where Clause)**
When querying, we pass a `where` clause. The database uses standard boolean logic to instantly narrow the search space down from millions of vectors to only those belonging to `org_apple` in `2024`. *Then*, it performs the heavy vector similarity search only on that small subset.

### 5. ASCII Data Flow

```text
Query: "Project status?" + Context: [User=org_apple, Time=2024]

[ Vector Database ]
       |
       |-- 1. Metadata Pre-Filter (B-Tree)
       |      Where tenant_id == "org_apple" AND year == 2024
       |      Reduces 1M documents -> 5,000 documents.
       |
       |-- 2. Vector Similarity Search (ANN / HNSW)
       |      Compares query vector to the remaining 5,000 vectors.
       |
Result: Top 3 most semantically relevant documents that passed security checks.
```

### 6. Noob Trap vs Pro Tip
- **Noob Trap:** Concatenating metadata directly into the text chunk (e.g., `Chunk: Tenant: org_google. Bob's salary is $90k`) and relying on the LLM or embedding model to figure it out. The model will frequently leak data across tenants because "org_apple" and "org_google" are semantically close in vector space.
- **Pro Tip:** Treat multi-tenancy at the database level. For true zero-trust architecture, some databases (like Qdrant or Pinecone) allow you to physically partition data by `namespace` or `partition_key`, ensuring tenant data never even shares the same index graph.

### Level 2: Real-World
**Challenge:** Implement Role-Based Access Control (RBAC). A user with `role="standard"` can only see chunks where `access_level="public"`. A user with `role="admin"` can see `public` OR `confidential`. Write a function `build_security_filter(tenant_id, role)` that returns the correct ChromaDB `where` dictionary.
<details>
<summary>Hint</summary>
Use an `if role == "standard"` statement. For standard, use an `$and` with `access_level: public`. For admin, use an `$in` operator for `access_level: ["public", "confidential"]` (or in Chroma, omit the access_level filter entirely if admin can see everything).
</details>

<details>
<summary>Solution Walkthrough</summary>
```python
def build_security_filter(tenant_id, role):
    base_filter = {"tenant_id": tenant_id}

    if role == "standard":
        return {
            "$and": [
                base_filter,
                {"access_level": "public"}
            ]
        }
    elif role == "admin":
        # Admins can see everything within their tenant
        return base_filter

# Usage
where_clause = build_security_filter("org_google", "standard")
# The query will now safely block the HR document for standard users.
```
</details>

Add `source_url` and `page_number` to the metadata of a new document. Run a query, and in the print loop, format the output exactly like: `Answer found in: [source_url] (Page X)`.
<details>

</details>

<details>
<summary>Solution Walkthrough</summary>
```python
collection.add(
    documents=["The servers must be restarted every Sunday."],
    metadatas=[{"tenant_id": "org_apple", "source_url": "https://wiki.corp.apple/IT", "page_number": 42}],
    ids=["doc4"]
)

results = collection.query(
    query_texts=["When do servers restart?"],
    n_results=1,
    where={"tenant_id": "org_apple"}
)

for doc, meta in zip(results['documents'][0], results['metadatas'][0]):
    print(f"Content: {doc}")
    # Safely get metadata, defaulting if missing
    url = meta.get('source_url', 'Unknown Source')
    page = meta.get('page_number', 'N/A')
    print(f"Citation: Read more at {url} (Page {page})")
```
This is how Perplexity and enterprise RAG systems build trustworthy, verifiable citations.
