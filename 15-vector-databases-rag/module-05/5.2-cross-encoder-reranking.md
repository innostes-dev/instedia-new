# 5.2 Cross-Encoder Re-Ranking

## Phase A: Core Concept

### 1. Real-World Pain Point (The Why)
Standard vector embeddings (Bi-Encoders) are fast because they embed the Query and the Document separately. However, this independent embedding process misses deep linguistic nuance. If the query is "How to get a visa for the US from the UK", standard vector search might return a document about "How to get a visa for the UK from the US" with a 99% similarity score because the words and concepts are identical, just swapped. You need a way to mathematically evaluate the relationship *between* the exact query and the document together.

### 2. Plain English Metaphor (The What)
- **Bi-Encoder (Standard Vector Search):** Like a resume-screening robot. It quickly scans 10,000 resumes and puts the Top 10 on your desk based on keyword and skill overlap. It's incredibly fast, but sometimes makes dumb mistakes (like picking someone who managed a "coffee shop" when you wanted someone who managed a "machine shop").
- **Cross-Encoder (Re-Ranker):** Like an actual human hiring manager. They sit down and meticulously read the Top 10 resumes *in the context of the exact job description*. It's very slow, so they can't do it for all 10,000, but they can easily do it for the Top 10 to put them in the perfect order.

### 3. Complete Runnable Code
Let's see how a Bi-Encoder fails, and how a Cross-Encoder fixes it.

```python
# pip install sentence-transformers numpy
from sentence_transformers import SentenceTransformer, CrossEncoder
import numpy as np

# 1. The tricky data
query = "Visa for US from UK"
documents = [
    "Process for getting a UK visa from the US.", # Wrong direction!
    "How to apply for a United States visa as a British citizen." # Correct!
]

# 2. First Stage: Bi-Encoder (Standard Vector Search)
print("--- Stage 1: Fast Bi-Encoder Search ---")
bi_encoder = SentenceTransformer('all-MiniLM-L6-v2')

q_emb = bi_encoder.encode(query)
doc_embs = bi_encoder.encode(documents)

# Cosine Sim
scores = [np.dot(q_emb, d) / (np.linalg.norm(q_emb)*np.linalg.norm(d)) for d in doc_embs]

for i, score in enumerate(scores):
    print(f"[{score:.4f}] {documents[i]}")

# Notice how the Bi-Encoder scores the WRONG document higher (or virtually identical)
# because the concepts "Visa", "US", and "UK" are heavily present in both.

# 3. Second Stage: Cross-Encoder Re-Ranking
print("\n--- Stage 2: Cross-Encoder Re-Ranking ---")
# A Cross-Encoder doesn't produce vectors. It takes (Query, Document) pairs
# and runs them through the Transformer network TOGETHER, allowing attention
# mechanisms to connect the words "from" and "to" correctly.
cross_encoder = CrossEncoder('cross-encoder/ms-marco-TinyBERT-L-2-v2')

# Create the pairs
pairs = [[query, doc] for doc in documents]

# Get the strict relational scores
cross_scores = cross_encoder.predict(pairs)

for i, score in enumerate(cross_scores):
    print(f"[{score:.4f}] {documents[i]}")

# The Cross-Encoder correctly gives the British citizen document a MASSIVELY higher score.
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: The Bi-Encoder Bottleneck**
In a Bi-Encoder, the query is embedded without knowing what the documents are, and the documents are embedded without knowing what the query is. They are reduced to points in space. Directional relationships ("from X to Y") often collapse in this space.

**Step 2: The Two-Stage Pipeline**
Because Cross-Encoders are so computationally heavy, you cannot run them against 1,000,000 documents. You use the fast Bi-Encoder (Vector DB) to narrow the 1,000,000 documents down to a "Top K" of 50.

**Step 3: The Cross-Encoder Evaluation**
You take those 50 documents and pair them with the query: `(Query, Doc1)`, `(Query, Doc2)`. The Cross-Encoder processes both inputs simultaneously. The self-attention heads inside the Transformer can now look at the word "from" in the query, and link it directly to "British" in the document, yielding an incredibly accurate relevance score. You sort the 50 docs by this new score and return the Top 5 to the LLM.

### 5. ASCII Data Flow

```text
1 Million Documents
      |
[ Stage 1: Vector DB (Bi-Encoder) ] -> Extremely Fast (ANN/HNSW)
      |
      |-- Returns Top 50 potential matches.
      v
[ Stage 2: Re-Ranker (Cross-Encoder) ] -> Heavy Compute (Self-Attention)
      |
      |-- Pairs Query + Doc1 -> Score: -2.1
      |-- Pairs Query + Doc2 -> Score:  8.5
      |-- Re-sorts the 50 documents.
      v
[ Final Top 5 Sent to LLM Context ]
```

### 6. Noob Trap vs Pro Tip
- **Noob Trap:** Passing a massive Top K (e.g., 1000) from the Vector DB to the Cross-Encoder. Because the Cross-Encoder runs a full Neural Network inference on every single pair, passing 1000 items will add 5-10 seconds of latency to your API, making the chat app feel broken.
- **Pro Tip:** Commercial APIs exist for this! You don't have to host heavy Cross-Encoder models yourself. Cohere's ReRank API or Jina AI's ReRanker can take a list of texts and return the sorted scores via a fast API call.

**Challenge:** Simulate the "Top K limit". Imagine the Bi-encoder returned 10 documents, but you only have the compute budget to re-rank the Top 3. Write the slicing logic that takes only the first 3 documents from the Bi-encoder output, runs them through the cross-encoder, and returns the newly sorted 3 documents.
<details>
<summary>Hint</summary>
Sort the original documents by `bi_encoder` scores first (to simulate the Vector DB output). Slice `[:3]`. Build the `pairs` list from that slice. Predict, sort, and print.
</details>

<details>
<summary>Solution Walkthrough</summary>
```python
# 1. Sort by Bi-Encoder scores descending (Simulating Vector DB)
sorted_by_bi = [doc for _, doc in sorted(zip(scores, documents), reverse=True)]

# 2. Slice Top 3 for compute budget
top_k_bi = sorted_by_bi[:3]

# 3. Cross-Encode only the slice
budget_pairs = [[query, doc] for doc in top_k_bi]
rerank_scores = cross_encoder.predict(budget_pairs)

# 4. Re-sort the slice
final_sorted = [doc for _, doc in sorted(zip(rerank_scores, top_k_bi), reverse=True)]

print("\nFinal Re-Ranked Output:")
for doc in final_sorted:
    print(doc)
```
</details>

<details>
<summary>Solution Walkthrough</summary>
```python
def mock_cohere_rerank(query, docs_dict, top_n):
    # Extract texts
    texts = [d["text"] for d in docs_dict]
    pairs = [[query, txt] for txt in texts]

    # Get scores
    scores = cross_encoder.predict(pairs)

    # Combine original index with score
    indexed_scores = [{"index": i, "relevance_score": float(score)} for i, score in enumerate(scores)]

    # Sort descending by score
    indexed_scores.sort(key=lambda x: x["relevance_score"], reverse=True)

    # Return top N
    return indexed_scores[:top_n]

docs = [{"id": 101, "text": documents[0]}, {"id": 102, "text": documents[1]}]
api_response = mock_cohere_rerank(query, docs, top_n=1)
print("\nMock API Response:\n", api_response)
```
This is exactly how you would integrate a 3rd party ReRanker into a production RAG pipeline.
