# 5.3 Automated RAGAS Evaluation

## Phase A: Core Concept

### 1. Real-World Pain Point (The Why)
You built a RAG pipeline. You typed "What is the refund policy?" and it gave a great answer. You push it to production. A week later, you tweak the chunk size from 500 to 1000 characters and change the LLM from GPT-3.5 to Claude 3 Haiku to save money. You test the refund query again, it looks fine. But unbeknownst to you, the system is now failing on complex multi-document questions, hallucinating answers, and retrieving the wrong contexts. You are flying blind. **You cannot improve what you cannot measure.**

### 2. Plain English Metaphor (The What)
Testing software usually involves assert statements (`assert 2 + 2 == 4`). But LLM answers are non-deterministic (they change every time). You can't use exact string matching.
**RAGAS (Retrieval Augmented Generation Assessment)** is like hiring an automated panel of judges for a debate competition. Instead of checking if the answer exactly matches an answer key, the AI judges score the system on three strict rubrics:
1. Did you find the right evidence? (Context Precision)
2. Is your answer strictly based on the evidence, or did you make things up? (Faithfulness)
3. Did your answer actually address the prompt? (Answer Relevance)

### 3. Complete Runnable Code
Let's see how we use an "LLM-as-a-Judge" to evaluate a RAG pipeline's Faithfulness (preventing hallucinations).

```python
# Note: In a real environment, you would use the `ragas` library.
# We will simulate the core concept of LLM-as-a-judge for pedagogy.

import json

# 1. The Scenario
question = "What is the battery life of the new X-Phone?"
retrieved_context = "The new X-Phone features a stunning OLED display and a 4000mAh battery. Tests show it lasts up to 14 hours on a single charge."

# Scenario A: Good Answer
answer_good = "The X-Phone battery lasts up to 14 hours."

# Scenario B: Hallucinated Answer (The RAG system made something up!)
answer_hallucinated = "The X-Phone battery lasts up to 14 hours and supports 120W fast charging."

# 2. The RAGAS Faithfulness Prompt (LLM-as-a-Judge)
# We ask a powerful model (like GPT-4) to evaluate the generated answer
# against the provided context.
def evaluate_faithfulness(question, context, answer):
    prompt = f"""
    Given the following Question, Context, and Answer, determine if the Answer is
    strictly FAITHFUL to the Context.

    An answer is faithful if EVERY claim made in the answer can be directly inferred from the context.
    If the answer contains information NOT present in the context, it is UNFAITHFUL.

    Question: {question}
    Context: {context}
    Answer: {answer}

    Output JSON exactly like this: {{"faithful": true/false, "reason": "..."}}
    """
    return prompt

print("--- Evaluating Good Answer ---")
prompt_a = evaluate_faithfulness(question, retrieved_context, answer_good)
print(f"Sending to LLM Judge...\n")
# Simulated LLM Response:
response_a = '{"faithful": true, "reason": "The claim of 14 hours is directly stated in the context. No extra claims are made."}'
print(f"Judge Verdict: {json.loads(response_a)}\n")

print("--- Evaluating Hallucinated Answer ---")
prompt_b = evaluate_faithfulness(question, retrieved_context, answer_hallucinated)
print(f"Sending to LLM Judge...\n")
# Simulated LLM Response:
response_b = '{"faithful": false, "reason": "The answer claims it supports 120W fast charging, but this is never mentioned in the context."}'
print(f"Judge Verdict: {json.loads(response_b)}")
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: The RAG Triad**
A proper evaluation framework tests specific components independently.
- If Faithfulness fails, the LLM is hallucinating (prompt engineering issue).
- If Context Precision fails, the Vector DB retrieved the wrong chunks (embedding/chunking issue).
- If Answer Relevance fails, the LLM gave a true fact, but didn't answer the user's specific question.

**Step 2: The Evaluation Dataset**
To automate this, you must construct a "Golden Dataset" of 50-100 `(Question, Ground_Truth)` pairs.

**Step 3: CI/CD Pipeline**
Every time a developer pushes a PR that changes the chunk size, the embedding model, or the LLM prompt, a GitHub Action runs the Golden Dataset through the new RAG pipeline, captures the `Contexts` and `Answers`, and sends them to the LLM-Judge. If the overall Faithfulness score drops below 0.90, the build fails.

### 5. ASCII Data Flow

```text
[ Developer changes chunk size to 1000 ]

[ Test Suite Runs 50 Queries ] -> Retrieves Contexts -> Generates Answers

[ RAGAS Evaluator (GPT-4) ]
      |
      |-- Checks Answer 1 vs Context 1 -> Faithfulness: 1.0
      |-- Checks Answer 2 vs Context 2 -> Faithfulness: 0.0 (Hallucination detected)
      |
      |-- Aggregates Scores -> Average Faithfulness: 0.85

[ CI/CD Pipeline ] -> 0.85 < Threshold (0.90). Build FAILED. PR Blocked.
```

### 6. Noob Trap vs Pro Tip
- **Noob Trap:** Using a cheap, fast model (like Llama-3-8B or GPT-3.5) as the Judge to save money. Cheap models are terrible at following strict JSON rubrics and often incorrectly pass hallucinations.
- **Pro Tip:** Always use the most capable model available (GPT-4o, Claude 3.5 Sonnet) as the Evaluator Judge. Yes, it costs money to run the test suite, but it's drastically cheaper than losing a major enterprise client because your production bot hallucinated a fake contract clause.

### Level 2: Real-World
**Challenge:** The LLM Judge might output flaky JSON (e.g., adding markdown ````json` blocks around the output). Write a robust JSON parser function `parse_judge_output(raw_string)` that attempts to clean the string and return a Python dictionary, with a fallback `try/except` block that returns `{"faithful": False, "reason": "Parsing failed"}` if it crashes.
<details>
<summary>Hint</summary>
Use `.replace('```json', '').replace('```', '').strip()`. Then wrap `json.loads()` in a `try/except`.
</details>

<details>
<summary>Solution Walkthrough</summary>
```python
def parse_judge_output(raw_string):
    cleaned = raw_string.replace('```json', '').replace('```', '').strip()
    try:
        return json.loads(cleaned)
    except json.JSONDecodeError:
        print("[ERROR] LLM Judge returned invalid JSON.")
        return {"faithful": False, "reason": "JSON Parsing failed."}

# Test it
bad_output = "```json\n{\"faithful\": true, \"reason\": \"Looks good\"}\n```"
print(parse_judge_output(bad_output))
```
This defensive programming is required when dealing with LLM outputs in automated pipelines.
</details>

### Level 3: Boss Level
**Challenge:** Aggregate Pipeline Scoring. You have a list of test results: `results = [{"faithful": True}, {"faithful": False}, {"faithful": True}]`. Write a function that calculates the overall pipeline score (percentage of True) and compares it to a `threshold = 0.90`. If the score is below the threshold, raise an `Exception("CI/CD Pipeline Failed")`.
<details>
<summary>Hint</summary>
Count the `True` values, divide by `len(results)`. Use `if score < threshold: raise Exception(...)`.
</details>

<details>
<summary>Solution Walkthrough</summary>
```python
def evaluate_test_suite(results, threshold=0.90):
    total = len(results)
    passed = sum(1 for r in results if r["faithful"] is True)

    score = passed / total
    print(f"Pipeline Faithfulness Score: {score * 100:.1f}%")

    if score < threshold:
        raise Exception(f"CI/CD Pipeline Failed! Score {score} is below threshold {threshold}")
    else:
        print("Pipeline Passed! Safe to merge PR.")

results = [{"faithful": True}, {"faithful": False}, {"faithful": True}]

try:
    evaluate_test_suite(results)
except Exception as e:
    print(f"ACTION REQUIRED: {e}")
```
This is exactly what runs in a GitHub Action to prevent regressions in production RAG systems.
</details>
