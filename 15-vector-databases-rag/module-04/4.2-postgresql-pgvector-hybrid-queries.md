# 4.2 PostgreSQL pgvector & Hybrid Queries

## Phase A: Core Concept

### 1. Real-World Pain Point (The Why)
You already have a massive PostgreSQL database holding all your user profiles, tenant configurations, e-commerce products, and order history. If you use a standalone Vector Database (like Pinecone or Chroma) for AI features, you now have the "Dual Database Problem": you have to keep Postgres and the Vector DB in sync. If a user deletes an e-commerce product in Postgres, but your cron job fails to delete it in the Vector DB, your LLM will recommend a product that doesn't exist.

### 2. Plain English Metaphor (The What)
- **Standalone Vector DB:** Having a separate filing cabinet in another room just for "meaning" searches. You have to walk back and forth between your main filing cabinet and the new one to make sure they agree.
- **pgvector:** Upgrading your existing main filing cabinet with a new type of folder. Your vector data lives directly alongside your standard data. You can do a traditional lookup (User ID = 5) and a vector search (Similarity to Query) in the *exact same sentence*.

### 3. Complete Runnable Code
Let's see how `pgvector` allows you to mix standard SQL `WHERE` clauses with vector similarity operators (`<=>`).

*Note: This code requires a PostgreSQL instance with the `pgvector` extension installed. We will use `sqlalchemy` to simulate the interaction.*

```python
# pip install psycopg2-binary pgvector sqlalchemy
from sqlalchemy import create_engine, Column, Integer, String, Text
from sqlalchemy.orm import declarative_base, sessionmaker
from pgvector.sqlalchemy import Vector
import numpy as np

# 1. Setup Postgres Connection (Requires running PG instance with pgvector)
# Engine setup is simulated here for pedagogy.
# engine = create_engine('postgresql://user:password@localhost/mydb')
# Session = sessionmaker(bind=engine)
# session = Session()

Base = declarative_base()

# 2. Define the Schema (Notice how standard columns and vector columns mix perfectly)
class AirbnbListing(Base):
    __tablename__ = 'listings'

    id = Column(Integer, primary_key=True)
    tenant_id = Column(String(50), index=True) # Strict tenant isolation
    city = Column(String(50))
    price_per_night = Column(Integer)
    description = Column(Text)

    # The magical pgvector column. We define the dimension size (e.g., 3).
    embedding = Column(Vector(3))

# Base.metadata.create_all(engine) # Creates table

print("--- Simulated SQL Generation for pgvector ---")

# 3. Inserting Data (Standard SQL Insert)
# session.add(AirbnbListing(
#     tenant_id="host_123", city="Paris", price_per_night=150,
#     description="Cozy apartment near Eiffel Tower",
#     embedding=[0.8, 0.2, 0.1]
# ))
print("""
INSERT INTO listings (tenant_id, city, price_per_night, description, embedding)
VALUES ('host_123', 'Paris', 150, 'Cozy apartment...', '[0.8, 0.2, 0.1]');
""")

# 4. The Hybrid Query (The real power of pgvector)
query_vector = [0.9, 0.1, 0.1] # E.g., User searched for "Romantic spot near tower"

# SQLAlchemy representation:
# results = session.query(AirbnbListing).filter(
#     AirbnbListing.city == 'Paris',
#     AirbnbListing.price_per_night <= 200
# ).order_by(
#     AirbnbListing.embedding.cosine_distance(query_vector)
# ).limit(5).all()

print("\n--- The Hybrid SQL Query ---")
print(f"""
SELECT id, city, description,
       embedding <=> '{query_vector}' AS cosine_distance
FROM listings
WHERE city = 'Paris'
  AND price_per_night <= 200
ORDER BY cosine_distance ASC
LIMIT 5;
""")
print("Result: ACID-compliant, instantly consistent Hybrid Search!")
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: The `Vector` Data Type**
`pgvector` adds a native `vector` data type to PostgreSQL. You define the exact number of dimensions (e.g., 1536 for OpenAI). It is stored as a blob of floats in the table row.

**Step 2: The Operator (`<=>`)**
`pgvector` introduces custom SQL operators. `<=>` means Cosine Distance. `<#>` means Inner Product. `<->` means L2 Euclidean distance. You use these operators in the `ORDER BY` clause to sort the rows by semantic similarity.

**Step 3: ACID Compliance & Hybrid Filtering**
Because it's just SQL, the database engine executes the `WHERE` clause first (City = Paris, Price <= 200), using standard B-Tree indexes. Then, it only calculates vector distances on the rows that survived the filter. If a listing is deleted, it is instantly gone from both standard searches and vector searches. Zero sync issues.

### 5. ASCII Data Flow

```text
User Query: "Romantic apartment under $200 in Paris" -> [Vector: 0.9, 0.1, 0.1]

[ PostgreSQL Engine ]
      |
      |-- 1. WHERE city = 'Paris' AND price <= 200 (Uses standard B-Tree Index)
      |      (Filters 1,000,000 global listings down to 500 listings)
      |
      |-- 2. ORDER BY embedding <=> '[0.9, 0.1, 0.1]'
      |      (Calculates Cosine Distance only on those 500 listings)
      |
      |-- 3. LIMIT 5
      |
Result: 5 perfectly matching rows.
```

### 6. Noob Trap vs Pro Tip
- **Noob Trap:** Doing a sequential scan on 10 million rows. If you just run `ORDER BY embedding <=> query`, Postgres calculates the math against every single row. It will take 10 seconds and kill your CPU.
- **Pro Tip:** You MUST add an HNSW index to your vector column in pgvector for production scale.
  ```sql
  CREATE INDEX ON listings USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);
  ```
  This builds the Navigable Small World graph *inside* Postgres, making searches milliseconds fast.

### Level 2: Real-World
**Challenge:** The user wants to search for similar listings to one they are currently looking at (e.g., Listing ID 42). Write a single SQL query (using a Subquery) that grabs the embedding of Listing 42, and uses it to find the 3 most similar other listings in the same city.
<details>
<summary>Hint</summary>
Use `(SELECT embedding FROM listings WHERE id = 42)` as the right side of the `<=>` operator. Don't forget `WHERE id != 42` so you don't return the exact same listing!
</details>

<details>
<summary>Solution Walkthrough</summary>
```sql
SELECT id, description,
       embedding <=> (SELECT embedding FROM listings WHERE id = 42) AS distance
FROM listings
WHERE city = (SELECT city FROM listings WHERE id = 42)
  AND id != 42
ORDER BY distance ASC
LIMIT 3;
```
This is a powerful "Find Similar Products" feature achieved in a single database trip.
</details>

### Level 3: Boss Level
**Challenge:** Understand `ivfflat` vs `hnsw` index building. If you use an `ivfflat` index in pgvector, you *must* wait until you have a lot of data inserted before building the index. Why? What happens if you build an `ivfflat` index on an empty table, and then insert 1 million rows? Write a brief text explanation.
<details>
<summary>Hint</summary>
Recall Module 3.2. IVF uses K-Means clustering. K-Means needs to look at the data distribution to figure out where to place the centroids.
</details>

<details>
<summary>Solution Walkthrough</summary>
**Explanation:**
If you build an `ivfflat` index on an empty table (or a table with only 10 rows), K-Means has no data to analyze. It places all the centroids in terrible, random locations. When you later insert 1 million rows, those rows get assigned to those terrible centroids, completely ruining search accuracy and speed.
**Pro-Tip:** Always load your initial bulk data (at least 10,000+ rows) *before* running `CREATE INDEX ... USING ivfflat`. (Note: `hnsw` does not suffer from this and can be created on an empty table because it builds the graph dynamically upon insert).
</details>
