# 4.1 Local Prototyping with ChromaDB

## Phase A: Core Concept

### 1. Real-World Pain Point (The Why)
When you are building a new AI feature, you want to test RAG pipelines immediately. If you have to spin up a Docker container, configure PostgreSQL with pgvector, set up connection pools, and write SQL schemas just to test if your PDF chunking works, you waste hours of engineering time. You need a database that runs directly inside your Python script with zero setup, but still offers production-grade features like metadata filtering and HNSW indexing.

### 2. Plain English Metaphor (The What)
- **Enterprise Vector DBs (pgvector/Pinecone):** Like building a massive commercial warehouse. It takes weeks of planning, permits, and heavy machinery, but it holds a million boxes.
- **ChromaDB:** Like a pop-up storage tent. You unbox it, and it's instantly ready to hold your stuff right in your backyard. If you want to keep the stuff, you just zip it up (save to disk).

### 3. Complete Runnable Code
Let's build a fully functional Vector Search CLI tool using ChromaDB in under 30 lines of code.

```python
# pip install chromadb
import chromadb

# 1. Initialize ChromaDB (In-Memory for extreme speed, or Persistent for saving)
# We will use Persistent so our data survives script restarts
client = chromadb.PersistentClient(path="./chroma_data")

# 2. Create or Get a Collection (Think of a collection like a SQL table)
collection = client.get_or_create_collection(name="local_docs")

# 3. Add data (Chroma automatically embeds text using a lightweight local model!)
print("--- Ingesting Documents ---")
documents = [
    "To install the software, run npm install in the root directory.",
    "The default port for the database is 5432.",
    "API rate limits are 100 requests per minute."
]
ids = ["doc_install", "doc_db_port", "doc_api_limit"]
metadatas = [{"topic": "setup"}, {"topic": "database"}, {"topic": "api"}]

# Chroma uses a built-in SentenceTransformer model if you don't provide your own
collection.upsert(
    documents=documents,
    ids=ids,
    metadatas=metadatas
)
print("Data ingested successfully!")

# 4. Query the Database
print("\n--- Querying ---")
query = "What port should I connect to?"
results = collection.query(
    query_texts=[query],
    n_results=1
)

print(f"Query: {query}")
print(f"Result: {results['documents'][0][0]}")
print(f"Metadata: {results['metadatas'][0][0]}")
print(f"Distance (Lower is better): {results['distances'][0][0]:.4f}")
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: The Client**
`chromadb.PersistentClient(path="./chroma_data")` creates a SQLite database and binary files for the HNSW graph directly in your project folder. No Docker, no network calls.

**Step 2: Collections**
`get_or_create_collection` ensures the script is idempotent. You can run it 100 times without throwing an error.

**Step 3: Upsert & Automatic Embeddings**
The `upsert` command is magical. You just hand it raw strings (`documents`). You don't have to call OpenAI or run SentenceTransformers yourself. ChromaDB downloads a lightweight local embedding model (default: `all-MiniLM-L6-v2`) and encodes the text automatically. `Upsert` means "Insert if new, Update if ID already exists."

**Step 4: Querying**
You pass raw text to `query_texts`. Chroma automatically embeds your query using the same local model and performs the HNSW vector search against the collection.

### 5. ASCII Data Flow

```text
[ Python Script ]
      |
      |-- `collection.upsert(texts)`
      |
[ ChromaDB Internal Engine ]
      |-- (Downloads local Embedding Model)
      |-- Embeds Texts -> Vectors
      |-- Saves Texts/Metadata to local SQLite
      |-- Saves Vectors to local HNSW Graph (.bin)
      |
[ Disk: ./chroma_data folder ]
```

### 6. Noob Trap vs Pro Tip
- **Noob Trap:** Using Chroma's default local embedding model for production data. It is fast and free, but it struggles with complex semantic reasoning and multi-lingual text compared to `text-embedding-3`.
- **Pro Tip:** You can easily swap Chroma's embedder to OpenAI.
  ```python
  import chromadb.utils.embedding_functions as embedding_functions
  openai_ef = embedding_functions.OpenAIEmbeddingFunction(api_key="sk-...", model_name="text-embedding-3-small")
  collection = client.get_or_create_collection(name="prod_docs", embedding_function=openai_ef)
  ```
  Now, Chroma handles the API calls to OpenAI for you during ingest and search!

## Phase B: Engineering Challenges

### Level 1: Warm-Up
**Challenge:** The script created a `./chroma_data` folder on your disk. Write a separate, tiny script that connects to that exact same path, gets the `local_docs` collection, and prints the total number of documents in the database.
<details>
<summary>Hint</summary>
Use `client = chromadb.PersistentClient(path="./chroma_data")`, then `collection = client.get_collection("local_docs")`, then print `collection.count()`.
</details>

<details>
<summary>Solution Walkthrough</summary>
```python
import chromadb
client = chromadb.PersistentClient(path="./chroma_data")
collection = client.get_collection("local_docs")
print(f"Total documents on disk: {collection.count()}")
```
</details>

### Level 2: Real-World
**Challenge:** Metadata Filtering. Update the query in the main script to search for the phrase "How do I configure things?" but apply a `where` filter so it ONLY searches documents where the metadata `topic` is exactly equal to `api`.
<details>
<summary>Hint</summary>
Add the `where={"topic": "api"}` parameter to the `collection.query()` function call.
</details>

<details>
<summary>Solution Walkthrough</summary>
```python
results = collection.query(
    query_texts=["How do I configure things?"],
    n_results=1,
    where={"topic": "api"}
)
print(results['documents'][0][0])
# Even though the query semantic meaning might be closer to the "setup" document,
# it will rigidly return the "api_limit" document because of the strict metadata filter.
```
</details>

### Level 3: Boss Level
**Challenge:** Updating Data (Upsert in action). The API rate limit has been increased to 500 requests per minute. Write code to update the existing document in the database without deleting it or changing its ID. Run a query afterward to prove it updated.
<details>
<summary>Hint</summary>
Call `collection.upsert()` again. Pass the exact same `ids=["doc_api_limit"]`, but provide the new string in the `documents` list.
</details>

<details>
<summary>Solution Walkthrough</summary>
```python
print("\n--- Updating Document ---")
collection.upsert(
    ids=["doc_api_limit"],
    documents=["API rate limits are 500 requests per minute."],
    metadatas=[{"topic": "api"}] # Must provide metadata again to avoid overwriting with null
)

# Verify
results = collection.query(
    query_texts=["What is the rate limit?"],
    n_results=1
)
print(f"Updated Result: {results['documents'][0][0]}")
```
This is how you keep a Vector Database synced with a constantly changing primary source of truth.
</details>
