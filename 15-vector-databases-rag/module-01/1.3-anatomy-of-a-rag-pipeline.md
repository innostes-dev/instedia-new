# 1.3 Anatomy of a RAG Pipeline

## Phase A: Core Concept

### 1. Real-World Pain Point (The Why)
Large Language Models (LLMs) hallucinate. If you ask ChatGPT "What is the vacation policy in my company's employee handbook?", it will make up a generic policy because it hasn't read *your* specific, private company handbook. Fine-tuning a model on your private data is horribly expensive, slow, and hard to update. You need a way to give the LLM external, up-to-date facts on the fly.

### 2. Plain English Metaphor (The What)
Imagine you are taking an open-book exam.
- The **LLM** is your brain. It's smart and knows grammar, logic, and general knowledge.
- The **Database** is the open book.
- **RAG (Retrieval-Augmented Generation)** is the process of you using the index to find the relevant page (Retrieval), reading the exact paragraph (Augmentation), and writing your final answer on the test paper (Generation).

### 3. Complete Runnable Code
Let's reverse-engineer a basic Notion AI Q&A RAG pipeline.

```python
# pip install sentence-transformers numpy openai
from sentence_transformers import SentenceTransformer
import numpy as np
import os

# Note: You need an OPENAI_API_KEY environment variable for the generation step
# export OPENAI_API_KEY="sk-..."

# 1. Ingestion & Indexing
documents = [
    "Notion Employee Handbook: Employees get 20 days of PTO per year.",
    "Notion Remote Policy: Remote work is allowed 3 days a week.",
    "Notion IT Policy: All laptops must be encrypted with FileVault."
]

embedder = SentenceTransformer('all-MiniLM-L6-v2')
doc_embeddings = embedder.encode(documents)

# 2. Retrieval
question = "How many vacation days do I get?"
question_embedding = embedder.encode(question)

# Cosine similarity search
def cosine_sim(v1, v2):
    return np.dot(v1, v2) / (np.linalg.norm(v1) * np.linalg.norm(v2))

scores = [cosine_sim(question_embedding, doc_emb) for doc_emb in doc_embeddings]
best_doc_idx = np.argmax(scores)
retrieved_context = documents[best_doc_idx]

print(f"Retrieved Context: {retrieved_context}")

# 3. Augmentation & Generation (Simulated LLM call)
prompt = f"""
Answer the user's question using ONLY the provided context.

Context: {retrieved_context}
Question: {question}

Answer:
"""
print(f"Prompt sent to LLM:\n{prompt}")

# In a real app, you send this prompt to OpenAI/Anthropic:
# response = client.chat.completions.create(model="gpt-4o", messages=[{"role": "user", "content": prompt}])
# print(response.choices[0].message.content)
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: Ingestion & Indexing**
We take our private knowledge base (`documents`) and convert them into vector embeddings. In a production system, this step involves reading PDFs, chunking text, and storing vectors in a database like Pinecone or pgvector.

**Step 2: Retrieval**
When the user asks a question, we embed the question into a vector using the *exact same embedding model*. We compare the question vector to all document vectors to find the most mathematically similar context.

**Step 3: Augmentation & Generation**
We inject the retrieved text into a prompt template, effectively saying to the LLM: "Here are the facts. Now answer the question." The LLM synthesizes the final human-readable response.

### 5. ASCII Data Flow

```text
[ Private Documents ] -> (Embedder) -> [ Vector Database ]
                                              ^
                                              | (Similarity Search)
[ User Question ] -> (Embedder) -> [ Question Vector ]
       |
       |--------------------------------------|
                                              v
[ Retrieved Context ] + [ User Question ] -> [ Prompt ] -> (LLM) -> [ Final Answer ]
```

### 6. Noob Trap vs Pro Tip
- **Noob Trap:** Retrieving too much context or full 50-page documents and stuffing them into the prompt. It wastes tokens, costs money, and causes the LLM to suffer from "Lost in the Middle" syndrome (forgetting context in the middle of a massive prompt).
- **Pro Tip:** Enforce strict chunking strategies and instruct the LLM to respond with "I don't know based on the context provided" if the retrieved chunks don't actually contain the answer, preventing hallucinations.

### Level 2: Real-World
**Challenge:** Top-K Retrieval. Instead of returning just the single best document (Top-1), retrieve the top 2 documents and combine them into the context. This is vital when the answer is spread across multiple chunks.
<details>
<summary>Hint</summary>
Use `np.argsort(scores)[::-1][:2]` to get the indices of the top 2 scores. Loop through those indices and join the documents together.
</details>

<details>
<summary>Solution Walkthrough</summary>
```python
top_k = 2
top_indices = np.argsort(scores)[::-1][:top_k]

retrieved_chunks = [documents[i] for i in top_indices]
combined_context = "\n".join(retrieved_chunks)

print("Combined Context:\n", combined_context)
```
</details>

### Level 3: Boss Level
**Challenge:** Implement a "Relevance Guardrail". If the cosine similarity score of the best retrieved document is below `0.2`, bypass the LLM entirely and return "I'm sorry, I don't have information about that." This prevents the pipeline from trying to answer questions using completely irrelevant documents.
<details>
<summary>Hint</summary>
Check `scores[best_doc_idx]`. If it is `< 0.2`, short-circuit the logic. Otherwise, construct the prompt.
</details>

<details>
<summary>Solution Walkthrough</summary>
```python
best_score = scores[best_doc_idx]

if best_score < 0.2:
    print("Guardrail triggered: No relevant context found.")
    print("Final Answer: I'm sorry, I don't have information about that.")
else:
    retrieved_context = documents[best_doc_idx]
    prompt = f"Context: {retrieved_context}\nQuestion: {question}\nAnswer:"
    print("Prompting LLM...")
    # call LLM here
```
This is a crucial production guardrail to save API costs and prevent hallucinations on out-of-domain queries.
