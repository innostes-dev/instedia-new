# 3.2 Function Calling and Tool Use

## Phase A: Core Intuition

### Real-World Pain Point (The Why)
A user asks your AI: "What's the weather in Tokyo right now?" The LLM replies: "I am an AI and my knowledge cutoff is January 2023. I cannot check current weather."
LLMs are trapped in a static box of their training data. They cannot browse the web, check your live database, or trigger an email. Without access to external systems, an LLM is just a highly articulate encyclodpedia, not an autonomous agent.

### Plain English Metaphor (The What)
Imagine a manager (the LLM) sitting in a room with no windows or internet. If you ask them the weather, they don't know.
**Function Calling (Tools)** is like putting a telephone on the manager's desk with a list of contacts (Tools). The manager can't go outside, but they can pick up the phone, call the Weather Department (your Python function), ask for Tokyo, listen to the result, and then relay that answer to you. The LLM decides *when* to use a tool and *what arguments* to pass to it, but your local code actually executes the action.

### Complete Runnable Code

```python
# Weather & Database Look-up AI Assistant with Tools
import json

# 1. The Actual Python Functions (The Tools)
def get_current_weather(location):
    # A fake weather API.
    print(f"[SYSTEM: Executing weather lookup for {location}]")
    weather_data = {"Tokyo": "75°F and sunny", "London": "60°F and rainy"}
    return weather_data.get(location, "Unknown weather")

def query_customer_db(customer_name):
    # A fake database lookup.
    print(f"[SYSTEM: Querying DB for {customer_name}]")
    db = {"Alice": "Premium Tier", "Bob": "Free Tier"}
    return db.get(customer_name, "Customer not found")

# 2. Define the Tools for the LLM
tools = [
    {
        "type": "function",
        "function": {
            "name": "get_current_weather",
            "description": "Get the current weather for a given city.",
            "parameters": {
                "type": "object",
                "properties": {
                    "location": {"type": "string", "description": "The city name, e.g. Tokyo"}
                },
                "required": ["location"]
            }
        }
    },
    {
        "type": "function",
        "function": {
            "name": "query_customer_db",
            "description": "Check the account tier of a customer by name.",
            "parameters": {
                "type": "object",
                "properties": {
                    "customer_name": {"type": "string"}
                },
                "required": ["customer_name"]
            }
        }
    }
]

# Mock API demonstrating the Agent Loop
def mock_agent_loop(user_prompt):
    print(f"USER: {user_prompt}\n")

    # --- STEP A: LLM Decides to call a tool ---
    if "weather" in user_prompt.lower():
        llm_decision = {"name": "get_current_weather", "arguments": '{"location": "Tokyo"}'}
    elif "alice" in user_prompt.lower():
        llm_decision = {"name": "query_customer_db", "arguments": '{"customer_name": "Alice"}'}
    else:
        return "I don't need tools to say hello!"

    print(f"LLM DECIDES TO CALL TOOL: {llm_decision['name']} with args {llm_decision['arguments']}")

    # --- STEP B: Your Code Executes the Tool ---
    args = json.loads(llm_decision["arguments"])

    if llm_decision["name"] == "get_current_weather":
        tool_result = get_current_weather(args["location"])
    elif llm_decision["name"] == "query_customer_db":
        tool_result = query_customer_db(args["customer_name"])

    print(f"TOOL RESULT: {tool_result}")

    # --- STEP C: LLM Summarizes Result ---
    print(f"LLM FINAL RESPONSE: Based on the system data, the result is: {tool_result}\n")

mock_agent_loop("What is the weather in Tokyo?")
mock_agent_loop("What tier is Alice on?")
```

### Progressive Step-by-Step Breakdown

**Step 1: Defining the JSON Schema (The Manual)**
The `tools` array is a JSON schema that describes your Python functions to the LLM. It includes the `name`, `description`, and the required `parameters`. The LLM reads this and learns what tools it has available.

**Step 2: The LLM Pauses and Requests a Tool Call**
When you ask "What's the weather in Tokyo?", the LLM realizes it needs data. Instead of generating a text response, it halts and sends back a special payload: `tool_calls=[{"name": "get_current_weather", "arguments": "{\"location\": \"Tokyo\"}"}]`. The LLM *does not execute the code*. It is simply asking you to do it.

**Step 3: Local Execution and Context Return (The Agent Loop)**
Your Python code intercepts this request, parses the arguments, and runs `get_current_weather("Tokyo")`.
Then, you append the result ("75°F and sunny") to the conversation history as a `tool` role message, and you call the LLM *again*. The LLM reads the new data and finally generates a natural language response: "It's currently 75°F and sunny in Tokyo!"

### ASCII Data Flow

```text
User: "Weather in Tokyo?" --> LLM
                               |--> LLM Output: [ToolCall: get_current_weather("Tokyo")]
                               v
                       Your Python Code runs API --> Result: "75°F"
                               |
LLM <-- (Appends Result) <-----/
 |
 v--> LLM Final Output: "It is 75°F in Tokyo."
```

### Noob Trap vs Pro Tip
**Noob Trap:** Creating a tool called `do_action` with a description "Does something." The LLM relies entirely on the `description` and `name` to know when to use the tool. If your descriptions are vague, the LLM will hallucinate arguments or call the wrong tool.
**Pro Tip:** Treat tool descriptions like prompt engineering. Be explicitly clear. E.g., `description: "Fetches live weather. ONLY use this if the user asks for current conditions. Requires a city name."`

    if "location" not in args:
