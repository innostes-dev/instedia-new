# 3.1 Structured Outputs and Forcing JSON

## Phase A: Core Intuition

### Real-World Pain Point (The Why)
You write a prompt: "Extract the user's name and age from this text. Output in JSON."
The LLM outputs:
```json
{
  "name": "Alice",
  "age": "twenty-five"
}
```
Your database expects `age` to be an integer. The application crashes. The next day, it outputs: "Here is the JSON you requested: `{"name": "Bob", "age": 30}`". Your `json.loads()` fails because of the conversational prefix. Standard LLMs are eager to please and chatty, making them terrible at generating the strict data types required by modern software APIs.

### Plain English Metaphor (The What)
Prompting for JSON is like asking a child to draw a blueprint for a house on a blank piece of paper. They might draw the walls in red crayon and add a sun in the corner.
Using **Structured Outputs** (like OpenAI's `response_format` or Pydantic schemas) is like giving the child a coloring book where the lines are rigidly defined. They can only fill in the exact boxes provided. If they try to write "twenty-five" in a box meant for a number, the system mathematically forces them to write "25".

### Complete Runnable Code

```python
# AI Resume Parser Extracting Typed JSON Records
from pydantic import BaseModel, Field
import json

# 1. Define the exact schema using Pydantic
class ResumeData(BaseModel):
    first_name: str = Field(description="The applicant's first name")
    last_name: str = Field(description="The applicant's last name")
    years_experience: int = Field(description="Total years of work experience")
    skills: list[str] = Field(description="List of technical skills")
    is_active: bool = Field(description="True if currently employed, else False")

# Mock OpenAI client demonstrating Structured Output behavior
class MockClient:
    class beta:
        class chat:
            class completions:
                @staticmethod
                def parse(model, messages, response_format):
                    # The API strictly enforces the Pydantic schema
                    # It intercepts the raw LLM output and maps it to the class
                    data = {
                        "first_name": "Alice",
                        "last_name": "Smith",
                        "years_experience": 5, # Forced to int!
                        "skills": ["Python", "SQL", "AWS"],
                        "is_active": True
                    }
                    class MockResponse:
                        class choices:
                            class _item:
                                class message:
                                    parsed = response_format(**data)
                            _list = [_item()]
                            def __getitem__(self, i): return self._list[i]
                    return MockResponse()

client = MockClient() # client = OpenAI(api_key="...")

def extract_resume(resume_text):
    # 2. Call the API using the .parse endpoint and passing the Pydantic model
    response = client.beta.chat.completions.parse(
        model="gpt-4o-2024-08-06", # Must use a model that supports Structured Outputs
        messages=[
            {"role": "system", "content": "Extract applicant data accurately."},
            {"role": "user", "content": resume_text}
        ],
        response_format=ResumeData # 3. Force the Schema!
    )

    # 4. The result is a fully typed Python object, not a string!
    return response.choices[0].message.parsed

# Test the extraction
resume = "Hi, I'm Alice Smith. I've worked in tech for five years using Python, SQL, and AWS. I am currently working at TechCorp."

extracted_data = extract_resume(resume)

# Because it's a Pydantic object, we get IDE autocomplete and guaranteed types
print(f"Name: {extracted_data.first_name} {extracted_data.last_name}")
print(f"Experience (Type): {type(extracted_data.years_experience)}")
print(f"Experience (Value): {extracted_data.years_experience}")

# We can easily convert it back to safe JSON if needed
print("\nSafe JSON Output:")
print(extracted_data.model_dump_json(indent=2))
```

### Progressive Step-by-Step Breakdown

**Step 1: Pydantic Schemas**
Pydantic is a data validation library for Python. By defining `years_experience: int`, we declare that this field *must* be an integer. The `Field(description="...")` gives the LLM context on what the field means.

**Step 2: The `response_format` Parameter**
In recent OpenAI updates, you can pass a Pydantic class directly to `response_format`. Under the hood, OpenAI translates your Python class into a JSON Schema and feeds it into the LLM's decoding engine.

**Step 3: Constrained Decoding (The Magic)**
When the LLM generates tokens, the API actively monitors it. If the LLM tries to generate the token "twenty", but the JSON schema requires an integer, the API physically blocks the "twenty" token and forces the LLM to pick a numerical token like "5". This guarantees 100% schema adherence.

**Step 4: Parsed Objects**
Because we used `client.beta.chat.completions.parse`, the API automatically takes the resulting JSON string and instantiates our `ResumeData` Python class. We no longer have to run `json.loads()` and pray; we have a safe, typed object.

### ASCII Data Flow

```text
Prompt -> LLM generates Token 1 ("{") -> Allowed? Yes.
          LLM generates Token 2 ("\"years_experience\": ") -> Allowed? Yes.
          LLM attempts Token 3 ("five") -> Allowed? NO! (Schema says int) -> Forces "5" ->
          Complete Valid JSON Output -> Converted to Pydantic Object
```

### Noob Trap vs Pro Tip
**Noob Trap:** Putting `{"type": "json_object"}` in the API call and assuming it will solve your problems. This is legacy "JSON Mode". It guarantees the output is *some* kind of valid JSON, but it does *not* guarantee the keys or the data types will match what you want.
**Pro Tip:** Always use **Structured Outputs** (Strict JSON Schema / Pydantic) for any LLM call where the output is read by code rather than a human. It eliminates the need for complex retry-loops and error-handling for bad formats.

**Task:** Update the `ResumeData` Pydantic model to include a new field: `education_level` which must be one of exactly three strings: "High School", "Bachelors", or "Masters".
**Goal:** Learn how to enforce Enums (Categorical choices) in Structured Outputs.

<details>
<summary>Hint</summary>
Use Python's `typing.Literal`. E.g., `education_level: Literal["High School", "Bachelors", "Masters"]`.
</details>

<details>
<summary>Solution Walkthrough</summary>
```python
from typing import Literal

class ResumeData(BaseModel):
    # ... existing fields
    education_level: Literal["High School", "Bachelors", "Masters"] = Field(
        description="The highest level of education completed."
    )
```
The LLM is now physically unable to output "PhD" or "Some College". It must choose from the Literal list.

**Goal:** Handle complex, deeply nested relational data extraction.

<details>
<summary>Hint</summary>
Define the `Ingredient` class first. Then define the `Recipe` class and use `list[Ingredient]` for the field type.
</details>

<details>
<summary>Solution Walkthrough</summary>
```python
class Ingredient(BaseModel):
    name: str = Field(description="Name of the ingredient")
    amount: float = Field(description="Quantity required")

class Recipe(BaseModel):
    title: str
    prep_time_minutes: int
    ingredients: list[Ingredient]

# Now, response_format=Recipe will extract a perfectly structured array of sub-objects!
```
