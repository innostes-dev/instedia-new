# 1.3 Deferrable Views for Sub-Second LCP

## Phase A: Concept & Application

### 1. Real-World Pain Point (The Why)
In enterprise applications, particularly analytics dashboards, the initial payload can easily exceed several megabytes due to heavy charting libraries (like Highcharts or D3), complex data grid components, and massive localized date/time libraries. If all of this is loaded immediately, the browser blocks rendering, resulting in a terrible Largest Contentful Paint (LCP) score. Users stare at a blank white screen. Previously, lazy loading required complex router configurations or manually managing dynamic component imports and `ViewContainerRef`, which was incredibly verbose and error-prone.

### 2. Plain English Metaphor (The What)
Imagine a massive library.
The old way of loading an Angular app is like the librarian forcing you to carry every single book in the building out to your car before you are allowed to read the first page of the book you actually want.
**Deferrable Views (`@defer`)** are like a smart retrieval system. You only carry out the book you want to read right now. As you turn your head to look at a different shelf (`on viewport`), or when you sit down and aren't doing anything else (`prefetch on idle`), the librarian automatically brings the next books to you in the background.

### 4. Progressive Step-by-Step Breakdown

**Step 1: The `@defer` block and triggers**
*Rationale: The `@defer` block tells the compiler to bundle the contents into a separate JavaScript chunk. The trigger (e.g., `on viewport`, `on idle`, `on interaction`, `on timer(5s)`) dictates exactly when that chunk is requested over the network and rendered.*
```html
@defer (on viewport) {
  <app-heavy-sales-chart />
}
```

**Step 2: Adding a `@placeholder`**
*Rationale: Before the chunk is downloaded, Angular needs something to show in the DOM to prevent layout shifts. The `@placeholder` is rendered immediately in the initial bundle. It is critical for maintaining Core Web Vitals (Zero CLS).*
```html
@defer (on viewport) {
  <app-heavy-sales-chart />
} @placeholder {
  <div>Loading area...</div>
}
```

**Step 3: Handling `@loading` and `@error` states, plus `prefetch`**
*Rationale: Network requests take time and can fail. `@loading` shows during the fetch (with a `minimum` duration to prevent flickering). `@error` handles failures. `prefetch` allows us to download the code before the trigger condition is met, so when the trigger happens, rendering is instant.*
```html
@defer (on interaction(btn); prefetch on idle) {
  <app-complex-data-grid />
} @loading (minimum 1s) {
  <div>Spinning icon...</div>
} @error {
  <div>Failed to load!</div>
}
```

### 5. ASCII / Architecture Data Flow
```
[Initial Page Load]
├── main.js (Lightweight)
│   ├── Renders Header, KPIs
│   ├── Renders @placeholder for Chart
│   └── Renders @placeholder for Grid
│
[Browser enters IDLE state]
├── Background Network Request --> prefetches chunk-grid.js
│
[User Scrolls Down (Viewport trigger met)]
├── Network Request --> fetches chunk-chart.js
├── Displays @loading for 1 second minimum
└── Swaps @placeholder -> @loading -> <app-heavy-sales-chart>
│
[User Clicks "View Grid" (Interaction trigger met)]
└── Instantly renders <app-complex-data-grid> (because it was prefetched!)
```

### 6. Noob Trap vs Pro Tip
**Noob Trap:** Using `@defer (on idle)` for absolutely everything on the page. While `idle` is the default, if you have 20 deferred components, Angular will queue up 20 network requests as soon as the main thread is free. On slow connections, this clogs the network and delays the loading of components the user actually scrolls to.
**Pro Tip:** Use `on viewport` for components below the fold. Use `on interaction` for heavy dialogs or hidden panels. Reserve `on idle` (or `prefetch on idle`) only for critical components you are highly confident the user will interact with next.

### Level 2 Real-World
**Task:** Build an e-commerce product page layout. The main product details load immediately. Below the fold, there is a `RelatedProductsComponent`.
1. The related products should load when they enter the viewport.
2. If the user's mouse hovers over the main product image (give it a template ref variable `#mainImage`), *prefetch* the related products chunk.

<details>
<summary>💡 Hint</summary>
You can combine triggers. The `prefetch` keyword can have its own condition: `prefetch on hover(mainImage)`.
</details>

<details>
<summary>✅ Solution Walkthrough</summary>

```typescript
import { Component } from '@angular/core';

@Component({
  selector: 'app-ecommerce-product',
  standalone: true,
  // Assuming RelatedProductsComponent is imported here
  template: `
    <div class="product-page">
      <h1>Super Fast Running Shoes</h1>
      <!-- Template ref for hover detection -->
      <img #mainImage src="shoes.jpg" alt="Shoes" style="width: 300px; height: 300px;">

      <p>Product description goes here. Loads instantly.</p>

      <div style="height: 100vh;"></div> <!-- Push related down -->

      <h2>You might also like...</h2>
      <!-- Defer on viewport, but prefetch if user hovers the image above -->
      @defer (on viewport; prefetch on hover(mainImage)) {
        <!-- <app-related-products /> -->
        <div>Related products loaded!</div>
      } @placeholder {
        <div>Scrolling down...</div>
      }
    </div>
  `
})
```

### Level 3 Boss Level (Cumulative)
**Task:** Combine Standalone (1.1), Control Flow (1.2), and Deferrable Views (1.3).
You have a dashboard displaying a list of server locations.
Create a layout where:
1. You use `@for` to loop through an array of server objects: `{ id: string, name: string, ip: string }`.
2. For *each* server, render a "View Metrics" button and a `@defer` block containing a `<app-server-metrics>` component (you can mock this component).
3. The metrics component should *only* load and render when the specific "View Metrics" button for that server is clicked (`on interaction`).
4. Ensure you track the `@for` loop correctly.

<details>
<summary>💡 Hint</summary>
You need a unique template reference variable for each button inside the loop to tie it to the specific `@defer` block. In Angular, you can just use a local ref like `#metricsBtn` inside the loop, and the `@defer` block in that iteration will scope correctly to that button!
</details>

<details>
<summary>✅ Solution Walkthrough</summary>

```typescript
import { Component } from '@angular/core';

// Mock Component
@Component({
  selector: 'app-server-metrics',
  standalone: true,
  template: `<div style="padding:10px; background:#e2e8f0; margin-top:5px;">📈 CPU: 45% | RAM: 2.1GB</div>`

export class ServerMetricsComponent {}


@Component({
  selector: 'app-server-list',
  standalone: true,
  imports: [ServerMetricsComponent],
  template: `
    <div class="server-container">
      <h2>Server Fleet Overview</h2>

      @for (server of servers; track server.id) {
        <div class="server-card" style="border: 1px solid #ccc; padding: 1rem; margin-bottom: 1rem;">
          <h3>{{ server.name }} ({{ server.ip }})</h3>

          <!-- The local template ref scopes to this loop iteration -->
          <button #metricsBtn>View Detailed Metrics</button>

          <!-- Only loads chunk when THIS button is clicked -->
          @defer (on interaction(metricsBtn)) {

      }
    </div>
  `
})
export class ServerListComponent {
  servers = [
    { id: 'srv_eu1', name: 'Frankfurt DB', ip: '192.168.1.10' },
    { id: 'srv_us1', name: 'N. Virginia Edge', ip: '10.0.0.45' },
    { id: 'srv_ap1', name: 'Tokyo Cache', ip: '172.16.2.99' },
  ];
}
```
