# 3.2 Clean Architecture & CQRS with MediatR

## Phase A: The Core Pedagogy

### 1. Real-World Pain Point (The Why)
You look at `OrderController.cs`. It's 2,000 lines long. It injects `DbContext`, `IEmailService`, `IPaymentGateway`, and `ILogger`. Every POST method contains validation logic, database saves, HTTP calls to Stripe, and email formatting. Your unit tests are a nightmare because you have to mock 15 dependencies just to test if a database save works. Multiple developers working on this file constantly cause merge conflicts. This is the "Fat Controller / Monolith" anti-pattern.

### 2. Plain English Metaphor (The What)
Imagine a Restaurant:
- **Fat Controller:** The Waiter takes your order, runs to the kitchen, cooks the food, swipes your credit card, and serves the food. The Waiter is a bottleneck.
- **Clean Architecture:** Separation of concerns. The Waiter (API/Controller) only takes orders. The Kitchen (Domain/Application) cooks. The Bank (Infrastructure) handles payments.
- **CQRS (Command Query Responsibility Segregation):** We separate Reading data (Queries: "Show me the menu") from Writing data (Commands: "Cook a burger").
- **MediatR:** A literal Middleman (the ticket rail in a kitchen). The Waiter places a ticket (Command) on the rail. The Chef (Handler) picks it up. The Waiter doesn't need to know *which* chef cooks it, they just wait for the result.

### 3. Complete Runnable Code
Here is an Enterprise Banking Transfer API refactored to CQRS with MediatR.

```csharp
using MediatR;
using Microsoft.AspNetCore.Mvc;
using System.Threading;
using System.Threading.Tasks;

namespace CleanCQRS
{
    // 1. The COMMAND (The Intent / The Ticket)
    // Represents a Write operation. Implements IRequest<ResultType>
    public class TransferFundsCommand : IRequest<bool>
    {
        public string FromAccount { get; set; }
        public string ToAccount { get; set; }
        public decimal Amount { get; set; }
    }

    // 2. The HANDLER (The Chef)
    // Contains the actual business logic. Isolated and easily testable.
    public class TransferFundsHandler : IRequestHandler<TransferFundsCommand, bool>
    {
        // Inject only what this specific operation needs!
        // private readonly AppDbContext _db;

        public async Task<bool> Handle(TransferFundsCommand request, CancellationToken cancellationToken)
        {
            // 1. Validate
            if (request.Amount <= 0) return false;

            // 2. Business Logic (e.g., deduct from A, add to B via _db)
            // await _db.SaveChangesAsync(cancellationToken);

            // Simulate work
            await Task.Delay(100, cancellationToken);
            return true;
        }
    }

    // 3. The CONTROLLER (The Waiter)
    // Extremely thin. Only handles HTTP concerns (Routing, Status Codes).
    [ApiController]
    [Route("api/[controller]")]
    public class TransferController : ControllerBase
    {
        private readonly IMediator _mediator;

        // Only inject MediatR. No DbContext, no EmailServices!
        public TransferController(IMediator mediator)
        {
            _mediator = mediator;
        }

        [HttpPost]
        public async Task<IActionResult> Transfer([FromBody] TransferFundsCommand command)
        {
            // Send the ticket to the rail. MediatR finds the right Handler.
            var result = await _mediator.Send(command);

            if (result) return Ok("Transfer Successful");
            return BadRequest("Transfer Failed");
        }
    }
}
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: The Command/Query (The Request)**
*Why this precedes Step 2:* Before we do work, we must define the intent. In CQRS, we create simple POCO (Plain Old CLR Object) classes. A `Command` mutates state (Create/Update/Delete). A `Query` reads state. They implement `IRequest<TResponse>`.

**Step 2: The Handler**
*Why this precedes Step 3:* For every Command/Query, there is exactly ONE Handler implementing `IRequestHandler<TRequest, TResponse>`. This is the core of Clean Architecture. This class has a single responsibility. If a bug occurs in the Transfer logic, you know exactly which file to open (`TransferFundsHandler`), and you can unit test it in total isolation.

**Step 3: The Controller and IMediator**
*Why this concludes the breakdown:* The Controller no longer contains business logic. It acts as an adapter between the HTTP world and the Domain world. It accepts JSON, creates a Command, and calls `_mediator.Send()`. MediatR uses reflection at startup to map the Command to the correct Handler, decoupling the invoker from the executor.

### 5. ASCII Architecture Data Flow
```text
[ HTTP POST ] -> [ TransferController ] -> Create Command
                                              |
                                     _mediator.Send(cmd)
                                              |
                          (MediatR Pipeline / Cross-cutting concerns)
                                              |
[ AppDbContext ] <--- [ TransferFundsHandler.Handle() ] ---> [ NotificationService ]
```

### 6. Noob Trap vs Pro Tip
- **Noob Trap:** Using MediatR, but still putting massive amounts of code in the Controller, or having one Handler call `_mediator.Send()` to trigger another Handler. Handlers should not depend on other Handlers.
- **Pro Tip:** MediatR supports `IPipelineBehavior`. You can write a single Validation Behavior using `FluentValidation` that runs automatically before *any* Handler is executed. If validation fails, it short-circuits, removing all `if(!ModelState.IsValid)` checks from your entire app!

### Level 3: Boss Level (Cumulative)
**Challenge:** Combine Mod 3.1 (EF Core AsNoTracking) and Mod 3.2 (CQRS). Write a complete MediatR Query and Handler for `GetActiveProductsQuery`. The Handler must inject `AppDbContext` and return a list of `ProductDto`. The query must use `.AsNoTracking()`, `.Where()`, and `.Select()` for maximum performance.
<details>
<summary>Hint</summary>
Setup the `IRequest<List<ProductDto>>`. In the handler, use the DB context to filter by `IsActive`, apply `Select`, and ensure no tracking is used.
</details>
<details>
<summary>Solution Walkthrough</summary>
```csharp
using MediatR;
using Microsoft.EntityFrameworkCore;
using System.Collections.Generic;
using System.Linq;
using System.Threading;
using System.Threading.Tasks;

// The Query (Read Operation)
public class GetActiveProductsQuery : IRequest<List<ProductDto>> { }

public class ProductDto { public int Id { get; set; } public string Name { get; set; } }

// The Handler (Isolated Logic)
public class GetActiveProductsHandler : IRequestHandler<GetActiveProductsQuery, List<ProductDto>>
{
    private readonly AppDbContext _context;

    public GetActiveProductsHandler(AppDbContext context)
    {
        _context = context;
    }

    public async Task<List<ProductDto>> Handle(GetActiveProductsQuery request, CancellationToken cancellationToken)
    {
        // Mod 3.1: High-Performance EF Core Query inside Clean Architecture
        return await _context.Products
            .AsNoTracking()
            .Where(p => p.IsActive)
            .Select(p => new ProductDto
            {
                Id = p.Id,
                Name = p.Name
            })
            .ToListAsync(cancellationToken);
    }
}
```
This is the gold standard for enterprise ASP.NET Core API development: perfectly isolated, perfectly optimized.
</details>
