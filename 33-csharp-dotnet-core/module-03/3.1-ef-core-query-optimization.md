# 3.1 EF Core Query Optimization

## Phase A: The Core Pedagogy

### 1. Real-World Pain Point (The Why)
Your E-Commerce site has a "Search Products" API. It works fine with 100 products. But now the catalog has 100,000 items. When users search for "Shoes", the API takes 5 seconds to load and memory consumption spikes to 4GB. You check SQL Server, and the query is fast. The problem is in the API server. Entity Framework Core is pulling down 10,000 `Product` objects, taking "snapshots" of every single property, storing them in a Change Tracker dictionary, and trying to resolve thousands of one-to-many relationships (Cartesian Explosion). Your API is dying under the weight of EF's internal state management.

### 2. Plain English Metaphor (The What)
Imagine you are taking inventory of a warehouse:
- **Default Tracking Query:** You find an item, write down its serial number on your clipboard, take a photo of its current condition, and put it in a temporary holding area just in case the manager asks you to update its price later. You do this for 10,000 items. It's exhausting and takes up all your desk space.
- **AsNoTracking() (Read-Only):** You just print a list of names and prices and hand it to the customer. You don't track anything. It's instant and uses almost no desk space.
- **Cartesian Explosion (Joins):** You ask for a list of 10 Authors and all their Books. The database returns a massive table: Author 1 + Book A, Author 1 + Book B, Author 1 + Book C. Author 1's data is duplicated over and over.
- **Split Queries:** You ask for Authors (1 small list), and then you ask for Books (1 small list), and EF stitches them together in memory.

### 3. Complete Runnable Code
Here is a High-Performance E-Commerce Product Search API demonstrating bad vs good queries.

```csharp
using System;
using System.Collections.Generic;
using System.Linq;
using System.Threading.Tasks;
using Microsoft.EntityFrameworkCore;

namespace EFCoreOptimizations
{
    public class Product
    {
        public int Id { get; set; }
        public string Name { get; set; }
        public decimal Price { get; set; }
        public List<Review> Reviews { get; set; } = new();
    }

    public class Review
    {
        public int Id { get; set; }
        public string Text { get; set; }
        public int ProductId { get; set; }
    }

    public class AppDbContext : DbContext
    {
        public DbSet<Product> Products { get; set; }
        // (Omitted OnConfiguring for brevity)
    }

    public class ProductService
    {
        private readonly AppDbContext _context;
        public ProductService(AppDbContext context) => _context = context;

        // BAD: Tracks changes, causes Cartesian Explosion with Include
        public async Task<List<Product>> GetProductsBadAsync(string search)
        {
            return await _context.Products
                .Include(p => p.Reviews) // Joins create massive duplicated data rows
                .Where(p => p.Name.Contains(search))
                .ToListAsync();
        }

        // GOOD: No Tracking, Split Queries, Select Projection
        public async Task<List<ProductDto>> GetProductsGoodAsync(string search)
        {
            return await _context.Products
                .AsNoTracking() // 1. Bypasses the Change Tracker entirely
                .AsSplitQuery() // 2. Prevents Cartesian Explosion on Includes
                .Where(p => p.Name.Contains(search))
                .Select(p => new ProductDto // 3. Select only what we need
                {
                    Id = p.Id,
                    Name = p.Name
                })
                .ToListAsync();
        }
    }

    public class ProductDto
    {
        public int Id { get; set; }
        public string Name { get; set; }
    }
}
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: The Change Tracker (`AsNoTracking`)**
*Why this precedes Step 2:* By default, when EF pulls entities from the database, it registers them in the `DbContext` Change Tracker. This requires allocating extra memory and CPU to take snapshots of the object state. If you are only reading data (e.g., a GET API), you don't need this. `.AsNoTracking()` disables this, improving speed and memory by 50%+.

**Step 2: Projections (`Select`)**
*Why this precedes Step 3:* Even without tracking, pulling `SELECT *` on a table with 50 columns just to display the `Name` is a waste of network bandwidth and memory. Using `.Select(p => new Dto { ... })` forces EF to generate a `SELECT Name, Id FROM Products` query, transferring only exactly what is needed.

**Step 3: Cartesian Explosion (`AsSplitQuery`)**
*Why this concludes the breakdown:* If you must pull full object graphs (e.g., Products + Reviews + Categories), doing standard SQL JOINs multiplies the data returned over the network. 10 products with 100 reviews each means the DB sends back 1000 rows, duplicating the Product data 100 times. `.AsSplitQuery()` sends 2 separate SQL queries (one for Products, one for Reviews) and efficiently wires them up in memory.

### 5. ASCII Architecture Data Flow
```text
[ DEFAULT EF CORE ]
API -> SELECT * FROM Products LEFT JOIN Reviews -> DB Returns 1000 rows (Duplicated Product Data) -> Change Tracker Memory Bloat -> API OOM Crash

[ OPTIMIZED EF CORE ]
API -> SELECT Id, Name FROM Products (Query 1)
    -> SELECT Id, Text FROM Reviews (Query 2)
    -> DB returns tiny datasets -> EF Maps instantly (No Tracking) -> Fast API Response
```

### 6. Noob Trap vs Pro Tip
- **Noob Trap:** Pulling the entire table into memory (`.ToList()`) and *then* filtering (`.Where(x => ...)`). This executes `SELECT * FROM Table`, downloads all 10GB of data to the server, and filters it in C# RAM.
- **Pro Tip:** Always apply `.Where()` *before* `.ToListAsync()`. To achieve maximum throughput for highly repetitive queries, use `EF.CompileAsyncQuery` to cache the SQL query generation plan.

## Phase B: Real-World Engineering Challenges

### Level 1: Warm-Up
**Challenge:** Look at this code: `var users = db.Users.ToList().Where(u => u.IsActive);`. Why is this disastrous for performance, and how do you fix it?
<details>
<summary>Hint</summary>
The position of `.ToList()` determines when the SQL query is actually sent to the database.
</details>
<details>
<summary>Solution Walkthrough</summary>
`ToList()` executes the query immediately. This means `SELECT * FROM Users` happens first. Then the `.Where` runs in memory.
**Fix:** Swap them. `var users = db.Users.Where(u => u.IsActive).ToList();` translates to `SELECT * FROM Users WHERE IsActive = 1`.
</details>

### Level 2: Real-World
**Challenge:** You have an API endpoint `GET /api/orders/{id}` that returns an `Order` and its `LineItems`. You do not plan to modify the order. Write the EF Core query using `Include`, ensuring it avoids Change Tracking and Cartesian Explosion.
<details>
<summary>Hint</summary>
Chain `.Include()`, `.AsNoTracking()`, and `.AsSplitQuery()`.
</details>
<details>
<summary>Solution Walkthrough</summary>
```csharp
public async Task<Order> GetOrderAsync(int id)
{
    return await _context.Orders
        .Include(o => o.LineItems)
        .AsNoTracking()   // Read-only, save memory
        .AsSplitQuery()   // Avoid Cartesian Join data duplication
        .FirstOrDefaultAsync(o => o.Id == id);
}
```
</details>

### Level 3: Boss Level (Cumulative)
**Challenge:** Combine Mod 1.2 (Structs) and EF Core optimizations. You need to write a background report generator. It queries 50,000 `Transaction` records (Id, Amount, Date) from EF Core. To avoid LOH fragmentation and Gen 2 GC pauses, you want to project this directly into a `readonly struct` instead of an Entity Class, and you must use AsNoTracking. Write the query.
<details>
<summary>Hint</summary>
Define a `readonly struct TransactionDto`. Use `.Select()` to map the Entity directly to the Struct before `.ToListAsync()`.
</details>
<details>
<summary>Solution Walkthrough</summary>
```csharp
using Microsoft.EntityFrameworkCore;
using System;
using System.Collections.Generic;
using System.Linq;
using System.Threading.Tasks;

// Mod 1.1: Struct to avoid Heap Allocation for 50,000 items
public readonly struct TransactionDto
{
    public int Id { get; }
    public decimal Amount { get; }
    public DateTime Date { get; }

    public TransactionDto(int id, decimal amount, DateTime date)
    {
        Id = id; Amount = amount; Date = date;
    }
}

public class ReportService
{
    private readonly AppDbContext _context;

    public async Task<List<TransactionDto>> GenerateReportAsync()
    {
        // Mod 3.1: NoTracking + Projection
        return await _context.Transactions
            .AsNoTracking()
            .Select(t => new TransactionDto(t.Id, t.Amount, t.Date))
            .ToListAsync();

        // NOTE: The List<T> itself is allocated on the heap (and might hit the LOH),
        // but the 50,000 individual structs are stored inline within the List's internal array,
        // saving us from creating 50,000 separate object references on the heap!
    }
}
```
</details>
