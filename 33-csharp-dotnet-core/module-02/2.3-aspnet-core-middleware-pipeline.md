# 2.3 ASP.NET Core Middleware Pipeline & Minimal APIs

## Phase A: The Core Pedagogy

### 1. Real-World Pain Point (The Why)
You have an API with 50 different controller endpoints. For every single endpoint, you need to measure the response time, log the request payload, check if a specific API Key header exists, and handle unhandled exceptions globally. If you copy and paste this logic into all 50 controller methods, your code becomes an unmaintainable, bloated mess. If you try to use Action Filters, you miss errors that happen before routing even occurs.

### 2. Plain English Metaphor (The What)
Imagine a high-security office building (ASP.NET Core Server) where a visitor (The HTTP Request) wants to see the CEO (The Endpoint/Controller).
- **Middleware:** The security checkpoints along the hallway.
- Checkpoint 1 (Logging): Scans the visitor's ID card. Passes them along.
- Checkpoint 2 (Auth): Checks if they have an appointment. If NO, security turns them around immediately (Short-circuit). If YES, passes them along.
- CEO's Office (Endpoint): Does the actual business work, hands the visitor a signed document (The HTTP Response).
- **The Pipeline:** The visitor must walk back through the exact same checkpoints on the way out, allowing Checkpoint 1 to record exactly how long the visit took.

### 3. Complete Runnable Code
Here is an Enterprise API Gateway Pipeline using Custom Middleware and Minimal APIs.

```csharp
using Microsoft.AspNetCore.Builder;
using Microsoft.AspNetCore.Http;
using System.Diagnostics;
using System.Threading.Tasks;

namespace MiddlewareDemo
{
    // Custom Middleware Class
    public class GlobalMetricsMiddleware
    {
        private readonly RequestDelegate _next;

        // _next points to the next checkpoint in the hallway
        public GlobalMetricsMiddleware(RequestDelegate next)
        {
            _next = next;
        }

        public async Task InvokeAsync(HttpContext context)
        {
            var sw = Stopwatch.StartNew();

            // 1. INBOUND phase: Code here runs BEFORE the controller
            context.Response.Headers.Append("X-Server-Id", "Node-01");

            // 2. PASS TO NEXT: Call the next middleware (or the endpoint)
            await _next(context);

            // 3. OUTBOUND phase: Code here runs AFTER the controller
            sw.Stop();
            // Log the total time taken by everything downstream
            System.Console.WriteLine($"Request {context.Request.Path} took {sw.ElapsedMilliseconds}ms");
        }
    }

    class Program
    {
        static void Main(string[] args)
        {
            var builder = WebApplication.CreateBuilder(args);
            var app = builder.Build();

            // Register our custom middleware
            app.UseMiddleware<GlobalMetricsMiddleware>();

            // Inline Middleware (Short-circuiting example)
            app.Use(async (context, next) =>
            {
                if (context.Request.Path == "/block")
                {
                    context.Response.StatusCode = 403;
                    await context.Response.WriteAsync("Blocked by Security!");
                    return; // SHORT CIRCUIT: Do not call next()
                }
                await next(context);
            });

            // Minimal API Endpoint (The "CEO")
            app.MapGet("/hello", () => "Hello World from Minimal APIs!");

            app.Run();
        }
    }
}
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: The RequestDelegate (`_next`)**
*Why this precedes Step 2:* Middleware is structured as a linked list (the "Russian Doll" model). `RequestDelegate next` represents the *rest of the pipeline*. When your middleware is done with its inbound tasks, it MUST call `await _next(context)` to pass the request along.

**Step 2: Inbound vs Outbound Execution**
*Why this precedes Step 3:* Because we `await _next(context)`, execution pauses inside our middleware, runs everything downstream (the controllers, etc.), and then resumes. This is why we start a stopwatch *before* `next`, and stop it *after* `next`.

**Step 3: Short-Circuiting**
*Why this concludes the breakdown:* If a middleware decides the request is invalid (e.g., unauthorized), it can write directly to the `HttpContext.Response` and simply *return* without calling `_next()`. This short-circuits the pipeline, saving server resources by skipping the controller entirely.

### 5. ASCII Architecture Data Flow
```text
REQUEST ---> [ Metrics Middle ] ---> [ Auth Middle ] ---> [ Endpoint (Minimal API) ]
             (Starts Timer)          (Checks Header)        (Returns "Hello")
                   |                        |                       |
RESPONSE <---[ Metrics Middle ] <--- [ Auth Middle ] <--------------+
             (Stops Timer)           (Passes through)
```

### 6. Noob Trap vs Pro Tip
- **Noob Trap:** Writing to the `HttpContext.Response.Body` *after* calling `await _next(context)`. The controller downstream already wrote to the body and started sending it to the client. Attempting to modify headers or the body after it has started sending throws an `InvalidOperationException: Headers are read-only`.
- **Pro Tip:** Middleware execution order is critical. Always put `UseExceptionHandler` first, `UseRouting` in the middle, and `UseAuthorization` right before your endpoints.

## Phase B: Real-World Engineering Challenges

### Level 1: Warm-Up
**Challenge:** Write an inline middleware using `app.Use(...)` that adds a custom header `"X-Environment": "Production"` to every response before passing it to the next middleware.
<details>
<summary>Hint</summary>
Add the header to `context.Response.Headers` and then call `await next(context);`.
</details>
<details>
<summary>Solution Walkthrough</summary>
```csharp
app.Use(async (context, next) =>
{
    // Modify before next()
    context.Response.Headers.Append("X-Environment", "Production");

    // Pass along
    await next(context);
});
```
</details>

### Level 2: Real-World
**Challenge:** You want to catch any unhandled exceptions globally and return a standard JSON format. Write a `GlobalExceptionMiddleware` class. If an exception occurs, catch it, set status to 500, and write `{"error": "Internal Server Error"}` to the response.
<details>
<summary>Hint</summary>
Wrap `await _next(context);` in a `try/catch` block.
</details>
<details>
<summary>Solution Walkthrough</summary>
```csharp
public class GlobalExceptionMiddleware
{
    private readonly RequestDelegate _next;
    public GlobalExceptionMiddleware(RequestDelegate next) => _next = next;

    public async Task InvokeAsync(HttpContext context)
    {
        try
        {
            await _next(context); // Try to process request
        }
        catch (Exception ex)
        {
            // Catch globally
            context.Response.StatusCode = StatusCodes.Status500InternalServerError;
            context.Response.ContentType = "application/json";
            await context.Response.WriteAsync("{\"error\": \"Internal Server Error\"}");
        }
    }
}
```
</details>

### Level 3: Boss Level (Cumulative)
**Challenge:** Combine Mod 2.2 (Channels) and Middleware. Write a `TelemetryMiddleware`. For every request, it should extract the Path, generate an `EventPayload` struct, write it to a singleton `ChannelWriter<EventPayload>` in the background (zero-blocking), and then immediately pass the request to `_next(context)`.
<details>
<summary>Hint</summary>
Inject `Channel<EventPayload>` into the middleware constructor via DI, or pass it directly. Use `TryWrite` to fire-and-forget.
</details>
<details>
<summary>Solution Walkthrough</summary>
```csharp
using System.Threading.Channels;

public readonly struct TelemetryEvent
{
    public string Path { get; }
    public TelemetryEvent(string path) { Path = path; }
}

public class TelemetryMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ChannelWriter<TelemetryEvent> _channelWriter;

    // Injected via DI
    public TelemetryMiddleware(RequestDelegate next, Channel<TelemetryEvent> channel)
    {
        _next = next;
        _channelWriter = channel.Writer;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        // 1. Create struct (Zero-alloc, Mod 1.1)
        var evt = new TelemetryEvent(context.Request.Path);

        // 2. Fire and forget to background channel (No lock contention, Mod 2.2)
        _channelWriter.TryWrite(evt);

        // 3. Continue pipeline immediately (Fast API response)
        await _next(context);
    }
}
```
This architecture is extremely common in high-performance enterprise systems for offloading metric collection without impacting API latency.
</details>
