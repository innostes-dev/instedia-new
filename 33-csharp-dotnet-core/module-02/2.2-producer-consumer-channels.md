# 2.2 Producer-Consumer with System.Threading.Channels

## Phase A: The Core Pedagogy

### 1. Real-World Pain Point (The Why)
Your API receives thousands of webhooks per second. You need to process these webhooks (e.g., send emails, write to a database). If you process them synchronously during the HTTP request, your API becomes slow and drops connections. If you spin up a `Task.Run()` for every request, you exhaust the thread pool and crash. If you use a `ConcurrentQueue<T>` with a `lock`, the threads spend all their time fighting for access to the lock (lock contention) rather than doing actual work. You need a fast, thread-safe queue with built-in async support and backpressure.

### 2. Plain English Metaphor (The What)
Imagine a busy coffee shop:
- **Producer (The Cashier):** Takes orders (webhooks) and writes them on a cup.
- **The Queue:** The physical counter where empty cups are placed.
- **Consumer (The Barista):** Takes cups from the counter and makes the coffee.
- **ConcurrentQueue / Locks:** The Cashier and Barista are constantly fighting over the exact same spot on the counter, bumping into each other.
- **System.Threading.Channels:** A highly efficient conveyor belt. The Cashier drops a cup on one end. The Barista pulls from the other. If the belt gets too full (Bounded Channel), the Cashier is forced to stop taking orders (Backpressure) so the shop doesn't explode.

### 3. Complete Runnable Code
Here is a High-Throughput Background Email Queue using Channels.

```csharp
using System;
using System.Threading.Channels;
using System.Threading.Tasks;

namespace ChannelDemo
{
    public record EmailMessage(string To, string Body);

    class Program
    {
        static async Task Main()
        {
            // 1. Create a Bounded Channel (Max 100 items). Provides Backpressure.
            var options = new BoundedChannelOptions(100)
            {
                FullMode = BoundedChannelFullMode.Wait, // Wait if full
                SingleReader = true,  // Optimize for 1 consumer
                SingleWriter = false  // Multiple producers allowed
            };

            var channel = Channel.CreateBounded<EmailMessage>(options);

            // 2. Start Consumer (Barista) in the background
            var consumerTask = Task.Run(() => ProcessEmailsAsync(channel.Reader));

            // 3. Producers (Cashiers) pushing data
            Console.WriteLine("Producers generating emails...");
            for (int i = 0; i < 10; i++)
            {
                var email = new EmailMessage($"user{i}@test.com", $"Hello {i}");
                await channel.Writer.WriteAsync(email);
            }

            // Tell the channel no more data is coming
            channel.Writer.Complete();

            // Wait for consumer to finish processing the remaining items
            await consumerTask;
            Console.WriteLine("All emails processed.");
        }

        static async Task ProcessEmailsAsync(ChannelReader<EmailMessage> reader)
        {
            // ReadAllAsync natively yields when the channel is empty!
            await foreach (var email in reader.ReadAllAsync())
            {
                Console.WriteLine($"[Consumer] Sending email to {email.To}...");
                await Task.Delay(100); // Simulate network I/O
            }
        }
    }
}
```

### 4. Progressive Step-by-Step Breakdown

**Step 1: The Channel Creation and Options**
*Why this precedes Step 2:* You must define the rules of the conveyor belt before using it. `Channel.CreateUnbounded<T>()` creates an infinite queue (dangerous, can cause OutOfMemory). `Channel.CreateBounded<T>()` creates a capped queue. The `BoundedChannelOptions` allow you to specify how many writers/readers exist. Setting `SingleReader = true` allows the CLR to strip out heavy locks, making reading blazing fast.

**Step 2: The Producer (`ChannelWriter<T>`)**
*Why this precedes Step 3:* We need data in the pipeline. The producer uses `channel.Writer.WriteAsync()`. If the bounded channel is full, this `WriteAsync` will actually `await` (suspend) until there is space. This prevents the producer from overwhelming the consumer (Backpressure).

**Step 3: The Consumer (`ChannelReader<T>`)**
*Why this concludes the breakdown:* The consumer uses `await foreach (var item in channel.Reader.ReadAllAsync())`. This is magical. It asynchronously waits for data. If the channel is empty, it doesn't block a thread; the state machine yields. When new data arrives, it wakes up and processes it.

### 5. ASCII Architecture Data Flow
```text
[ API Request 1 ] --WriteAsync--> [                         ]
[ API Request 2 ] --WriteAsync--> [ BOUNDED CHANNEL (100)   ] --ReadAllAsync--> [ Background Worker ]
[ API Request 3 ] --WriteAsync--> [ (Conveyor Belt)         ]                   (Sends Emails DB/SMTP)
```

### 6. Noob Trap vs Pro Tip
- **Noob Trap:** Using `List<T>` with a `lock` statement for a background worker queue, or using `Channel.CreateUnbounded` which eventually crashes the server due to OOM when the producer outpaces the consumer.
- **Pro Tip:** When setting up an ASP.NET Core HostedService (BackgroundService), use a singleton `Channel<T>` to decouple your fast web controllers from your slow background processing tasks safely.

## Phase B: Real-World Engineering Challenges

### Level 1: Warm-Up
**Challenge:** Modify a `BoundedChannelOptions` configuration so that if the channel is full, it drops the *oldest* item in the queue instead of waiting.
<details>
<summary>Hint</summary>
Look at the `FullMode` property on `BoundedChannelOptions`.
</details>
<details>
<summary>Solution Walkthrough</summary>
```csharp
var options = new BoundedChannelOptions(100)
{
    // Instead of waiting, drop the oldest item to make room
    FullMode = BoundedChannelFullMode.DropOldest
};
```
This is useful for metrics or telemetry where the latest data is more important than old data.
</details>

### Level 2: Real-World
**Challenge:** Write a Consumer method that reads from a `ChannelReader<int>` but cancels immediately if a provided `CancellationToken` is triggered.
<details>
<summary>Hint</summary>
Pass the token to `ReadAllAsync(cancellationToken)`.
</details>
<details>
<summary>Solution Walkthrough</summary>
```csharp
public async Task ProcessDataAsync(ChannelReader<int> reader, CancellationToken token)
{
    try
    {
        await foreach (var item in reader.ReadAllAsync(token))
        {
            Console.WriteLine($"Processed: {item}");
        }
    }
    catch (OperationCanceledException)
    {
        Console.WriteLine("Processing was cancelled.");
    }
}
```
</details>

### Level 3: Boss Level (Cumulative)
**Challenge:** Build an "Ingestion Service". Create a Controller method (API) that accepts an event and writes it to a singleton `Channel`. Then, imagine a Background Consumer that processes these events. Ensure zero-allocations on the event model by using a `readonly struct` (from Mod 1.1) and use `ValueTask` (from Mod 2.1) where appropriate.
<details>
<summary>Hint</summary>
Define a `readonly struct EventPayload`. The Controller will use `channel.Writer.WriteAsync`.
</details>
<details>
<summary>Solution Walkthrough</summary>
```csharp
using System.Threading.Channels;
using System.Threading.Tasks;

// Mod 1.1: Struct for zero heap allocation
public readonly struct EventPayload
{
    public int EventId { get; }
    public EventPayload(int id) { EventId = id; }
}

public class IngestionAPI
{
    private readonly ChannelWriter<EventPayload> _writer;

    public IngestionAPI(Channel<EventPayload> channel)
    {
        _writer = channel.Writer;
    }

    // Mod 2.1: ValueTask for performance
    public async ValueTask AcceptEventAsync(int id)
    {
        var payload = new EventPayload(id);

        // WaitToWriteAsync / TryWrite is highly optimized
        if (await _writer.WaitToWriteAsync())
        {
            _writer.TryWrite(payload);
        }
    }
}
```
</details>
