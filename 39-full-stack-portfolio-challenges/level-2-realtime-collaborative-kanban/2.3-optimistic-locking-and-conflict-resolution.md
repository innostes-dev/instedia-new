# 2.3 Optimistic Locking and Conflict Resolution

## Phase A: The Core Concept

### 🚨 Real-World Pain Point (The Why)
User A and User B are both viewing a Kanban card titled "Fix Login Bug." User A changes the title to "Fix Login Bug (Urgent)" and clicks Save. Exactly 50 milliseconds later, User B, who hadn't seen User A's change yet, changes the description and clicks Save. User B's save payload sends the *old* title back to the server. The server blindly accepts User B's payload, silently overwriting and destroying User A's "Urgent" title update. This is known as the "Lost Update" problem.

### 💡 Plain English Metaphor (The What)
Imagine two editors working on a shared **Google Doc offline**. Editor A changes Chapter 1. Editor B changes Chapter 2. They both connect to the internet. If the system uses "Last Write Wins," Editor B's upload completely wipes out Editor A's changes.
Optimistic Locking is like adding a **Version Number** to the document. The server says, "I will only accept your save if you are editing Version 4." Editor A saves, making it Version 5. Editor B tries to save Version 4, but the server rejects it: "Conflict! Your version is outdated. Download Version 5 first, re-apply your changes, and try again."

### 💻 Complete Runnable Architecture/Code Example (TypeScript & Prisma)

**Database Schema (Prisma)**
```prisma
model Card {
  id          String   @id @default(uuid())
  boardId     String
  title       String
  description String?
  version     Int      @default(1) // 👈 The Optimistic Lock Counter
  updatedAt   DateTime @updatedAt
}
```

**TypeScript (Express Backend)**
```typescript
import express, { Request, Response } from 'express';
import { PrismaClient } from '@prisma/client';

const prisma = new PrismaClient();
const app = express();
app.use(express.json());

app.put('/api/cards/:id', async (req: Request, res: Response) => {
  const { id } = req.params;
  const { title, description, expectedVersion } = req.body;

  if (!expectedVersion) {
    return res.status(400).json({ error: "expectedVersion is required for updates" });
  }

  try {
    // 1. Attempt update ONLY if the database version matches the client's expected version
    const updatedCard = await prisma.card.update({
      where: {
        id: id,
        version: expectedVersion // Optimistic Lock Condition!
      },
      data: {
        title,
        description,
        version: { increment: 1 } // Automatically bump version on success
      }
    });

    res.json({ status: 'success', data: updatedCard });

  } catch (error: any) {
    // Prisma throws P2025 (RecordNotFound) if the WHERE clause (including version) fails
    if (error.code === 'P2025') {

      // Fetch the latest state to send back to the client for manual merging
      const latestCard = await prisma.card.findUnique({ where: { id } });

      return res.status(409).json({
        error: "Conflict! Another user modified this card.",
        code: "OPTIMISTIC_LOCK_FAILURE",
        serverState: latestCard
      });
    }

    res.status(500).json({ error: "Internal Server Error" });
  }
});
```

**Frontend (React Conflict Handler)**
```tsx
import React, { useState } from 'react';

export default function CardEditor({ initialCard }) {
  const [card, setCard] = useState(initialCard);
  const [conflict, setConflict] = useState<any>(null);

  const handleSave = async () => {
    const response = await fetch(`/api/cards/${card.id}`, {
      method: 'PUT',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({
        title: card.title,
        description: card.description,
        expectedVersion: card.version // Send the version we *think* it is
      })
    });

    if (response.status === 409) {
      const data = await response.json();
      setConflict(data.serverState); // Show conflict UI
    } else {
      const data = await response.json();
      setCard(data.data); // Update to new version (e.g., version 2)
      setConflict(null);
    }
  };

  return (
    <div className="p-4 border rounded">
      {conflict && (
        <div className="bg-red-100 p-2 mb-4 text-red-800 rounded">
          ⚠️ <strong>Conflict Detected!</strong> Someone else updated this card.
          <br/>Server Title: {conflict.title}
          <button onClick={() => {
            setCard(conflict); // Accept server changes
            setConflict(null);
          }}>
            Override my changes with Server Version
          </button>
        </div>
      )}

      <input
        value={card.title}
        onChange={e => setCard({...card, title: e.target.value})}
        className="border p-1 w-full"
      />
      <button onClick={handleSave} className="mt-2 bg-blue-500 text-white p-2 rounded">
        Save
      </button>
    </div>
  );
}
```

### 🪜 Progressive Step-by-Step Breakdown

#### Step 1: The Version Column
We add an integer `version` column to the database schema. This acts as a clock or generation counter for the row.

#### Step 2: The Atomic Update (Compare-and-Swap)
When the backend executes the `UPDATE` statement, it includes `WHERE id = ? AND version = ?`. Because SQL databases execute updates atomically (using row-level locks internally during the transaction), if two requests hit the database at the exact same millisecond, one will win. It updates the row and increments the version to `2`. The second request immediately fails because it is looking for `version = 1`, which no longer exists.

#### Step 3: Handling HTTP 409 Conflict
When the update fails due to a version mismatch, we don't just return a 500 error. We catch the specific ORM error, fetch the *current* state of the row, and return it with an `HTTP 409 Conflict` status. The frontend intercepts this 409 and displays a UI prompting the user to decide how to merge the conflicting data.

### 🔀 ASCII / Architecture Flow

```text
[ Database: Card 1 (Version 1) ]
       |                  |
       v                  v
[ User A reads V1 ]  [ User B reads V1 ]
       |                  |
       v                  |
User A Saves V1           |
(Success! DB now V2)      |
                          v
                     User B Saves V1
                     (WHERE version=1 FAILS!)
                          |
                          v
                     [ HTTP 409 Conflict ] ---> Frontend shows "Merge UI"
```

### ⚠️ Noob Trap vs 👑 Pro Tip
* **Noob Trap**: Implementing "Pessimistic Locking" (e.g., `SELECT ... FOR UPDATE` that locks the row while the user is typing on the frontend). If the user closes their browser, the row remains locked forever, breaking the app for everyone else.
* **Pro Tip**: Use Optimistic Locking (versions) for UI-driven CRUD apps. Use Pessimistic Locking only in short-lived, backend-only financial transactions (like transferring money between two accounts) where the transaction takes milliseconds.

## Phase B: Engineering Challenges

### 🟢 Level 1: Warm-Up
**Task:** Modify the `UPDATE` query so that instead of an integer `version`, it uses the `updatedAt` timestamp for optimistic locking.
<details>
<summary>💡 Hint</summary>
The client sends `expectedUpdatedAt`. The Prisma query becomes `where: { id: id, updatedAt: expectedUpdatedAt }`. (Note: integer versions are generally safer due to potential timezone or precision loss issues with timestamps across different DB drivers).
</details>

### 🟡 Level 2: Real-World
**Task:** Implement a "Force Save" feature on the frontend. If a 409 conflict occurs, the user can click "Overwrite Server". The frontend makes a new request that bypasses the optimistic lock.
<details>
<summary>💡 Hint</summary>
Add a boolean flag `force: true` to the request body. If the backend sees this flag, it executes the update without the `version: expectedVersion` condition in the `WHERE` clause (but still increments the version!).
</details>

### 🔴 Level 3: Boss Level
**Task:** Implement a basic Operational Transformation (OT) or Field-Level merging algorithm. If User A changes the `title`, and User B changes the `description`, there is technically no conflict! The backend should detect this and merge both changes automatically, only throwing a 409 if they modified the *exact same field*.
<details>
<summary>💡 Hint & Solution</summary>
Instead of a single version for the row, track versions for fields, or have the client send a patch (diff) instead of the whole object.

**Solution Approach (Diffing):**
1. Client sends: `{ id: 1, expectedVersion: 1, updates: { description: "new text" } }`
2. Backend queries current state (now V2, title was changed by User A).
3. Backend checks if `description` was modified between V1 and V2. (Requires an audit log or tracking field hashes).
4. If `description` was untouched by User A, apply User B's `description` update and increment to V3.
5. (For true Google Docs style text merging, you need CRDTs like Yjs or Automerge, which is a massive leap in complexity).
</details>
