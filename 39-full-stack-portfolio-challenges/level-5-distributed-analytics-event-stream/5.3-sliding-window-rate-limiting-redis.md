# 5.3 Sliding Window Rate Limiting (Redis)

## Phase A: The Core Concept

### 🚨 Real-World Pain Point (The Why)
Your high-throughput telemetry API is public. A malicious user (or a bug in an IoT device's firmware) decides to send 1,000,000 requests in 5 seconds. If you don't block them at the API Gateway, they will saturate your network bandwidth, exhaust your memory buffers, and fill your Kafka cluster with garbage, causing an outage for all other legitimate users.
If you use a basic "Fixed Window" rate limiter (e.g., 100 requests per minute), the user can send 100 requests at 12:00:59, and another 100 requests at 12:01:01. They bypassed the spirit of the limit by bursting 200 requests in just 2 seconds right at the minute boundary.

### 💡 Plain English Metaphor (The What)
Fixed Window is like a **Monthly Data Plan**. On the 31st you use 10GB, and on the 1st you use 10GB. You used 20GB in two days, but the phone company allows it because the calendar month rolled over.
Sliding Window is like a **Rolling 24-Hour Pass**. It doesn't care about the calendar date. If you check your pass at 3:00 PM, it looks back exactly 24 hours to 3:00 PM yesterday. If you've used your quota in that specific window, you are blocked. As time slowly ticks forward, your oldest usage slowly "slides" out of the window, freeing up capacity.

### 💻 Complete Runnable Architecture/Code Example (TypeScript & Redis)

**TypeScript (Express & Redis Lua Script)**
```typescript
import express, { Request, Response, NextFunction } from 'express';
import Redis from 'ioredis';

const app = express();
const redis = new Redis({ host: 'localhost', port: 6379 });

const MAX_REQUESTS = 100;
const WINDOW_SIZE_SECONDS = 60;

// 1. The Atomic Lua Script
// We use Lua because it executes atomically inside Redis. No race conditions!
// ARGVs: [window_size_ms, current_time_ms, max_requests]
const slidingWindowLuaScript = `
  local key = KEYS[1]
  local window_size = tonumber(ARGV[1])
  local now = tonumber(ARGV[2])
  local limit = tonumber(ARGV[3])

  -- Step 1: Remove all timestamps older than the sliding window
  local clearBefore = now - window_size
  redis.call('ZREMRANGEBYSCORE', key, 0, clearBefore)

  -- Step 2: Count how many requests are currently in the window
  local requestCount = redis.call('ZCARD', key)

  -- Step 3: Check if we are over the limit
  if requestCount < limit then
    -- We are good! Add the current timestamp to the Sorted Set.
    -- Score is the timestamp, Value is the timestamp (or a UUID to prevent duplicates)
    redis.call('ZADD', key, now, now)

    -- Set an expiration on the whole key so it cleans itself up if the user goes away
    redis.call('EXPIRE', key, math.ceil(window_size / 1000))
    return { 1, limit - requestCount - 1 } -- 1 means allowed, plus remaining quota
  else
    return { 0, 0 } -- 0 means blocked
  end
`;

// Pre-load the script into Redis for performance (returns a SHA hash)
// ioredis lets us define custom commands easily
redis.defineCommand('slidingWindowRateLimit', {
  numberOfKeys: 1,
  lua: slidingWindowLuaScript,
});

// Custom type augmentation for the new Redis command
declare module "ioredis" {
  interface Redis {
    slidingWindowRateLimit(key: string, windowMs: number, nowMs: number, limit: number): Promise<[number, number]>;
  }
}

// 2. The Express Middleware
const rateLimiter = async (req: Request, res: Response, next: NextFunction) => {
  // Use IP address, or better, the authenticated API Key
  const clientId = req.ip || 'anonymous';
  const redisKey = `rate_limit:${clientId}`;
  const now = Date.now();
  const windowMs = WINDOW_SIZE_SECONDS * 1000;

  try {
    // 3. Execute the atomic check
    const [allowed, remaining] = await redis.slidingWindowRateLimit(
      redisKey,
      windowMs,
      now,
      MAX_REQUESTS
    );

    // Set standard rate limit headers
    res.setHeader('X-RateLimit-Limit', MAX_REQUESTS);
    res.setHeader('X-RateLimit-Remaining', remaining);

    if (allowed === 1) {
      next();
    } else {
      res.setHeader('Retry-After', WINDOW_SIZE_SECONDS);
      res.status(429).json({ error: 'Too Many Requests' });
    }
  } catch (error) {
    console.error("Rate limiter failed, failing open...", error);
    // If Redis goes down, we usually choose to "fail open" (allow the request)
    // rather than taking down the entire API, depending on business requirements.
    next();
  }
};

app.use('/api/', rateLimiter);

app.post('/api/telemetry', (req, res) => {
  res.status(202).send({ status: 'Accepted' });
});

app.listen(3000, () => console.log('API running with Rate Limiting on port 3000'));
```

### 🪜 Progressive Step-by-Step Breakdown

#### Step 1: Redis Sorted Sets (`ZSET`)
We use a specific Redis data structure called a Sorted Set. A Sorted Set stores elements ordered by a "score". We use the current timestamp (in milliseconds) as BOTH the value and the score. So the set looks like: `[ (1690000000, 1690000000), (1690000500, 1690000500) ]`.

#### Step 2: The Sliding Mechanism (`ZREMRANGEBYSCORE`)
When a new request arrives at time `T`, we immediately delete all elements in the set whose score is less than `T - 60 seconds`. This is the "sliding" part. The old requests literally fall off the back of the queue.

#### Step 3: Atomic Evaluation via Lua
If we did this in Node.js (Call 1: `ZREMRANGEBYSCORE`, Call 2: `ZCARD`, Call 3: `ZADD`), and the user sent 50 concurrent requests, a race condition would occur. Multiple requests might read a count of 99 simultaneously and all insert their timestamps, allowing 149 requests through. By writing a Lua script, we hand the logic to the Redis engine. Redis is single-threaded; it executes the entire Lua script atomically. No other commands can interrupt it.

### 🔀 ASCII / Architecture Flow

```text
Time: 12:00:00 (Window is 60s, Limit is 3)

[ Req 1 ] -> Lua Script
             1. Remove < 11:59:00 (None)
             2. Count = 0. Allowed? YES.
             3. ZADD 12:00:00
             [ Redis Set: 12:00:00 ]

[ Req 2 ] -> Lua Script
             1. Remove < 11:59:05 (None)
             2. Count = 1. Allowed? YES.
             3. ZADD 12:00:05
             [ Redis Set: 12:00:00, 12:00:05 ]

... (Req 3 allowed at 12:00:10) ... [ Redis Set: 12:00:00, 12:00:05, 12:00:10 ]

[ Req 4 ] (Arrives at 12:00:15)
             1. Remove < 11:59:15 (None)
             2. Count = 3. Allowed? NO! (Returns 429)

[ Req 5 ] (Arrives at 12:01:02)
             1. Remove < 12:00:02 (Removes the 12:00:00 entry!)
             2. Count = 2. Allowed? YES!
             3. ZADD 12:01:02
             [ Redis Set: 12:00:05, 12:00:10, 12:01:02 ]
```

### ⚠️ Noob Trap vs 👑 Pro Tip
* **Noob Trap**: Using the Sliding Window pattern for a limit of 10,000 requests per minute. `ZADD`ing 10,000 timestamps and counting them takes significantly more CPU and memory in Redis than a simple `INCR` counter.
* **Pro Tip**: If you need high limits (like 10k/min), use the **Sliding Window Counter** algorithm instead of the Sliding Window Log. It divides the window into buckets (e.g., 60 buckets of 1 second). You just increment the current bucket, and sum the buckets. It uses $O(1)$ memory regardless of how many millions of requests occur.

### 🟡 Level 2: Real-World
**Task:** Implement multi-tiered rate limiting. A user is allowed 10 requests per second, AND 100 requests per minute. They must pass both checks. If they fail either, return 429.
<details>
<summary>💡 Hint</summary>
Run the Lua script twice (or modify the Lua script to accept multiple keys/limits).
`const [secAllowed] = await check(clientId + ':sec', 1000, 10);`
`const [minAllowed] = await check(clientId + ':min', 60000, 100);`
If `!secAllowed || !minAllowed`, block the request. Note: You should check *both* before incrementing *either* to avoid stealing quota for a failed request.
</details>

### 🔴 Level 3: Boss Level
**Task:** Convert the Lua Script to use the "Sliding Window Counter" algorithm (O(1) memory) instead of the Sorted Set log. Use Redis Hashes to store bucket counts.
<details>
<summary>💡 Hint & Solution</summary>
Divide the time into buckets.

**Solution Approach (Lua):**
```lua
local key = KEYS[1]
local limit = tonumber(ARGV[1])
local now = tonumber(ARGV[2]) -- Current time ms
local bucket_size = tonumber(ARGV[3]) -- e.g. 1000 (1 sec)
local window_buckets = tonumber(ARGV[4]) -- e.g. 60 (60 secs total)

local current_bucket = math.floor(now / bucket_size)
local oldest_bucket = current_bucket - window_buckets

-- Clean up old buckets
local all_buckets = redis.call('HKEYS', key)
for _, b in ipairs(all_buckets) do
    if tonumber(b) <= oldest_bucket then
        redis.call('HDEL', key, b)
    end
end

-- Sum up the remaining buckets
local vals = redis.call('HVALS', key)
local sum = 0
for _, v in ipairs(vals) do sum = sum + tonumber(v) end

-- Check limit
if sum < limit then
    redis.call('HINCRBY', key, tostring(current_bucket), 1)
    redis.call('EXPIRE', key, window_buckets * bucket_size / 1000 + 5)
    return 1
else
    return 0
end
```
</details>
