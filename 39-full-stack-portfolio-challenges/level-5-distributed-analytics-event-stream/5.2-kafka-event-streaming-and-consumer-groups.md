# 5.2 Kafka Event Streaming and Consumer Groups

## Phase A: The Core Concept

### 🚨 Real-World Pain Point (The Why)
Your high-throughput API is successfully dumping 10,000 events/second into a basic Redis queue. You spin up 5 worker processes to read from the queue and write to a Data Warehouse.
1. **Worker Starvation:** Worker A is super fast, Worker B is slow. Because it's a simple queue, they both pull data randomly. Worker B becomes a bottleneck, while Worker A sits idle.
2. **Ordering Chaos:** An event "User Created" and "User Deleted" enter the queue. Worker B grabs "User Created". Worker A grabs "User Deleted". Worker A is faster, so it tries to delete a user before Worker B has even created them. The database crashes.

### 💡 Plain English Metaphor (The What)
A standard Queue is like a **Crowded Bakery Ticket Dispenser**. Customers (Events) pull a number. Any available clerk (Worker) helps the next number. You have no control over which clerk helps which customer.
Kafka with Partitions is like **Checkout Lanes at a Grocery Store**. You define a rule: "Everyone buying Alcohol must go to Lane 1. Everyone buying Produce must go to Lane 2."
A Consumer Group is the **Staff Shift**. If you have 3 Lanes (Partitions) and 3 Cashiers (Workers in a Consumer Group), each cashier takes one lane. If Cashier 1 goes on break, Cashier 2 takes over Lane 1 AND Lane 2 (Rebalancing). Crucially, the people in Lane 1 will *always* be processed in the exact order they lined up.

### 💻 Complete Runnable Architecture/Code Example (TypeScript & KafkaJS)

**TypeScript (Node.js & KafkaJS)**
```typescript
// npm install kafkajs
import { Kafka, Partitioners } from 'kafkajs';

const kafka = new Kafka({
  clientId: 'telemetry-app',
  brokers: ['localhost:9092']
});

const producer = kafka.producer({ createPartitioner: Partitioners.DefaultPartitioner });
const consumer = kafka.consumer({ groupId: 'data-warehouse-writers' });

// 1. The Producer (API Server sending data)
async function startProducer() {
  await producer.connect();

  // Simulating an API endpoint receiving data for a specific user
  const userId = "user_123";
  const eventPayload = { event: "PAGE_VIEW", url: "/home" };

  await producer.send({
    topic: 'user-telemetry-events',
    messages: [
      {
        // 2. The Partition Key!
        // All events with the same key ("user_123") are GUARANTEED to go to the exact same partition.
        key: userId,
        value: JSON.stringify(eventPayload)
      }
    ]
  });
  console.log("Message sent!");
}

// 3. The Consumer (Background Worker)
async function startConsumer() {
  await consumer.connect();

  // Subscribe to the topic. 'fromBeginning: false' means only read new events.
  await consumer.subscribe({ topic: 'user-telemetry-events', fromBeginning: false });

  // 4. Processing the stream
  await consumer.run({
    // Auto-commit tells Kafka "I successfully processed this".
    // If set to false, you must manually commit the offset.
    autoCommit: false,
    eachMessage: async ({ topic, partition, message, heartbeat }) => {
      try {
        const payload = JSON.parse(message.value!.toString());
        console.log(`[Partition ${partition}] Processing event for User: ${message.key}`);

        // Simulate DB write
        await writeToDataWarehouse(payload);

        // 5. Manual Offset Commit (Durability)
        // Only mark it as "done" in Kafka AFTER the DB write succeeds.
        // If the worker crashes here, another worker will re-read this message.
        await consumer.commitOffsets([{ topic, partition, offset: (BigInt(message.offset) + 1n).toString() }]);

        // Heartbeat tells Kafka this worker is still alive
        await heartbeat();
      } catch (error) {
        console.error("Failed to process message", error);
        // Do not commit! Let it retry or send to a Dead Letter Queue
      }
    },
  });
}

// Mock DB function
async function writeToDataWarehouse(data: any) {
  return new Promise(resolve => setTimeout(resolve, 50));
}

```

### 🪜 Progressive Step-by-Step Breakdown

#### Step 1: The Partition Key (Strict Ordering)
When producing the message, we set `key: userId`. Kafka uses a hash of this key to assign the message to a specific partition (e.g., Partition 3). This guarantees that *every* action performed by `user_123` goes into Partition 3 in the exact order it occurred.

#### Step 2: Consumer Groups and Assignments
When we start the Consumer with `groupId: 'data-warehouse-writers'`, Kafka does magic. If our topic has 10 partitions, and we start 1 Node.js worker, it reads all 10. If we scale to 5 workers, Kafka automatically "rebalances" and assigns 2 partitions to each worker. Because `user_123` is always in Partition 3, and Partition 3 is assigned to Worker B, *only* Worker B will process `user_123`'s events, ensuring strict sequential processing for that user and preventing race conditions.

#### Step 3: Manual Offset Commits (At-Least-Once Delivery)
Kafka doesn't delete messages when read. It keeps a pointer (an "Offset") for each Consumer Group showing how far they've read. By setting `autoCommit: false`, we take control. We only tell Kafka to advance the pointer *after* `writeToDataWarehouse()` succeeds. If the server loses power during the DB write, the pointer never moves. When the server reboots, it reads the message again, guaranteeing no data is lost.

### 🔀 ASCII / Architecture Flow

```text
[ API Producers ]
  (User 123) ---------> [ Kafka Topic: user-telemetry ]
  (User 456)            |
                        |-- [ Partition 0 ] (User 456 goes here)
                        |-- [ Partition 1 ] (User 123 goes here)
                        |-- [ Partition 2 ]

                                       | (Kafka Group Coordinator assigns partitions)
                                       v
[ Consumer Group: 'data-warehouse-writers' ]
  Worker A <--- Reads Partition 0
  Worker B <--- Reads Partition 1 & 2
```

### ⚠️ Noob Trap vs 👑 Pro Tip
* **Noob Trap**: Creating a topic with only 1 partition, or scaling up to 20 workers when you only have 10 partitions. In Kafka, **you cannot have more active workers in a group than you have partitions**. If you have 10 partitions and 20 workers, 10 workers will sit completely idle 100% of the time.
* **Pro Tip**: Always over-partition early. If you think you need 5 workers, create the topic with 30 partitions. It costs virtually nothing, but it gives you massive headroom to scale up to 30 workers in the future without needing to stop the world and re-key all your data.

### 🔴 Level 3: Boss Level
**Task:** Batch processing for maximum DB throughput. Instead of using `eachMessage` (which writes to the DB one row at a time), use KafkaJS's `eachBatch` to pull arrays of up to 500 messages at once. Write them to the mock Data Warehouse in a single bulk transaction, and commit the offset only for the entire batch.
<details>
<summary>💡 Hint & Solution</summary>
```typescript
await consumer.run({
  eachBatchAutoResolve: false, // Take control of commits
  eachBatch: async ({ batch, resolveOffset, heartbeat, commitOffsetsIfNecessary }) => {
    const payloads = batch.messages.map(m => JSON.parse(m.value!.toString()));

    // Perform bulk DB insert! (Massively faster than individual inserts)
    await bulkWriteToDataWarehouse(payloads);

    // Get the highest offset in the batch
    const lastOffset = batch.messages[batch.messages.length - 1].offset;

    // Resolve the offset in memory
    resolveOffset(lastOffset);
    // Push the commit to Kafka
    await commitOffsetsIfNecessary();
    await heartbeat();
  },
});
```
</details>
