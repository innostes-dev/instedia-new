# 5.1 High-Throughput Ingestion API

## Phase A: The Core Concept

### 🚨 Real-World Pain Point (The Why)
Imagine an IoT fleet of 500,000 smart thermostats. They all wake up at exactly 8:00 AM and send a `{ "temp": 72 }` payload to your API. If your API server synchronously connects to a PostgreSQL database, writes the row, and waits for the database disk to acknowledge the write for every single request, your database connection pool instantly exhausts. Your web servers crash under the weight of 10,000 concurrent blocking requests, returning 502 Bad Gateway to the devices.

### 💡 Plain English Metaphor (The What)
Synchronous ingestion is like a **Post Office with one clerk who insists on personally driving every letter to its destination** before helping the next person in line. The line goes out the door.
High-Throughput Ingestion is like a **Mail Drop Box**. The clerk just takes the letter from you, drops it in a massive bin behind the counter, and immediately says "Next!" The bin (Memory Buffer) is periodically emptied into a truck (Batching) and taken to the sorting facility (Database/Kafka) in one fast trip.

### 💻 Complete Runnable Architecture/Code Example (TypeScript & Node.js)

**TypeScript (Fastify - High Performance Node.js Framework)**
```typescript
import Fastify from 'fastify';

const app = Fastify({ logger: true });

// The Memory Buffer
let eventBuffer: Array<any> = [];
const BATCH_SIZE_LIMIT = 1000;
const FLUSH_INTERVAL_MS = 5000;

// Mock external storage (Kafka, ClickHouse, or Postgres)
const flushToStorage = async (batch: any[]) => {
  // In reality, this would be a bulk insert or Kafka publish
  console.log(`[Storage] Flushed batch of ${batch.length} events to disk.`);
};

// The Flush Mechanism
const flushBuffer = async () => {
  if (eventBuffer.length === 0) return;

  // 1. Atomic Swap: Instantly swap the buffer so the API can keep accepting new
  // requests into an empty array while we process the old data.
  const batchToProcess = eventBuffer;
  eventBuffer = [];

  try {
    // 2. Asynchronous Bulk Write
    await flushToStorage(batchToProcess);
  } catch (error) {
    console.error("Failed to flush batch!", error);
    // In a bulletproof system, you would write this failed batch to a local file (WAL)
    // or re-insert it at the front of eventBuffer.
  }
};

// Flush every 5 seconds regardless of size to prevent stale data
setInterval(flushBuffer, FLUSH_INTERVAL_MS);

// 3. The Non-Blocking Endpoint
app.post('/api/telemetry', async (request, reply) => {
  const event = request.body;

  // Just push to RAM. Takes ~0.001 milliseconds.
  eventBuffer.push({ ...event as any, receivedAt: Date.now() });

  // If we hit our batch limit, trigger an early flush asynchronously
  if (eventBuffer.length >= BATCH_SIZE_LIMIT) {
    setImmediate(flushBuffer);
  }

  // 4. Return immediately. Do NOT await the database.
  return reply.status(202).send({ status: 'Accepted' });
});

const start = async () => {
  try {
    // Fastify is much faster than Express for raw throughput
    await app.listen({ port: 3000 });
  } catch (err) {
    app.log.error(err);
    process.exit(1);
  }
};
start();
```

### 🪜 Progressive Step-by-Step Breakdown

#### Step 1: The Memory Buffer
Instead of opening a DB connection, we just `push()` a JSON object into a standard Javascript Array. This operates entirely in RAM and is blisteringly fast.

#### Step 2: Atomic Swapping
When it's time to save to the database, we don't lock the array. We assign the reference of `eventBuffer` to a new variable `batchToProcess`, and immediately set `eventBuffer = []`. The API endpoint can continue pushing to the new empty array without pausing.

#### Step 3: HTTP 202 Accepted
We return a `202 Accepted` status code, not `200 OK` or `201 Created`. `202` explicitly tells the client: "I have received your data, but I have not fully processed or saved it yet." This is the contract of asynchronous ingestion.

#### Step 4: Time + Size based Flushing
We flush the data to the database based on two triggers:
1. **Size (`BATCH_SIZE_LIMIT`)**: If 1000 events come in 1 second, flush immediately to prevent running out of RAM.
2. **Time (`FLUSH_INTERVAL_MS`)**: If only 5 events come in, we don't want them stuck in RAM forever. Flush every 5 seconds regardless.

### 🔀 ASCII / Architecture Flow

```text
[ IoT Device 1 ] --(POST)-->|
[ IoT Device 2 ] --(POST)-->|--> [ API Server RAM Buffer (Array) ]
[ IoT Device N ] --(POST)-->|               |
                                            | (Triggers on 1000 items OR 5 seconds)
  <--(HTTP 202 Accepted)-- (Instantly)      |
                                            v
                              [ Bulk Insert / Kafka Producer ]
                                            |
                                            v
                             [ Distributed Broker / Data Warehouse ]
```

### ⚠️ Noob Trap vs 👑 Pro Tip
* **Noob Trap**: Using this RAM buffering pattern on Serverless platforms (like AWS Lambda or Vercel Edge functions). Serverless functions freeze their memory immediately after returning the HTTP response. The `setInterval` will never run, and your data will be permanently lost when the function shuts down.
* **Pro Tip**: Use this pattern only on long-running servers (Docker containers, EC2, Kubernetes). If you must use Serverless for ingestion, push directly to a managed broker like AWS Kinesis, SQS, or Confluent Kafka from the edge function.

## Phase B: Engineering Challenges

### 🟢 Level 1: Warm-Up
**Task:** Convert the Express framework (from previous examples) to Fastify. Why use Fastify here?
<details>
<summary>💡 Hint</summary>
Fastify uses `pino` for zero-allocation logging and highly optimized JSON parsing (`fast-json-stringify`), allowing it to handle ~2x more requests per second than Express for raw payload ingestion.
</details>

### 🟡 Level 2: Real-World
**Task:** Implement Graceful Shutdown. If a developer deploys a new version of the API, the Node process receives a `SIGTERM` signal. If you just exit the process, anything currently sitting in `eventBuffer` is destroyed. Trap the signal, stop accepting new HTTP requests, flush the buffer one last time, and then exit.
<details>
<summary>💡 Hint</summary>
```typescript
process.on('SIGTERM', async () => {
  console.log("Shutting down...");
  await app.close(); // Stops accepting new requests
  await flushBuffer(); // Flush remaining items
  process.exit(0);
});
```
</details>

### 🔴 Level 3: Boss Level
**Task:** Implement a Disk-Backed Write-Ahead Log (WAL). If the Node server completely crashes (power failure, Out Of Memory) before the 5-second interval, RAM is wiped. Instead of pushing purely to an Array, write the raw bytes to an append-only file on disk (`events.log`) instantly, and only delete the file after a successful bulk flush to the database.
<details>
<summary>💡 Hint & Solution</summary>
Use Node's `fs.createWriteStream` for high-performance file appending.

**Solution Approach:**
```typescript
import fs from 'fs';
const walStream = fs.createWriteStream('wal.log', { flags: 'a' });

app.post('/api/telemetry', async (req, reply) => {
  const rawJson = JSON.stringify(req.body) + '\n';
  // Fast append to disk (OS handles buffering, much safer than just Node RAM)
  walStream.write(rawJson);
  return reply.status(202).send();
});

// In the background cron:
// 1. Rename 'wal.log' to 'processing.log'
// 2. Open new 'wal.log' for incoming traffic
// 3. Read 'processing.log', parse JSON, send to Kafka/DB
// 4. Delete 'processing.log' on success.
```
</details>
