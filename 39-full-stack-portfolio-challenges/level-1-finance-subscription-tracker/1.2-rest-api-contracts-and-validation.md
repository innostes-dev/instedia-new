# 1.2 REST API Contracts and Validation

## Phase A: The Core Concept

### 🚨 Real-World Pain Point (The Why)
A frontend client sends `{ "amount": "one hundred", "date": "yesterday" }` to your financial API. Without strict validation, this payload crashes the database driver or corrupts financial records. When the error occurs, the server responds with a generic `500 Internal Server Error`, leaving frontend engineers guessing what went wrong. Furthermore, querying a user's transactions without pagination causes memory exhaustion when returning 10,000 records.

### 💡 Plain English Metaphor (The What)
Think of an API Contract like a **Customs Declaration Form** at an airport. The form explicitly states what you are allowed to bring in. If you declare "Apples", customs (the API Validator) checks if they are actually apples. If you try to sneak in forbidden items, customs rejects you immediately and gives you a specific reason ("Item X is prohibited"), rather than just yelling "Error!" and locking the airport.

### 💻 Complete Runnable Architecture/Code Example (TypeScript & Python)

**TypeScript (Express & Zod)**
```typescript
import express, { Request, Response } from 'express';
import { z } from 'zod';

const app = express();
app.use(express.json());

// DTO Validation Schema
const TransactionSchema = z.object({
  accountId: z.string().uuid("Invalid Account ID format"),
  amount: z.number().multipleOf(0.01, "Amount must be in currency format").min(0.01, "Amount must be positive"),
  type: z.enum(['CREDIT', 'DEBIT']),
  date: z.string().datetime("Invalid ISO 8601 date string")
});

type TransactionDTO = z.infer<typeof TransactionSchema>;

// Middleware for validation
const validateDTO = (schema: z.ZodSchema) => (req: Request, res: Response, next: express.NextFunction) => {
  try {
    req.body = schema.parse(req.body);
    next();
  } catch (error) {
    if (error instanceof z.ZodError) {
      // RFC 7807 Problem Details Standard
      return res.status(400).json({
        type: "https://api.example.com/errors/validation",
        title: "Request Validation Failed",
        status: 400,
        detail: "One or more fields are invalid.",
        instance: req.originalUrl,
        invalidParams: error.errors.map(e => ({ name: e.path.join('.'), reason: e.message }))
      });
    }
    next(error);
  }
};

app.post('/api/transactions', validateDTO(TransactionSchema), (req: Request, res: Response) => {
  const data: TransactionDTO = req.body;
  // Database logic here...
  res.status(201).json({ status: "success", data });
});
```

**Python (FastAPI & Pydantic)**
```python
from fastapi import FastAPI, HTTPException, Request, status
from fastapi.responses import JSONResponse
from fastapi.exceptions import RequestValidationError
from pydantic import BaseModel, Field, UUID4
from enum import Enum
from datetime import datetime

app = FastAPI()

class TransactionType(str, Enum):
    CREDIT = 'CREDIT'
    DEBIT = 'DEBIT'

class TransactionDTO(BaseModel):
    account_id: UUID4 = Field(..., description="The UUID of the account")
    amount: float = Field(..., gt=0, description="Amount must be positive")
    type: TransactionType
    date: datetime = Field(..., description="ISO 8601 Date string")

# Override default FastAPI validation error to match RFC 7807
@app.exception_handler(RequestValidationError)
async def validation_exception_handler(request: Request, exc: RequestValidationError):
    invalid_params = [{"name": ".".join(map(str, err["loc"][1:])), "reason": err["msg"]} for err in exc.errors()]
    return JSONResponse(
        status_code=status.HTTP_422_UNPROCESSABLE_ENTITY,
        content={
            "type": "https://api.example.com/errors/validation",
            "title": "Request Validation Failed",
            "status": 422,
            "detail": "One or more fields are invalid.",
            "instance": str(request.url),
            "invalidParams": invalid_params
        }
    )

@app.post("/api/transactions", status_code=201)
async def create_transaction(transaction: TransactionDTO):
    # Database logic here...
    return {"status": "success", "data": transaction.model_dump()}
```

### 🪜 Progressive Step-by-Step Breakdown

#### Step 1: Strict DTO Validation (Data Transfer Object)
We use schemas (Zod in TS, Pydantic in Python) to strictly define the shape, type, and boundaries of incoming data. It isn't just a "string"; it's a "UUID string". It isn't just a "number"; it's a "positive number up to 2 decimal places".

#### Step 2: RFC 7807 Problem Details
Instead of standard `{ "error": "Bad Request" }`, we format errors according to RFC 7807. This provides a standardized way for frontend clients to parse errors. They get `type`, `title`, and an `invalidParams` array showing exactly which fields failed and why.

#### Step 3: Date/Cursor Based Pagination (Implicit)
For large financial ledgers, returning all data is impossible. While not shown in the exact snippet above, the contract design implies that fetching transactions must involve `GET /transactions?cursor=DATE_ISO&limit=50`.

### 🔀 ASCII / Architecture Flow

```text
[ Client Payload ]
   { amount: -5 }
        |
        v
[ API Gateway / Validator ] --(Invalid Schema)--> [ RFC 7807 Error Response ]
        |                                           { title: "Validation Failed",
        | (Valid Schema)                              invalidParams: [{name: "amount", reason: "must be positive"}] }
        v
[ Controller / Handler ]
        |
        v
[ Database Insertion ]
```

### ⚠️ Noob Trap vs 👑 Pro Tip
* **Noob Trap**: Hand-writing `if (!req.body.amount) throw Error()` logic inside your route handlers. It gets messy, misses edge cases, and doesn't generate standardized API docs.
* **Pro Tip**: Use a declarative validation library (Zod, Joi, Pydantic). Let the middleware catch errors and map them to RFC 7807. Use these schemas to auto-generate Swagger/OpenAPI documentation so your frontend team never has to guess the contract.

### 🔴 Level 3: Boss Level
**Task:** Implement cross-field validation. If `type` is `DEBIT`, the `amount` must not exceed a theoretical max daily limit of $5000. If `type` is `CREDIT`, there is no limit.
<details>
<summary>💡 Hint & Solution</summary>
You need a schema refinement or root validator that evaluates multiple fields at once.

**Solution (Zod):**
```typescript
const AdvancedTransactionSchema = TransactionSchema.refine((data) => {
  if (data.type === 'DEBIT' && data.amount > 5000) {
    return false;
  }
  return true;
}, {
  message: "Debit transactions cannot exceed $5000",
  path: ["amount"] // Path points to the field causing the error
});
```

**Solution (Pydantic):**
```python
from pydantic import model_validator

class AdvancedTransactionDTO(TransactionDTO):
    @model_validator(mode='after')
    def check_debit_limit(self):
        if self.type == TransactionType.DEBIT and self.amount > 5000:
            raise ValueError('Debit transactions cannot exceed $5000')
        return self
```
</details>
