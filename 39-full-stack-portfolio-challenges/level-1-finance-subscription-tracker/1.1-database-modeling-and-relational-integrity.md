# 1.1 Database Modeling and Relational Integrity

## Phase A: The Core Concept

### 🚨 Real-World Pain Point (The Why)
Imagine a financial tracking application where a user deletes their account, but their recurring subscriptions and historical transactions remain orphaned in the database. Or worse, two users in a shared family budget can see other people's data due to missing tenant isolation. These issues arise from "error-prone spreadsheets" acting as databases, lacking relational integrity, cascading deletions, and multi-tenant scoping.

### 💡 Plain English Metaphor (The What)
Think of a multi-tenant database like an **apartment building**. The building (database) houses many tenants (users or organizations). Each tenant has their own apartment (tenant ID), and everything inside that apartment (transactions, accounts, subscriptions) belongs strictly to them. You wouldn't want a master key that accidentally opens your neighbor's door. Relational integrity is like the **building management rules**: if a tenant moves out, management automatically clears out their furniture (foreign key cascades) instead of leaving it to clutter the building.

**TypeScript (Prisma ORM)**

```typescript
// schema.prisma
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")

model User {

  email         String         @unique
  tenantId      String         @map("tenant_id") // Multi-tenant isolation
  accounts      Account[]
  subscriptions Subscription[]

  user         User          @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId])
}

model Transaction {
  id        String   @id @default(uuid())
  accountId String   @map("account_id")
  amount    Decimal  @db.Decimal(19, 4)

  userId    String   @map("user_id")
  name      String
```

**Python (SQLAlchemy / FastAPI)**
```python
from sqlalchemy import Column, String, Numeric, ForeignKey, DateTime, Index
from sqlalchemy.orm import declarative_base, relationship
from sqlalchemy.sql import func
import uuid

Base = declarative_base()

class User(Base):
    __tablename__ = 'users'
    id = Column(String, primary_key=True, default=lambda: str(uuid.uuid4()))
    email = Column(String, unique=True, nullable=False)
    tenant_id = Column(String, nullable=False, index=True)
    created_at = Column(DateTime(timezone=True), server_default=func.now())

    accounts = relationship("Account", back_populates="user", cascade="all, delete-orphan")
    subscriptions = relationship("Subscription", back_populates="user", cascade="all, delete-orphan")

class Account(Base):
    __tablename__ = 'accounts'
    id = Column(String, primary_key=True, default=lambda: str(uuid.uuid4()))
    user_id = Column(String, ForeignKey('users.id', ondelete='CASCADE'), nullable=False, index=True)
    name = Column(String, nullable=False)
    balance = Column(Numeric(19, 4), nullable=False, default=0.0)

    user = relationship("User", back_populates="accounts")
    transactions = relationship("Transaction", back_populates="account", cascade="all, delete-orphan")

class Transaction(Base):
    __tablename__ = 'transactions'
    id = Column(String, primary_key=True, default=lambda: str(uuid.uuid4()))
    account_id = Column(String, ForeignKey('accounts.id', ondelete='CASCADE'), nullable=False, index=True)
    amount = Column(Numeric(19, 4), nullable=False)
    type = Column(String, nullable=False) # 'CREDIT' or 'DEBIT'
    created_at = Column(DateTime(timezone=True), server_default=func.now())

    account = relationship("Account", back_populates="transactions")

class Subscription(Base):
    __tablename__ = 'subscriptions'
    id = Column(String, primary_key=True, default=lambda: str(uuid.uuid4()))
    user_id = Column(String, ForeignKey('users.id', ondelete='CASCADE'), nullable=False, index=True)
    name = Column(String, nullable=False)
    cost = Column(Numeric(19, 4), nullable=False)
    frequency = Column(String, nullable=False)

    user = relationship("User", back_populates="subscriptions")
```

### 🪜 Progressive Step-by-Step Breakdown

#### Step 1: Multi-Tenant Schema Design
We introduce `tenant_id` on the `User` model. This is the foundation of multi-tenancy. Every query made to the database by a specific user MUST include a filter `WHERE tenant_id = ?`. This prevents data leakage between organizations or isolated family units.

#### Step 2: Referential Integrity (Foreign Keys)
Notice the `user_id` and `account_id` fields. Instead of just storing string IDs, we define strict foreign key relationships. The database engine guarantees that an `Account` cannot exist without a valid `User`, and a `Transaction` cannot exist without an `Account`.

#### Step 3: Cascading Deletes
We configure `onDelete: Cascade` (Prisma) or `ondelete='CASCADE'` and `cascade="all, delete-orphan"` (SQLAlchemy). This solves the orphaned data pain point. If a user deletes their account, the database automatically drops their accounts, transactions, and subscriptions in one atomic sweep.


### ⚠️ Noob Trap vs 👑 Pro Tip
* **Noob Trap**: Using floating-point numbers (`FLOAT` or `DOUBLE`) for financial amounts. You will encounter rounding errors (e.g., `0.1 + 0.2 = 0.30000000000000004`).
* **Pro Tip**: Always use `DECIMAL(19, 4)` or `NUMERIC` for precise financial data, or store values as integers representing the smallest unit (e.g., cents) and divide by 100 on the frontend. Ensure foreign keys have indexes; without them, cascading deletes can lock entire tables and cause severe performance degradation.

### 🔴 Level 3: Boss Level
**Task:** Design a historical audit ledger. Every time a `Subscription` cost changes, you must record the change in a separate `subscription_audit_logs` table without losing the previous cost, capturing the `old_cost`, `new_cost`, and `changed_at` timestamp.
<details>
<summary>💡 Hint & Solution</summary>
You can implement this at the application layer using a transaction that updates the subscription and inserts an audit log row, OR at the database layer using a Postgres trigger `AFTER UPDATE ON subscriptions`.

**Solution (SQL Trigger):**
```sql
CREATE TABLE subscription_audit_logs (
    id UUID PRIMARY KEY,
    subscription_id UUID REFERENCES subscriptions(id),
    old_cost DECIMAL(19, 4),
    new_cost DECIMAL(19, 4),
    changed_at TIMESTAMP DEFAULT NOW()
);

CREATE OR REPLACE FUNCTION log_subscription_changes()
RETURNS TRIGGER AS $$
BEGIN
    IF OLD.cost IS DISTINCT FROM NEW.cost THEN
        INSERT INTO subscription_audit_logs(id, subscription_id, old_cost, new_cost)
        VALUES (gen_random_uuid(), NEW.id, OLD.cost, NEW.cost);
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trigger_subscription_cost_change
AFTER UPDATE ON subscriptions
FOR EACH ROW EXECUTE FUNCTION log_subscription_changes();
```
