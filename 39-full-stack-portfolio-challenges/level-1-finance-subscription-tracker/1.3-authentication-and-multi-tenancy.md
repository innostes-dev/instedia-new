# 1.3 Authentication and Multi-Tenancy

## Phase A: The Core Concept

### 🚨 Real-World Pain Point (The Why)
Imagine logging into a SaaS dashboard for your company, but due to a missed `WHERE tenant_id = ?` clause in the backend code, you see financial records belonging to a competitor. Data leakage between tenants is a catastrophic security failure. Furthermore, using long-lived JWTs without a rotation strategy means if a token is stolen, the attacker has permanent access until the token expires, with no way for you to revoke it.

### 💡 Plain English Metaphor (The What)
Multi-tenant authentication is like a **Hotel Keycard System**. When you check into a hotel (authenticate), you get a keycard (Access Token). This card only opens your specific room (Tenant Isolation). The card expires every few hours (Short-lived JWT), requiring you to stop by the front desk (Refresh Token Endpoint) to get it renewed. If you lose your card, the front desk cancels it immediately (Token Revocation), rendering the stolen card useless.

### 💻 Complete Runnable Architecture/Code Example (TypeScript & Python)

**TypeScript (Express & JWT)**
```typescript
import express, { Request, Response, NextFunction } from 'express';
import jwt from 'jsonwebtoken';

const app = express();
app.use(express.json());

const JWT_SECRET = process.env.JWT_SECRET || 'super-secret-key';
const REFRESH_SECRET = process.env.REFRESH_SECRET || 'super-refresh-key';

// In-memory store for refresh tokens (use Redis in production)
const activeRefreshTokens = new Set<string>();

interface JWTPayload {
  userId: string;
  tenantId: string;
}

// Custom request interface to hold user context
declare global {
  namespace Express {
    interface Request {
      user?: JWTPayload;
    }
  }
}

// 1. Authentication Middleware
const requireAuth = (req: Request, res: Response, next: NextFunction) => {
  const authHeader = req.headers.authorization;
  if (!authHeader?.startsWith('Bearer ')) return res.status(401).json({ error: 'Unauthorized' });

  const token = authHeader.split(' ')[1];
  try {
    const payload = jwt.verify(token, JWT_SECRET) as JWTPayload;
    req.user = payload; // Attach context to request
    next();
  } catch (err) {
    res.status(401).json({ error: 'Invalid or expired token' });
  }
};

// 2. Login Endpoint (Issues Access & Refresh Tokens)
app.post('/api/login', (req, res) => {
  // Assume user credentials verified, fetch user from DB
  const mockUser = { id: 'u_123', tenantId: 't_abc' };

  const accessToken = jwt.sign(
    { userId: mockUser.id, tenantId: mockUser.tenantId },
    JWT_SECRET,
    { expiresIn: '15m' } // Short lived
  );

  const refreshToken = jwt.sign(
    { userId: mockUser.id },
    REFRESH_SECRET,
    { expiresIn: '7d' } // Long lived
  );
  activeRefreshTokens.add(refreshToken);

  // Send tokens (Refresh token should ideally be HttpOnly Cookie)
  res.json({ accessToken, refreshToken });
});

// 3. Tenant-Isolated Endpoint
app.get('/api/accounts', requireAuth, (req, res) => {
  const { tenantId } = req.user!;

  // Database Query MUST use tenantId from the verified token, NOT the request body
  // db.accounts.findMany({ where: { tenantId } })

  res.json({ data: `Returning accounts for tenant: ${tenantId}` });
});
```

**Python (FastAPI & python-jose)**
```python
from fastapi import FastAPI, Depends, HTTPException, Security
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials
from jose import JWTError, jwt
from datetime import datetime, timedelta
from typing import Optional

app = FastAPI()
security = HTTPBearer()

JWT_SECRET = "super-secret-key"
ALGORITHM = "HS256"

# Mock Database
active_refresh_tokens = set()

def create_access_token(data: dict, expires_delta: timedelta):
    to_encode = data.copy()
    expire = datetime.utcnow() + expires_delta
    to_encode.update({"exp": expire})
    return jwt.encode(to_encode, JWT_SECRET, algorithm=ALGORITHM)

# Dependency to verify token and extract tenant context
async def get_current_user(credentials: HTTPAuthorizationCredentials = Security(security)):
    try:
        payload = jwt.decode(credentials.credentials, JWT_SECRET, algorithms=[ALGORITHM])
        user_id: str = payload.get("sub")
        tenant_id: str = payload.get("tenant_id")
        if user_id is None or tenant_id is None:
            raise HTTPException(status_code=401, detail="Invalid token payload")
        return {"user_id": user_id, "tenant_id": tenant_id}
    except JWTError:
        raise HTTPException(status_code=401, detail="Could not validate credentials")

@app.post("/api/login")
async def login():
    # Mock authentication
    user = {"id": "u_123", "tenant_id": "t_abc"}

    access_token = create_access_token(
        data={"sub": user["id"], "tenant_id": user["tenant_id"]},
        expires_delta=timedelta(minutes=15)
    )
    # Refresh token omitted for brevity, logic identical to TS example
    return {"access_token": access_token, "token_type": "bearer"}

@app.get("/api/accounts")
async def get_accounts(current_user: dict = Depends(get_current_user)):
    tenant_id = current_user["tenant_id"]
    # Enforce isolation: Query DB using tenant_id from token
    # return db.query(Account).filter(Account.tenant_id == tenant_id).all()
    return {"data": f"Returning accounts for tenant: {tenant_id}"}
```

### 🪜 Progressive Step-by-Step Breakdown

#### Step 1: JWT Payload & Context
The JWT payload must contain the `tenantId`. When a request is made, the authentication middleware verifies the signature, decodes the payload, and attaches this context (`req.user`) to the request object.

#### Step 2: Tenant-Scoped Queries
In the route handler (`/api/accounts`), we never trust a `tenantId` provided by the client in the body or query params. We **always** extract it from the verified `req.user` context and force it into the database `WHERE` clause. This guarantees isolation.

#### Step 3: Refresh Token Rotation
Access tokens are kept intentionally short-lived (e.g., 15 minutes). A longer-lived Refresh Token (7 days) is used to obtain a new Access Token. If an Access Token is compromised, the window of vulnerability is small. If a user logs out or is banned, their Refresh Token is removed from the `activeRefreshTokens` store, preventing future access.

### 🔀 ASCII / Architecture Flow

```text
[ Client ] ---(Login Credentials)---> [ Auth Server ]
                                          |
                                          |-- 1. Validates creds
                                          |-- 2. Creates short-lived Access Token (JWT)
                                          |-- 3. Creates long-lived Refresh Token (DB/Redis)
                                          v
[ Client ] <---(Access + Refresh)--------
    |
    |---(GET /data + Access Token)--> [ Resource API ]
                                          |
                                          |-- 4. Middleware verifies Token Signature
                                          |-- 5. Extracts tenant_id from Token
                                          |-- 6. DB Query: SELECT * WHERE tenant_id = token.tenant_id
                                          v
[ Client ] <---(Isolated Data)-----------
```

### ⚠️ Noob Trap vs 👑 Pro Tip
* **Noob Trap**: Storing the JWT in `localStorage`. This makes it vulnerable to Cross-Site Scripting (XSS) attacks. Any rogue JavaScript on the page can steal the token.
* **Pro Tip**: Send the Refresh Token in a `Secure, HttpOnly, SameSite=Strict` cookie. The frontend cannot access it via JS, but the browser will automatically send it to the `/refresh` endpoint. Keep the Access Token in memory on the frontend (e.g., in a closure or React state) and fetch a new one when the app loads or the token expires.

## Phase B: Engineering Challenges

### 🟢 Level 1: Warm-Up
**Task:** Implement the `/api/refresh` endpoint. It should accept a refresh token, verify it exists in `activeRefreshTokens`, and if valid, issue a brand new Access Token.
<details>
<summary>💡 Hint</summary>
Decode the refresh token to get the `userId`. Look up the user's `tenantId` in the database. Generate a new Access Token and return it.
</details>

### 🟡 Level 2: Real-World
**Task:** Implement a "Logout All Devices" feature. When a user changes their password, all existing sessions should be invalidated immediately.
<details>
<summary>💡 Hint</summary>
Instead of a simple `Set`, use Redis to store refresh tokens grouped by `userId` (e.g., `sadd user:u_123:tokens <token>`). On password change, delete the entire set `del user:u_123:tokens`.
</details>

### 🔴 Level 3: Boss Level
**Task:** Implement Row-Level Security (RLS) in PostgreSQL as a second layer of defense. Instead of relying purely on application code (`WHERE tenant_id = ?`), configure the database to automatically reject queries that don't match the current tenant context.
<details>
<summary>💡 Hint & Solution</summary>
You must pass the tenant context to Postgres before running the query using `SET LOCAL`.

**Solution (PostgreSQL RLS):**
```sql
-- 1. Enable RLS on the table
ALTER TABLE accounts ENABLE ROW LEVEL SECURITY;

-- 2. Create a policy
CREATE POLICY tenant_isolation_policy ON accounts
    USING (tenant_id = current_setting('app.current_tenant')::uuid);

-- 3. Application code execution (pseudo-code)
BEGIN;
-- Set the context for this transaction
SET LOCAL app.current_tenant = 'tenant-uuid-from-jwt';
-- Execute query (automatically scoped by RLS policy)
SELECT * FROM accounts;
COMMIT;
```
If the app developer forgets the `WHERE` clause, Postgres will still return 0 rows for other tenants, preventing the data leak!
</details>
