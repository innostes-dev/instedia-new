# 3.3 Atomic Wallet Transfers and ACID Transactions

## Phase A: The Core Concept

### 🚨 Real-World Pain Point (The Why)
User A has $100 in their digital wallet. They rapidly click "Send $100 to User B" twice. The server receives both requests simultaneously.
- Request 1 checks balance: $100 >= $100 (Pass).
- Request 2 checks balance: $100 >= $100 (Pass).
- Request 1 subtracts $100, saving balance as $0.
- Request 2 subtracts $100, saving balance as -$100 (or $0 if not using relative updates).
User A just conjured $100 out of thin air, crashing your company's accounting. This is a classic Race Condition.

### 💡 Plain English Metaphor (The What)
Atomic transfers are like a **Bank Teller's Drawer**. If two people walk up to two different tellers and try to withdraw the last $100 from a shared joint account at the exact same second, the computer locks the account folder (Pessimistic Lock). Teller 1 gets the folder, subtracts the money, puts it in the drawer, and unlocks the folder. By the time Teller 2 gets the folder, the balance is $0, and they reject the second person.
ACID means the withdrawal from A and deposit to B happen as an *indivisible unit* (Atomic). If the computer catches fire after withdrawing from A but before depositing to B, it puts the money back in A's account (Rollback).

### 💻 Complete Runnable Architecture/Code Example (TypeScript & PostgreSQL)

**Database Schema (SQL)**
```sql
CREATE TABLE wallets (
    id UUID PRIMARY KEY,
    user_id UUID NOT NULL,
    balance DECIMAL(19, 4) NOT NULL DEFAULT 0.0 CHECK (balance >= 0) -- Database level invariant!
);

CREATE TABLE ledger_entries (
    id UUID PRIMARY KEY,
    wallet_id UUID REFERENCES wallets(id),
    amount DECIMAL(19, 4) NOT NULL, -- Negative for debit, Positive for credit
    reference_id UUID NOT NULL, -- To link the sender and receiver entries
    created_at TIMESTAMP DEFAULT NOW()
);
```

**TypeScript (Node.js & pg library for raw SQL control)**
```typescript
import { Pool } from 'pg';
import { v4 as uuidv4 } from 'uuid';

const pool = new Pool({ connectionString: process.env.DATABASE_URL });

async function transferMoney(fromWalletId: string, toWalletId: string, amount: number) {
  if (amount <= 0) throw new Error("Transfer amount must be positive");

  const client = await pool.connect();
  const referenceId = uuidv4();

  try {
    // 1. BEGIN the ACID Transaction
    await client.query('BEGIN');

    // 2. Lock the rows in a deterministic order to prevent Deadlocks!
    // If we don't sort, Tx1 might lock A then B, while Tx2 locks B then A, causing a deadlock.
    const [firstId, secondId] = [fromWalletId, toWalletId].sort();

    // FOR UPDATE applies a Pessimistic Lock.
    // No other transaction can read or modify these rows until we COMMIT or ROLLBACK.
    await client.query(
      `SELECT id FROM wallets WHERE id IN ($1, $2) FOR UPDATE`,
      [firstId, secondId]
    );

    // 3. Check Balance of Sender
    const senderRes = await client.query(`SELECT balance FROM wallets WHERE id = $1`, [fromWalletId]);
    if (senderRes.rows.length === 0) throw new Error("Sender wallet not found");
    const senderBalance = parseFloat(senderRes.rows[0].balance);

    if (senderBalance < amount) {
      throw new Error("Insufficient funds");
    }

    // 4. Execute the Double-Entry Ledger Updates
    // Subtract from sender
    await client.query(
      `UPDATE wallets SET balance = balance - $1 WHERE id = $2`,
      [amount, fromWalletId]
    );
    await client.query(
      `INSERT INTO ledger_entries (id, wallet_id, amount, reference_id) VALUES ($1, $2, $3, $4)`,
      [uuidv4(), fromWalletId, -amount, referenceId]
    );

    // Add to receiver
    await client.query(
      `UPDATE wallets SET balance = balance + $1 WHERE id = $2`,
      [amount, toWalletId]
    );
    await client.query(
      `INSERT INTO ledger_entries (id, wallet_id, amount, reference_id) VALUES ($1, $2, $3, $4)`,
      [uuidv4(), toWalletId, amount, referenceId]
    );

    // 5. COMMIT - All changes are saved atomically
    await client.query('COMMIT');
    console.log(`Successfully transferred $${amount}`);

  } catch (error) {
    // 6. ROLLBACK - If ANYTHING fails (even a syntax error), undo all changes
    await client.query('ROLLBACK');
    console.error("Transaction failed, rolled back.", error);
    throw error;
  } finally {
    // Release the client back to the pool
    client.release();
  }
}
```

### 🪜 Progressive Step-by-Step Breakdown

#### Step 1: The Database Invariant
We added `CHECK (balance >= 0)` directly in the SQL schema. This is your ultimate safety net. Even if your application code has a bug and bypasses locks, the database engine itself will throw an error and refuse to allow a negative balance.

#### Step 2: Pessimistic Locking (`FOR UPDATE`)
By executing `SELECT ... FOR UPDATE`, we tell Postgres to lock those specific wallet rows. If concurrent request #2 arrives, it will pause and hang at this line of code until request #1 finishes (commits or rolls back). This completely eliminates the race condition.

#### Step 3: Deadlock Prevention (Sorting IDs)
If Tx1 wants to transfer from A to B, it locks A, then tries to lock B. If simultaneously Tx2 wants to transfer from B to A, it locks B, then tries to lock A. Both wait for each other infinitely (Deadlock). By always locking rows in alphabetical order of their UUIDs, we guarantee all transactions acquire locks in the same sequence, preventing deadlocks.

#### Step 4: Double-Entry Accounting
We don't just update the `wallets` table. We insert two rows into `ledger_entries` (one negative, one positive) tied together by a `reference_id`. The sum of all ledger entries for a wallet must *always* equal its current balance. The sum of the entire `ledger_entries` table must *always* equal zero.

### 🔀 ASCII / Architecture Flow

```text
[ Request 1: A -> B ]                        [ Request 2: A -> C ]
         |                                            |
      (BEGIN)                                      (BEGIN)
         |                                            |
[ LOCK Row A & B ]                                    |
         |                                            v
(Check A > $100: YES)                        [ Tries to LOCK Row A... ]
         |                                   [ WAITS... BLOCKING...   ]
(A = A - 100)                                         |
(B = B + 100)                                         |
         |                                            |
      (COMMIT) -----> Unlocks Row A ----------------->|
                                                      |
                                             [ LOCK Acquired! ]
                                                      |
                                             (Check A > $100: NO, Balance is 0)
                                                      |
                                                  (ROLLBACK)
                                              (Throws Insufficient Funds)
```

### ⚠️ Noob Trap vs 👑 Pro Tip
* **Noob Trap**: Doing math in Node.js instead of SQL. `const newBalance = oldBalance - 100; update wallets set balance = newBalance`. If the balance changed between your read and write, you overwrite it with stale math.
* **Pro Tip**: Always use relative updates in SQL: `UPDATE wallets SET balance = balance - 100`. And for absolute safety, rely on the `CHECK (balance >= 0)` constraint rather than purely relying on application logic.

### 🟡 Level 2: Real-World
**Task:** Implement a daily reconciliation cron job. Write a script that iterates over all wallets, sums up their history in `ledger_entries`, and compares it to their current `balance` in the `wallets` table. If there is a mismatch, alert the engineering team.
<details>
<summary>💡 Hint</summary>
```sql
SELECT w.id, w.balance, COALESCE(SUM(l.amount), 0) as ledger_sum
FROM wallets w
LEFT JOIN ledger_entries l ON w.id = l.wallet_id
GROUP BY w.id, w.balance
HAVING w.balance != COALESCE(SUM(l.amount), 0);
```
Execute this query; if it returns > 0 rows, send a Slack alert!
</details>

### 🔴 Level 3: Boss Level
**Task:** High-throughput wallets (e.g., a central "Fee Collection" wallet) suffer from lock contention. If 1,000 transactions per second try to deposit $1 into the Fee wallet, the `FOR UPDATE` lock becomes a severe bottleneck. Redesign the schema to avoid locking the receiver's wallet during deposits.
<details>
<summary>💡 Hint & Solution</summary>
Use an asynchronous ledger or "Wallet Sharding". You only need to lock a wallet when withdrawing (to prevent negative balances). You don't need a lock to deposit!

**Solution Approach (Insert-Only Ledger):**
Do not update the `wallets` table inline. Just insert into `ledger_entries`.
```sql
-- Transaction
BEGIN;
-- Lock only the sender
SELECT * FROM wallets WHERE id = sender FOR UPDATE;
-- Verify balance...
INSERT INTO ledger_entries (wallet, amount) VALUES (sender, -100);
INSERT INTO ledger_entries (wallet, amount) VALUES (receiver, 100);
COMMIT;
```
To get the balance, you calculate it on the fly, or use a materialized view, or have a background worker that aggregates ledger entries into the `wallets.balance` table every 10 seconds.
</details>
