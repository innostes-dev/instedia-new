# 3.2 Stripe Webhook Verification and Resilience

## Phase A: The Core Concept

### 🚨 Real-World Pain Point (The Why)
Your FinTech app listens to a `/webhooks/stripe` endpoint to update a user's subscription to "Premium" when their payment succeeds.
1. **The Attack:** A malicious user discovers this URL, sends a fake JSON payload `{ "type": "payment_intent.succeeded", "customer": "my_user_id" }`, and successfully upgrades their account for free.
2. **The Outage:** Stripe sends a legitimate webhook, but your database is briefly down. Your server returns a `500 Error`. Stripe will retry, but if you process it synchronously, you risk blocking your webhook endpoint, dropping events, and leaving users who just paid in a "Free" tier limbo.

### 💡 Plain English Metaphor (The What)
Webhook Verification is like a **Wax Seal on a Letter**. Anyone can write a letter claiming to be the King (The JSON Payload). But only the real King has the specific signet ring (The Webhook Secret) to stamp the wax (The Cryptographic Signature). You check the seal before reading the letter.
Webhook Resilience (DLQ/Workers) is like an **Inbox Tray**. Instead of reading and acting on every letter the moment the courier hands it to you (Synchronous Processing), you verify the seal, toss the letter into your Inbox tray, tell the courier "Got it, thanks!" (HTTP 200), and then read the letters at your own pace later.

### 💻 Complete Runnable Architecture/Code Example (TypeScript & Express)

**TypeScript (Express & Stripe SDK)**
```typescript
import express from 'express';
import Stripe from 'stripe';

const app = express();
const stripe = new Stripe(process.env.STRIPE_SECRET_KEY!, { apiVersion: '2023-10-16' });
const endpointSecret = process.env.STRIPE_WEBHOOK_SECRET!;

// 1. Raw Body Middleware (CRITICAL for verification)
// Stripe needs the exact raw bytes of the request to verify the signature.
// Do NOT parse it into JSON yet.
app.post('/api/webhooks/stripe', express.raw({ type: 'application/json' }), async (req, res) => {
  const sig = req.headers['stripe-signature'];
  let event: Stripe.Event;

  try {
    // 2. Cryptographic Signature Verification & Replay Attack Prevention
    // This function throws an error if the signature is invalid or if the timestamp is too old (replay attack)
    event = stripe.webhooks.constructEvent(req.body, sig as string, endpointSecret);
  } catch (err: any) {
    console.error(`⚠️ Webhook signature verification failed.`, err.message);
    return res.status(400).send(`Webhook Error: ${err.message}`);
  }

  // 3. Immediately acknowledge receipt to Stripe (Resilience)
  res.status(200).send({ received: true });

  // 4. Asynchronous Processing (Fire and Forget)
  // In a real app, this should push to a Queue (RabbitMQ, SQS, Redis BullMQ).
  // For this example, we use a non-blocking Promise.
  processWebhookEvent(event).catch(error => {
    console.error("Failed to process event, saving to Dead Letter Queue (DLQ)...", error);
    // saveToDLQ(event);
  });
});

async function processWebhookEvent(event: Stripe.Event) {
  // Handle the event asynchronously
  switch (event.type) {
    case 'payment_intent.succeeded':
      const paymentIntent = event.data.object as Stripe.PaymentIntent;
      console.log(`💰 Payment for ${paymentIntent.amount} succeeded!`);
      // await database.updateUserTier(paymentIntent.metadata.userId, 'Premium');
      break;
    case 'customer.subscription.deleted':
      // Handle churn
      break;
    default:
      console.log(`Unhandled event type ${event.type}`);
  }
}

app.listen(4242, () => console.log('Running on port 4242'));
```

### 🪜 Progressive Step-by-Step Breakdown

#### Step 1: The Raw Body
Cryptographic hashes (`HMAC SHA256`) change completely if a single byte is altered. If Express parses the incoming data into a JavaScript object (`express.json()`), the spaces, newlines, and key ordering might change when it's stringified back. We MUST use `express.raw()` to grab the exact byte stream Stripe sent.

#### Step 2: Construct & Verify Event
Stripe's SDK handles the math. It hashes the raw body with your `STRIPE_WEBHOOK_SECRET` and compares it to the `stripe-signature` header. Crucially, the header includes a timestamp `t=1690000000`. The SDK checks if this timestamp is within the last 5 minutes. If a hacker intercepts a valid payload and tries to send it again tomorrow (Replay Attack), the SDK will reject it because the timestamp is too old.

#### Step 3: Fast Acknowledgment
Webhooks have strict timeouts (usually 3-10 seconds). If your database query takes 15 seconds, Stripe assumes your server is dead, drops the connection, and retries later. We immediately return `HTTP 200` to Stripe *before* we do any database work.

#### Step 4: Asynchronous Processing & DLQ (Dead Letter Queue)
Since we already told Stripe "we got it", if our database query fails, Stripe won't retry. Therefore, we must have our own resilience strategy. If `processWebhookEvent` fails, we catch the error and save the raw event to a Dead Letter Queue (a special database table or message broker queue for failed jobs). A developer can review the DLQ later and manually hit a "Retry" button.

### 🔀 ASCII / Architecture Flow

```text
[ Stripe ] ---(POST /webhook + Signature)--> [ Express Server ]
                                                  |
                                                  |-- 1. Validate Signature (HMAC + Timestamp)
                                                  |
[ Stripe ] <---(HTTP 200 OK)----------------------|-- 2. Immediate Response
                                                  |
                                                  v
                                      [ Message Queue / Redis BullMQ ]
                                                  |
                                                  | (Asynchronous Worker)
                                                  v
                                          [ Database Update ]
                                            /           \
                                       Success         Failure
                                                         |
                                                         v
                                              [ Dead Letter Queue (DLQ) DB Table ]
```

### ⚠️ Noob Trap vs 👑 Pro Tip
* **Noob Trap**: Blindly trusting the data inside the webhook payload. A webhook saying `payment_intent.succeeded` for `$100` might be mathematically signed, but you should still double-check your database. What if they applied a discount code? What if the user already cancelled?
* **Pro Tip**: Use the Webhook just as a "Notification Ping". When you receive `payment_intent.succeeded` with ID `pi_123`, don't trust the payload data. Make a fresh GET request to `stripe.paymentIntents.retrieve('pi_123')` to fetch the undeniable, current source of truth directly from Stripe's API before updating your database.

### 🟡 Level 2: Real-World
**Task:** Implement idempotency for webhook processing. Stripe guarantees "at least once" delivery, meaning they might send the *exact same valid webhook* twice. Ensure your system doesn't grant the user 2 months of Premium if a duplicate webhook arrives.
<details>
<summary>💡 Hint</summary>
Every Stripe event has a unique `event.id` (e.g., `evt_123`). Before processing, check your database: `SELECT 1 FROM processed_webhooks WHERE event_id = 'evt_123'`. If it exists, skip processing. If not, process it, and insert `evt_123` into the table inside the same database transaction.
</details>

### 🔴 Level 3: Boss Level
**Task:** Create a robust DLQ (Dead Letter Queue) processing system. Write a script that reads failed events from a Postgres table (`webhook_dlq`), attempts to re-process them, and if successful, removes them from the DLQ. Implement an exponential backoff retry strategy.
<details>
<summary>💡 Hint & Solution</summary>
Add `retry_count` and `next_retry_at` columns to your DLQ table.

**Solution Approach (Worker Cron Job):**
```sql
CREATE TABLE webhook_dlq (
    id UUID PRIMARY KEY,
    stripe_event_id VARCHAR,
    payload JSONB,
    error_message TEXT,
    retry_count INT DEFAULT 0,
    next_retry_at TIMESTAMP DEFAULT NOW()
);
```

```typescript
// Cron job running every 5 minutes
async function processDLQ() {
  // 1. Fetch events ready to be retried
  const failedEvents = await db.query(
    `SELECT * FROM webhook_dlq WHERE next_retry_at <= NOW() AND retry_count < 5`
  );

  for (const row of failedEvents) {
    try {
      // 2. Attempt processing
      await processWebhookEvent(row.payload);

      // 3. If successful, delete from DLQ
      await db.query(`DELETE FROM webhook_dlq WHERE id = $1`, [row.id]);
    } catch (err) {
      // 4. If fails again, increment retry and calculate exponential backoff (e.g., 2^retry_count hours)
      const nextRetryStr = `NOW() + INTERVAL '${Math.pow(2, row.retry_count)} hours'`;
      await db.query(
        `UPDATE webhook_dlq SET retry_count = retry_count + 1, next_retry_at = ${nextRetryStr}, error_message = $1 WHERE id = $2`,
        [err.message, row.id]
      );
    }
  }
}
```
</details>
