# 3.1 Idempotency Keys and Deduplication

## Phase A: The Core Concept

### 🚨 Real-World Pain Point (The Why)
A user clicks "Pay $100" on an e-commerce checkout page. The request reaches your server, the server successfully charges their credit card via Stripe, but right as the server sends the HTTP 200 Success response back to the frontend, the user's cell tower connection drops. The user sees a "Network Error". They panic and click "Pay $100" again. The server processes it as a brand new request, and the user is charged twice. This is a critical double-charging disaster.

### 💡 Plain English Metaphor (The What)
An Idempotency Key is like a **Ticket Number at a Coat Check**. When you hand the attendant your coat, they give you Ticket #42. If you walk away, forget you already gave them your coat, and come back 5 minutes later shouting, "Here is Ticket #42, please take my coat!", the attendant looks at the ticket and says, "I already processed Ticket #42. I'm not taking another coat from you, but I confirm your coat is safely stored."
The operation (giving the ticket) is *idempotent*—doing it once has the same result as doing it ten times.

### 💻 Complete Runnable Architecture/Code Example (TypeScript & Redis)

**TypeScript (Express & Redis)**
```typescript
import express, { Request, Response, NextFunction } from 'express';
import { createClient } from 'redis';
import crypto from 'crypto';

const app = express();
app.use(express.json());

const redis = createClient({ url: 'redis://localhost:6379' });
redis.connect();

// Mock Payment Gateway
const processStripePayment = async (amount: number) => {
  return { transactionId: `txn_${crypto.randomBytes(8).toString('hex')}` };
};

// 1. Idempotency Middleware
const enforceIdempotency = async (req: Request, res: Response, next: NextFunction) => {
  const idempotencyKey = req.headers['idempotency-key'];

  if (!idempotencyKey || typeof idempotencyKey !== 'string') {
    return res.status(400).json({ error: 'Idempotency-Key header is required' });
  }

  const redisKey = `idempotency:${req.user?.id || 'anon'}:${idempotencyKey}`;

  try {
    // 2. Distributed Lock & Deduplication Check (Atomic)
    // SETNX = Set if Not eXists. Returns 1 if set, 0 if it already existed.
    const isNewRequest = await redis.set(redisKey, 'PROCESSING', {
      NX: true, // Only set if it doesn't exist
      EX: 86400 // Expire in 24 hours
    });

    if (!isNewRequest) {
      // Key exists! Let's see what the state is.
      const existingStatus = await redis.get(redisKey);

      if (existingStatus === 'PROCESSING') {
        // The first request is still running. Tell the client to chill out.
        return res.status(409).json({ error: 'Concurrent request detected. Please wait.' });
      }

      // 3. Return the cached success response of the first request
      const cachedResponse = JSON.parse(existingStatus!);
      return res.status(200).json({
        message: 'Idempotent cache hit',
        data: cachedResponse
      });
    }

    // Pass the redisKey to the route handler so it can save the result later
    req.idempotencyKeyStr = redisKey;
    next();

  } catch (error) {
    next(error);
  }
};

// Custom type augmentation for Express
declare global { namespace Express { interface Request { idempotencyKeyStr?: string; user?: { id: string } } } }

// Route Handler
app.post('/api/checkout', enforceIdempotency, async (req: Request, res: Response) => {
  const { amount } = req.body;
  const redisKey = req.idempotencyKeyStr!;

  try {
    // Process Payment
    const paymentResult = await processStripePayment(amount);

    const responsePayload = {
      status: 'success',
      transaction: paymentResult.transactionId,
      amount
    };

    // 4. Save the result to Redis so future duplicate requests get this exact same response
    await redis.set(redisKey, JSON.stringify(responsePayload), { EX: 86400 });

    res.status(200).json(responsePayload);

  } catch (error) {
    // If the payment fails, delete the key so the user can try again safely
    await redis.del(redisKey);
    res.status(500).json({ error: 'Payment failed' });
  }
});
```

### 🪜 Progressive Step-by-Step Breakdown

#### Step 1: The Client Header
The frontend generates a unique UUID (e.g., `uuidv4()`) when the user clicks the Checkout button, and sends it in the `Idempotency-Key` HTTP header. If the frontend retries the request automatically due to a timeout, it must send the *exact same* UUID.

#### Step 2: Atomic Check-and-Set (SETNX)
We cannot do `redis.get()` followed by `redis.set()`. If two concurrent requests arrive at the exact same millisecond, they might both `get` nothing, and both proceed to charge the card. We use Redis `SET ... NX`, which guarantees atomically that only one thread will successfully write the key. The loser gets a `0` back and immediately knows it's a duplicate.

#### Step 3: Handling Concurrent vs Cached Requests
If a duplicate is detected, we check the value. If it says `PROCESSING`, it means the first request is still talking to Stripe. We reject the second request immediately. If it contains a JSON payload, it means the first request finished successfully in the past, so we just replay the JSON response without touching Stripe.

#### Step 4: Storing the Result & Failure Recovery
Once the actual payment finishes, we overwrite `PROCESSING` with the final JSON result. If the backend crashes or Stripe rejects the card, we `DELETE` the key from Redis, allowing the user to click the button and try again with the same idempotency key.

### 🔀 ASCII / Architecture Flow

```text
[ Client (Timeout Retry) ]
    |
    |-- (POST /checkout, Key: 123) --> [ API Middleware ]
                                              |
                                              |-- (SETNX key:123 "PROCESSING") --> [ Redis ] Returns 1 (Success)
                                              |
                                       [ Route Handler ] ---> (Charges Stripe) ---> Success!
                                              |
                                              |-- (SET key:123 '{"txn": "abc"}') --> [ Redis ]
    <--- (200 OK, {"txn": "abc"}) ------------|

    (1 minute later, Client didn't get response, Retries)
    |
    |-- (POST /checkout, Key: 123) --> [ API Middleware ]
                                              |
                                              |-- (SETNX key:123 "PROCESSING") --> [ Redis ] Returns 0 (Exists)
                                              |-- (GET key:123) --> Returns '{"txn": "abc"}'
                                              |
    <--- (200 OK, {"txn": "abc"}) ------------| (Never hits Route Handler/Stripe)
```

### ⚠️ Noob Trap vs 👑 Pro Tip
* **Noob Trap**: Generating the `Idempotency-Key` on the backend server. The whole point is to protect against network drops between the *client* and the server. If the server generates it, a dropped connection means the client will send a brand new request, the server will generate a new key, and charge them twice.
* **Pro Tip**: Pass the Idempotency Key all the way down to your third-party providers. Stripe, PayPal, and Adyen all accept an `Idempotency-Key` header natively in their APIs. If your server crashes right after calling Stripe, but before updating Redis, when your server reboots and retries, Stripe's idempotency engine will catch it and prevent the double charge.

## Phase B: Engineering Challenges

### 🟢 Level 1: Warm-Up
**Task:** Ensure the Idempotency Middleware also checks if the request body is identical. If a user sends Key `123` with `{ amount: 100 }`, and later sends Key `123` with `{ amount: 500 }`, reject it with a 400 error indicating an Idempotency Key mismatch.
<details>
<summary>💡 Hint</summary>
When saving the "PROCESSING" state in Redis, also save a hash of the request body. E.g., `redis.set(redisKey, JSON.stringify({ status: 'PROCESSING', hash: hash(req.body) }))`. When a duplicate is detected, hash the incoming body and compare it.
</details>

### 🟡 Level 2: Real-World
**Task:** Redis is an in-memory cache and can lose data if it restarts without persistence. Move the idempotency tracking to a PostgreSQL table for maximum durability, using a `UNIQUE` constraint and `ON CONFLICT` (or equivalent ORM logic) to handle the atomic lock.
<details>
<summary>💡 Hint</summary>
Create table `idempotency_keys(key UUID PRIMARY KEY, status VARCHAR, response JSONB)`. Use an atomic `INSERT ... ON CONFLICT DO NOTHING RETURNING *`. If no rows are returned, it means the key already exists (duplicate request).
</details>

### 🔴 Level 3: Boss Level
**Task:** Combine Idempotency with a Distributed Redlock for a multi-node backend. If two duplicate requests hit Server A and Server B at the exact same millisecond, ensure they don't both initiate the Stripe payment due to a race condition between checking Postgres/Redis and updating it.
<details>
<summary>💡 Hint & Solution</summary>
Use a formal distributed locking library like `redlock`.

**Solution Approach:**
```typescript
import Client from "ioredis";
import Redlock from "redlock";

const redisClient = new Client();
const redlock = new Redlock([redisClient], { retryCount: 0 });

app.post('/checkout', async (req, res) => {
  const key = req.headers['idempotency-key'];
  const resource = `locks:checkout:${key}`;

  try {
    // 1. Acquire Lock (Fails immediately if another server has it)
    const lock = await redlock.acquire([resource], 5000); // 5 sec TTL

    try {
      // 2. Check DB/Redis for existing completed status
      const existing = await checkDatabase(key);
      if (existing) return res.json(existing);

      // 3. Process payment
      const result = await processPayment();

      // 4. Save to DB
      await saveToDatabase(key, result);

      res.json(result);
    } finally {
      // 5. Release lock so future requests can read the DB
      await lock.release();
    }
  } catch (err) {
    // If acquire() fails, it's a concurrent request
    res.status(409).json({ error: "Concurrent request" });
  }
});
```
</details>
